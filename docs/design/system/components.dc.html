Components · reference sheet · [internal]
Purpose
The reference sheet for every primitive src/modules/ui ships, at every state the code can reach. It is the same surface as /dev/components (spec 004 §2's gallery, ENABLE_DEV_UI=true, noindex, refused in production) drawn as an artboard so it can be reviewed on the canvas without running the app.
In step with code
Every variant, tone, ratio, size and state below is an exported member of src/modules/ui — BUTTON_VARIANTS, BUTTON_SIZES, BUTTON_STATES, CHIP_TONES, PHOTO_RATIOS, DISPLAY_SIZES, TEXT_SIZES, TEXT_TONES, GAPS, CONTAINER_WIDTHS, ICON_NAMES, MIRRORED_IN_RTL. Nothing on this sheet is missing from code and nothing in code is missing from this sheet; see docs/design/README.md § “Keeping the sheet and the code in step”.
Specified, not yet shipped
One group is the exception to the sentence above and says so on itself: Country-page blocks (spec 007). Those six are drawn from the approved spec before /plan-tasks splits it, which is the order CLAUDE.md requires — artboards precede tasks. They are not exports of src/modules/ui today, and the implementer who builds them adds them to this sheet and to /dev/components in the same pull request; until then this group is a specification and every other group on this sheet is a mirror. Nothing here invents a token: all six are built from Chip, Stack, Grid, Text and the existing space, rule and ink scales.
Copy on the sheet
Developer-facing state and token names, plus the gallery's own sample strings from src/app/(dev)/dev/components/catalog.ts. These are deliberately not message keys — a translated “disabled” would make the sheet lie about the code it documents.

Country-page blocks (spec 007)

Six blocks, every state, none of them shipped yet

Drawn from spec 007 before its tasks exist, so that an implementer matches a drawing rather than a paragraph. Every one is composed from primitives that already ship — no new token, no new colour, no new radius — and every one has a state in which it renders nothing at all, which is the state the field always gets wrong. Server-rendered, zero client JavaScript between them: the FAQ is text, the calendar is a table, the breadcrumb is a list.

FAQ list

How many flowers should I send?

An odd number. Even-numbered bunches are for funerals and for graves in Poland, so a bouquet of ten says something nobody means to say.

Which flowers should I avoid?

Chrysanthemums. In Poland they belong on graves, and sending them to someone's home reads as a funeral tribute.

default · 8–12 items, every question a real <h3>, every answer visible. No <details>, no accordion, no JavaScript, nothing hidden behind a click.
Below 8 or above 12 items, or fewer than half of the questions naming the country, its cities, its currency, its language or one of its own days, the content gate fails the file and the page does not build. There is no visual state for “too few questions”: it is a build error, not a branch.out of range · no state, by design
The FAQPage JSON-LD is emitted from this same list and only where 8–12 visible questions exist, so structured data cannot describe an answer the page does not render.schema
