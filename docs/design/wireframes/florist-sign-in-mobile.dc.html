Florist sign-in · mobile 390 · spec 011 · [internal]
Purpose
The florist's one way in: an email link from the shared sign-in core (spec 012 task 1), florist instance. No password, no app. Phone first: the column is the screen; the button is 56 px; the language links sit under the card so the header is the logo alone.
URL
/demo/vendor-inbox/sign-in · the emailed link /demo/vendor-inbox/sign-in/confirm?t={token} (no email address in any URL, redirect or log; AC-19) · ?hl=pl / ?hl=de choose the language before sign-in (never Accept-Language, never an IP).
Index
noindex, private, no-store; 404 in production in Phase 0 (AC-22).
Reads
Nothing personal. The request posts SignInRequestSchema (email, hl); the confirm page's GET consumes nothing and renders one button, so a mail scanner cannot burn the token; the POST resolves the address from the hashed token on the server.
States
Request · check your email (the same page for every address: no account enumeration, AC-18) · confirm with one button · link expired or used (a new link is one tap away; WCAG 2.2.1 security exception) · the language links · the sign-in email (subject, body, plain-text part).
Components
Sign-in card, text field, primary button, notice (“Forms” on system/components.dc.html); the email is a React Email template under emails/ with a plain-text part, in the member's language.
Tokens
--color-card card, --radius-photo, --shadow-sm; the action --color-accent; the expired notice --color-blush.
Copy
Founder copy pending floristAuth.* and emails.floristSignIn.*, spec 011 Appendix A verbatim. The notice link is a [slot] (spec 011 §8 says the sign-in page links the notice; Appendix A has no words for it).
AC
spec 011 AC-18, AC-19, AC-20, AC-22, AC-32, AC-34
