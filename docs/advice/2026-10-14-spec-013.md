# Spec 013: payments and the money half of the order machine (draft @08a55a3c)

## 1. In one sentence
This spec is what lets the site take real money. It holds the card, captures the payment when a florist accepts, and handles webhooks, refunds and disputes. The money design is careful, but one launch payment method (BLIK) does not work with the checkout flow it chose, and some cross-spec details disagree with the 016 and 018 drafts.

## 2. Verdict: GO WITH FIXES
- **F1 (§5.2 "How a paid order flows" step 1; §13 Q5; AC-33, T-33).** Stripe's BLIK page lists deferred-intent support as "Client-side confirmation only (Private preview)" and says it is "not supported when collecting payment details before creating a PaymentIntent" ([Stripe BLIK](https://docs.stripe.com/payments/blik)). Step 3 is built exactly that way. Choose one: (a) launch with card, Apple Pay and Google Pay, and add BLIK in a later task; (b) create the intent before rendering for PLN orders; (c) get preview access in writing. Then make AC-33's BLIK case conditional on that choice.
- **F2 (§5.2 `prepare`; §12 task 2).** The Elements `captureMethod` option "should match the capture_method … on the Intent", and Elements has no per-card capture override ([Stripe.js](https://docs.stripe.com/js/elements_object/create_without_intent)). State the value: `'automatic'`, with the card's manual override set only on the server. Move one staging test-mode check into task 2: a 3DS card ends `requires_capture` under that setup. Today the first proof is T-33, in the last task. [inferred: the mix works, but nothing in the docs confirms it]
- **F3 (§5.1 item 5).** `webhook_inbox.livemode NOT NULL` and `event_type NOT NULL` would refuse spec 016's Resend rows (016 §5.1 widens `provider` to `resend`). Make them nullable, with `CHECK (provider <> 'stripe' OR livemode IS NOT NULL)`.
- **F4 (§5.1 Rollback).** The down file should **refuse** (raise) when any `payment` row has `livemode = true`, not delete rows. Deleting live payment rows destroys part of the accounting record (§8).
- **F5 (§3, §12, §5.2 events).** Spec 016 now folds in 017, so replace "spec 017" with 016. Name the refund events' payload fields `refund_id`, `amount_minor` and `currency_code` (018 §12 asks for them), and say that 018 reads the date from `succeededRefunds`, so there is only one source for "Refunded on {date}".
- **F6 (Appendix A `payments.confirmation.held`, `.paidNow`).** "Your order is confirmed" before a florist accepts contradicts `plan/07` §2.3: the contract is concluded on capture. Use wording such as "We have your order. Your card is held, not charged, until a florist accepts it." Send it to the lawyer with the legal set.
- **F7 (§13 Q1, Q3; §12 founder action 5).** Q1: name `request_three_d_secure: 'any'`, not `'challenge'`. Q3: Stripe's pricing page now puts custom rules in "Radar Plus" (from $14/month, or pay as you go; US page), not "Fraud Teams" ([Stripe Radar pricing](https://stripe.com/radar/pricing)). Rename it and check the EU price in the dashboard.

**PR 210: leave it as it is; A7 as a later migration is right.** PR 210 builds the approved A6. A7 is not approved yet, so changing PR 210 now would reopen review and break on five tasks to carry decisions nobody has made. `ALTER` on tables that hold no rows costs seconds, and no `test` or `live` order (so no payment or outbox row) can exist before this spec ships. The conditions are F3 and F4.

**Law and compliance** (not legal advice; a lawyer and the accountant sign off). (a) F6. (b) The perishable-goods exemption and "contract on capture" rest on the pre-contract wording, which is lawyer-gated (`plan/07` §2.1, B4). Live mode stays off until that is done. This is acceptable.

## 5. What looks right
No function takes a charge amount, every write to Stripe has an idempotency key, the webhook state is always re-read from Stripe, and A6 row numbers are cited on every money move. That is the right shape for "never charge twice, never charge wrong".
