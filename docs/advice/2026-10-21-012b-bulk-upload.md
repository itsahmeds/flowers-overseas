# Spec 012b amendment A-founder-2026-10-21b: bulk upload of a florist's bouquets and prices

2026-10-21 · read at the head of PR 311 (`specs/012b-cms.md` §14, §13.1 Q17 to Q28, AC-40 to AC-48, T-42 to T-53) · not legal advice

## 1. In one sentence
Upload a florist's price list as CSV or Excel, preview every row, then save all of it or nothing, using only slice A's own price and copy checks. It is a sound design, and five small gaps (live price jumps, go-live proof, zip bombs, formula text, PR size) are why it is "approve once fixed".

## 2. Verdict: GO WITH FIXES
No fix changes a founder default (Q17 to Q28 all stand as written).
- **F1 (§14.4, §14.6, AC-42, AC-44, T-46).** A price change on an already-active bouquet goes live the moment Apply commits (cache purge, no Publish step), for up to 1,000 rows. Today a change beyond 30 percent is only a flag. Fix: a change beyond 30 percent on an active product, and an update that reopens an approved copy locale, are each a soft warning that needs a typed reason (the Q24 mechanism, one more warning kind). Add one T-46 case.
- **F2 (AC-45, AC-42, T-47).** "An import cannot put anything on sale or open a country" is only proved for product status. AC-42's checksum list omits `countries`, the feature flags and the placeholder-window flag. Fix: AC-45 and T-47 assert that `countries.status`, `first_live_at` and every global flag (including `checkout.open`) are unchanged after Apply, and that the import code path cannot call `setCountryStatus` (spec 012's `status_flip_guard()` refuses it).
- **F3 (§14.3, AC-41, T-43).** The 20 MB zip-bomb limit must count bytes actually inflated, not the sizes a zip header declares (headers can lie). Add a lying-header fixture.
- **F4 (§14.4, AC-15, AC-40, AC-41).** `copy.formula_lead` covers only copy and alt text. Extend it to every free-text column (`size_label`, `vase`, `sku`). Otherwise a stored value starting with `-` or `+` gets a `'` on export and fails re-upload, breaking AC-40's "unchanged file = all skip".
- **F5 (§12 task 14).** One PR holds a migration, a new library, a parser, a planner, two pages, a photo step and 12 tests, and the breaker runs on it. Plan it as 14a (parse, template, preview) and 14b (Apply, photos) now, not "if it does not fit".

## 3. The four hats
- **Building:** 1. F5. 2. The XLSX library is chosen inside task 14 (§14.3); if no maintained reader passes `pnpm audit`, the task stalls, so name a fallback of CSV-only for A.2 [inferred]. 3. Every Apply command gains a transaction handle (§14.10): a change to tasks 5 to 7 code, so 14 must follow them (it does, §14.1).
- **Google:** 1. F1: a bulk edit to approved `en` or `pl` text takes those pages out of the index at once (AC-12). No page is indexed yet, so the risk is later. 2. No concern otherwise: Apply adds no URL (publish diff unchanged, AC-43) and slugs follow the existing rules (AC-46).
- **Law and compliance:** 1. Money is handled well: integer minor units through `parseMinorInput` only, number cells refused, no net-of-VAT key, `Offer.price` equals `quote()` (AC-44). 2. Accountant must still sign off the VAT rate that `suggestedPrice` uses (`vat_rate_bp`, `plan/06` §4) before real orders. 3. Lawyer: the florist photo licence clause (Q11) before any uploaded photo is approved; RoPA flow 2 update for the 24-hour payload (§14.11). Audit trail: no concern (AC-47).
- **Customer:** 1. F1 (a buyer sees a 30+ percent jump unannounced). 2. Refusing number-typed price cells (Q25) will trip a florist who pastes prices into Excel; the error message must say "format as text" (§14.3 does).

## 4. Questions the founder should ask before approving
1. After Apply, can I still change a live price by mistake without a warning? (Yes today beyond 30 percent; F1 fixes.)
2. Can an upload ever make Poland or another country sell? (No by design; F2 makes the test prove it.)
3. Can a florist's file hurt the server? (Limits are right; F3 closes the zip-header gap.)
4. Is a half-saved florist possible? (No: AC-43 is one transaction, with a plan-hash check against edits made after the preview.)
5. Does the XLSX library exist and pass the audit? (Unknown until task 14's first step.)

## 5. What looks right
All or nothing with a hash re-check at Apply, no ledger row written by an import, photos by file name with no URL fetching, and the same rule ids as the single editor and `catalogue:check`.
