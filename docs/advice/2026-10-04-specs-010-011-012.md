# Specs 010, 011 and 012: the Phase 0 backend

2026-10-04 · read at the heads of `docs/spec-010-checkout`, `docs/spec-011-for-florists` and `docs/spec-012-admin-v0` · not legal advice

## 1. In one sentence
Together the three specs give you a demo checkout, a florist landing page with a florist inbox, and an admin area. Each spec is well made on its own, but they were written side by side and disagree on six shared pieces: the order engine, sign-in, the demo marker, the event names, retention and routing. 012 also packs a large architecture change into a Phase 0 spec. So each verdict is "approve once these fixes are made".

## 3. The cross-spec conflicts, settled
**3.1 Who builds the order engine:** spec 010 (F1). It is the first code to create an order, and the five database changes in its Q6 belong with it. 011 and 012 only call `transition`. Spec 015 later adds commands, timeouts and payments to the same code (010 already says so).

**3.2 Vendor portal now (012 Q12):** a portal is only useful with real orders. Real orders need specs 013, 015, 016 and 017 merged, the company registered, and a florist under a signed agreement with processor clauses. As written, 011 already builds the portal's base: sign-in, per-florist access enforced by the database, the inbox, accept and decline, and the photo. Pulling 026 and 027 forward would add owner and staff roles, invites, a capacity calendar, substitutions, the card PDF, payout history and ratings. That is roughly 10–14 more tasks, perhaps 2–3 weeks of agent time [inferred], competing for the same 4–5 build slots as the Phase 0 deadline. Payout history and statements also wait on payouts (spec 030), which wait on real money. **Recommended:** keep 027 in Phase 2. Bring forward a small 026, "active florists can sign in on the live site", timed for your first signed florist in Phase 1. Florists then have a working portal from their first real order, and the plan's per-order links are never built.

**3.3 Which source sets the price:** they agree once F5 and H1 are made. The product page, its structured data and 011's payout example all read spec 005's price provider today, and 010's checkout reads the same one, so the shown price equals the charged price by construction (010 AC-15). A later cutover swaps the provider for all of them in one deploy. Cache lag (up to an hour of ISR, 60 s purge) is caught by 010's signed quote and its "the price changed" notice. Three gaps remain:
- 010 AC-28 reads the database price row directly (F5).
- A price editor that existed before the cutover would change the database while pages and checkout kept the file price. H1 removes the editor until 012b.
- The production database must be seeded insert-only from the same dataset before 010 places its first order.

**3.4 Order of work and timing** [inferred: the 11 serial tasks of spec 002's chain, at ½–1 day each with review and breaker]:
1. **Now, no database needed:** 011 task 1 (landing, walkthrough, apply page with the form off) and 010 tasks 1–2. The designer's drawings for all three specs, and your copy approval, come first. **The first thing you'll see live is the florist landing, in about a week.**
2. **TASK-017 → 023, about a week:** then 010's engine, the shared sign-in core, 012 tasks 1–2 and 011 task 4. With Resend set up, **admin sign-in and an empty order queue go live in about 1½–2 weeks**.
3. **TASK-024 → 027, a few more days:** then the 010 checkout (tasks 3–7), the 011 inbox (task 6), the 012 queue (task 12) and the 011 form turned on. **The full demo (product page → checkout → inbox → admin within 5 s) runs on staging in about 3–4 weeks, in early November.** That misses 16 Oct.
4. **Later:** the 011 photo needs TASK-082 (blocked) and the private R2 bucket. 012b comes before the December go-live.

Two ways to save time: bundle TASK-017–023 into two or three feature PRs, and use the live walkthrough on the 16 Oct calls (its screens are the inbox's own components).

**3.6 One sign-in core** (an extra conflict the brief didn't list): 011 and 012 each set up Auth.js separately, with their own adapter, mail sender, env names (`RESEND_API_KEY`/`EMAIL_FROM` against `AUTH_RESEND_KEY`/`ADMIN_MAIL_FROM`) and files (`src/lib/auth/` against `src/lib/auth.ts`, which collide). **012 task 1 owns one core:** one adapter, one `Mailer`, and the keys `AUTH_SECRET`, `RESEND_API_KEY` and `EMAIL_FROM`. It adopts 011's safer link design: no email in the URL, and a GET that doesn't use up the token. Admin and florists then get their own path, cookie scope and session length. Auth.js's `__Host-` CSRF cookie needs a new name, because a `__Host-` cookie must have `Path=/` ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)), which breaks 012 AC-3.

## 4. The four angles
- **Building:**
  - (all three) The six shared-piece conflicts above.
  - (012) The scale: 14 tasks and 17 drawing sets.
  - (012b) "Builds read the database" puts production data on the build path for Railway and CI, so a database outage stops deploys.
- **Google:**
  - (012b) A ledger import whose text hashes don't match could quietly un-index every page at the review cutover. Add an AC: the set of indexable URLs is identical before and after.
  - (011) `FAQPage` markup is harmless but earns no rich result; Google now shows those only for government and health sites ([Google, 2023](https://developers.google.com/search/blog/2023/08/howto-faq-changes)).
  - (010) No concern: checkout is noindex, robots-disallowed and never linked.
- **Law and compliance** (a lawyer signs off; this is not legal advice):
  - (010) The public types personal data into a demo on the live site before the company or a privacy notice exists. F4, the sample-details button and the inline notice reduce the risk; the legal basis needs the lawyer.
  - (011) A florist on a demo call may photograph a real doorstep. The 30-day deletion covers it; the runbook script should say so.
  - (012b) Imported approvals must show their true history. On 2026-09-16 the guides were approved "without a personal skim", and 526 strings were "transcribed by TASK-091". The ledger shouldn't present those as read by you.
- **The customer:**
  - (010) A real buyer may think they ordered. The banner and the "nothing is charged" button handle it. There's no Apple Pay or Google Pay until 013, which 013 must fix.
  - (011) A florist on a call has to get past the staging password and then an email link on their phone, at the moment you are selling to them.
  - (012) No concern.
