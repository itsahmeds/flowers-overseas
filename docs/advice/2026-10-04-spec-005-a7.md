# Spec 005 §14 A7: the Phase 0 FX bridge (build-time ECB fetch, weekday Railway rebuild)

Subject: `specs/005-catalogue-pricing-module.md` §14 A7 (main @ 977990a4), AC-29…AC-35, T-28…T-35, TASK-180/181. Advisor memo, 2026-10-04. This memo is not legal advice.

## 1. In one sentence
A7 replaces a hand-typed, long-stale exchange-rate file with the ECB's real daily rate, fetched at build and refreshed by a weekday Railway rebuild. The design is safe: a failure leads to "show the price in złoty", never to "show a wrong price". But three gaps could leave the site quietly stuck on that fallback, or cost it Google price snippets.

## 2. Verdict: GO WITH FIXES
1. **§14 A7 Corrected 2(i) + AC-31/T-30: say how a same-commit rebuild avoids the build cache.** The `Dockerfile` runs `COPY . .` (L28) and then `RUN pnpm build` (L59). At the same commit those inputs are identical, and Railway caches build layers by default, so the "rebuild" can reuse the old layer and fetch nothing. A7 forbids a cache layer holding the rate, but it names no mechanism and no test checks one. Name the mechanism: a build `ARG` whose value changes on every refresh, declared just before `RUN pnpm build`, or `NO_CACHE=1` on `web`. Pin it in `tests/unit/container.test.ts`.
2. **AC-34/T-34: the job must check that its rebuild worked.** Add: "the 19:30 UTC run exits red, naming the environment, if it finds that environment's `fxAsOf` still behind the ECB date." Today a cache hit, a ±15% band trip or an ECB format change gives a green job and a site stuck on złoty. The only signal would be Sentry, from 00:00Z the next weekday.
3. **Corrected 7 "SEO" bullet (and A3): stop using the FX date as `priceValidUntil`.** Under A7, a converted `Offer` carries `priceValidUntil` 1 to 4 days ahead. Google: "Your product snippet may not display if the `priceValidUntil` property indicates a past date." A young site's pages are recrawled less often than that [inferred], so the copy Google holds would usually show a past date. Leave `priceValidUntil` out when its only source is the rate, and keep the price row's `active_to`. Shown = charged still holds through the quote's own `ratePpm` (§13 Q5).

## 3. The four hats
**Building**
1. Same-commit rebuild may be a cache hit (fix 1). Source: Railway, "Disable caching with Dockerfile" (station.railway.com/questions/disable-caching-with-dockerfile-2b124156).
2. The job can be green while nothing works (fix 2). The ±15% band is always measured against the 2026-09-08 row, and the fetch is all-or-nothing across 11 currencies. So one flag-off currency (HUF, RON, USD…) drifting 15% blocks every fetch until someone edits the band.
3. Hidden dependency on GitHub Actions. Scheduled runs "can be delayed… some queued jobs may be dropped" (docs.github.com, schedule event); the 19:30 retry covers that. If the repo goes private again, the earlier billing failure stops the refresh entirely.

On your question, does a build fail closed or ship stale: **it fails closed.** A failed fetch exits 0 and serves the whole committed snapshot. That snapshot is past the age bound, so pages show the native złoty price with the `fxUnavailable` sentence. It never shows a wrong conversion (Corrected 2(iii), AC-15).

**Google**
1. `priceValidUntil` (fix 3).
2. Price churn: low concern. A converted price changes only when the conversion crosses a rounding step (x90, rounded upward) [inferred]. HTML stays the same for every visitor, and schema = visible comes from one projection (§6). Cloudflare does not cache HTML (spec 040 L288–304), so there is no mismatch across deployments.
3. Each production rebuild empties the ISR cache, so the first visits after it render cold, twice a day. Minor.

**Law and compliance**
1. Shown = charged holds only if spec 010/013 charge the amount in the quote (§13 Q5). That code is not built yet; check it there.
2. Omnibus Art. 6a covers *announced* reductions (Commission guidance 2021/C 526/02), so a euro price that drops because the rate moved is not a reduction. Never put "was/now" on a converted price: `lowestPriceInLast30Days` only exists in the destination currency.
3. During a fallback window, en-gb pages show only a złoty price. UK Price Marking Order 2004 Art. 6(1): "The indication of selling price… shall be in sterling" (legislation.gov.uk/uksi/2004/102/article/6). A lawyer must confirm how this applies before UK checkout opens. The ECB also says its rates are "for information purposes only… transaction purposes strongly discouraged" (ecb.europa.eu, reference-rates page). Your accountant should sign off on using them to set list prices.

**Customer**
1. Large gain: today's złoty prices on English pages go away, and Friday's rate covers the weekend.
2. A euro or pound price can move by one step from day to day. That is honest, and the change is small.
3. Fallback windows (about 16 h after a missed weekday, about 88 h at a Christmas that falls Thu–Fri) show a złoty price on a phone. Rare and truthful, but it will cost some sales.

## 4. Questions the founder should ask
1. Will the repo go private again, and if so, who pays for Actions so this job keeps running?
2. Who receives the job's red email, and do you check `fxSource` on `/api/health`?
3. Are you comfortable that production's build changes twice a day without a `/launch` run (same commit, only the rates differ)?
4. Will a UK lawyer check the złoty-only fallback against PMO Art. 6(1) before UK checkout goes live?
5. Should the ±15% check cover only the currencies you actually show (EUR, GBP, PLN), so a currency you never display cannot block the fetch?

## 5. What looks right
The fetch can never break a build or mix two rate dates, no page makes a network call at request time, and the committed rates are now tied to a real ECB file. The rebuild is pinned to the commit already running, guarded by a check against the `release` tip, and the stale signal is sent once instead of filling the log.
