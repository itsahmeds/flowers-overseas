## 1. Problem

No blog exists. `plan/05` #35 and #36 list a blog index and blog posts as Phase 0 pages, `plan/09` Phase 0 AC 1 expects "blog (≥6 reviewed posts across en/pl)" in the indexed set, and `plan/02` §12 names the intents only editorial content can win: diaspora questions ("how to send flowers to Poland from the UK", "Polish name days explained"), occasion timing, etiquette. Those queries are where a new domain can rank first, and each post passes authority to the corridor and occasion pages that sell (`plan/02` §11). The locale registry already reserves the `blog` segment in every locale (`src/config/locales.data.ts`), and the design system has a blog artboard pair drawn as layout direction only (`docs/design/wireframes/blog-*.dc.html`). Nothing else exists: no route, no content model, no link.

The founder asked for the blog to be in the CMS. `plan/01` §3 and `plan/03` §5 planned posts as MDX files in the repository, which means every post is a pull request, written by an agent or by the founder in a code editor. Spec 012b (approved 2026-10-20) has since made the database the master copy of the catalogue, with a review ledger bound to the exact text and a Publish button that rebuilds the live commit. This spec puts posts on the same machinery, so the founder writes, approves and publishes a post from `/admin` with no code change, and so no agent can make a post public.

### 2.2 Where posts live (slice A; proposed ADR-0023)

- **Posts are database rows**, edited in admin, reviewed through spec 012b's ledger (`review_attestation`), and made public by spec 012b's publish run. No post lives in the repository, and no `content/blog/` directory is created. This replaces `plan/03` §5's "MDX in repo under `content/{locale}/`" row and `plan/05` #36's "MDX" data source, recorded by ADR-0023 (Appendix B) if the founder accepts §13 Q1.
- **A post is written in one locale** (`plan/02` §12: "topics chosen per locale, not translated 1:1"). Slice A accepts `en` only. An `en` post is served at both `/en/blog/{slug}` and `/en-gb/blog/{slug}` with the same text, each self-canonical and hreflang alternates of each other, because a post carries no price, currency or law that differs (spec 041's `extends: en` precedent for trust pages; §13 Q3).
- **Revisions.** A post has a sequence of revisions. The editor saves into the post's one open draft revision; a revision freezes when it is approved or published, and the next edit opens a new draft. The public page serves the post's **published revision** only. Editing a live post therefore never changes or un-indexes what readers and Google see until the new text is approved and its changes are published (§2.6).
- **Authors are real people with an admin account** (`plan/02` §12: "named real people (founder first)... no fabricated personas"). An author record links to exactly one `users` row with a non-empty `display_name`, records the person's agreement to be named, and its byline is that display name (§13 Q4). Only the `admin` role creates or withdraws authors.

### 2.3 The editor and its rules (slice A)

- **Fields of a revision**: title (the `<h1>`, at most 110 characters), slug (on the post, ASCII, lowercase, hyphenated, unique per locale, generated from the title and editable until the first publish), excerpt (120 to 300 characters, rendered under the title and used as `BlogPosting.description`), SEO title (at most 60 characters), SEO description (at most 155 characters), body (the markdown subset below), cover image and its alt text (optional, §2.9), and the honesty allow list (below). On the post: the author, one or more **destination country tags** (ISO codes from the country registry; `plan/02` §12 "carries a `country` tag"), and zero or more **occasion tags** (keys of the occasion registry).
- **The markdown subset** (the corridor body's precedent, `src/modules/geo/content/markdown.ts`): `##` and `###` headings, paragraphs, `**bold**`, `*italic*`, bullet lists (`- `) and numbered lists (`1. `), and links whose target is an **internal reference**. It is parsed into typed blocks, never into an HTML string, so no post can inject markup into a cached document (ADR-0016, ADR-0020). An unknown construct renders as its literal text and the editor shows a warning naming the line. A `#` heading in the body is refused (the title is the only `<h1>`).
- **Internal references, not URLs.** A link is written `[descriptive anchor](fo:<kind>/<id>)`, inserted by the editor's link picker. Slice A kinds: `corridor/<iso2>`, `occasion-hub/<occasionKey>`, `category-hub/<categoryKey>`, `info/<InfoPageId>`, `post/<postId>`. Each resolves per locale through `localePath()` and the target's own existence predicate (`corridorExists`, the listing and info predicates, `blogPostExists`). Country-scoped shop, category, occasion and product pages are **not** linkable in slice A, because they can stop existing between builds (spec 012b §2.3), and a cached post must never carry a link to a 404. A reference whose target does not exist at render renders its anchor as plain text with no `<a>`.
- **Hard rules refuse the save** (each with a stable rule id under `blog/`, the spec 012b §2.5 pattern, run on every save and again on approval and on publish):
  1. Shape: slug rules above; slug not in the reserved set `topic`, `feed`, `page`, `authors`, `rss`; field lengths above; at least one country tag.
  2. **Link flow** (`plan/02` §11 "Blog post: ≥1 corridor and ≥1 occasion/category page, in-body, descriptive anchors"): at least one `corridor/` reference and at least one `occasion-hub/` or `category-hub/` reference that resolve to an existing page in the post's locale; every anchor at least two words and not in the generic-anchor list (`here`, `click here`, `read more`, `this page`, `link`, `more`, and their `de`/`pl` equivalents for slice B).
  3. **Substance**: body at least 500 words; body at least 70 % token-distinct from every other post in the same locale, using the measure `corridor:check` applies to corridor pages (spec 007 §2), extracted into one shared function rather than copied.
  4. **No raw links or contact data**: no URL-, email- or phone-shaped string anywhere in the text (the spec 012b §2.5 rule; links exist only as references).
  5. **The honesty gate** (spec 041 §2, the same lists in `src/config/honesty.ts`, `src/config/voice.ts` and `src/config/freshness-claim.ts`, imported, never copied): no price literal (`PRICE_LITERAL_PATTERN`); no digit-bearing claim of scale (`SCALE_CLAIM_PATTERN`); no relay-language match (`relayMatches`, with no exemption of any kind); none of the banned voice words (`bannedVoiceWordsIn`); no day-count freshness or guarantee claim (`freshnessClaims`, `guaranteeTextViolations`); no competitor brand name (spec 012b's validator); and none of `CLAIM_PATTERNS` (delivery timing, cutoff, delivery date, florist count, rating, review, delivery photo) **unless the exact sentence is in the revision's honesty allow list with a one-line reason**. An allow entry that matches no sentence fails, so the list cannot become a blanket licence. The allow list is part of the approved text (§2.4).
- **Soft rules warn and save** (no override reason needed; shown on the preview): title over 60 characters (it will be truncated in results that use the title); body over 3,000 words; no `##` heading in a body over 800 words.
- **Preview**: `/admin/blog/[postId]/preview` renders the draft revision with the public post template inside the admin shell, `noindex`, `no-store`, behind the admin session, with a banner saying it is a preview. It is the only place a draft renders.

### 2.4 Approval (slice A; spec 012b §2.4 extended)

- **A new ledger subject kind, `blog_post_revision`**: subject reference = the revision id, locale = the post's locale, `value_hash` = the SHA-256 of the canonical form of title, slug, excerpt, SEO title, SEO description, body, cover media id, cover alt, honesty allow list and author id. Changing any of them in a draft changes the hash, so an approval never covers text it did not see.
- **Only `attest()`** (spec 012b, `src/modules/i18n`) writes the approval. Who may approve is spec 012b's rule: a signed-in user with a non-empty `display_name` holding the post's locale in `reviewer_locale` (the founder holds `en` and `en-gb`). The approval dialog shows the revision as it will render and states what the approver attests: "I wrote or edited this text in {language}, and every claim in it is true." `plan/02` §12's machine-translation rule is met by this attestation: a post exists publicly only after a named human, writing in that language, approved its exact text.
- **The database enforces it.** `blog_publish_guard()` refuses to set a post's published revision to a revision that has no `approved` ledger row for its current hash (`BLOG_PUBLISH_WITHOUT_ATTESTATION`); `blog_revision_freeze()` refuses any change to a revision that has been approved or published (`BLOG_REVISION_FROZEN`); `blog_slug_lock()` refuses a slug change once the post has a `first_published_at` (`BLOG_SLUG_LOCKED`). The lint rule `fo/no-direct-review-write` (spec 012b) gains the publish pointer.

### 2.5 Publishing a new post (slice A)

- **Publish post** (in the editor, permission `blog.publish`) sets the post's published revision to the approved one, `status = 'published'` and, the first time, `first_published_at`. The post's URL is a structural change (spec 012b §2.0 item 1: the `[locale]` layout's `dynamicParams = false`), so the action then requests a spec 012b publish run when the existence diff is not empty, exactly as a go-live does (spec 012b §2.8), and the editor shows the run's state. Until the run is `verified`, the post answers 404 and is absent from the index, the sitemap and every link, because runtime existence is "database AND manifest" (spec 012b §2.3).
- **After `verified`**: the post is 200 at `/en/blog/{slug}` and `/en-gb/blog/{slug}`, listed on both blog indexes, in both editorial sitemaps, and the index is reachable from the footer of `en` and `en-gb` (§2.8). Spec 012b's warm step requests each added URL once.

### 2.6 Editing and unpublishing a live post (slice A)

- **Edit**: the first save after a publish opens a new draft revision; the public page keeps serving the published revision. When the new revision is approved, **Publish changes** moves the published pointer and calls `invalidate()` with `blog:post:{postId}`, `blog:{locale}` and `sitemap` (§5.4). The URL does not change, so no rebuild is requested, and the new text is in the edge HTML within 60 s. `dateModified` and the sitemap's `<lastmod>` become the new revision's publish time.
- **Unpublish** (permission `blog.unpublish`, `admin` only, reason required, typed slug to confirm): `status = 'unpublished'`; the URL answers 404 at once (the database half of existence), and the same `invalidate()` set removes it from the index, the sitemap and every other post's links within 60 s. 410 for an unpublished post is a later spec (`plan/02` §7's retired-page rule is the model).
- **Requirement on spec 012b** (§12): its §2.3 guard refuses a publish whose removal list contains a URL indexable in the running deployment once the placeholder window is closed. A blog post URL whose post was unpublished through `unpublishPost`, with its reason on the audit row, is exempt from that refusal; every other removal keeps it. Without the exemption, one unpublished post would block every later publish.
- **Withdrawing an author** (`admin` only) unpublishes each of their published posts in the same transaction, with the reason "author withdrawn", unless the post was first reassigned to another author, which opens a new draft that must be approved again (the author id is in the hash). So no byline outlives the person's agreement to be named.

### 2.7 The public pages (slice A)

| Page | URL (`plan/02` §4.1) | Exists when | Content |
|---|---|---|---|
| Blog index (`plan/05` #35) | `/en/blog`, `/en-gb/blog` | at least one post exists in that locale | `<h1>` and intro (message keys, Appendix A); up to 48 posts, newest `first_published_at` first: title as the link, excerpt, the absolute publish date, the cover thumbnail when present (lazy) |
| Blog post (`plan/05` #36) | `/en/blog/{slug}`, `/en-gb/blog/{slug}` | the post is `published`, has a published revision and is in the build manifest | breadcrumb (home, blog, post); `<h1>`; byline "By {name}"; "Published {date}" and, only when it differs, "Updated {date}", each in a `<time datetime>`; spec 041's `infoPages.status.notYetOpen` line while `anyDeliveryDatesOpen()` is false (an existing reviewed key, so a post about sending flowers never implies we deliver today); the cover image and, for an AI image, spec 006's visible provenance note; the excerpt; the body blocks |

- Both pages resolve through the existing one-route-per-depth files (`[locale]/[segment]/page.tsx`, `[locale]/[segment]/[child]/page.tsx`) and `resolveLocalePath()`, which gains the `blogIndex` and `blogPost` branches, so a path still has exactly one answer (spec 008 §14 A5). An unknown slug, a reserved slug, a casing variant or a `de`/`pl` blog path answers 404 from the router; a trailing slash answers 308 to the bare URL, as on every other page.
- Dates are absolute and formatted by `format.ts` (`Intl.DateTimeFormat`, the locale's long form). No relative time ("3 days ago") appears, so a cached page never states an age that has stopped being true.
- **No commerce on a post in slice A**: no price, no product card, no buy control, no `Offer` (§2.10 and §13 Q5).

### 2.8 Discovery (slice A)

- **Site link.** `site-links.ts` gains a target kind `{ kind: "blogIndex" }` whose per-locale existence is `blogIndexExists(locale)`, and one row `blog` (label `footer.link.blog`, surfaces `footer`), published in the slice A task that builds the index. The footer renders it in a locale only where the index exists, so `de` and `pl` footers do not change in slice A and no link points at a 404 (spec 004 AC-14).
- **Sitemap.** `/sitemaps/{loc}/editorial.xml` (`plan/02` §10) lists the index and every indexable post of the locale, with `xhtml:link` alternates and `<lastmod>` from the published revision's publish time (the index: the newest of its posts). The child is listed in the locale's sitemap index only when non-empty (spec 007 §2: "an absent child is correct; an empty one is noise"). Corridor guides stay in `corridors.xml`, where spec 007 put them.

### 2.9 Cover image (slice A, its own task)

- Optional. The editor attaches an existing `media_asset` with `depicts` `context` or `brand` and `review_state = 'approved'`, uploaded and reviewed through spec 012b §2.7 (the upload route, metadata stripping, provenance by source, spec 006's checklist: no people, no visible address or phone, no other brand). Alt text is required, per revision, non-empty and not a file name, and is in the hash.
- On the post page the cover is the LCP candidate (`priority`, preload, spec 006's variant ladder, fixed aspect ratio, ≤ 200 KB above the fold on mobile, `plan/01` §6); on the index it is a lazy thumbnail. An AI image renders spec 006's visible note (ADR-0014). A post without a cover renders no image block and its `BlogPosting` has no `image`.
- This task depends on spec 012b's photo task (TASK-299). A post can be written, approved and published without a cover before it lands (§13 Q10).

### 2.10 Slice B and C, bounded (not planned now)

- **Corridor to posts**: spec 007's corridor page renders "3 blog posts tagged with the country" (`plan/02` §11) in its reserved slot, gated on a `blog-corridor` site link and the posts' existence; tag `corridor:{iso2}` joins a post's invalidation set.
- **Related posts** on the post page (same country tag, then same occasion tag; up to 3).
- **Live product cards**: `fo:product/<sku>?country=<iso2>` references render a card with the price from spec 005's one price provider in the country's currency, only for a product that exists and is saleable in a `live` country (spec 012b AC-39); otherwise nothing renders. Prices never appear in post text (§13 Q5).
- **Author pages** (`plan/05` #38) with a short bio per locale; the URL uses a number, not the person's name (§13 Q4, `CLAUDE.md` "No PII in... URLs").
- **`pl` and `de` posts**, written in the language and approved by a reviewer holding that locale; optional translation groups so equivalent posts are hreflang alternates; Polish and German sets for the generic-anchor list and the claim patterns. The Polish name-day content `plan/02` §6 places under `/pl/blog` arrives here.
- **RSS 2.0** at `/{locale}/blog/feed.xml`: title, link, date and excerpt of indexable posts only (§13 Q8).
- **Slice C**: topic pages indexable at ≥5 posts; index pagination per `plan/02` §7 (`?page=N` self-canonical, `?page=1` 301) through spec 008's `_query` route.

The evergreen care post (`plan/05` #39, "how to keep flowers fresh") is a candidate too, and the gate will refuse any day-count claim in it.
- **Comments, likes, shares, newsletter sign-up** on posts: each is user content (DSA notice-and-action, `plan/07` §9) or a new personal-data flow with its own lawful basis.
- **External links** in post text in slice A (§13 Q11). **Images inside the body**, tables, embeds, video.
- **Machine drafting of posts** (`i18n:draft` for posts). `plan/02` §12 forbids machine translation for indexable posts; slice A takes typed or pasted text, and the approval attests it.
- **Scheduled publishing**, **a 410 page for unpublished posts**, **a redirect when a slug changes** (slugs lock at first publish instead). Each is a later spec.
- **Moving corridor guides or trust and legal pages into the database.** They stay as spec 007 and spec 041 built them; spec 012b slice B decides their review.
- **Paid placements, affiliate links, sponsored posts.** None exist; adding one is a compliance decision first (§8).
- **Editing `CLAUDE.md`, `plan/*` or an accepted ADR, or creating ADR files.** ADR-0023 is proposed in Appendix B and committed through `/adr` only if the founder accepts §13 Q1.

## 4. User stories

- As the **founder**, I open `/admin/blog`, write "How to send flowers to Poland from the UK", link the Poland guide and the sympathy flowers page from the picker, preview it as readers will see it, approve it under my name, press Publish post, and a few minutes later it is live at `/en/blog/...` and `/en-gb/blog/...`, in the sitemap and in the footer.
- As the **founder fixing a typo in a live post**, I edit, approve and publish the change; the page shows the new text within a minute and nobody saw the half-edited version.
- As a **buyer in Manchester searching "polish name day flowers"**, I land on a real article by a named person that links me to the Poland guide, with no price that might be wrong and no claim the site cannot keep.
- As **Googlebot**, every post I find is server-rendered, self-canonical, has a `BlogPosting` that matches the visible headline, byline and dates word for word, links to at least one corridor and one occasion or category page, and no link points at a page that does not exist.
- As an **implementer agent**, I cannot make a draft public, approve a post or change approved text: the database refuses, and the public database role cannot even read a draft.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

One migration, **`NNNN_blog`**, numbered at implementation after spec 012b's `NNNN_review_attestation` and `NNNN_catalogue_cms` (it alters the ledger's subject-kind check and relies on `app_build`, `withAdminContext` and the audit trigger of TASK-218). It adds no `float`, no `enum`, no extension, and has a hand-written `.down.sql` run by the round-trip test.

1. `blog_author(id uuid PK, user_id uuid NOT NULL UNIQUE FK users, display_name text NOT NULL CHECK (length(trim(display_name)) > 0), consented_at timestamptz NOT NULL, withdrawn_at timestamptz NULL, created_at, updated_at)`. `display_name` is copied from the user at creation and follows later changes to it; the approval hash covers the author's id, not the spelling of the name, so correcting a name needs no new approval, while changing who the author is does.
2. `blog_post(id uuid PK, locale_code text NOT NULL FK locale, slug text NOT NULL, author_id uuid NOT NULL FK blog_author, status text NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','published','unpublished')), published_revision_id uuid NULL, first_published_at timestamptz NULL, unpublished_at timestamptz NULL, unpublish_reason text NULL, translation_group_id uuid NULL, created_at, updated_at, UNIQUE (locale_code, slug), CHECK (status <> 'published' OR published_revision_id IS NOT NULL), CHECK (status <> 'unpublished' OR unpublish_reason IS NOT NULL), CHECK (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'))`. `translation_group_id` is unused until slice B and stays null.
3. `blog_post_revision(id uuid PK, post_id uuid NOT NULL FK blog_post, title text NOT NULL, excerpt text NOT NULL, seo_title text NOT NULL, seo_description text NOT NULL, body_md text NOT NULL, cover_media_id uuid NULL FK media_asset, cover_alt text NULL, honesty_allow jsonb NOT NULL DEFAULT '[]', value_hash char(64) NOT NULL, created_by uuid NOT NULL FK users, created_at timestamptz NOT NULL DEFAULT now(), frozen_at timestamptz NULL, published_at timestamptz NULL, CHECK ((cover_media_id IS NULL) = (cover_alt IS NULL)), CHECK (published_at IS NULL OR frozen_at IS NOT NULL))`, with a partial unique index on `(post_id) WHERE frozen_at IS NULL` (one open draft per post). `frozen_at` is set only by `attest()` on an `approved` decision for the revision, under spec 012b's `app.allow_review_write`, and is never cleared. `blog_post.published_revision_id` then gains its FK (`DEFERRABLE INITIALLY DEFERRED`).
4. `blog_post_country(post_id FK, country_id FK, PK (post_id, country_id))` and `blog_post_occasion(post_id FK, occasion_id FK, PK (post_id, occasion_id))`.
5. Triggers: `blog_revision_hash()` (BEFORE INSERT OR UPDATE on revisions, recomputes `value_hash` from the canonical form `subjectHash()` uses; a contract test pins that both agree), `blog_revision_freeze()`, `blog_publish_guard()` (also refuses a published revision of another post, and any publish while the author is withdrawn), `blog_slug_lock()`; error codes as in §2.4.
6. `review_attestation`'s `subject_kind` check is replaced by the same list plus `'blog_post_revision'`.
7. **RLS and grants**: `app_web` and `app_build` (spec 012b, `app.role = 'public'`) get `SELECT` on `blog_post`, `blog_post_revision`, `blog_post_country`, `blog_post_occasion` and on `blog_author (id, display_name)` only. Public policies: a post row is visible only when `status = 'published'`; a revision only when it is the published revision of a visible post; an author only when they have a visible post. Admin reads and writes through `withAdminContext`. The audit trigger is attached to all five tables.

**Rollback** (`NNNN_blog.down.sql`): detach the triggers, drop the five tables, and restore the previous `subject_kind` check as `NOT VALID`, so any `blog_post_revision` ledger rows stay as history (the ledger is append-only and the down migration deletes none).

**Seed**: none in production. `seed/` gains a fixture author and two fixture posts (one published, one draft) for local, CI and preview, marked `source = 'seed'`, so e2e and visual tests have real pages; `db:seed --insert-only` never writes them in production (spec 012b AC-1).

## 6. SEO considerations (mandatory)

- **Indexability**: one predicate (ADR-0007, spec 007's rule engine). A blog page is indexable iff it exists (which already requires a published, attested revision and the build manifest) **and** `isLocaleIndexable(locale)` **and** `isIndexingEnvironment()`; the `reviewed` term is passed as "the published revision's attestation matches its current hash", so a database edit that bypassed the guard could never index. Robots directive, canonical, alternates and sitemap membership come from the same call. A draft has no public URL at all, which is `plan/02` §6's "not created (404), not `noindex`" applied to editorial.
- **Canonical**: self, absolute, lowercase, no trailing slash, no parameters (`plan/02` §7); never cross-locale. `/en/...` and `/en-gb/...` copies of an `en` post are each self-canonical.
- **hreflang** (`plan/02` §8): from `alternatesFor()` (spec 003), restricted to the locales where the post exists; an `en` post's cluster is `en` with its regional aliases, `en-GB` and `x-default`, reciprocal by construction; no `de` or `pl` alternate in slice A. The same data feeds the `<head>` and the sitemap.
- **URLs** (`plan/02` §4): `/{locale}/blog/{slug}` with the `blog` segment already in `locales.data.ts`; slugs ASCII, lowercase, hyphenated, unique per locale, never one of the reserved child names; slugs lock at first publish, so an indexed URL never moves.
- **Schema** (`plan/02` §9): `BlogPosting` built from the page's view model: `headline` = the `<h1>`, `description` = the visible excerpt, `author` = `Person` with `name` = the visible byline (slice B adds `url` to the author page), `datePublished` and `dateModified` = the visible `<time datetime>` values, `inLanguage` = the document's `lang`, `image` = the rendered cover's URL when present, `mainEntityOfPage` = the canonical, `publisher` = `Organization` with name and logo only. `BreadcrumbList` mirrors the visible breadcrumb on both pages. Never `Product`, `Offer`, `Review`, `AggregateRating`, `FAQPage` or `LocalBusiness` on a blog page. CI validates the fixtures through `seo:validate` (`plan/09` Phase 0 AC 3).
- **Sitemaps** (`plan/02` §10): `editorial.xml` per locale; `<lastmod>` from real publish times, never "now"; nothing `noindex` can appear because membership and robots come from one call.
- **Internal links** (`plan/02` §11, §12): out, at least one corridor and one occasion or category hub per post, in-body, with descriptive anchors, enforced on save, approval and publish; breadcrumb to the index and home. In: the footer (`en`, `en-gb`), the index, other posts. Crawl depth from a locale home: footer → index → post = 2. Links only to pages that cannot disappear between builds (§2.3), and a vanished target renders as text, so the spec 004 AC-14 crawl stays at zero links to a non-200. Slice B adds corridor → 3 posts.
- **Thin content**: at least 500 words, 70 % token-distinct from every other post in the locale, an authored excerpt and SEO fields, a human attestation per revision; the index exists only with at least one post.
- **CWV**: no client JavaScript added to any public page; the cover is the single LCP candidate with variants and a fixed aspect ratio; the JS budget (`plan/01` §7, ≤ 120 KB) is unchanged. Lighthouse gains the fixture post and `/en/blog`; budgets still gate CI.

## 7. i18n considerations (mandatory)

- **Public message keys** (Appendix A, nine keys): `blog.index.h1`, `blog.index.intro`, `blog.index.seoTitle`, `blog.index.seoDescription`, `blog.post.byline`, `blog.post.published`, `blog.post.updated`, `breadcrumb.blog`, `footer.link.blog`. Added to all four catalogues; `en` and `en-gb` approved by the founder as one copy batch; `de` and `pl` are drafts, unused in slice A (no `de` or `pl` blog page exists) but counted in spec 003's unreviewed share. The task measures each locale's share first and, if any would cross 5 %, stops and reports rather than adding them. Admin strings go in `messages/admin/en.json` under `admin.blog`, outside every public share.
- **Post text is data**, not message keys: written per locale, never machine-drafted, approved by a reviewer holding that locale (`plan/03` §6; spec 012b §2.4). Slice A: `en` only, served at `en` and `en-gb`.
- **Formatting**: dates through `format.ts` in the page's locale with month names, absolute only; no number or currency formatting is needed because posts carry no amounts.
- **Slugs**: ASCII-folded per locale (`plan/02` §4), checked by the same slug rule as product copy.
- **RTL**: logical properties only (lint applies); body blocks inherit `dir` from the document; no RTL locale ships.
- **Address and phone formats**: none; phone-shaped strings are refused in post text.
- **Review and `noindex` gating**: existence requires an approval of the exact text; a locale's indexability still comes from `isLocaleIndexable`; an English source change never touches another locale's post because posts are not translations of each other (slice B's translation groups link equivalents for hreflang only). Slice B adds the `de` and `pl` claim-pattern and generic-anchor sets before any `de` or `pl` post can be approved.

## 8. Compliance considerations (mandatory)

- **Data flows added (→ RoPA, updated in the slice A records task)**:
  1. **Authors**: the author's user id, display name and agreement date; the display name is published as the byline and in `BlogPosting.author`. Subjects: the founder, later staff or guest writers with an admin account. Purpose: crediting a real person for published text (`plan/02` §12, trust). Basis: Art. 6(1)(f) for the founder and staff, with the recorded agreement; the right to object is honoured by withdrawal, which unpublishes or reassigns their posts at once (§2.6). Retention: while the author is active; after withdrawal the record keeps only what the audit trail needs, under spec 012's audit retention.
  2. **Approvals**: spec 012b's ledger flow, unchanged (attester name, pseudonymised 3 years after deactivation).
  No buyer or recipient data is read or written. No new processor (Railway publish and R2 storage are spec 012b's).
- **Lawful basis and consent**: no cookie, script, form, comment field or analytics event is added; blog pages load only what every public page loads (spec 004's consent banner, Consent Mode v2 default-denied).
- **Price display** (`plan/07` §4): no price in post text (`PRICE_LITERAL_PATTERN`, hard rule) and no product card in slice A, so no shown price can drift from the charged one; slice B's cards read the one price provider and render only for a saleable product in a `live` country (spec 012b AC-39).
- **Consumer information and unfair practices**: posts never promise what the terms and guarantee do not (the claim patterns, the freshness and guarantee day-count rules, the relay rule with no exemption); no fake urgency or scale claim; no review or testimonial (`plan/07` §7: none exist yet); no competitor named, so no comparative-advertising question arises. Posts are the trader's own editorial, published under the Flowers Overseas name with a named author; no paid or sponsored content exists (§3).
- **Copyright and images**: text is the author's own, attested at approval; covers come only through spec 012b's reviewed media pipeline with provenance and licence; AI images carry spec 006's visible note (ADR-0014); no people in covers, so no model release or personal-data question.
- **Accessibility** (`plan/07` §8; admin and public templates to WCAG 2.2 AA): one `<h1>` and heading levels in order (a `#` in the body is refused); descriptive link text enforced by rule (WCAG 2.4.4); alt text required for every cover; `<time datetime>` for dates; readable line length; axe in CI on both public templates and every admin state; focus and live-region rules for the admin as spec 012b.
- **Logs and PII**: no author email or user id in public HTML or any log line (only post ids, slugs and rule ids); URLs carry slugs that the hard rules keep free of email-, phone- and URL-shaped strings; slice B's author pages use a number, not a name (§13 Q4).
- **Security**: post text becomes typed blocks, never raw HTML, so no stored XSS path and no CSP change (ADR-0016, ADR-0020); the public role reads only published rows (RLS); every admin action checks its permission first and is found by spec 012's enumerated unauthenticated and `noindex` suites.
- **Takedown**: an unlawful or mistaken post comes down at once through Unpublish (§2.6); `docs/runbooks/blog.md` records the steps beside spec 041's takedown runbook.

## 13. Open questions ("044 defaults")

The spec stays `draft` until the founder answers. Each question carries the default the spec is written against; "044 defaults" accepts all of them.

- **Q1. Where do posts live?** **Recommended: in the database, written and approved in admin**, on the same machinery as the bouquets (drafts, your approval under your name, Publish). The alternative, posts as files in the code repository, means every post is a pull request. This changes a line of the plan (`plan/03` §5), so it is recorded as ADR-0023 (Appendix B).
- **Q2. How does a post go live?** A new post appears after Publish (the same rebuild as for new bouquets, a few minutes). An edit to a live post shows within a minute once you approve it, and readers keep seeing the old text until then. **Recommended: yes.**
- **Q3. English posts.** **Recommended: you write a post once in English, and it appears at both `/en/blog/...` and `/en-gb/blog/...`**, linked to each other for Google. A post has no prices, so the two need not differ. A UK-only English version can come later if a post needs one.
- **Q4. Who can be an author?** **Recommended: only real people with an admin account who have agreed to be named, you first; no invented personas.** The byline is the name on their account. Author pages with a short bio come in slice B, at an address with a number rather than the name (`/en/authors/1`), because the project rules forbid personal data in URLs.
- **Q5. Prices in posts.** **Recommended: no prices in the text at all** (the save refuses them), because text cannot follow a price change. In slice B a post can show a bouquet card whose price is read live, only for a bouquet on sale in a live country.
- **Q6. The rules a post must pass.** **Recommended: the same honesty rules as the help and guarantee pages** (no claims about delivery times, florist numbers, reviews or ratings unless you list the sentence with a reason; never prices, numbers of florists or cities, "how many days flowers stay fresh", partner or relay wording, or competitor names), **at least 500 words, and at least one link to a destination guide and one to an occasion or flower-type page.**
- **Q7. Categories and tags.** **Recommended: every post is tagged with at least one destination country and optionally with occasions; no separate category list.** Topic pages come only when a topic has five posts (Phase 2), so none is thin.
- **Q8. RSS and pagination.** **Recommended: RSS in slice B; no pagination until a language has more than 48 posts** (the index shows them all until then).
- **Q9. Taking a post down.** **Recommended: you (admin only) can unpublish any post with a reason; it disappears at once, even after the site is open to Google.** A "gone" (410) page comes later.
- **Q10. Cover images.** **Recommended: optional in slice A**, so the blog does not wait for the photo uploader; when used, the same review and checklist as bouquet photos (no people), and AI images labelled as they are elsewhere.
- **Q11. Links to other websites.** **Recommended: none in slice A**; only links to our own pages, chosen from a list. Citing outside sources can be added later with its own rules.
- **Q12. Order of work.** **Recommended: slice A right after the CMS publishing tasks (TASK-293, TASK-295, TASK-296) merge; slice B when a Polish reviewer is engaged**, since Polish posts (name days) need one.
- **Q13. Copy.** Appendix A lists the nine English labels the blog pages need. **Approving them is your own act**; change any wording you like.

## Appendix B. Proposed ADR-0023: editorial posts live in the database and publish through spec 012b

*Text for `/adr` if the founder accepts §13 Q1. Not an ADR file.*

**Status**: proposed. **Supersedes**: `plan/03` §5's "Blog / guides: MDX in repo" row and `plan/05` #36's data source, for blog posts only (corridor guides, trust and legal pages are unchanged). **Related**: ADR-0007, proposed ADR-0021 and ADR-0022, specs 012b, 041, 044.

**Context.** The plan put posts in the repository as MDX. The founder wants to write them in the CMS, and spec 012b has made the database the master copy of the catalogue, with a review ledger bound to exact text and a Publish that rebuilds the live commit. The `[locale]` layout's `dynamicParams = false` means a URL must exist at build time.

**Options.** (1) MDX in the repository: every post is a pull request; approval is a flag in a file. (2) Database rows edited in admin, approved through the ledger, new URLs published by spec 012b's rebuild, edits by revision with tag invalidation. (3) A hosted headless CMS: a new processor, a second sign-in, and a webhook into the build, for a handful of posts.

**Decision.** Option 2. Posts are database rows with revisions; only a revision attested for its exact text can be published; the public database role reads only published rows; new posts appear at the next publish run; edits appear within 60 s.

**Consequences.** Easier: the founder writes and publishes alone, with no code change, and no agent can publish or approve a post. Harder: the build reads the database for posts as for the catalogue (an outage delays a publish, never takes the site down); backups now also protect editorial text (spec 012b §8); a new post waits a few minutes for a rebuild.
