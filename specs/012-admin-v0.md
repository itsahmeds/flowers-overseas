## 1. Problem

Every switch that decides what the public site shows is a line in a repository file today. Specs 003, 004, 007, 008 and 041 each record the same "bounded, stated deviation" from `CLAUDE.md`'s "Country/partner go-live is a data flip in admin, never a code change": `isLaunch` in `src/config/locales.ts`, `status` / `guidePublished` / `corridorPagePublished` in `src/config/countries.ts`, `published` in `src/config/site-links.ts`, `reviewed` in content frontmatter — and each says the deviation is "retired by spec 012". The catalogue is authored as TypeScript constants (`src/config/catalogue/*.data.ts`, ADR-0017) and projected into `seed/data/**`. The review flags that gate indexing are set by hand in `messages/*.meta.json` and frontmatter: `messages/en.meta.json` holds 526 `"reviewed": true` entries, several with a `reviewedBy` such as "founder (… transcribed by TASK-091)" — written by an agent on the founder's behalf. Nothing stops an agent, a script or a typo from marking text reviewed and thereby making a page indexable (`plan/03` §6 makes that flag the `noindex` gate). `plan/09` reserves `012` for 6–12 Oct: "admin v0 (partners, catalogue, countries, flags, translations queue)"; Phase 0 AC 4 requires the mock order to "appear in `/demo/vendor-inbox` and admin queue within 5 s".

The database is arriving underneath. Spec 002's chain (TASK-013 to TASK-016 merged; TASK-017 to TASK-031 to do) gives every table — `country`, `product*`, `country_price`, `fulfillment_partner*`, `partner_application`, `feature_flag*`, `audit_log`, `users`/`sessions`/`user_role`, `order*` — and the roles and RLS that make admin a session variable rather than a key. It gives no writer and no screen. On 2026-10-04 the founder asked for the rest, verbatim: "also remember site will be live on railway not vercel... also get everything ready for prod and launch whole site... and eveyrthing else. vendor portals cms order management product listing etc ete.. whole backend...". So this spec has four jobs, in order of consequence: decide **where the truth lives** once a human can edit it (the database, with the repo files as seed — §2.1, proposed ADR-0019); make **review an act only a named human can perform** (an attestation ledger bound to the exact text — §2.4, proposed ADR-0020); build the **admin surfaces** `plan/06` §6 schedules for Phase 0 plus the read-only order queue Phase 0 AC 4 needs; and **audit every admin write** in the database itself, so no code path can forget to.

## 2. Scope

Each bullet is testable; §9 names the AC.

### 2.1 The system of record and the migration path (proposed ADR-0019)

**Decision.** Admin writes go to the database. Once an entity family is **cut over**, the database is its only runtime source; the repo files that author it today become **seed**: they populate a fresh database (local, CI, staging) and remain the test fixtures, and they are never read by a production page again. Cutover is one PR per family that swaps the composition root inside the owning module from its static provider to its database provider — the seam specs 003, 005, 006, 007 and 041 built for exactly this, with no call-site change outside the module.

| Family | Phase 0 source (today) | After cutover | Edited in admin v0? | Review authority |
|---|---|---|---|---|
| Products, tiers, add-ons, facets, `partner_only` | `src/config/catalogue/*.data.ts` → `seed/data/*.json` | `product`, `product_tier`, `addon`, `product_category`, `product_occasion` | yes | — |
| Product, category, add-on, occasion **copy** (name, slug, description, SEO fields, intros) | `seed/data/copy/{locale}/*.json` | `*_translation` rows | yes | ledger |
| Country and add-on **prices** | `prices.data.ts` → `seed/data/prices/*` | `country_price`, `addon_country_price` (superseded, never updated) | yes | — |
| Product media, alt text | `seed/data/media.json`, `alt/{locale}.json`, R2 | `media_asset`, `product_media`, `product_media_alt` | yes | ledger (asset approval; alt text) |
| Countries: status, `guidePublished`, `corridorPagePublished`, operations, holidays, occasion rows | `src/config/countries.ts`, `seed/data/holidays.json`, `occasion-country.json` | `country`, `country_holiday`, `occasion_country` | yes | — |
| Locale "advertised and indexable" switch (`isLaunch`) | `src/config/locales.ts` | `feature_flag` `locale.{code}` overlay | yes (flag) | — |
| Site-link `published` | `src/config/site-links.ts` | `feature_flag` `link.{id}` overlay | yes (flag) | — |
| Feature flags | none at runtime | `feature_flag`, `feature_flag_scope` (60 s cache) | yes | — |
| Partners, coverage, blackouts, payouts per product | demo seed (spec 002) | `fulfillment_partner*`, `partner_catalog_mapping` | yes | — |
| UI strings | `messages/{locale}.json` | **stays in the repo** (`plan/03` §5; spec 002 §5.1 design note) | no — reviewers approve or request a change | ledger |
| Corridor guides | `content/corridors/**` | **stays in the repo** for v0 | no — approve only | ledger |
| Trust, help and legal pages | `content/pages/**`, `content/legal/**` (spec 041) | **stays in the repo** for v0; `lawyerReviewed` / `inForce` unchanged | no — approve only | ledger (translation review only) |

**Migration path (per family, in this order, each step a PR or a founder action):** (1) production is migrated and seeded **insert-only** from the files (`pnpm db:seed --insert-only`; a plain seed refuses to run when `APP_ENV=production`); (2) `pnpm attestations:import` carries every review already recorded in a file — with its recorded name and date — into the ledger, once; (3) the family's cutover PR swaps the provider; (4) from then on admin is the editor. Rows an admin has written carry `source = 'real'` (set by the audit trigger, §5.1), so no seed run in any environment can overwrite them (`plan/10` §4). `pnpm seed:diff --target=db` (spec 006) remains as a read-only report of how far production has moved from the files. Rolling a family back is reverting its cutover PR: the static provider returns, database rows stay.

**Builds read the database.** A page built from seed files while checkout charges from the database could show one price and charge another — the one failure `CLAUDE.md` forbids outright. So after cutover `next build` reads the database (Railway build variables in staging and production; CI's `build` job gains the Postgres 16 service, `db:migrate` and `db:seed`, as the integration job already has), and the database-backed routes at URL depths 2 and 3 move to the depth-4 pattern already shipped (`dynamicParams = true`, existence decided by the resolver, `notFound()` otherwise), so a page a go-live flip creates exists without a deploy (§5.4, §13 Q4).

### 2.2 Access: identity, roles, the shell, never indexable

- **Auth.js v5** with the Drizzle adapter over spec 002's `users` / `accounts` / `sessions` / `verification_tokens` (TASK-022), **email magic link sent through Resend** (ADR-0013; §13 Q1), database sessions. The whole auth surface lives under `/admin`: `basePath` `/admin/api/auth`, every Auth.js cookie `Path=/admin`, `Secure`, `HttpOnly`, `SameSite=Lax`, session `maxAge` 12 h (§13 Q6). Nothing is set on, or sent to, a public path.
- **Allowlist, not sign-up.** A link is sent only to an email whose `users` row has an active `admin_profile` and at least one `user_role`; any other address receives the identical page and no email. At most 5 links per address per hour (`auth_email_send`, keyed by a SHA-256 of the normalised address, kept 7 days). No IP is read or stored.
- **Roles** are spec 002's `user_role` (`admin`, `ops`, `finance`, `content`); **reviewer locales** are a new `reviewer_locale` grant. The permission matrix is one constant (`ADMIN_PERMISSIONS`, §5.2) read by the guard, the navigation and the tests. Every server action and route handler under `/admin` calls `requirePermission(…)` before anything else; the admin layout redirects an unauthenticated page request to `/admin/sign-in` (Next's `redirect()`, decided by session state, never by location — ADR-0006 is about geography, and `src/proxy.ts` stays redirect-free).
- **Bootstrap and users.** `pnpm admin:grant --email <e> --name <n> --role <r> [--locale <l>]` creates or updates a user, profile, role and reviewer locale over the direct URL (audit channel `cli`); it is how the founder creates themself. `/admin/users` (admin only) grants and revokes roles and locales and deactivates accounts; revoking or deactivating deletes that user's sessions in the same transaction.
- **Never indexable, never discoverable.** Every `/admin` response — page, sign-in, 401/403/404, server action, `/admin/api/**` — carries `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store, private`; every admin HTML document carries `<meta name="robots" content="noindex,nofollow">`; `robots.txt` keeps `Disallow: /admin/` (spec 007); no sitemap child and no public page links to `/admin`; Cloudflare bypasses `/admin*` (spec 040's existing rule). No locale prefix (`plan/02` §4.1).
- **Admin copy** lives in a separate catalogue, `messages/admin/en.json` (+ `en.meta.json`), typed, ICU, checked by `i18n:check`, loaded only by the admin layout — never in a public bundle and never counted in a public locale's reviewed share. The admin interface is English only in v0 (§13 Q9). The spec 004 §14 A5 voice rule keeps "partner", "vendor" and "corridor" out of customer copy and explicitly allows them in admin, so the banned-word scan in `tests/unit/design-docs.test.ts` exempts `messages/admin/` and `docs/design/wireframes/admin-*` — and only those.

### 2.3 Audit of every admin write (in the database)

- **A trigger, not a convention.** One `audit_row_change()` trigger function is attached to every table admin can write (§5.1 lists them). When `app.role = 'admin'` it writes one `audit_log` row per affected row — actor user id, actor label, `app.audit_action`, table, row id, masked `before`/`after`, `request_id`, `reason`, `channel` — in the same transaction, and sets `source = 'real'` on tables that carry `source`. An admin-context write with no `app.audit_action` raises `AUDIT_ACTION_MISSING` and rolls back, so a new server action cannot ship unaudited.
- `withAdminContext` (spec 002, `src/lib/db.ts`) gains a required `action` (dotted, e.g. `country.status.live`) and optional `reason`, issued as `SET LOCAL app.audit_action` / `app.audit_reason`.
- `audit_log` becomes **append-only** (UPDATE/DELETE raise). Columns holding personal data are written masked (`partner.contact_email`, `partner.contact_phone`, `partner.legal_name`, every `partner_application` contact field) — the log records *that* they changed, never what they were.
- **Go-live only in admin, enforced by Postgres.** An `UPDATE` that changes `country.status` or `fulfillment_partner.status` outside an admin context raises `STATUS_FLIP_OUTSIDE_ADMIN` — including a raw `UPDATE` in a migration run as `app_owner`. Inserts (the seed) are untouched. This is `plan/10` §4's "no PR flips a country or partner status through code or migration" made a database fact rather than a review item.
- **Reads of personal data are logged too.** Opening an order detail or an application detail writes an `audit_log` row (`order.viewed`, `application.viewed`; no before/after) — who looked at whose recipient or contact data (§13 Q10).
- `/admin/audit` (admin only): filter by entity, actor, action and date; masked values render as "changed".

### 2.4 Review as attestation (proposed ADR-0020) and the translations queue

- **The ledger.** `review_attestation` is append-only, like `order_event`. Each row binds a **decision** (`approved` / `changes_requested` / `rejected`) to a **subject** (kind + reference + field + locale), the **SHA-256 of the exact text** reviewed (`value_hash`), the hash of the English source it was reviewed against (`source_hash`), the **attester's user id and name** and the **server time**. A subject is *reviewed* exactly when its latest decision is `approved` **and** its `value_hash` equals the hash of the text served now. Change one character and it is unreviewed; change only the English source and it stays reviewed but is flagged *stale* (`plan/03` §6 step 5).
- **One writer.** `attest()` in the `i18n` module is the only code that writes the ledger and the only code that may set the denormalised `reviewed` / `reviewed_by` / `reviewed_at` columns (and `media_asset.review_state`). Postgres enforces it: those columns change only under `SET LOCAL app.allow_review_write = 'on'` **and** only with a matching ledger row in the same transaction (`REVIEW_DIRECT_WRITE`, `REVIEW_WITHOUT_ATTESTATION`) — the order-status guard of spec 002, applied to review. A lint rule `fo/no-direct-review-write` catches the attempt before the database does.
- **Who may attest.** A signed-in user with a non-empty `display_name` and the subject's locale in their `reviewer_locale` grants (media approval: the `media.review` permission). The founder is granted `en` and `en-gb`; native reviewers their own language (§13 Q3). The name on the record is the profile's `display_name`; the date is the database's `now()`.
- **Files stop claiming review.** After the import, the `reviewed`, `reviewedBy` and `reviewedAt` fields are removed from `messages/*.meta.json`, corridor frontmatter, info/legal frontmatter and `seed/data/copy/**`; `i18n:check`, `corridor:check`, the spec 041 content gate and `seed:check` fail on a file that adds one back. A file-backed text's review is the ledger's answer for its current hash, computed at build into the generated typed index the corridor and content modules already use.
- **The import** (`pnpm attestations:import`) is the one bridge: every file entry with `reviewed: true` **and** a recorded name **and** date becomes a ledger row with `channel = 'import'`, that name and that date; an entry missing either is imported as unreviewed and listed in the report. It is idempotent, it writes `seed/data/attestations.json` (the seed snapshot for fresh databases and tests), and the queue shows imported approvals under their own filter so the founder can re-confirm them in admin (§13 Q2).
- **The queue** — `/admin/translations`: per locale, every subject that is unreviewed (machine draft, never attested, or edited since), stale, or has a change requested, grouped by kind (UI strings, product copy, category and occasion intros, add-on copy, corridor guides, trust and legal pages, image alt text, images), with counts; side by side source and target; glossary terms from `content/i18n/glossary.{locale}.md` highlighted; **Approve** (writes `approved`) and **Request change** (note required, optional suggested text). Database-backed text (catalogue copy) is editable in place; repo-backed text (UI strings, guides, pages) is read-only with its file path, and `pnpm i18n:requests` prints every open change request for an implementer to apply in a normal PR.
- **Indexability reads the ledger.** `isLocaleIndexable()`, the locale beta tag, the corridor, info-page and product indexability predicates, hreflang alternates and sitemap membership all read review state through an `AttestationProvider` (database implementation at runtime with a 60 s cache; snapshot implementation in tests), so the one predicate of spec 007 stays one predicate with a new source.

### 2.5 Catalogue CMS (product listing management)

- **Products**: list (filters: type, status, facet, priced country, review state) and create/edit — SKU, the six facets from the closed taxonomy (`src/config/catalogue/schemas.ts`; a new facet value is a code change), stem count, vase, freshness days, substitution class, `partner_only`, status. `draft → active` requires an `en` name, slug and description, at least one tier with exactly one default, and an active price in at least one country. `active → retired` is refused while the product is priced in a country that is or has ever been `live` (the 200-with-alternatives-then-410 page `plan/02` §7 requires does not exist yet — §3).
- **Tiers** (key, label key, stems, sort, default) and **add-ons** (copy, allergen note, per-country prices; the wine add-on stays behind `addon.wine.{country}`).
- **Copy per locale** (name, slug, description, SEO title and description; category and occasion intros): edited in a locale only by a user granted that locale; saving changes the text hash, so the subject drops out of *reviewed* until attested (§2.4). **Slugs** are editable only while no country the entity is shown in is or has ever been `live`; after that a slug change needs redirect history (§3).
- **Validators are shared with the gates.** The rules `catalogue:check` and `seed:check` apply to files are extracted into pure functions in `catalog` and run on every admin save. **Hard rules block** (slug shape and uniqueness, integer minor units, currency equals the country's, one open price row, banned words, no price literal in copy, `seoTitle` ≤ 60, `seoDescription` ≤ 155, no PII- or competitor-shaped strings); **soft rules warn** (price outside its `plan/10` §2.3 band, description outside 60–90 words, psychological ending) and save only with an override reason, stored on the audit row.
- **Prices** (`country_price`, `addon_country_price`): amounts are typed as a decimal string and parsed to integer minor units by string arithmetic against the currency's exponent (no float at any step; `.` or `,` as the decimal separator; no grouping). A change **supersedes**: the open row gets `active_to = today` (country zone) and a new row opens — `retail_minor` is never updated. The confirm step shows the formatted old and new price in every launch locale, the change in per cent, a warning beyond ±30%, and the 30-day lowest price (`lowestPriceInLast30Days`, spec 005). One change per (product, country, tier, surcharge) per calendar day (§13 Q8). The form has no buyer-country field and no "price excluding VAT" input: the amount typed is the all-in price.
- **Margin view** per (product, tier, country): gross retail, VAT, net, the lowest and highest payout among active and onboarding partners mapped to it, and the margin — integer minor units, converted through spec 005's `convert()` with a dated rate when the payout currency differs, never a float (`plan/06` §6 "margin view").

### 2.6 Media (attach and review)

- **Upload** in admin: the original goes to R2 under `originals/{assetId}` through `src/lib/storage.ts`, a `media_asset` row is written with the provenance spec 006 §2.4 requires (source, generator, model, prompt hash, seed, credit, licence, depicts), and `media.derive_variants` (spec 006's worker) is enqueued; variants are EXIF/GPS-stripped by that worker. `depicts = 'delivery'` is refused (delivery photos are spec 018/027/029, with consent).
- **Review**: `pending → approved | rejected` through `attest()` (kind `media_asset`), with the spec 006 checklist shown beside the image. An asset that is not approved cannot be attached as primary and is never rendered (spec 006's honest-placeholder rule).
- **Attach** to a product: sort, one primary (the partial unique index of spec 002), alt text per locale (`product_media_alt`, required to render in that locale; reviewed through the queue as kind `media_alt`).

### 2.7 Countries and the go-live flip

- `/admin/countries` lists every country with status, guide flag, live partners and priced products. A country's page edits operations (`vat_rate_bp`, IANA zone, same-day cutoff, delivery days, Sunday rule, `supply_model`), holidays and `occasion_country` rows, each validated by the zod schemas the seed uses.
- **Go-live preflight** (`demo → live`) lists every unmet condition and offers the action only when none remain: operations complete; `vat_rate_bp` and `supply_model` set (the accountant's answer, `plan/06` §4); at least one `active` partner whose coverage is in the country; every `active` product the country lists has an open price; a `live`-state corridor text that is reviewed in at least `en`; the country not on the sanctions list (`plan/07` §9). The flip asks for the ISO code to be typed, writes one row, is audited, and then invalidates (§5.4).
- `live → demo` is the rollback (pages return to `noindex,follow` and leave the sitemaps; the corridor returns to its guide state). `demo → disabled` and `disabled → demo` are allowed; `live → disabled` is refused in v0, because a once-published corridor must answer 410, which spec 007 places in Phase 1 (§13 Q11).
- **Partner go-live** is the same pattern in §2.9; neither flip is possible outside admin (§2.3).

### 2.8 Flags, locales, site links

- `src/config/feature-flags.ts` is the **registry**: every key, its scope kinds, a description, a risk level, and the cache tags a change dirties. `src/lib/flags.ts` reads `feature_flag` / `feature_flag_scope` with a 60 s in-process cache (spec 002: flags in the database, never in env). Admin lists and toggles only registered keys; a key in the database that the registry does not name is shown as orphaned and cannot be toggled.
- **High-risk flags** (`checkout.demo_guard`, `payments.stripe`, `payments.mollie`) are admin-only and need the key typed to confirm.
- **Locale switch.** `locale.{code}` overlays `isLaunch` through `LocaleRegistryProvider` (the seam spec 003 built): off means not advertised in the switcher, not indexable, absent from hreflang and sitemaps. **Routability does not change** — the four locale segments stay built and answer 200 `noindex`; adding a fifth locale remains config + catalogue + review (code), as spec 003 requires.
- **Site links.** `link.{id}` overlays `published` in `site-links.ts` through the existing `isPublished()` predicate; a link may be published only when its target page exists (`existsFor(linkId)`), so a flag cannot create a link to a 404.

### 2.9 Partners and applications

- **Partners**: create (status `onboarding`; `demo` is seed-only), edit (legal name, city label, country, notification channel, contact email, contact phone validated as E.164 for the partner's country, payout currency, capacity per day), **terms** (`terms_signed_at` + `terms_version` — the partner agreement with its Art. 28 processor clauses, `plan/07` §1.1), coverage (city or postcode zone, capacity), blackout dates, and the **catalogue mapping** (product, tier, can fulfil, payout as integer minor units + currency).
- **Status graph**: `onboarding → active | offboarded`, `active → paused | offboarded`, `paused → active | offboarded`; `demo` rows can move only to `offboarded`. `→ active` requires signed terms, at least one coverage row, at least one fulfillable mapping with a payout, and the contact for the chosen channel. Partner names and contacts never appear on a public page in v0 (`plan/09` Phase 0 AC 6; public profiles are a later spec).
- **Applications** (`partner_application`, written by spec 011's form): list and detail; `new → contacted → converted | rejected`; **convert** creates an `onboarding` partner pre-filled from the application and links it; **reject** needs a reason. Applications never converted are deleted 12 months after their last change by `retention.sweep` (§13 Q5).

### 2.10 Order queue (read-only in v0) and transitions through the service

- `/admin/orders`: newest first, 50 per page, filters by status, destination country, delivery date and created date. A row shows the short order id, created time, delivery date in the destination zone, destination city, internal status with its buyer projection, total via `formatMoney`, assigned partner and a demo marker when the order carries spec 010's demo flag. **No recipient name, phone or street in the list.**
- **Arrival within 5 s.** While the page is visible, a small client island polls `GET /admin/api/orders/head` (`{ latestCreatedAt, count }`) every 3 s and refreshes the server-rendered list when it changes; it pauses after 15 minutes without interaction and says so, so an idle tab does not keep Neon's compute awake (spec 002 §11).
- `/admin/orders/[id]`: lines, totals and VAT breakdown, recipient snapshot (only for `orders.view_pii`), the `order_event` timeline with raw payloads expandable, assignments, payments (read). Opening it is logged (§2.3). The order's `public_token` never appears in admin HTML, URLs or logs.

## 4. User stories

- As the **founder taking Poland live**, I open Poland in admin, read a checklist that tells me exactly what is missing, fix it, type `PL`, and within a minute the Polish pages are live, indexable and in the sitemap — with no deploy and no code.
- As the **founder changing a price**, I type `249.00` for PLN, see what it will look like in all four languages, see the change in per cent and the lowest price of the last 30 days, and confirm; the old price stays on record, and the product page, its structured data and the checkout all show the new one.
- As a **native Polish reviewer**, I sign in with a link in my email, see only Polish, read each text beside its English source, and either approve it under my name or say what to change. Nothing I have not approved can make a Polish page indexable, and nobody else can approve in my name.
- As the **founder**, every change anyone made in admin is in a log I can filter, and none of it can be edited afterwards — including by me.
- As **Googlebot**, I never see an admin URL, and a page becomes indexable only after a named person approved the exact words on it.
- As the **founder during the 16 October demo**, the mock order a florist just placed appears on my order screen within five seconds.
- As the **founder onboarding a Warsaw florist**, I convert their application, record their signed terms, map their payouts, set their coverage and switch them to active; the switch refuses until the terms are recorded.
- As an **implementer agent**, I cannot mark text reviewed, flip a country or skip the audit by writing SQL or editing a file: the database refuses.

### 5.4 Rendering & caching (per plan/01 §3)

- **Admin**: SSR `no-store`, auth-gated, `noindex` (`plan/01` §3 "Account, admin, vendor portal"); never cached at the edge (spec 040's bypass rule); the database is on the request path, as it must be for an editor.
- **Public pages after cutover**: still ISR (`revalidate` 3600 as a backstop) and still HTML at the edge; the database is read only when a page is (re)generated, never on a cache hit (spec 002 §5.4). Builds read the database (§2.1); `generateStaticParams` prebuilds what `plan/01` §3 names (live countries, top products) from it.
- **Existence at request time.** The depth-2 and depth-3 routes (`src/app/[locale]/[segment]/page.tsx`, `[segment]/[child]/page.tsx`) move from `dynamicParams = false` to the depth-4 pattern: `dynamicParams = true`, and the existing resolver returns `notFound()` for anything the data does not contain — so a corridor, shop or category page created by a go-live flip exists without a rebuild, and every unknown slug or casing still answers 404. This is an amendment to the routing of specs 007 and 008, owned by task 6 and recorded in their §14 by the orchestrator. The `[locale]` segment keeps `dynamicParams = false` (locale routability stays code, §2.8).
- **Invalidation.** Every admin write calls `invalidate()` with the tag set its command returns (the command, not the page, knows what it dirtied): price → `product:{id}`, `catalog:{iso2}`; copy → `product:{id}` (or the category/occasion listing tags), `sitemap`; country status → `country:{iso2}`, `corridor:{iso2}`, `catalog:{iso2}`, `hub:{locale}` ×4, `home:{locale}` ×4, `sitemap`; flags → the tags the registry declares; attestation → the subject's page tags and, for messages, every document of that locale. `invalidate()` revalidates the Railway origin first (single replica, so one `revalidatePath` per URL is enough — spec 040), then purges Cloudflare by URL. Target: the change is visible at the edge within **60 s**.
- `pnpm cache:warm` requests every sitemap URL once after a deploy and after a country flip, so the first buyer after a change does not pay for the render.

## 6. SEO considerations (mandatory)

Admin is the lever that decides what Google may see, so its SEO surface is less about its own pages (which must be invisible) than about making every indexability change deliberate, reversible and correct.

- **Indexability of admin**: none, by five independent means (§2.2): `X-Robots-Tag` on every response, meta robots, `robots.txt` disallow, no sitemap membership, no inbound link from any public page; plus Cloudflare bypass and `no-store`. Admin has no locale prefix and no canonical (`plan/02` §4.1).
- **Indexability is still one predicate**, now fed by data (ADR-0007, spec 007's rule engine): `country.status`, the corridor flags, `locale.{code}`, the six-product floor (spec 008's loader, unchanged), and review state from the ledger. Nothing in admin writes an indexability flag directly; it writes the facts the predicate reads.
- **Go-live preflight prevents thin and false pages**: a country cannot go live without operations data (so no cutoff is invented), an active partner (so no unbuyable `Offer` is indexed), open prices for every listed product (so no product page without an `Offer`), and a reviewed live-state guide (`plan/02` §5.1–§5.2). Rollback (`live → demo`) returns pages to `noindex,follow` rather than deleting them; `live → disabled` is refused until 410 handling exists.
- **Canonical and URL stability**: slugs lock once an entity has been shown on a page in a live country (§2.5), and retiring such a product is refused until the retired-page behaviour of `plan/02` §7 exists; so admin cannot orphan an indexed URL or create a duplicate canonical. Slug rules (ASCII, lowercase, hyphenated, unique per locale, `plan/02` §4) are the same validators the seed gate runs.
- **hreflang**: an alternate exists only for a locale whose text on that page is attested for its current hash; editing a Polish description removes the Polish alternate (and the page's indexability) until re-approved, and adds it back after — reciprocity is preserved because the cluster and the sitemap are generated from the same predicate (`plan/02` §8).
- **Schema and price**: `Offer.price` equals the visible price equals the charged amount after every admin price change, because prices are superseded rows read by spec 005's single `priceProjection()`; the Omnibus 30-day lowest price keeps its history because rows are never updated. Partner names never reach a page, so no `LocalBusiness` claim can appear (`plan/02` §9).
- **Sitemaps and `<lastmod>`**: admin writes advance `updated_at` (spec 002 trigger), so `<lastmod>` stays truthful; a flip purges the sitemap index and children (§5.4), so membership changes within 60 s of the predicate changing.
- **Thin and duplicate content**: the shared validators block or flag short and duplicate descriptions, banned superlatives and price literals in copy on every admin save, not just in CI over files.
- **Internal links**: `link.{id}` cannot publish a link whose target does not exist (§2.8), keeping spec 004's "no link to a non-200" rule under admin control.
- **CWV**: public pages ship no new JavaScript. The routing change makes un-prebuilt pages render on first request (TTFB on a miss); `cache:warm` and prebuilt live countries keep the measured Lighthouse URL set warm; the existing budgets are unchanged and still gate CI. Admin's own JavaScript is not on any public page.
- **Crawl efficiency**: unchanged; `/admin/` and `/admin/api/` are disallowed and return a redirect or 401 without content to an unauthenticated client.

## 7. i18n considerations (mandatory)

- **New message keys**: one new catalogue, `messages/admin/en.json`, namespaces `admin.nav`, `admin.signIn`, `admin.orders`, `admin.translations`, `admin.catalogue`, `admin.media`, `admin.countries`, `admin.flags`, `admin.partners`, `admin.applications`, `admin.audit`, `admin.users`, `admin.errors`, `admin.confirm`. It is excluded from public reviewed shares and from `de`/`pl` drafting; `i18n:check` still parses it, checks ICU and unused keys. The magic-link email reads it too. No public namespace changes.
- **Formatting**: every number, amount, date and time goes through `src/modules/i18n/format.ts` with an explicit zone (spec 003 §14 A10): delivery dates and cutoffs in the destination's zone, order and audit instants in the viewer's `admin_profile.time_zone`, always with the zone named. Price previews render the amount with `formatMoney` in all four launch locales so the founder sees `229,00 zł` and `PLN 229.00` before confirming. Money input is parsed by string against the currency's exponent, never by `parseFloat` (`fo/no-float-money` covers the module).
- **RTL**: admin uses logical properties only (lint applies); no RTL locale ships.
- **Address and phone formats**: partner phones are E.164 validated against the partner's country (spec 003's phone data); recipient addresses are displayed with `formatAddressBlock()` for the destination country; nothing new is captured from buyers.
- **Translation review plan and `noindex` gating — this spec is the plan's mechanism** (`plan/03` §6): drafts arrive as unreviewed (spec 003's `i18n:draft`, admin edits), the queue lists them, a granted native reviewer attests the exact text, indexability and hreflang read the ledger, edits and source changes reopen the subject. Corridor guides and legal text still never ship machine-only (their gates keep refusing `source: machine`); `isLocaleIndexable()` keeps its 5% rule with the ledger as its input. Imported approvals are visible as such so the founder can re-confirm them (§13 Q2).

## 8. Compliance considerations (mandatory)

- **Data flows added (→ RoPA, updated by the reviewer at PASS)**:
  1. **Admin users and reviewers** — email, display name, roles, reviewer locales, sessions, sign-in send times (hashed address). Subjects: the founder, contractors (native reviewers). Purpose: access control and accountability. Basis: Art. 6(1)(b) for contractors, 6(1)(f) for accountability records. Retention: sessions until expiry; send log 7 days; attestation names pseudonymised 3 years after deactivation (§13 Q5).
  2. **Resend (sign-in email)** — new processor use (ADR-0013 named it for Phase 1; admin sign-in is its first use): admin email addresses and the link. EU data region, DPA accepted and filed (founder action, §12).
  3. **Partner and applicant contact data** — business and contact names, email, phone (personal data for sole traders); `partner_application` from spec 011. Basis: 6(1)(b) pre-contract and contract. Retention: unconverted applications 12 months; partners per `plan/07` §1.2 (contract + 10 years financial).
  4. **Audit log** — actor ids, actions, masked before/after; reads of order and application detail. Basis: 6(1)(f) and Art. 5(2)/32 accountability. Retention 3 years.
  Recipient data is not newly collected; admin and ops can *view* it (need to know, `orders.view_pii`), finance and content cannot, and every view is logged.
- **Lawful basis and consent**: no consent is required — no non-essential cookie or script is added. Auth.js cookies are strictly necessary, set only on `/admin`, and added to `docs/compliance/cookie-register.md` (`plan/07` §5). No analytics on admin.
- **Price display (`plan/07` §4)**: the amount typed is by definition the all-in price (VAT and delivery included); the form has no net-price input and no buyer-country dimension; changes supersede so the Omnibus 30-day lowest price (`plan/07` §2.1) is always computable; surcharges remain rows shown on the date chip (spec 005/009 unchanged).
- **Geo-blocking (EU 2018/302)**: admin can set prices by destination only; there is no field that could vary access or price by buyer location (ADR-0006).
- **Consumer information**: the go-live preflight requires `supply_model` (the accountant's answer, `plan/06` §4) before a country can take orders; partner activation requires signed terms with processor clauses (`plan/07` §1.1, §1.3: florists receive recipient data only under Art. 28 terms).
- **Reviews (Omnibus)**: admin offers no way to create a review or testimonial (review moderation is spec 022); demo rows stay marked.
- **Sanctions (`plan/07` §9)**: a sanctioned destination cannot go live (preflight) and is set `disabled`.
- **Accessibility**: admin targets WCAG 2.1 AA like the site (contractors and future staff use it; UK Equality Act duties apply regardless of size, `plan/07` §8): axe runs on every admin template in CI, forms have programmatic labels and error association, the confirmation dialog traps and returns focus, the poll island announces new orders through a polite live region.
- **Logs and PII**: no email, name, phone, address, token or magic link in any log line; Auth.js's logger is routed through `src/lib/logger.ts` with its redaction list (gaining `identifier`, `email`, `token`, `display_name`, `attester_name`); `public_token` never appears in admin; audit values are masked for personal columns; URLs carry ids only (`plan/07` §1.3, `CLAUDE.md`).
- **Security**: allowlisted sign-in, 5 links per address per hour, database sessions revoked on role change, 12-hour sessions, server-action origin checks (Next), a permission check as the first statement of every action (proved by a source scan and by calling each action unauthenticated), least privilege per role, `app_web` without `BYPASSRLS` (spec 002).

## 9. Acceptance criteria

**Access and invisibility**
- **AC-1** Without a session, every `/admin/**` page except `/admin/sign-in` answers a 3xx redirect whose `Location` is `/admin/sign-in`, with no admin data in the body, and every admin server action and `/admin/api/**` handler (auth endpoints excepted) answers 401 and writes nothing; the set of routes and actions tested is enumerated from the file tree, not listed by hand.
- **AC-2** A sign-in request for an allowlisted email sends exactly one Resend message; for any other email the response is byte-identical and zero messages are sent; the sixth request for one address within an hour sends nothing.
- **AC-3** Auth.js cookies carry `Path=/admin`, `Secure`, `HttpOnly`, `SameSite=Lax` and expire within 12 h; no public response sets or names an Auth.js cookie; revoking a user's role or deactivating them makes their next request unauthenticated.
- **AC-4** For every (role, permission) cell of `ADMIN_PERMISSIONS` the guard allows exactly the marked cells; a denied action answers 403 and changes no row; a `content` user with reviewer locale `pl` gets 403 on a `de` copy edit or attestation.
- **AC-5** Every `/admin` response — pages, sign-in, 401/403/404, server actions, `/admin/api/**`, auth endpoints — carries `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store, private`, and every admin HTML document carries `<meta name="robots" content="noindex,nofollow">`.
- **AC-6** `robots.txt` disallows `/admin/`; no sitemap child contains an `/admin` URL; no HTML document in the built public URL set contains an `href` beginning `/admin`.

**Audit**

## 11. Observability

- **Every admin write is an `audit_log` row** with `request_id`, actor and action (§2.3); the log line for the request carries the same `request_id`, the action name and the duration — never values.
- **Events logged** (`info`, no PII): `admin.sign_in.sent` (hashed identifier only), `admin.sign_in.refused` (reason: not allowlisted / rate limited), `admin.session.revoked`, `admin.country.status` (iso2, from, to), `admin.partner.status` (code, from, to), `admin.price.superseded` (product id, country, tier), `admin.attestation` (kind, locale, decision — not the attester), `admin.flag.toggled` (key, scope), `cache.invalidate` (tags, URL count, origin and edge outcomes).
- **Warnings and Sentry**: a failed purge or origin revalidation after a write (`warn` + Sentry, with the tags) — the change is saved but not yet visible; `REVIEW_*`, `AUDIT_ACTION_MISSING` and `STATUS_FLIP_OUTSIDE_ADMIN` raised in production (`error` + Sentry: they mean a bug or a bypass attempt).
- **Cost signals**: the order poll pauses after 15 minutes idle, and `neon.usage_probe` (spec 002) is the place to see admin's share of compute; builds now read the database, so build count shows in the same probe.
- **Not instrumented here**: order-lifecycle alerts (`paid` without `routed`, SLA cascade) belong to spec 025; admin analytics to `plan/11` §7.

## 12. Rollout

- **Feature flags.** Admin itself is not flagged: it exists in every environment and is useless without a granted account. ## 13. Open questions

Each has a recommended default; the spec stays `draft` until the founder answers or accepts the defaults.

- **Q1 — How do you and your reviewers sign in?** Options: a sign-in link by email (needs a Resend account and two DNS records), or "Sign in with Google". **Recommended: the email link**, because reviewers need nothing but an email address, Resend is already the chosen email service for order emails, and only addresses you have added can receive a link.
- **Q2 — Does the database become the master copy (proposed ADR-0019), and is UI text, country guides and info/legal pages editing left to a later admin spec?** **Recommended: yes to both.** Products, copy, prices, images, countries, flags and partners are edited in admin and the repo files become the starting data; UI text, country guides and info/legal pages stay in git for now (reviewers approve them in admin or ask for a change). Also recommended: the approvals already written in files (526 English UI strings, among others) are carried over marked "imported", so English pages stay indexable on the day of the switch, and you re-confirm the ones you stand behind in the queue.
- **Q3 — Only a named person can approve text, bound to the exact words (proposed ADR-0020) — and may you approve German or Polish yourself?** **Recommended: yes to the ledger; you are granted English and British English only, and native reviewers their own language.** You can grant yourself another language (it is logged), but the default keeps an honest "a native speaker read this".
- **Q4 — The website build will read the database, and pages created by a go-live switch appear without a rebuild.** This means the CI build gets a small test database and URL depths 2 and 3 work like product pages already do. **Recommended: yes** — the alternative (build from files) could show one price and charge another.
- **Q5 — How long to keep things.** **Recommended:** florist applications never converted: deleted after 12 months; audit log: 3 years (personal values already masked); reviewers' names on approvals: replaced by "Reviewer n" 3 years after their account is closed; sign-in send log: 7 days.
- **Q6 — Session length and second factor.** **Recommended: 12-hour sessions, no second factor in v0**; add passkeys when someone other than you and reviewers gets access to orders.
- **Q7 — Order actions wait for the order service (spec 015).** **Recommended: yes** — in Phase 0 the order queue is read-only (orders appear within 5 s, you can open each one); the action buttons arrive with spec 015, because the rule is that order status changes only through that service.
- **Q8 — Price changes: one change per product, size and country per day.** Every price shown must stay on record for the 30-day lowest-price rule, so a price cannot be silently overwritten. The confirm step shows the new price in all four languages and warns above ±30%. **Recommended: accept**; a price that must vanish the same day is handled by moving the country back to demo.
- **Q9 — Admin in English only for now.** **Recommended: yes**; a Polish admin for reviewers is cheap to add later because every admin string is already a message key.
- **Q10 — Log who opened an order's recipient details or a florist application.** **Recommended: yes** — cheap, and it is the evidence a data-protection question would ask for.
- **Q11 — A live country can go back to demo but not to "disabled" in v0.** Disabling a country that was once public needs a "gone" (410) page that is scheduled for Phase 1. **Recommended: accept.**
- **Q12 — Vendor portal timing.** Your 2026-10-04 message asks for vendor portals too. They are specs 026–027 in Phase 2; until then florists act through links in their email and WhatsApp (Phase 1), and you edit their coverage, capacity and days off here. **Recommended: keep the portal in Phase 2**; bringing it forward is a roadmap decision for `/status`, not part of this spec.
