## 1. Problem

Every switch that decides what the public site shows is a line in a repository file today. Specs 003, 004, 007, 008 and 041 each record the same "bounded, stated deviation" from `CLAUDE.md`'s "Country/partner go-live is a data flip in admin, never a code change": `isLaunch` in `src/config/locales.ts`, `status` / `guidePublished` / `corridorPagePublished` in `src/config/countries.ts`, `published` in `src/config/site-links.ts`, `reviewed` in content frontmatter — and each says the deviation is "retired by spec 012". The catalogue is authored as TypeScript constants (`src/config/catalogue/*.data.ts`, ADR-0017) and projected into `seed/data/**`. The review flags that gate indexing are set by hand in `messages/*.meta.json` and frontmatter: `messages/en.meta.json` holds 526 `"reviewed": true` entries, several with a `reviewedBy` such as "founder (… transcribed by TASK-091)" — written by an agent on the founder's behalf. Nothing stops an agent, a script or a typo from marking text reviewed and thereby making a page indexable (`plan/03` §6 makes that flag the `noindex` gate). `plan/09` reserves `012` for 6–12 Oct: "admin v0 (partners, catalogue, countries, flags, translations queue)"; Phase 0 AC 4 requires the mock order to "appear in `/demo/vendor-inbox` and admin queue within 5 s".

The database is arriving underneath. Spec 002's chain (TASK-013 to TASK-016 merged; TASK-017 to TASK-031 to do) gives every table — `country`, `product*`, `country_price`, `fulfillment_partner*`, `partner_application`, `feature_flag*`, `audit_log`, `users`/`sessions`/`user_role`, `order*` — and the roles and RLS that make admin a session variable rather than a key. It gives no writer and no screen. On 2026-10-04 the founder asked for the rest, verbatim: "also remember site will be live on railway not vercel... also get everything ready for prod and launch whole site... and eveyrthing else. vendor portals cms order management product listing etc ete.. whole backend...".

The first draft of this spec answered all of it at once: where the truth lives once a human can edit it, review as an act only a named human can perform, the full set of admin screens, and an audit of every write. The advisor's review of 2026-10-04 (H1) found that this packs a large architecture change into a Phase 0 spec. It split the spec. **Admin v0** (this spec, Phase 0) builds what the demo and the first florists need now:

- one sign-in core, shared with spec 011's florist inbox;
- the audit trail and the database guard on status flips;
- partners and applications;
- the read-only order queue Phase 0 AC 4 needs;
- the records;
- a flags page for the two database flags spec 010's checkout reads.

**Spec 012b** (§15) takes the architecture change: the database as master copy (proposed ADR-0019), review as an attestation ledger (proposed ADR-0020), the catalogue editor, media, country go-live, and the locale and link overlays. It is Phase 1 work, advised again before the first go-live (before 18 Dec). Until 012b, the bounded config-file deviations of specs 003, 004, 007, 008 and 041 stay in force, and nothing moves out of the repository.

## 2. Scope

Each bullet is testable; §9 names the AC.

### 2.1 Where the truth lives in v0

- **Nothing moves.** Products, tiers, add-ons, prices, countries, locale switches, site links, UI text, guides, trust and legal pages, media and review flags stay where they are today (repo files, ADR-0017), read by the providers that read them today. The database is the runtime source only for what already lives only there: users and roles, partners with their coverage, blackouts and payouts, applications, feature flags, orders and the audit log.
- **Price shown = price charged holds by construction.** The product page, its structured data, spec 011's payout example and spec 010's checkout all read spec 005's one price provider. v0 has no price editor, so the database cannot drift from the price a page shows. Whether the database ever becomes the price's master copy is 012b's question (§15.1).
- **Partner go-live is a data flip in admin from v0** (`fulfillment_partner.status`, §2.5). Country go-live and its preflight are 012b's (§15.5). Until then a country's status stays the config value spec 007 reads, under the recorded deviation. The database guard of §2.3 already refuses a status flip of `country` or `fulfillment_partner` outside admin.

### 2.2 Access: the shared sign-in core, roles, the shell, never indexable

- **One sign-in core, built by this spec's task 1, for admin and for spec 011's florist inbox** (advisor memo §3.6). It lives in `src/lib/auth/`. It is Auth.js v5 with the Email provider (a magic link sent through Resend, ADR-0013; §13 Q1) and database sessions in spec 002's `users` / `accounts` / `sessions` / `verification_tokens` (TASK-022). It has:
  - **one adapter**: our own `Adapter`, each method one `withSystemContext('auth', …)` transaction, because `src/lib/db.ts` exports no raw client (spec 002 AC-3) and the auth tables' RLS admits `app.role = 'system'`;
  - **one `Mailer`** (`src/modules/notifications/mailer.ts`): `resendMailer` in `staging` and `production`, and `capturingMailer` in `development`, `test` and `preview`, which exposes the last messages to the e2e suite through `GET /api/internal/mail-capture` behind `INTERNAL_CRON_SECRET` (refused in `production` and `staging`);
  - **one set of environment names**: `AUTH_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM` and `MAILER`.

  No other file configures Auth.js, an adapter or a mailer.
- **The link design is spec 011's, for every surface.** The emailed URL is `{surfaceBase}/sign-in/confirm?t={token}` and carries no email address. A `GET` of it uses nothing up and renders one "Continue" button, so a mail scanner's or a chat app's link preview cannot burn the token. The `POST` resolves the identifier from the hashed token on the server and invokes Auth.js's email callback in process, so the identifier never travels in a URL, a redirect or an access log. Tokens are single-use and expire after one hour.
- **One instance per surface**, made by the core's factory `createAuthSurface(AuthSurfaceSchema)`. Each has its own base path, cookie names and scope, session length, sign-in pages and allow predicate:

| Surface | `basePath` | Cookies (each `Secure`, `HttpOnly`, `SameSite=Lax`) | Session | Who may receive a link |
|---|---|---|---|---|
| admin (this spec) | `/admin/api/auth` | `__Secure-fo-admin.session-token`, `__Secure-fo-admin.csrf-token`, `__Secure-fo-admin.callback-url`, each `Path=/admin` | 12 h (§13 Q6) | an email whose `users` row has an active `admin_profile` and at least one `user_role` |
| florist (spec 011) | `{FLORIST_BASE_PATH}/api/auth` | `__Secure-fo-florist.*`, each `Path={FLORIST_BASE_PATH}` | 30 days, rolling | spec 011's `signInPolicy` and `partner_member` |

  **No cookie has a `__Host-` name.** Auth.js's default CSRF cookie is `__Host-authjs.csrf-token`, and a `__Host-` cookie must carry `Path=/` ([MDN, Set-Cookie cookie prefixes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)), which would contradict a per-surface path. So each instance names its CSRF cookie with the `__Secure-` prefix and its own path. A session from one surface never authenticates a request to the other. Nothing is set on, or sent to, a public path.
- **Allowlist, not sign-up; a send limit for both surfaces.** Any address the surface's predicate refuses receives the identical page and no email. At most 5 links per address per hour (`auth_email_send`, keyed by a SHA-256 of the normalised address, kept 7 days). No IP is read or stored.
- **Roles** are spec 002's `user_role` (`admin`, `ops`, `finance`, `content`). The permission matrix is one constant (`ADMIN_PERMISSIONS`, §5.2) read by the guard, the navigation and the tests. Every server action and route handler under `/admin` calls `requirePermission(…)` before anything else; the admin layout redirects an unauthenticated page request to `/admin/sign-in` (Next's `redirect()`, decided by session state, never by location — ADR-0006 is about geography, and `src/proxy.ts` stays redirect-free). Reviewer locales are 012b's (§15.2).
- **Bootstrap and users.** `pnpm admin:grant --email <e> --name <n> --role <r>` creates or updates a user, profile and role over the direct URL (audit channel `cli`); it is how the founder creates their own account. `/admin/users` (admin only) grants and revokes roles and deactivates accounts; revoking or deactivating deletes that user's sessions in the same transaction.
- **Never indexable, never discoverable.** Every `/admin` response — page, sign-in, 401/403/404, server action, `/admin/api/**` — carries `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store, private`; every admin HTML document carries `<meta name="robots" content="noindex,nofollow">`; `robots.txt` keeps `Disallow: /admin/` (spec 007); no sitemap child and no public page links to `/admin`; Cloudflare bypasses `/admin*` (spec 040's existing rule). No locale prefix (`plan/02` §4.1).
- **Admin copy** lives in a separate catalogue, `messages/admin/en.json` (+ `en.meta.json`), typed, ICU, checked by `i18n:check`, loaded only by the admin layout — never in a public bundle and never counted in a public locale's reviewed share. The admin interface is English only in v0 (§13 Q9). The spec 004 §14 A5 voice rule keeps "partner", "vendor" and "corridor" out of customer copy and explicitly allows them in admin, so the banned-word scan in `tests/unit/design-docs.test.ts` exempts `messages/admin/` and `docs/design/wireframes/admin-*` — and only those.

### 2.3 Audit of every admin write (in the database)

- **A trigger, not a convention.** One `audit_row_change()` trigger function is attached to every table admin can write in v0 (§5.1 lists them; 012b attaches it to the tables it makes writable). When `app.role = 'admin'` it writes one `audit_log` row per affected row — actor user id, actor label, `app.audit_action`, table, row id, masked `before`/`after`, `request_id`, `reason`, `channel` — in the same transaction, and sets `source = 'real'` on tables that carry `source`. An admin-context write with no `app.audit_action` raises `AUDIT_ACTION_MISSING` and rolls back, so a new server action cannot ship unaudited. Spec 011's `setFloristApplicationStatus` runs inside `withAdminContext` and is audited by this trigger; it writes no audit row of its own.
- `withAdminContext` (spec 002, `src/lib/db.ts`) gains a required `action` (dotted, e.g. `partner.status.active`) and optional `reason`, issued as `SET LOCAL app.audit_action` / `app.audit_reason`.
- `audit_log` becomes **append-only** (UPDATE/DELETE raise). Columns holding personal data are written masked (`partner.contact_email`, `partner.contact_phone`, `partner.legal_name`, every `partner_application` contact field) — the log records *that* they changed, never what they were.
- **Go-live only in admin, enforced by Postgres.** An `UPDATE` that changes `country.status` or `fulfillment_partner.status` outside an admin context raises `STATUS_FLIP_OUTSIDE_ADMIN` — including a raw `UPDATE` in a migration run as `app_owner`. Inserts (the seed) are untouched. This is `plan/10` §4's "no PR flips a country or partner status through code or migration" made a database fact rather than a review item. It holds from v0, before 012b builds the country flip.
- **Reads of personal data are logged too.** Opening an order detail or an application detail writes an `audit_log` row (`order.viewed`, `application.viewed`; no before/after) — who looked at whose recipient or contact data (§13 Q10).
- `/admin/audit` (admin only): filter by entity, actor, action and date; masked values render as "changed".

### 2.4 Flags: the database flags only

- `src/config/feature-flags.ts` is the **registry**: every key, its scope kinds, a description, a risk level, and the cache tags a change dirties. In v0 it registers exactly the two database flags spec 010's checkout reads: `checkout.open` (country scope; dirties `catalog:{iso2}`) and `checkout.demo_guard` (global; high-risk). `src/lib/flags.ts` reads `feature_flag` / `feature_flag_scope` with a 60 s in-process cache (spec 002: flags in the database, never in env). Admin lists and toggles only registered keys; a key in the database that the registry does not name is shown as orphaned and cannot be toggled.
- **High-risk flags** are admin-only and need the key typed to confirm. In v0 that is `checkout.demo_guard`; spec 013 registers `payments.stripe` and `payments.mollie` as high-risk when it lands.
- Toggling `checkout.open` for a country calls `invalidate(['catalog:{iso2}'])`, so the PDP's demo button follows within 60 s (spec 010 §5.4). `src/lib/cache.ts`'s `urlsForTag` learns that one tag here; the other resolver tags are 012b's (§15.10).
- **Not in v0:** the locale switch (`locale.{code}`) and the site-link overlay (`link.{id}`) are 012b's (§15.6). `isLaunch` and `published` stay in their config files.

### 2.5 Partners and applications

- **Partners**: create (status `onboarding`; `demo` is seed-only), edit (legal name, city label, country, notification channel, contact email, contact phone validated as E.164 for the partner's country, payout currency, capacity per day), **terms** (`terms_signed_at` + `terms_version` — the partner agreement with its Art. 28 processor clauses, `plan/07` §1.1), coverage (city or postcode zone, capacity), blackout dates, and the **catalogue mapping** (product, tier, can fulfil, payout as integer minor units + currency).
- **Status graph**: `onboarding → active | offboarded`, `active → paused | offboarded`, `paused → active | offboarded`; `demo` rows can move only to `offboarded`. `→ active` requires signed terms, at least one coverage row, at least one fulfillable mapping with a payout, and the contact for the chosen channel. Partner names and contacts never appear on a public page in v0 (`plan/09` Phase 0 AC 6; public profiles are a later spec).
- **Applications** (`partner_application`, written by spec 011's form) are read and moved **through spec 011's queries**, `listFloristApplications` and `setFloristApplicationStatus`; this spec defines no application query of its own. List and detail; `new → contacted → converted | rejected`; **convert** (`convertApplication`, this spec) creates an `onboarding` partner pre-filled from the application and links it; **reject** needs a reason, stored in `status_reason` (§5.1) in the same admin transaction.
- **Retention** of applications and of expired sessions is spec 011's rule (applications deleted 12 months after their last change unless converted; sessions at expiry). This spec keeps no copy of either (§13 Q5).

### 2.6 Order queue (read-only in v0)

- `/admin/orders`: newest first, 50 per page, filters by status, destination country, delivery date and created date, rendered from spec 010's `listOrdersForAdmin(filter)`. A row shows the short order id, created time, delivery date in the destination zone, destination city, internal status with its buyer projection, total via `formatMoney`, assigned partner and a **demo marker when `order.mode` is `demo` or `test`** (never read from `source`, which spec 002 keeps for seed rows). **No recipient name, phone or street in the list.** In production, demo orders placed by the public show only here; the florist inbox runs on staging (spec 010 §2).
- **Arrival within 5 s.** While the page is visible, a small client island polls `GET /admin/api/orders/head` (`{ latestCreatedAt, count }`) every 3 s and refreshes the server-rendered list when it changes; it pauses after 15 minutes without interaction and says so, so an idle tab does not keep Neon's compute awake (spec 002 §11).
- `/admin/orders/[id]`: lines, totals and VAT breakdown, recipient snapshot (only for `orders.view_pii`), the `order_event` timeline with raw payloads expandable, assignments, payments (read). Opening it is logged (§2.3). The order's `public_token` never appears in admin HTML, URLs or logs.
- **No actions in v0.** Every order write goes through spec 010's engine (`orderService.transition`), and this spec calls none. The action panel arrives with spec 020, through the same engine (§13 Q7; the requirement is in §12). Until then no action control renders.

### 2.7 Docs and records

`docs/runbooks/admin.md` (sign in, grant a role, deactivate a user, onboard and activate a partner, read and answer applications, toggle the checkout flags, read the audit log, what to do when a toggle did not show), `docs/compliance/ropa.md` (admin users; Resend for sign-in mail on both surfaces; partner and applicant contact data; audit log), `docs/compliance/cookie-register.md` (the admin instance's cookies), `docs/architecture.md` (the sign-in core and its surfaces; module ownership of the write commands), `.env.example` and `src/lib/env.schema.ts` (`AUTH_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`, `MAILER`), `config/railway.json`.

## 4. User stories

- As the **founder during the 16 October demo**, the mock order a florist just placed appears on my order screen within five seconds.
- As the **founder onboarding a Warsaw florist**, I convert their application, record their signed terms, map their payouts, set their coverage and switch them to active; the switch refuses until the terms are recorded.
- As the **founder**, I open or close the demo checkout for a country, and turn the demo guard on or off, from one page; the guard asks me to type its name first.
- As the **founder**, every change anyone made in admin is in a log I can filter, and none of it can be edited afterwards — including by me.
- As the **founder and a florist on a demo call**, we sign in the same way, with a link that never carries our email address and that a mail scanner cannot use up; my admin session and their florist session never open each other's pages.
- As **Googlebot**, I never see an admin URL.
- As an **implementer agent**, I cannot flip a country or partner status or skip the audit by writing SQL: the database refuses.

(The stories of the deferred half are in §15.15.)

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

Spec 002's tables are used as they are. This spec adds three migrations. Each is numbered at implementation time after the last one merged (today the chain ends at `0012`, TASK-024; spec 011's `NNNN_florists_v0` may land first). Each has a hand-written `.down.sql` that the round-trip test runs; no table gains a `float`, an `enum` or an extension.

**`NNNN_admin_identity`** (task 1) — `admin_profile(user_id uuid PK FK users ON DELETE RESTRICT, display_name text NOT NULL CHECK (char_length(display_name) BETWEEN 2 AND 80), time_zone text NOT NULL DEFAULT 'Europe/Tallinn', deactivated_at timestamptz NULL, created_at, updated_at)` — the name the audit log shows (and, in 012b, the name an attestation carries) and the zone admin shows instants in (always labelled); `auth_email_send(id, identifier_hash char(64) NOT NULL, sent_at timestamptz NOT NULL DEFAULT now())` with an index on `(identifier_hash, sent_at)`, written by the core for both surfaces. RLS on both: admin and system roles only. Rollback: drop the two tables. (`reviewer_locale` is 012b's, §15.7.)

**`NNNN_audit_trail`** (task 2) — `audit_log` gains `reason text NULL` and `channel text NOT NULL DEFAULT 'admin' CHECK (channel IN ('admin','cli','import','system'))`; a `BEFORE UPDATE OR DELETE` trigger makes it append-only; `audit_row_change()` (AFTER INSERT/UPDATE/DELETE, FOR EACH ROW; plus a BEFORE INSERT/UPDATE companion that sets `source = 'real'` where the column exists) is attached to the tables admin can write in v0: `country` (so a flip is audited from the day 012b builds it), `fulfillment_partner`, `partner_coverage`, `partner_blackout`, `partner_catalog_mapping`, `partner_application`, `feature_flag`, `feature_flag_scope`, `user_role`, `admin_profile`. The masked-column list is a constant inside the function. `status_flip_guard()` (BEFORE UPDATE OF status ON `country`, `fulfillment_partner`) raises `STATUS_FLIP_OUTSIDE_ADMIN` when the status changes and `current_setting('app.role', true) <> 'admin'`. Rollback: drop triggers and functions, then the two columns.

**`NNNN_partner_terms_and_retention`** (task 11) — `fulfillment_partner` gains `terms_signed_at date NULL` and `terms_version text NULL` with `CHECK ((terms_signed_at IS NULL) = (terms_version IS NULL))`; `partner_application` gains `status_reason text NULL`; `retention_policy` gains rows `audit_log` (delete after 3 years; personal values are already masked) and `auth_email_send` (delete after 7 days) — §13 Q5. The `partner_application` (unless converted) and expired-session rules are spec 011's and are not repeated here. `retention.sweep` (TASK-025) gains a handler per new row. Rollback: delete the rows, drop the columns.

- **Data flows added (→ RoPA, updated by the reviewer at PASS)**:

Retention: unconverted applications 12 months (spec 011's rule); partners per `plan/07` §1.2 (contract + 10 years financial).

  Recipient data is not newly collected; admin and ops can *view* it (need to know, `orders.view_pii`), finance and content cannot, and every view is logged. In production the only recipient data is what the public types into spec 010's demo, cleared after 24 hours by spec 010's rule.

## 9. Acceptance criteria

**Access and the shared sign-in core**
- **AC-1** Without a session, every `/admin/**` page except `/admin/sign-in` answers a 3xx redirect whose `Location` is `/admin/sign-in`, with no admin data in the body, and every admin server action and `/admin/api/**` handler (auth endpoints excepted) answers 401 and writes nothing; the set of routes and actions tested is enumerated from the file tree, not listed by hand.
- **AC-2** A sign-in request for an allowlisted email sends exactly one message through the core's `Mailer` (Resend in staging and production); for any other email the response is byte-identical and zero messages are sent; the sixth request for one address within an hour sends nothing.
- **AC-3** The admin instance's cookies — session, CSRF and callback URL — are named `__Secure-fo-admin.*`, none has a `__Host-` name, and each carries `Path=/admin`, `Secure`, `HttpOnly` and `SameSite=Lax`; the session expires within 12 h; no public response sets or names an Auth.js cookie; revoking a user's role or deactivating them makes their next request unauthenticated.

- **AC-5** Every `/admin` response — pages, sign-in, 401/403/404, server actions, `/admin/api/**`, auth endpoints — carries `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store, private`, and every admin HTML document carries `<meta name="robots" content="noindex,nofollow">`.

## 11. Observability

- **Every admin write is an `audit_log` row** with `request_id`, actor and action (§2.3); the log line for the request carries the same `request_id`, the action name and the duration — never values.
- **Events logged** (`info`, no PII): `admin.sign_in.sent` (hashed identifier only), `admin.sign_in.refused` (reason: not allowlisted / rate limited), `admin.session.revoked`, `admin.partner.status` (code, from, to), `admin.flag.toggled` (key, scope), `cache.invalidate` (tags, URL count, origin and edge outcomes).
- **Warnings and Sentry**: a failed purge or origin revalidation after a flag toggle (`warn` + Sentry, with the tags) — the change is saved but not yet visible; `AUDIT_ACTION_MISSING` and `STATUS_FLIP_OUTSIDE_ADMIN` raised in production (`error` + Sentry: they mean a bug or a bypass attempt); adapter and mailer errors from the core, for both surfaces.
- **Cost signals**: the order poll pauses after 15 minutes idle, and `neon.usage_probe` (spec 002) is the place to see admin's share of compute.

### 15.1 The system of record and the migration path (proposed ADR-0019; pre-split §2.1)

**Decision (proposed).** Admin writes go to the database. Once an entity family is **cut over**, the database is its only runtime source; the repo files that author it today become **seed**: they populate a fresh database (local, CI, staging) and remain the test fixtures, and they are never read by a production page again. Cutover is one PR per family that swaps the composition root inside the owning module from its static provider to its database provider — the seam specs 003, 005, 006, 007 and 041 built for exactly this, with no call-site change outside the module. A price cutover swaps spec 005's provider for the product page, its structured data, spec 011's payout example and spec 010's checkout in one deploy.

**Migration path (per family, in this order, each step a PR or a founder action):** (1) production is migrated and seeded **insert-only** from the files (`pnpm db:seed --insert-only`; a plain seed refuses to run when `APP_ENV=production`); (2) `pnpm attestations:import` carries every review already recorded in a file — with its recorded name and date — into the ledger, once; (3) the family's cutover PR swaps the provider; (4) from then on admin is the editor. Rows an admin has written carry `source = 'real'` (set by the audit trigger, §2.3), so no seed run in any environment can overwrite them (`plan/10` §4). `pnpm seed:diff --target=db` (spec 006) remains as a read-only report of how far production has moved from the files. Rolling a family back is reverting its cutover PR: the static provider returns, database rows stay.

**Builds read the database.** A page built from seed files while checkout charges from the database could show one price and charge another — the one failure `CLAUDE.md` forbids outright. So after cutover `next build` reads the database (Railway build variables in staging and production; CI's `build` job gains the Postgres 16 service, `db:migrate` and `db:seed`, as the integration job already has). This puts production data on the build path, so a database outage stops deploys (§15.0).

**Correction (advisor H2): pages created by a go-live do not render without a rebuild today.** The pre-split draft said the depth-4 route already renders unbuilt pages (`dynamicParams = true`, existence decided by the resolver), and proposed moving depths 2 and 3 to that pattern so that a page a go-live flip creates exists without a deploy. That is false. The `[locale]` layout exports `dynamicParams = false`. Next computes a route's `dynamicParams` as every segment's, so a URL the build did not emit is a router 404 at every depth, depth 4 included. The depth-4 file's own `dynamicParams = true` is inert (`src/app/[locale]/[segment]/[child]/[grandchild]/page.tsx` L91–95; decisions log 2026-10-03, SPEC-009 A6 and the TASK-170 ruling). Every page must exist at build time. **012b must choose:**
- (a) a go-live in admin triggers a redeploy, which is still a data flip with no code change; or
- (b) a different mechanism, proven in a spike first.

### 15.2 Review as attestation (proposed ADR-0020) and the translations queue (pre-split §2.4)

- **The ledger.** `review_attestation` is append-only, like `order_event`. Each row binds a **decision** (`approved` / `changes_requested` / `rejected`) to a **subject** (kind + reference + field + locale), the **SHA-256 of the exact text** reviewed (`value_hash`), the hash of the English source it was reviewed against (`source_hash`), the **attester's user id and name** and the **server time**. A subject is *reviewed* exactly when its latest decision is `approved` **and** its `value_hash` equals the hash of the text served now. Change one character and it is unreviewed; change only the English source and it stays reviewed but is flagged *stale* (`plan/03` §6 step 5).
- **One writer.** `attest()` in the `i18n` module is the only code that writes the ledger and the only code that may set the denormalised `reviewed` / `reviewed_by` / `reviewed_at` columns (and `media_asset.review_state`). Postgres enforces it: those columns change only under `SET LOCAL app.allow_review_write = 'on'` **and** only with a matching ledger row in the same transaction (`REVIEW_DIRECT_WRITE`, `REVIEW_WITHOUT_ATTESTATION`) — the order-status guard of spec 002, applied to review. A lint rule `fo/no-direct-review-write` catches the attempt before the database does.
- **Who may attest.** A signed-in user with a non-empty `display_name` and the subject's locale in their `reviewer_locale` grants (media approval: the `media.review` permission). The founder is granted `en` and `en-gb`; native reviewers their own language (§13 Q3). The name on the record is the profile's `display_name`; the date is the database's `now()`.
- **Files stop claiming review.** After the import, the `reviewed`, `reviewedBy` and `reviewedAt` fields are removed from `messages/*.meta.json`, corridor frontmatter, info/legal frontmatter and `seed/data/copy/**`; `i18n:check`, `corridor:check`, the spec 041 content gate and `seed:check` fail on a file that adds one back. A file-backed text's review is the ledger's answer for its current hash, computed at build into the generated typed index the corridor and content modules already use.
- **The import** (`pnpm attestations:import`) is the one bridge: every file entry with `reviewed: true` **and** a recorded name **and** date becomes a ledger row with `channel = 'import'`, that name and that date; an entry missing either is imported as unreviewed and listed in the report. It is idempotent, it writes `seed/data/attestations.json` (the seed snapshot for fresh databases and tests), and the queue shows imported approvals under their own filter, as "imported, not re-read", so the founder can re-confirm them in admin (§13 Q2, §15.0 item 4).
- **The queue** — `/admin/translations`: per locale, every subject that is unreviewed (machine draft, never attested, or edited since), stale, or has a change requested, grouped by kind (UI strings, product copy, category and occasion intros, add-on copy, corridor guides, trust and legal pages, image alt text, images), with counts; side by side source and target; glossary terms from `content/i18n/glossary.{locale}.md` highlighted; **Approve** (writes `approved`) and **Request change** (note required, optional suggested text). Database-backed text (catalogue copy) is editable in place; repo-backed text (UI strings, guides, pages) is read-only with its file path, and `pnpm i18n:requests` prints every open change request for an implementer to apply in a normal PR.
- **Indexability reads the ledger.** `isLocaleIndexable()`, the locale beta tag, the corridor, info-page and product indexability predicates, hreflang alternates and sitemap membership all read review state through an `AttestationProvider` (database implementation at runtime with a 60 s cache; snapshot implementation in tests), so the one predicate of spec 007 stays one predicate with a new source.

### 15.3 Catalogue CMS (product listing management; pre-split §2.5)

- **Products**: list (filters: type, status, facet, priced country, review state) and create/edit — SKU, the six facets from the closed taxonomy (`src/config/catalogue/schemas.ts`; a new facet value is a code change), stem count, vase, freshness days, substitution class, `partner_only`, status. `draft → active` requires an `en` name, slug and description, at least one tier with exactly one default, and an active price in at least one country. `active → retired` is refused while the product is priced in a country that is or has ever been `live` (the 200-with-alternatives-then-410 page `plan/02` §7 requires does not exist yet).
- **Tiers** (key, label key, stems, sort, default) and **add-ons** (copy, allergen note, per-country prices; the wine add-on stays behind `addon.wine.{country}`).
- **Copy per locale** (name, slug, description, SEO title and description; category and occasion intros): edited in a locale only by a user granted that locale; saving changes the text hash, so the subject drops out of *reviewed* until attested (§15.2). **Slugs** are editable only while no country the entity is shown in is or has ever been `live`; after that a slug change needs redirect history.
- **Validators are shared with the gates.** The rules `catalogue:check` and `seed:check` apply to files are extracted into pure functions in `catalog` and run on every admin save. **Hard rules block** (slug shape and uniqueness, integer minor units, currency equals the country's, one open price row, banned words, no price literal in copy, `seoTitle` ≤ 60, `seoDescription` ≤ 155, no PII- or competitor-shaped strings); **soft rules warn** (price outside its `plan/10` §2.3 band, description outside 60–90 words, psychological ending) and save only with an override reason, stored on the audit row.
- **Prices** (`country_price`, `addon_country_price`): amounts are typed as a decimal string and parsed to integer minor units by string arithmetic against the currency's exponent (no float at any step; `.` or `,` as the decimal separator; no grouping). A change **supersedes**: the open row gets `active_to = today` (country zone) and a new row opens — `retail_minor` is never updated. The confirm step shows the formatted old and new price in every launch locale, the change in per cent, a warning beyond ±30%, and the 30-day lowest price (`lowestPriceInLast30Days`, spec 005). One change per (product, country, tier, surcharge) per calendar day (§13 Q8). The form has no buyer-country field and no "price excluding VAT" input: the amount typed is the all-in price. A price editor exists only after the price family's cutover, so the database never holds a price the pages do not show (memo §3.3).
- **Margin view** per (product, tier, country): gross retail, VAT, net, the lowest and highest payout among active and onboarding partners mapped to it, and the margin — integer minor units, converted through spec 005's `convert()` with a dated rate when the payout currency differs, never a float (`plan/06` §6 "margin view").

### 15.11 SEO, i18n and compliance of the deferred half

- **Indexability is still one predicate**, fed by data (ADR-0007, spec 007's rule engine): `country.status`, the corridor flags, `locale.{code}`, the six-product floor (spec 008's loader, unchanged), and review state from the ledger. Nothing in admin writes an indexability flag directly; it writes the facts the predicate reads.
- **Go-live preflight prevents thin and false pages**: a country cannot go live without operations data (so no cutoff is invented), an active partner (so no unbuyable `Offer` is indexed), open prices for every listed product (so no product page without an `Offer`), and a reviewed live-state guide (`plan/02` §5.1–§5.2). Rollback (`live → demo`) returns pages to `noindex,follow` rather than deleting them; `live → disabled` is refused until 410 handling exists.
- **Canonical and URL stability**: slugs lock once an entity has been shown on a page in a live country (§15.3), and retiring such a product is refused until the retired-page behaviour of `plan/02` §7 exists; so admin cannot orphan an indexed URL or create a duplicate canonical. Slug rules (ASCII, lowercase, hyphenated, unique per locale, `plan/02` §4) are the same validators the seed gate runs.
- **hreflang**: an alternate exists only for a locale whose text on that page is attested for its current hash; editing a Polish description removes the Polish alternate (and the page's indexability) until re-approved, and adds it back after — reciprocity is preserved because the cluster and the sitemap are generated from the same predicate (`plan/02` §8).
- **Schema and price**: `Offer.price` equals the visible price equals the charged amount after every admin price change, because prices are superseded rows read by spec 005's single `priceProjection()`; the Omnibus 30-day lowest price keeps its history because rows are never updated.
- **Sitemaps and `<lastmod>`**: admin writes advance `updated_at` (spec 002 trigger), so `<lastmod>` stays truthful; a flip purges the sitemap index and children.
- **Thin and duplicate content**: the shared validators block or flag short and duplicate descriptions, banned superlatives and price literals in copy on every admin save, not just in CI over files.
- **Internal links**: `link.{id}` cannot publish a link whose target does not exist (§15.6).
- **CWV**: depends on the §15.1 choice; with a redeploy, nothing renders on first request, and the Lighthouse set is unchanged.
- **i18n**: the ledger is `plan/03` §6's mechanism — drafts arrive as unreviewed (spec 003's `i18n:draft`, admin edits), the queue lists them, a granted native reviewer attests the exact text, indexability and hreflang read the ledger, edits and source changes reopen the subject. Corridor guides and legal text still never ship machine-only; `isLocaleIndexable()` keeps its 5% rule with the ledger as its input. Price previews render the amount with `formatMoney` in all four launch locales (`229,00 zł`, `PLN 229.00`); money input is parsed by string against the currency's exponent, never by `parseFloat`.
- **Compliance**: reviewers join the admin-users RoPA flow (reviewer locales; attester names pseudonymised 3 years after deactivation); the redaction list gains `attester_name`; the typed price is by definition the all-in price, with no net-price input and no buyer-country dimension, and changes supersede so the Omnibus 30-day lowest price is always computable; the go-live preflight requires `supply_model` and refuses a sanctioned destination (set `disabled`).
