## 1. Problem

The founder, 2026-10-23, verbatim: "why didn't you build a search bar on our website? You also have to do that. And whenever someone searches for a product, if we have multiple, many products or something like that, like the query of the user, we will show the most relevant ones and based on their location and everything. And we will always show the products, like we will always prefer the products in where we have more profit margin, because in the back end we will have set like how much profit margin we have on a certain product or from a certain vendor, you know. So plan these things accordingly as well."

**What exists today.** `plan/05` §1 row 16 reserves a search results page, `plan/02` §4.1 its URL (`/en-gb/search?q=`, `noindex`), `plan/01` §3 its rendering (SSR, `noindex`) and `plan/01` §2 its engine ("Postgres full-text … no external search at launch"). Spec 008 owned it and never built it. The header carries a dormant site link `search` (`src/config/site-links.ts` L334 to L342: `published: false`, `owningSpec: "008"`, target `pending`) and, since spec 004 §14 A20, draws nothing for it, because a field that does nothing is worse than no field. Its three keys exist and are reviewed by the founder in `en`: `nav.search.label` ("Search flowers, occasions, a city or a country"), `nav.search.submit` ("Search") and `nav.search.help` ("Search opens when the shop does."). So a buyer who knows what they want ("white roses", "urodziny", "Geburtstag") must click through the header's eight links and page through a grid of 84 bouquets.

**Why now.** Florists are joining with their own bouquets (spec 012b §2.5, spec 030b A-founder-2026-10-22), so the catalogue grows past what a header and a grid can show, and the founder asked. He also asked that among the results we prefer the bouquets that earn us more. That is a lawful commercial choice for a shop selling its own goods, but our listings today say the opposite: `shop.toolbar.disclosure` reads "Our order is the order we chose ourselves. It is not a ranking by sales, by popularity or by payment, and it does not change with who you are." A margin preference that the page does not mention would make that sentence incomplete at best. This spec builds the search, defines the preference as a strong boost among results that match equally well and never above a more relevant result, and rewrites the disclosure so it stays true (§2.6).

## 2. Scope

### 2.1 The search box in the header

- **Desktop and tablet (from `md`).** (amended by §14 A-orchestrator-2026-10-24 item 4) The header row holds a search icon: the `<summary>` (44 px, named by `nav.search.submit`) of a native `<details>` whose panel, under the header row, holds the header's one real `<form role="search" method="get">`, holding one `<input type="search" name="q" maxlength="80" autocomplete="off" enterkeyhint="search">` named by `nav.search.label` and a submit button reading `nav.search.submit`. Its `action` is the locale's search URL (§2.2) on a page whose URL names a destination with a shop, and the chooser path `/{locale}/{chooseSegment}/search` (spec 004 §14 A-founder-2026-10-24a item 3) on every other page. Drawn in PR 372's chrome and in `search-results-desktop.dc.html` ("Header search opened"); the row does not grow, so `HEADER_STICKY_HEIGHTS` is unchanged.
- **Phone (below `md`).** The 64 px row keeps the logo and the Menu and gains one search control: a link to the locale's search page named by `nav.search.submit`, whose page opens with the field first. `MenuSheet` also holds the same form as the desktop. With JavaScript off both work, because one is a link and the other a GET form.
- **The destination travels with the query, from the URL only.** On a page whose URL names a destination with a shop (spec 043 §2 A's rule, the same one the header's shop links use), the form holds `<input type="hidden" name="to" value="{iso2 lowercase}">` and the phone link carries `?to={iso2}`. Elsewhere there is no `to`. The value comes from the page's own URL, so the cached HTML is the same for every visitor (no `headers()`, `cookies()` or `searchParams` read is added to a prebuilt route).
- **Publishing.** The `search` site link becomes `published: true`, `owningSpec: "045"`, with a `route` target for the new page type `search`. `nav.search.help` is deleted (it described the dormant state).

### 2.2 The results page

- **URL per locale:** `/{locale}/{searchSegment}?q=…[&to=…][&date=…][&page=…]`, with the localised segment defined once in `src/config/locales.data.ts`: `en` and `en-gb` `search`, `de` `suche`, `pl` `szukaj` (`plan/02` §4: localised, ASCII, lowercase).
- **Server-rendered, works with JavaScript off.** The page is SSR on every request (`plan/01` §3 row "Search results": SSR, `noindex`). Everything a buyer needs (the form, the destination line, the hub links, the cards with prices, pagination) is in the server HTML. No client data fetch renders results.
- **`noindex, follow`, never in a sitemap**, in both the `<meta name="robots">` and the `X-Robots-Tag` header (§6).
- **Layout** (drawn by `/design`): H1; the search form with the query filled in; the destination line ("Where is it going? Poland · change destination", spec 043 §2 B's reviewed keys) with a `<select name="to">` of the destinations that have a shop; the date control when the destination takes delivery dates (§2.4); a "Pages" block of up to three hub links (§2.3); the count line (`shop.toolbar.count`); "How we sort" (§2.6); the grid of spec 008's product cards (the same `ProductCardView`, the same all-in price); pagination.
- **Pagination**: 12 cards per page (spec 008's page size), at most 10 pages. "Previous" and "Next" are submit buttons of small GET forms carrying `q`, `to`, `date` and `page`, never `<a href>` with the query in it (§6, §8).

### 2.3 Relevance: what the words match

- **What is searched.** One document per (product, locale) for every product the destination's shop lists (spec 008's listing set for that country, merged and retired products excluded, existence per spec 012b §2.3). Fields, each normalised (below):
  - **name** in the request locale (the name the product page shows);
  - **facets**: the labels of the product's flower types, colours, occasions, product type and categories (`plan/10` §1.1) in the request locale, plus the same labels in the other launch locales as an **alt** field, so "róże" typed on `/en` still finds roses;
  - **description** in the request locale;
  - **SKU**, exact only (support and the founder type "FO-BQ-001").
- **Normalisation** (`normaliseForSearch`, pure, one function for documents and queries): NFC, then NFKD with combining marks removed (`róża` to `roza`, `Kraków` to `krakow`), the letters NFKD does not split mapped by a table (`ł` to `l`, `ß` to `ss`, `æ` to `ae`, `ø` to `o`, `đ` to `d`), the German digraphs `ae`, `oe`, `ue` folded to `a`, `o`, `u` on both sides (so `Maigloeckchen` and `Maiglöckchen` meet), lower case, every other character a space, spaces collapsed. This is `plan/03` §7's "search uses `unaccent`", done in the application (§2.9).
- **Tokens and stop words.** Split on spaces; drop a small closed stop-word list per launch locale (`for`, `the`, `a`, `to`, `with`; `für`, `der`, `die`, `das`, `und`, `mit`, `nach`; `dla`, `i`, `z`, `na`, `do`, `w`); keep at most 8 tokens.
- **Matching, per token, in this order:** exact; stem (a light, closed suffix list per language: Polish `ami`, `ach`, `om`, `ow`, `y`, `i`, `e`, `a`; German `en`, `er`, `e`, `n`, `s`; English `ies` to `y`, `es` after `ss`, `x`, `ch`, `sh`, else `s`; the stem keeps at least 3 letters; against the alt field a query token is stemmed with that field's locale as well, so "róże" on `/en` meets the Polish label's stem); prefix (the **last** query token only, at least 3 letters, so "sunfl" finds sunflowers while the buyer types); typo (Damerau-Levenshtein distance 1 for tokens of 4 to 7 letters, 2 for 8 or more, never for 3 or fewer, against the index vocabulary of normalised tokens and their stems).
- **Match tier** of a document (higher is better):
  - **5** the whole normalised query equals the normalised name, or the SKU;
  - **4** every token matches the name or the facets (request or alt locale), none by typo;
  - **3** every token matches some field (description included), none by typo;
  - **2** every token matches some field, at least one by typo;
  - **1** the query has 3 or more tokens and at least half of them (rounded up) match some field;
  - otherwise the document is not a result.
- **Relevance band** inside a tier: **2** when at least half of the tokens (rounded up) hit the name, **1** when at least one token hits the name or a facet of the request locale, **0** otherwise.
- **Pages (hub links).** An occasion or category whose label (any launch locale) every non-destination token matches at tier 3 or better yields a link: to the destination's country occasion or country category page when that page exists (`existsNow`), else to the hub (`/{locale}/occasions/{slug}`, `/{locale}/flowers/{slug}`). At most three, occasions before categories, then by label in the locale's collation (`Intl.Collator`). A link is drawn only to a page that answers 200.

### 2.4 "Based on their location": the destination they chose, the date they chose, the language they read

The founder's "based on their location" means **where the flowers are going**, which the buyer chooses. It never means where the buyer is. **Search never reads the visitor's IP address, `cf-ipcountry`, any geolocation API, `Accept-Language` or a cookie to decide what to show or in what order** (ADR-0006, `plan/03` §1 invariant 4, `plan/07` §3). The one place an IP address is touched is abuse protection (§2.8), which never changes a result.

- **Destination**, from exactly one of, in this order:
  1. a country named in the query: tokens that match a destination's name in any launch locale (`poland`, `polska`, `polen`; endonym and exonyms from `country_translation`) set the destination and leave the query; "flowers to poland" searches "flowers" in Poland and adds the country's shop root to the Pages block;
  2. the `to` parameter (from the header form on a country page, or the results page's own select);
  3. otherwise **none**: the search is country-less (amended by §14 A-orchestrator-2026-10-24 item 1). There is no default search destination and no code names a country (spec 004 §14 A-founder-2026-10-24a items 1 to 3, AC-73). The header form on a country-less page goes to the chooser first; a search URL with no destination renders the country-less state of §2.7 (no price, the chooser's form carrying the words). The search route never reads `fo_dest` (spec 004 item 1: only the chooser route and the deferred island read it).
- **Scope by destination.** Results are only products the destination's shop lists; each card shows that destination's all-in price in the locale's default currency, exactly as its listing card does (spec 005 `priceProjection`, spec 008 AC-6 and AC-7). A product with no open price in the destination never appears.
- **Deliverability.** Without a date: products `availability()` calls saleable come before those it does not, inside the same tier and relevance band (§2.5's key). With a date: the `date` parameter (ISO `YYYY-MM-DD`) is honoured only when the destination takes delivery dates (`deliveryDatesOpen(iso2)`) and the date is inside the bookable window; products that cannot be delivered on it (`CutoffEvaluator.isDateAvailable`, spec 009) leave the results, and one line says how many and offers the same search without the date. Today no destination takes dates, so the date control is absent.
- **Language.** The locale in the URL decides the fields searched at full weight and every word on the page; the alt field (§2.3) helps a Polish speaker on `/en`. The locale never changes the destination and the destination never changes the locale (`plan/03` §1 invariants 1 and 2).

### 2.5 The margin preference ("prefer the products where we have more profit margin")

- **What the margin is.** For each (product, destination country) with an open default-size price: gross `G` is the all-in price (VAT and delivery included, integer minor units, the country's currency); net `N` is `G` less VAT at the country's flower rate (spec 005 `vatBreakdown`, one line); the florist price `P` is the **highest** payout for the default size among the florists who can make it there by spec 012b §2.5's saleability rule (`active`, not `demo`, `can_fulfil`, coverage in the country), each converted to the price currency exactly as spec 012b's `marginView` converts it (the shared `mappingMarginRow` of spec 030b A-founder-2026-10-22, never a copy); margin `M = N − P`; margin share `S = floor(M × 10 000 / N)` in basis points, integers only. The highest payout is the cautious choice: routing (spec 016 `rankCandidates`) picks by rating before payout, so we cannot know in advance which florist will make it (§13 Q3).
- **Margin band** `B` from `S` and the configured thresholds `MARGIN_BAND_THRESHOLDS_BP = [3000, 3500, 4000, 4500]` (`src/config/search.ts`): `B` = the number of thresholds at or below `S`, so 0 to 4. A product with no such florist, `N ≤ 0` or `M < 0` has `B = 0`. The thresholds sit around `plan/06` §2's target (a payout of 55 to 65 % of net is a margin of 35 to 45 %), so typical bouquets spread over the bands. Bands, not raw margins, because they are coarse (a 1 % price change rarely reorders the shop), bounded (the next bullet), and reveal less if the order is ever inferred.
- **Where it is stored.** A job computes `B` for every (product, country) into `product_rank_signal` (§5.1). The money stays in the admin and system contexts; the web and build roles read only the band.
- **How strongly it counts: a strong boost among results of equal match strength and relevance** (founder, 2026-10-24: "search ok, strong boost"; §13 Q4). Search orders results by this key, compared left to right (§5.2 `rankSearchResults`):
  1. match tier (match strength), high first;
  2. relevance band, high first;
  3. **margin band, high first**;
  4. saleable (or deliverable on the date), yes first;
  5. approved primary photograph, yes first (spec 043 §2 F, every product list);
  6. spec 005's curation order;
  7. SKU.

  So **margin decides first among results of the same match tier and relevance band, ahead of deliverability, the photograph and our own order**: a bouquet with a higher band ranks above an equally relevant bouquet with a lower band even when the lower one has a photograph or is the one we can send to the destination more readily. **Margin can never lift a result into a higher match tier or relevance band**: a less relevant product stays below a more relevant one whatever its margin, and a product that does not match is not a result at all (§2.3), so margin never surfaces an irrelevant bouquet. Inside a tier and band it always decides, which is the founder's "always prefer". The cost the founder accepted: an equally relevant bouquet with no photograph, or one we can send less readily, can sit above one with a photograph when its band is higher; the disclosure says so (§2.6).
- **Listings too (default "Our order").** With the preference on, the default order of every product list that uses spec 005's curation order (country shop root, country category, country occasion, the home and corridor rows that read the same order) becomes: margin band high first, then approved photograph first (spec 043 §2 F, now inside each band), then curation, then SKU, the same preference as in search and equally strong (founder, 2026-10-24; §13 Q1). Price sorts are unchanged. `ItemList` still equals the cards (spec 008). §5.5 lists what changes in specs 043, 008 and 005; §13 Q1 asks the founder.
- **Never shown to buyers.** No band, margin, payout or florist price is in any HTML, JSON, `data-*` attribute, URL, log line or analytics event. The view models that reach the browser have no field for it.
- **Inert until real florists price real bouquets.** Before the database cutover (TASK-070, spec 012b §2.2) and while every mapping is a demo florist's, every band is 0, so every order equals today's. The switch `ranking.margin_preference` (spec 012's flag registry, default on) sets every band to 0 when off and selects the disclosure without the margin clause (§2.6).
- **Paid placement by florists is out of scope and stays out.** No florist pays, bids, or is offered a better place for a lower price, in outreach, contracts or the florist portal (§2.6, §8).

### 2.6 The honest ranking disclosure, and the law it meets

- **On the results page**: one native `<details data-fo-ranking-disclosure>` whose `<summary>` reads "How we sort" (`shop.toolbar.howWeSort`, spec 043 §14 A-founder-2026-10-22 item 2), closed in the server HTML, beside the count line, holding `search.ranking.disclosureWithMargin` while the preference is on and `search.ranking.disclosure` while it is off. Texts in Appendix A; in English (`en`):
  - with the margin preference: "Bouquets that match your words most closely come first. Among equally close matches, we put first the bouquets that earn us more, then those we can send to the destination you chose, then those with a photograph, then our own order. Nobody pays us to place a bouquet higher, and the order does not depend on who you are or where you are."
  - without: the same sentence without "we put first the bouquets that earn us more, then", reading "Among equally close matches, those we can send to the destination you chose come first, then those with a photograph, then our own order."
- **On listings**: `shop.toolbar.disclosure` stays as the text while the preference is off; while it is on the listings render the new key `shop.toolbar.disclosureWithMargin`: "Our order is the order we chose ourselves: we put first the bouquets that earn us more, then those with a photograph, then our own picks. It is not a ranking by sales or popularity, nobody pays us to place a bouquet higher, and it does not change with who you are."
- **The legal standard (checked 2026-10-23; §8 has the detail).**
  - **EU UCPD Art. 7(4a)** (inserted by Omnibus Directive (EU) 2019/2161) makes the main ranking parameters and their relative importance material information where consumers search "products offered by different traders or by consumers", in a section "directly and easily accessible from the page where the query results are presented". Spec 043's amendment records the Commission's reading (Notice 2021/C 526/01) that a trader searching only its own offers is outside it. Under `plan/07` §1.1 Model A we sell our own goods, so it most likely does not bind us; under an agent model (`plan/13` B1) it would. The disclosure is written to that standard anyway: it names every parameter and their order, one activation away from the results.
  - **EU UCPD Annex I point 11a** bans search results that do not clearly disclose "any paid advertisement or payment specifically for achieving higher ranking". Our own margin is not a payment by anyone for placement, so nothing here is paid placement. The risk to manage is the **indirect** reading: if florists were told that a lower price gets their bouquet placed higher, a lower price would start to look like payment for ranking. The rule in §2.5 (never offered, never promised, never shown to florists) closes that door, and the disclosure says "nobody pays us to place a bouquet higher", which stays true only while that rule holds.
  - **Misleading actions and omissions** (UCPD Art. 6 and 7; UK DMCC Act 2024 s.226 and s.227): today's sentence "not a ranking … by payment" would be incomplete once margin counts. The new sentences state it plainly, so nothing material is omitted.
  - **UK.** DMCC Act 2024 Schedule 20 has no search-ranking item (spec 043 amendment, checked on legislation.gov.uk 2026-10-23); only the general clauses apply, and a true disclosure meets them.
  - **The work order's "UCPD/Omnibus/UK DMCC require it"** reads, correctly: the EU standard is met voluntarily under Model A, required under an agent model; no UK-specific duty; Annex I 11a is respected by having no paid placement at all.

### 2.8 Privacy and abuse

- **A query can hold a name, an address or a phone number.** We never put personal data into a URL ourselves; a buyer may type anything into `q`. So: the query is **never logged** (the request logger writes the pathname only for the search routes), never sent to Sentry (URLs scrubbed of `q` in `beforeSend` and `beforeBreadcrumb`), never sent to analytics (§8), never cached at the edge (`Cache-Control: private, no-store`), never passed on (`Referrer-Policy: strict-origin` on search responses, so a click to a product page carries no query), never put into an `<a href>` by us, and rendered only escaped, inside `<bdi>` (`plan/03` §4).
- **Search insights keep anonymised aggregates only** (§2.10): a normalised query is stored only when it passes `isStorableQuery`, with a count per day, locale, destination and outcome; no IP, user agent, cookie, session or time of day.
- **Abuse.** At most 80 characters (`maxlength` and server truncation at a code-point boundary), 8 tokens. Per client, 60 results requests and 120 suggestion requests a minute, then 429 with `Retry-After`; the client key is an HMAC of the connecting address (`CF-Connecting-IP`) under a random per-process key, held in memory for the window only, never written, logged or used for anything else (security of the service, GDPR Recital 49). At most 32 searches run at once in the process; above that, 503 with `Retry-After: 5`. No regular expression is built from user input. A Cloudflare rate-limiting rule on `/*/search*` and `/api/search/*` is a runbook step, not code.

### 2.9 The engine: an in-process index now, Postgres when a threshold says so

| | In-process index (chosen for v1) | Postgres `unaccent` + `pg_trgm` + full text on Neon | Hosted engine (Meilisearch, Typesense) |
|---|---|---|---|
| New vendor, processor, DPA | none | none | yes: a new processor that receives every query, which can hold personal data (RoPA, DPA, SCCs) |
| Cost | zero | zero (both extensions are on Neon's supported list) | roughly 20 to 30 USD a month for the smallest managed tier, or a self-hosted Railway service to run (🔍 re-verify) |
| Latency | microseconds per query over at most a few thousand documents; no network | one database round trip per query, plus Neon's cold start after its compute suspends (🔍 seconds on a cold compute) | one network hop to another region or service |
| Languages | our own normaliser and light stemmers, tested by fixtures | `unaccent` and trigram are language-free; Postgres ships Snowball stemmers for English and German but **none for Polish**, so Polish needs the application's stemmer or trigram anyway | good multilingual support |
| Works without a database | yes (`check:no-db`, development, tests, the static catalogue before TASK-070) | no | no |
| Ops for a solo founder | none | one migration, indexes, one more query to watch | another service, sync, keys, outages |

- **Decision.** v1 builds one `SearchEngine` interface with one implementation, `memoryEngine`: an index built in the web process from the catalogue read API (spec 005's providers, whichever is active). Before TASK-070 that is the static catalogue; after spec 012b's cutover the same code reads the database providers, so "static now, database later" needs no switch. It is rebuilt lazily: marked stale whenever `invalidate()` receives a `catalog:*`, `product:*` or `country:*` tag (spec 012b §5.4; one in-process listener in `src/lib/cache.ts`), and at most 300 seconds old in any case. The rank bands (§2.5) load with it.
- **Switch rule** (to a `pgEngine` over `unaccent`, `pg_trgm` and a `search_document` table, built by a later task under this spec's interface and ACs): when any of these holds for a week on production: more than 20 000 (product, locale) documents; an index build over 2 seconds; the index over 64 MB of memory; more than one web replica serving search; or search p95 server time over the §2.11 budget with the load explained by search. A hosted engine is considered only if `pgEngine` misses the budget. This refines `plan/01` §2's "Postgres full-text" without leaving it: no external search, and Postgres when size justifies it (§13 Q7).

### 2.10 Search insights in admin

- **`/admin/search`** (English, SSR `no-store`, `noindex`; permission `search.insights.view`: admin, ops and content, not finance): for the last 7, 30 or 90 days, filtered by locale and destination: total searches, the share with no results, the top 50 queries, the top 50 queries with no results, and the count of withheld queries. A query appears only when it was searched at least 3 times in the window (`SEARCH_INSIGHTS_MIN_COUNT = 3`). Read-only; no export in v1.
- **What is stored** (§5.1): per (day, locale, destination, normalised query, outcome) a count; per (day, locale, destination) totals. `isStorableQuery` keeps a normalised query only when it has 2 to 40 characters, 1 to 4 tokens, letters and spaces only (no digit at all), no token over 20 letters, and, when it has 2 or more tokens, at least one token that is in the search vocabulary (so "roses anna" is kept as a query about roses, "anna kowalska" is withheld). Withheld queries are counted, never stored.
- **Written in batches.** Searches are counted in memory and flushed every 60 seconds (and at shutdown) in one statement, under the system context. Only page 1 of a search counts. A crash loses at most a minute of counts. With no database (development, tests) insights are off.
- **Retention:** query rows 90 days, totals 400 days, by `retention.sweep` (spec 002's retention policy table).

### 2.11 Performance and the suggestions island

- **Budgets.** Search's own server time (normalise, match, rank, page) p95 at most 50 ms over the committed fixture query set on CI's runner, with the index warm; index build at most 300 ms for the committed catalogue in four locales. The results page joins the Lighthouse set (`/en/search?q=roses&to=pl`) with `plan/01` §7's budgets: LCP under 2.0 s, CLS under 0.05, script at most 131 072 B Brotli (spec 004 A1). The header form adds no client JavaScript to any route.
- **Suggestions (slice 2, off by default).** A small client island, loaded through spec 004's `AfterPaint` after the LCP paint and only on the first focus of the field, turns the header field into an ARIA 1.2 combobox (APG "combobox with listbox popup"): after 2 letters and 150 ms of no typing it asks `GET /api/search/suggest` for at most 6 suggestions (hub links and product names, never a price) and lists them; arrow keys move, Enter on an option follows it, Enter otherwise submits the form, Escape closes. The deferred chunk is at most 4 096 B Brotli and no route's first-load JavaScript grows by more than 512 B. Gated by `SEARCH_CONFIG.suggestions` in `src/config/search.ts` (default `false`); the founder turns it on after the budget run (§13 Q9).

## 4. User stories

- As a **buyer on `/en/poland/flowers`**, I type "white roses" in the header and see the white rose bouquets that can go to Poland, with the same all-in prices as the shop, and nothing else first.
- As a **Polish speaker in Germany on `/pl`**, I type "roze" without the accents and still find "róże", priced for the destination I chose, in Polish.
- As a **buyer who misspells**, I type "sunflwers" and still find the sunflower bouquets, or I am offered "Did you mean sunflowers?".
- As a **buyer who types an occasion**, I type "Geburtstag" on `/de` and get a link to the birthday page for Poland as well as the bouquets.
- As a **buyer with JavaScript off or a screen reader**, I can search, read the results, change the destination and page through them.
- As the **founder**, I want the bouquets that earn us more to come first among equally good matches, said plainly on the page, and to see what people search for and fail to find.
- As **Googlebot**, I never find a search URL in a sitemap or a link, and if I fetch one from an outside link I am told `noindex`.

## 6. SEO considerations (mandatory)

- **Indexability.** Every search URL answers `noindex, follow` in the meta tag and the `X-Robots-Tag` header (`plan/02` §4.1 "Search … noindex", §7 "Search: noindex"), in every environment. "follow" lets a crawler that arrives from an outside link reach the product pages, which are the pages we want found.
- **Not blocked in `robots.txt`, deliberately.** Google: for `noindex` to work, "the page or resource must not be blocked by a robots.txt file" ([Google Search Central, Block indexing with noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing)). A disallowed search URL linked from a spam site could still be indexed by URL alone; a crawlable `noindex` one cannot. Crawl budget is not at stake at our size: Google's crawl-budget guide is for large sites and notes that `noindex` pages are still requested ([Google, Large site crawl budget](https://developers.google.com/search/docs/crawling-indexing/large-site-managing-crawl-budget)). This is `plan/02` §7's facet rule applied to search, and it departs from `plan/01` §3's robots column ("blocks … `/search`"), which predates the locale prefix. Revisit trigger: Search Console showing more than 1 000 crawled search URLs in a month; then a `Disallow` is a one-line change (§13 Q10).
- **Never discoverable from our pages.** No sitemap lists a search URL (the sitemap builders read indexable page types only; `plan/02` §10 "nothing noindex ever appears in a sitemap"). No `<a href>` we render carries `q=`: pagination, "Did you mean" and "any date" are GET form buttons, and the language switcher on the search page links to the bare search page of each locale.
- **Canonical:** `/{locale}/{searchSegment}` (bare, parameter-free) on every search URL, per `plan/02` §4.1's "noindex; canonical to base". **hreflang:** none (alternates exist only between indexable pages, `plan/02` §8).
- **The query is never a title or heading Google can index:** the page is `noindex`; the `<title>` is `search.meta.title` ("Search") with the site name, never the query, so a spammed URL cannot put words into a title.
- **Structured data:** none on the results page (no `ItemList`, no `Product`); the product pages carry their own. No `SearchAction` (§3).
- **Internal links out:** hub links (Pages block), product cards and "Our selection" point only at pages that answer 200 (`existsNow`), the same targets the listings use, so search adds no broken link and no new URL shape.
- **Thin content:** not applicable (not indexable). Spam injection (attackers linking `?q=spam`) is defused by `noindex`, the title rule and escaping.
- **Core Web Vitals on indexable pages:** the header form is plain HTML in a reserved box, so CLS stays 0 and no route's first-load JavaScript grows (slice 1). The suggestions island loads after the LCP paint, on first focus, outside first-load JavaScript (slice 2). Listings with the margin preference ship no new byte.
- **Listings' order changes are not an SEO risk:** the URL set, canonicals, `ItemList` equality and sitemaps are unchanged; only the order of cards within a page moves, and it stays deterministic (`plan/02` §7 "default sort deterministic").

## 8. Compliance considerations (mandatory)
