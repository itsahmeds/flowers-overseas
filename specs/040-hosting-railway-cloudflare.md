## 1. Problem

The project is hosted on Vercel **Hobby**, a plan whose terms forbid commercial use and which
rate-limited builds for 24 h on 2026-09-09. On 2026-09-16 the founder ruled that Vercel Pro is not
affordable now and that Railway is already paid for; ADR-0018 records the decision and fires
`plan/08` §4's documented fallback — **Railway (`web` + `worker`, Amsterdam `europe-west4`) behind
Cloudflare's free CDN** — on cost, earlier than planned. The Railway project (`flowers-overseas`,
id `6a1ae3cb-…`, environments `production` and `staging`) and the Cloudflare zone
(`flowersoverseas.com`, nameservers switched at GoDaddy, propagation pending) both exist already;
neither has a service, a rule or a deploy.

The move is blocked on one thing, and it is not infrastructure. Environment detection in this
codebase keys on `VERCEL_ENV` (`src/lib/env.schema.ts` `deploymentEnvironment()`), and the note
left on TASK-007's review says exactly what happens on the fallback host: `VERCEL_ENV` is unset, so
the function answers `development`, which is the safe direction for `noindex` and the wrong
direction for everything else — the production placeholder guard from PR 62 stops discriminating,
`isIndexingEnvironment()` (spec 007) can never be true, the CSP keeps a `vercel.live` allowance on a
host that has no `vercel.live`, and `ENABLE_DEV_UI` / `ENABLE_PSEUDO_LOCALES` stop being refused.
ADR-0018 states the consequence as a rule: **until an `APP_ENV` abstraction lands, there is no
production deploy on Railway.** This spec owns that abstraction and the platform underneath it.

Two further constraints shape every choice below, and both are about not breaking things that are
already true. ADR-0016 puts a **build-time `sha256` hash of one inline script** into a CSP that is
served on *cached* HTML: any Cloudflare feature that injects, rewrites or minifies HTML or JS
invalidates that hash and starts reporting (later: blocking) on every page — so the do-not-enable
list in §5.3 is a correctness requirement, not a preference. And spec 007 AC-12 makes `robots.txt`
**byte-exact per environment** with exactly one `Sitemap:` line, which rules out Cloudflare's
managed `robots.txt` and Bot Preference Sync (already off on the zone) for the life of the product.

## 2. Scope

Each bullet is testable; §9 names the AC.

**The environment abstraction (§5.2)**

- `APP_ENV ∈ {development, test, preview, staging, production}` as the single environment signal,
  set by whichever platform runs the app, read by one function, mirrored to the browser as
  `NEXT_PUBLIC_APP_ENV`. Unset ⇒ `development` ⇒ `noindex`: **fail-closed**.
- Every current `VERCEL_ENV` reader moves behind it: the production placeholder guard and the https
  origin rule (`validateEnv`), the blanket `X-Robots-Tag: noindex` (`src/lib/robots-headers.ts`),
  the `production` refusals of `ENABLE_PSEUDO_LOCALES` and `ENABLE_DEV_UI`, the CSP's `vercel.live`
  allowance and HSTS gate (`src/lib/csp.ts`), Sentry's `environment` tag (`src/lib/sentry.ts`), and
  spec 007's `isIndexingEnvironment()`.
- Backwards compatibility: while Vercel Hobby stays linked as a cold fallback, `VERCEL_ENV` is
  accepted as a *fallback source* for `APP_ENV` and nothing else. A grep gate keeps the read in one
  file.

**The Railway topology (§5.3)**

- `web` service: Next.js `output: "standalone"`, Node 24, region `europe-west4`, healthcheck,
  restart policy, memory/CPU sizing, **single replica** until a shared ISR cache handler exists.
- `worker` service: provisioned, wired to the same variables, **not started** — spec 002 TASK-024
  owns the pg-boss consumer and TASK-028 the nightly `pg_dump` cron. This spec provides the seat.
- Environments `production`, `staging`, and ephemeral PR environments forked from staging sharing
  the seeded staging database by connection string (`plan/08` §3.5).
- The variable contract per environment (the 26 keys of PR 62 plus `APP_ENV`, `NEXT_PUBLIC_APP_ENV`
  and `NEXT_PUBLIC_SITE_URL`), sealed, never in the repo, drift-checked.
- Build method (Dockerfile vs Nixpacks — §13 Q1), deploy triggers, and rollback by redeploying the
  previous image.

**Cloudflare in front (§5.4)**

- DNS, TLS, protocol and compression settings; cache rules that **respect origin `Cache-Control`**
  and bypass every dynamic path; rate limiting on `/api/*` and form POSTs.
- The **do-not-enable list** with a reason per row, machine-checked.
- `revalidateTag` → Cloudflare **URL purge** emulation inside `src/lib/cache.ts` (Cache-Tag purge is
  Enterprise-only).
- Non-production access protection replacing Vercel Deployment Protection.
- All of it expressed as an **idempotent script** — `scripts/cloudflare/apply-zone-settings.ts`,
  with `--check` mode that diffs live settings against the declared ones and fails CI on drift —
  plus `docs/runbooks/railway-cloudflare-setup.md`.

**CI/CD, observability, cutover (§5.5, §11, §12)**

- `ci.yml`: preview discovery against the Railway PR environment, Lighthouse against the
  Cloudflare-fronted preview with `aggregationMethod: median`, `env-build-failure` keyed on
  `APP_ENV`, a `cloudflare-check` drift job, and what runs locally while GitHub Actions is
  billing-blocked.
- Health, uptime, logs, Sentry; the EU-residency caveat and the RoPA/DPA updates.
- Cutover order, what is never done before `APP_ENV` lands, and the exit signal.

## 3. Non-goals

- **Turning indexing on.** The `noindex` → indexable flip is spec 007 §12 / TASK-096 and stays a
  configuration act owned there. This spec only guarantees that the flip works the same way on the
  new host.
- **Starting the worker or the backup job.** pg-boss consumers are spec 002 TASK-024; the nightly
  `pg_dump` to R2 is spec 002 TASK-028. This spec provisions the service and the cron seat and
  proves they can run.
- **A shared ISR cache handler / Redis.** Required before a second `web` replica; §13 Q4 sets the
  trigger. Until then, one replica is a correctness constraint (ADR-0018).
- **Cloudflare Images / Polish / R2 `media.` custom domain.** The image pipeline is spec 006's; the
  `media.` hostname is added by the spec that first serves R2 objects publicly.
- **A WAF ruleset beyond one rate-limit rule.** Cloudflare Pro's WAF is §13 Q3.
- **Deleting the Vercel project.** Unlinking timing is §13 Q5; the project stays as a cold fallback
  until the exit signal of §12 is met.
- **Log drains to an EU store.** `plan/08` §7 puts it in Phase 1; §8 records the gap.

## 4. User stories

- As **Googlebot**, I fetch a corridor page from a Cloudflare PoP in Frankfurt and get cached HTML
  in under 200 ms with no `Vary`, no cookie, no injected script and the same bytes every time, so
  the page is cheap to crawl and safe to index.
- As **an AI agent** (ClaudeBot, GPTBot, PerplexityBot, an agentic browser), I am not challenged,
  rate-limited or served an interstitial, because the founder ruled on 2026-09-16 that AI agents may
  crawl this site.
- As **a buyer in Warsaw**, my checkout request bypasses the CDN and is rendered in Amsterdam
  against EU data, and nothing about my request is cached.
- As **the founder**, I deploy by merging to `main`, roll back by redeploying the previous image,
  and can tell from one command whether the Cloudflare zone still matches what the repository says
  it should be.
- As **the reviewer agent**, I read a PR's preview URL from the CI summary, and the same suites that
  ran on Vercel previews run against it.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

**None.** This spec adds no table, column, index or migration; `supabase/migrations/` is untouched
and `pnpm db:check` keeps printing its current verdict. The only persisted state it introduces is
configuration: environment variables in the Railway variable store (per environment, sealed) and
zone settings in Cloudflare. Both are declared in the repository as data — `config/railway.json`
(service, region, replicas, healthcheck, restart policy) and
`config/cloudflare/zone-settings.json` (every setting this spec pins, with its required value) —
and applied by idempotent scripts.

The rollback for each is therefore not SQL but a declared previous state: both files are versioned
in git, both scripts are idempotent, and `--check` reports drift in both directions, so reverting
the commit and re-running the script restores the previous configuration exactly. No money value,
no personal data and no currency is introduced anywhere in this spec.

### 5.2 `APP_ENV` — the environment abstraction

**The values.** `DeploymentEnvironment` becomes
`"development" | "test" | "preview" | "staging" | "production"`. `staging` is new: it exists on
Railway today and is the florist demo environment of `plan/08` §9, and it must be production-like in
configuration while remaining permanently `noindex`.

**The one reader.** `appEnvironment(source: EnvSource): DeploymentEnvironment` in
`src/lib/env.schema.ts` replaces `deploymentEnvironment()` (the old name is kept as a deprecated
re-export for one PR, then deleted). Resolution order, and it is fail-closed at every step:

1. `APP_ENV`, when it parses as one of the five values.
2. `VERCEL_ENV`, when `APP_ENV` is absent and it parses as `preview` or `production` — the
   compatibility path for the cold Vercel fallback, and the only remaining read of that key.
3. `NODE_ENV === "test"` ⇒ `test`.
4. Otherwise `development`.

A value of `APP_ENV` that is present and does **not** parse is a **build failure**, not a silent
fallback: a typo like `prod` must not quietly produce a `development` build that then passes the
placeholder guard it was supposed to fail.

**The client mirror.** `NEXT_PUBLIC_APP_ENV` is added to `clientEnvSchema` with the same enum,
optional. `NEXT_PUBLIC_VERCEL_ENV` stays in the schema, optional and unused by application code,
until the Vercel unlink of §13 Q5 deletes both it and `VERCEL_ENV` from the contract.

**The call sites that change**, and what each becomes:

| Today | After |
|---|---|
| `deploymentEnvironment(process.env)` in `next.config.ts` | `appEnvironment(process.env)` |
| `noindexHeaderRules(env)`: header unless `production` | unchanged rule, new input — `staging` and `preview` both get `X-Robots-Tag: noindex`; `development` (the unset case) does too |
| `validateEnv`: placeholder + https rules for `preview \| production` | `preview \| staging \| production` |
| `validateEnv`: refuse `ENABLE_PSEUDO_LOCALES` / `ENABLE_DEV_UI` in `production` | refuse in `production` **and** `staging` — staging is shown to florists |
| `allowsPreviewFeedback(env)`: true unless `production` | `hostPlatform(source) === "vercel" && env !== "production"`. On Railway it is false in **every** environment, so `vercel.live` leaves the policy of every Railway deploy (ADR-0016: a shorter allowlist is strictly better) |
| `sendsHsts(env)`: `production` only | unchanged; `staging` sends no HSTS because it runs on a Railway subdomain we do not want pinned |
| `cspValue`: `upgrade-insecure-requests` for `preview \| production` | add `staging` |
| `src/lib/sentry.ts`: `VERCEL_ENV ?? NEXT_PUBLIC_VERCEL_ENV` | `APP_ENV ?? NEXT_PUBLIC_APP_ENV`; release from `RAILWAY_GIT_COMMIT_SHA ?? VERCEL_GIT_COMMIT_SHA` |
| spec 007 `isIndexingEnvironment()` | `appEnvironment() === "production"` **and** `NEXT_PUBLIC_SITE_URL` host equals the canonical host — semantics unchanged, source changed |

`hostPlatform(source)` is a three-value helper (`"vercel" | "railway" | "local"`) derived from
`VERCEL === "1"` / `RAILWAY_ENVIRONMENT_NAME` being present. It exists only for the `vercel.live`
row above and for the CI preview-URL discovery of §5.5; nothing else in the application may branch
on it, which is what the grep gate below enforces.

**The grep gate.** `pnpm check:no-vercel-env` (a step of the `lint` job, beside `check:no-db`)
fails when `VERCEL_ENV`, `NEXT_PUBLIC_VERCEL_ENV` or `VERCEL_GIT_COMMIT_SHA` is read anywhere under
`src/`, `scripts/` or `tests/` except `src/lib/env.schema.ts` and `src/lib/sentry.ts`. This is the
mechanism that makes "the abstraction is complete" a check rather than a claim, and it is what makes
the eventual Vercel unlink a two-file diff.

### 5.3 Railway topology

**Build.** `next.config.ts` gains `output: "standalone"`. The image is produced from a committed
multi-stage `Dockerfile` (§13 Q1 defaults to Dockerfile over Nixpacks): `node:24-slim` base, corepack
pnpm pinned to the repo's version, `pnpm install --frozen-lockfile`, `pnpm build`, then a runtime
stage copying `.next/standalone`, `.next/static` and `public/` only, running as a non-root user,
`CMD ["node", "server.js"]`, `EXPOSE 3000`. The reason to prefer it over Nixpacks is reproducibility:
the same image builds locally, in CI and on Railway, `sharp`'s native build is pinned rather than
inferred, and the Node major version is in the repository instead of in a dashboard.

**Services.**

| Service | Command | Region | Replicas | Memory / CPU | Healthcheck | Restart |
|---|---|---|---|---|---|---|
| `web` | `node server.js` (standalone) | `europe-west4` (Amsterdam) | **1**, pinned | 1 GB / 1 vCPU (`plan/08` §3.6's 10k-visit line; `sharp` OOMs at 512 MB) | `GET /api/health`, 200 within 5 s, 30 s interval, 300 s grace | on-failure, max 10, exponential backoff |
| `worker` | `pnpm worker` (spec 002 TASK-024) | `europe-west4` | 0 until TASK-024 | 512 MB / 0.5 vCPU | process-liveness only (no HTTP port) | on-failure, max 10 |

Single replica is a **correctness** constraint, not a cost one: Next's self-hosted ISR cache is
in-process, so a second replica serves two divergent caches and a `revalidateTag` purges one of
them (ADR-0018, `plan/08` §3.4). `config/railway.json` declares `numReplicas: 1` and
`pnpm railway:check` fails when the live value differs, so raising it is a reviewed diff that must
come with the shared cache handler of §13 Q4.

The `worker` service has **no public domain** and no Cloudflare record: it is reachable only from
inside the Railway private network, and its only outbound dependencies are Neon and R2. The cron
seat is Railway's cron on the `worker` service (a scheduled invocation of the same image with a
different command), chosen over an HTTP `/api/internal/cron/tick` route because a long-lived
process is exactly what Railway is good at and it keeps `INTERNAL_CRON_SECRET` off the public
surface.

**Environments and variables.**

| Environment | `APP_ENV` | Database | Domain | Protection |
|---|---|---|---|---|
| `production` | `production` | Neon production branch | `flowersoverseas.com` (+ `www` → apex) via Cloudflare | none (public site) |
| `staging` | `staging` | Neon staging branch, seeded | `staging.flowersoverseas.com`, proxied | Cloudflare Access or basic-auth middleware |
| PR (ephemeral) | `preview` | **shares the staging connection string** (`plan/08` §3.5: no per-PR Postgres) | `pr-<n>.flowersoverseas.com` via a wildcard record, proxied | same as staging |
| local | `development` | local / staging | `localhost:3000` | — |

Every environment carries the full variable contract: the 26 keys of PR 62, plus `APP_ENV`,
`NEXT_PUBLIC_APP_ENV` and an environment-appropriate `NEXT_PUBLIC_SITE_URL`. Secrets are set in the
Railway variable store only — never in `railway.json`, never in the repository, never in a CI log —
and `.env.example` gains the two new keys so `pnpm env:check` keeps both lists in step. PR
environments inherit from `staging` at fork time, and the two keys that must differ per PR
(`NEXT_PUBLIC_SITE_URL`, `APP_ENV=preview`) are set by the fork.

`pnpm railway:check [--env <name>]` compares the live **key set** (never a value) of an environment
against the declared contract and exits non-zero on a missing or unexpected key, printing key names
only.

**Deploys and rollback.** GitHub integration: `main` → `production`, PR branches → their ephemeral
environment. No deploy from a local machine. Rollback is a Railway redeploy of the previous image
(the image is retained, so no rebuild is needed) and is the first step of
`docs/runbooks/rollback.md`'s hosting section, with a target of under five minutes from decision to
served.

### 5.4 Cloudflare in front

**DNS.** `flowersoverseas.com` (apex) and `www` are CNAMEs to the Railway-issued domain, flattened
at the apex, both **proxied** (orange cloud). `www` is 301'd to the apex by a Cloudflare redirect
rule, which is `plan/02` §7's "`www` → apex, 301 at the edge". A `*.flowersoverseas.com` wildcard
serves PR environments. The GoDaddy parking A/CNAME records imported at zone creation are deleted;
the `_dmarc` TXT is kept. `media.` is **not** added here (§3).

**TLS and protocol.**

| Setting | Value | Why |
|---|---|---|
| SSL/TLS mode | **Full (strict)** | Railway presents a valid certificate; anything less lets a MITM between Cloudflare and the origin |
| Always Use HTTPS | on | with HSTS from the origin (production only) |
| Minimum TLS | 1.2 | 1.0/1.1 are deprecated and no buyer needs them |
| TLS 1.3 + 0-RTT | on | 0-RTT is applied to idempotent GETs only; POSTs (checkout, forms) are never replayed |
| HTTP/2, HTTP/3 (QUIC) | on | HTTP/2 is what lets LHCI move from `optimistic` to `median` (§5.5) |
| Brotli | on | spec 004 §14 A1's budget is measured in Brotli; the origin proxy of A12 exists only because the Vercel-free origin spoke HTTP/1.1 without it |
| Early Hints | on | costs nothing; note honestly that it has **no effect until the origin emits `Link` preload headers**, which no task in this spec adds — it is enabled so the day a `Link` header appears the benefit is automatic |
| Automatic HTTPS Rewrites | **off** | it rewrites HTML (see the do-not-enable list) |

**Cache rules.** The single most important rule is the one we do *not* write: there is **no "Cache
Everything"** override. Next already sends `Cache-Control: s-maxage=…, stale-while-revalidate=…`
for ISR routes (spec 007 AC-23: `revalidate` 86400 on corridor pages) and `no-store` for the
dynamic ones, and Cloudflare's default behaviour of respecting origin `Cache-Control` for HTML is
exactly the behaviour ISR needs. Writing our own "cache everything, edge TTL 2 h" rule would cache
`no-store` checkout HTML — the failure mode that ends a company.

| Rule | Expression | Action |
|---|---|---|
| 1 — bypass dynamic | `starts_with(path, "/api/") or starts_with(path,"/checkout") or starts_with(path,"/account") or starts_with(path,"/admin") or starts_with(path,"/vendor") or starts_with(path,"/track")` (per locale prefix too) | Bypass cache |
| 2 — respect origin | everything else | Cache eligibility: respect origin; **cache key ignores** `utm_*`, `gclid`, `fbclid` (`plan/02` §7); no cookie in the cache key |
| 3 — rate limit | `starts_with(path,"/api/") or (http.request.method eq "POST")` | 60 requests / minute / IP, action **managed challenge → block after**; one free-plan rule, and the app-level limits of `plan/01` §9 stay |

Because no response that is cached may carry a cookie or a `Vary` (spec 003 AC-12, spec 007 AC-23,
`plan/02` §14), the cache configuration adds nothing here: it simply must not *introduce* one. The
`--check` mode asserts the absence of any cache rule that sets a cookie, adds a `Vary`, or enables
"Cache Everything".

**Tag invalidation → URL purge.** `src/lib/cache.ts` gains `cloudflareCacheAdapter`, implementing
the existing `CacheAdapter` interface, so no caller changes (that seam was created for exactly this
in spec 001 §5.4). Behaviour:

- `invalidate(tags)` maps each tag to the set of absolute URLs carrying it, via a pure
  `urlsForTag(tag): string[]` built from the same registries the pages are generated from (locales ×
  countries; `home:{locale}` → one URL per locale). Purely computed, never fetched.
- URLs are de-duplicated, chunked **≤30 per request** (the Cloudflare API limit `plan/08` §3.1
  names) and POSTed to the zone purge endpoint with bounded concurrency.
- Failures are retried twice with backoff, then logged at `error` with the **count** of URLs and the
  tag names — never a URL list in a single log line, and never a PII-bearing value (there are none:
  no PII ever appears in a URL, `CLAUDE.md`).
- When `CLOUDFLARE_API_TOKEN` or `CLOUDFLARE_ZONE_ID` is absent — locally, in CI, on Vercel — the
  adapter is the existing no-op. A missing token must never fail a build or a request.
- Stale-while-revalidate means a purge is a latency optimisation, not a correctness requirement:
  a failed purge shows stale HTML for at most the `s-maxage` window, and that is the accepted
  trade-off ADR-0018 already names.

**The do-not-enable list.** Every row is off today and must stay off; `--check` fails when any is
on. The reason column is the point of the table.

| Feature | State | Reason |
|---|---|---|
| Rocket Loader | **off** | rewrites and defers `<script>` elements — breaks the ADR-0016 inline hash and reorders the consent bootstrap |
| Auto Minify (HTML/CSS/JS) | **off** | mutates the inline script's bytes; the build-time `sha256` no longer matches (and Cloudflare has deprecated it anyway) |
| Email Address Obfuscation | **off** | injects JavaScript into HTML; same hash breakage, plus it mangles `mailto:` in the Impressum |
| Server-Side Excludes | **off** | conditional HTML rewriting |
| Mirage / Polish (on HTML documents) | **off** | image rewriting in the document; spec 006 owns the image pipeline and the LCP element must stay predictable |
| Hotlink Protection / Scrape Shield changes | **off** | blocks legitimate image fetches, including Googlebot Images |
| Managed `robots.txt` / Bot Preference Sync | **off** (already, at zone creation) | spec 007 AC-12 requires `robots.txt` to be **byte-exact and application-owned**, with exactly one `Sitemap:` line |
| Bot Fight Mode / Super Bot Fight Mode | **off** | challenges Lighthouse, headless Playwright, legitimate crawlers and AI agents; it is the single most likely way to silently lose indexing |
| AI Scrapers & Crawlers blocking / AI Labyrinth / pay-per-crawl | **off**; Search, Agent and Training set to **Allow** | founder direction 2026-09-16: **AI agents may crawl this site** |
| Under Attack mode | off (manual, incident only) | interstitial HTML for every visitor |
| IP-geolocation redirect rules; any use of `cf-ipcountry` to route | **never** | ADR-0006, and `fo/no-geo-redirect` already fails the lint |
| Cloudflare Access on **production** | never | it would put an auth wall in front of the indexable site |
| Cloudflare Access / basic-auth on **staging and PR** | **required** | replaces Vercel Deployment Protection; `plan/01` §10 keeps non-production password-protected |
| Workers / Snippets injecting HTML | not used | same hash argument; if one is ever needed it must not touch the document body |

**Non-production protection.** Default: a **basic-auth check in `src/proxy.ts`**, gated on
`appEnvironment() !== "production"` and on a `STAGING_BASIC_AUTH` variable being set, answering 401
with `WWW-Authenticate` and exempting `/api/health`. It is chosen over Cloudflare Access because it
costs nothing, works identically on Railway without Cloudflare (so a PR environment is protected
even before DNS), and is testable in the e2e suite with a header. Playwright and Lighthouse send the
credential the same way they sent `VERCEL_AUTOMATION_BYPASS_SECRET`. §13 Q6 offers Access instead.

**The script.** `scripts/cloudflare/apply-zone-settings.ts` reads
`config/cloudflare/zone-settings.json` and applies it through the Cloudflare API:

- `--check` (CI mode) fetches every declared setting, diffs it against the file, prints one line per
  difference (`setting · declared · live`) and exits non-zero. It performs **no write**.
- Default mode applies differences and is **idempotent**: a second run reports `0 changes`.
- It reads `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ZONE_ID` from the environment; both absent ⇒ it
  exits 0 with `skipped: no token` so a contributor's local run is never a failure, and CI's
  `cloudflare-check` job requires the token explicitly.
- **Token scopes, exactly**: `Zone → Zone Settings → Edit`, `Zone → DNS → Edit`,
  `Zone → Cache Purge → Purge`, `Zone → Zone → Read`, scoped to the single zone
  `flowersoverseas.com`. **No account-level scope of any kind.** A unit test pins the endpoint list
  the script may call, so an account-scoped call cannot be added without failing a test, and a 403
  is reported as "the token is missing scope X" rather than as a stack trace.

### 5.5 CI/CD

`.github/workflows/ci.yml` changes, and nothing else in it moves:

- **`preview` job** no longer waits for a Vercel deployment. It resolves the Railway PR
  environment's public URL by polling the Railway GraphQL API for the environment whose name matches
  `pr-<number>` and whose latest deployment is `SUCCESS`, with the same 45 × 20 s budget, and fails
  loudly (never skips) when none appears. Its verification step keeps the same three assertions in
  their new form: the unauthenticated request is refused (basic-auth 401 instead of the Vercel SSO
  302), the response proves the Amsterdam origin (a `x-fo-region` header the health route emits from
  `RAILWAY_REGION`, because there is no `x-vercel-id` any more), and `X-Robots-Tag: noindex` is
  present. The preview URL handed to the downstream jobs is the **Cloudflare-proxied** hostname, so
  e2e, visual, a11y and Lighthouse all measure what a visitor gets.
- **`lighthouse`**: `lighthouserc.json` switches `aggregationMethod` from `optimistic` to `median`
  (the orchestrator's 2026-09-16 ruling, spec 004 §14 A18), and the Brotli origin proxy of spec 004
  §14 A12 is **deleted** — Cloudflare supplies Brotli over HTTP/2, which is why the proxy existed.
- **`env-build-failure`**: keyed on `APP_ENV=production` instead of an absent `VERCEL_ENV`, which
  makes it a stronger check than it was — it now proves the production placeholder guard fires.
- **`cloudflare-check`** (new job, `needs: typecheck`, the `plan/08`-style placement rule of spec 001
  §14 A9): runs `pnpm cloudflare:check`. On PRs it runs only when `config/cloudflare/**` changed or
  the `ci:full` label is present; it also runs on the nightly schedule, because zone drift is
  usually somebody clicking in a dashboard rather than opening a PR.
- **`railway-check`** is a step of `cloudflare-check`, not a job: it is one API call comparing key
  sets.

**While GitHub Actions is billing-blocked** (the repository's Actions minutes are unavailable as of
2026-09-16), every gate above runs locally and its result is recorded in `TASKS.md` by the
implementer and re-run by the reviewer, exactly as specs 004–007 have been verified since
2026-09-09: `pnpm lint && pnpm typecheck && pnpm test && pnpm build`, then `pnpm cloudflare:check`
and `pnpm railway:check` against the real zone and project, then the Playwright suites and LHCI
against the staging URL rather than a PR environment. The workflow file is still edited and its
assertions pinned by `tests/unit/ci-workflow.test.ts`, so the jobs are correct on the day billing is
restored — that test is the gate that keeps a non-running workflow honest.

### 5.6 UI (pages, components, states)

No new page and no new component. Two user-visible surfaces change state:

- `/api/health` gains `region` and `appEnv` fields (no PII, no secret, no database call) and keeps
  its `X-Robots-Tag: noindex`.
- Non-production environments answer **401 with a browser auth prompt** before any route renders,
  except `/api/health`, which must stay open for the uptime monitor and the CI probe.

### 5.7 Rendering & caching (per plan/01 §3)

Unchanged by design — that is the whole claim of this spec. `plan/01` §3's table stands: ISR for
programmatic pages, SSG for editorial, SSR `no-store` for transactional. What changes is the
implementation of the seam its "implementation notes" already anticipated: "ISR is realised with
`revalidate` + `revalidateTag()` on Vercel, and with Cloudflare cache rules + purge … when fronting
Railway. The application calls one internal `invalidate(tags[])` function." This spec writes the
second adapter. Corridor pages keep `revalidate: 86400` and their tags (spec 007 AC-23); the home
keeps `home:{locale}`; no route's caching semantics change, and none may start varying by header or
setting a cookie.

## 6. SEO considerations (mandatory)

SEO is priority #1 and this is the spec most able to damage it, so the criteria are specific.

- **TTFB.** `plan/01` §7's budget is < 200 ms for cached HTML from FRA/AMS/LHR/ARN/WAW. Target on a
  Cloudflare **HIT**: ≤ 100 ms from those PoPs (ADR-0018's "within ~30 ms of Vercel"). On a **MISS**
  the Amsterdam render applies: ≤ 600 ms, and the MISS rate is kept small by `stale-while-revalidate`
  — a revalidation serves stale immediately and refreshes behind it, so Googlebot rarely pays the
  render. Measured by AC-27's synthetic curl set, not asserted by hope.
- **No `Vary`, no cookie on cached HTML.** Carried forward verbatim from spec 003 AC-12 and spec 007
  AC-23 and re-asserted *through the CDN*: the byte body of a document fetched through Cloudflare
  must equal the body fetched from the origin, with and without `fo_locale` / `fo_currency` /
  `fo_consent`. This is also the ADR-0016 integrity test: equal bytes means no injected script and a
  valid inline hash.
- **HTTP/2 + HTTP/3 + Brotli** on every document. Beyond the raw win, HTTP/2 is what makes the
  Lighthouse numbers stable enough to move LHCI to `median` (spec 004 §14 A18) — i.e. this spec
  *tightens* a CWV gate rather than relaxing one.
- **Crawler access is explicitly open.** No bot-management feature may challenge, delay or block
  Googlebot, Bingbot, Applebot, Yandex, Lighthouse's headless Chrome, or the AI agents the founder
  named (ClaudeBot, GPTBot, PerplexityBot, and agentic browsers). A challenge served to Googlebot is
  indistinguishable from a soft-404 farm; a rate limit that fires on a crawl burst is a crawl-budget
  cut. The rate-limit rule of §5.4 is scoped to `/api/*` and POSTs precisely so no document fetch can
  ever hit it.
- **`robots.txt` and `sitemap.xml` are application responses, unmodified by the edge.** Cloudflare's
  managed `robots.txt` and Bot Preference Sync stay off (spec 007 AC-12 requires byte-exactness and
  exactly one `Sitemap:` line). AC-19 asserts the bytes through the CDN.
- **Indexability is unchanged and still fail-closed.** `APP_ENV` unset ⇒ `development` ⇒ `noindex`;
  `staging` and every PR environment are `noindex` and behind auth, so a preview URL cannot be
  indexed even if it is linked. ADR-0007 and spec 007's rule engine are the only place indexability
  is decided; this spec adds no second branch.
- **Canonical host.** `www` → apex 301 at the edge and `NEXT_PUBLIC_SITE_URL` are the only two
  places the canonical host is expressed, and AC-14 ties them together: a mismatch would make every
  canonical point at a redirecting host.
- **No IP redirects** at the edge — ADR-0006, restated as a Cloudflare configuration rule because
  Cloudflare makes them a two-click affair. `cf-ipcountry` is never read.
- **Thin content / duplication risk:** none. This spec creates no URL.
- **CWV budget impact:** net positive (Brotli + HTTP/2 + PoP termination); the one regression risk
  is a cache MISS on an uncached corridor page, bounded above.

## 7. i18n considerations (mandatory)

No new message key, no new namespace, no formatting change and no RTL surface: this spec ships no
user-visible string except the browser's own basic-auth prompt on non-production, which is rendered
by the browser in the user's own language and is never seen by a buyer.

What it must actively **not** do is the whole i18n content of the spec, and it is not trivial,
because a CDN is the classic place locale routing goes wrong:

- **No geo redirect, ever** (ADR-0006, `plan/03` §2). Cloudflare offers IP-country redirect rules;
  none is created, `cf-ipcountry` is never read by application code or by a rule, and the
  `fo/no-geo-redirect` lint rule continues to cover the application side. AC-20's crawler checks
  double as evidence: a request with a US IP and a Polish `Accept-Language` must receive exactly the
  same bytes as any other.
- **Locale stays in the URL** and the cache key is the URL. No `Vary: Accept-Language`, no
  language-based cache segmentation, no cookie in the cache key — so `/pl/…` and `/en/…` are
  distinct cache entries for the only correct reason.
- **Currency stays in a cookie and never enters cached HTML** (spec 003 AC-12); bypassing the cache
  for a currency cookie would be the easy, wrong fix and is forbidden by the same rule.
- **Translation review and `noindex` gating** are untouched: `isLocaleIndexable()` and the ≤5%
  unreviewed-share gate of spec 003 keep deciding, from `APP_ENV` now instead of `VERCEL_ENV`.
- The one i18n-shaped *risk* this spec accepts: Cloudflare's per-PoP caching multiplies the number
  of caches holding a locale's HTML, so a bad purge is visible per region. The URL-purge adapter
  purges globally in one call, which is why a tag must map to a complete URL list (AC-22) rather
  than to a "current locale" subset.

## 8. Compliance considerations (mandatory)

**Data flows added.** No new personal-data flow, no new lawful basis, no consent surface, no price
display and no consumer-information change. What changes is **who processes the existing
platform-log flow**: `docs/compliance/ropa.md` **row 2** ("Website hosting, edge routing and
serverless function execution (platform logs)") is rewritten from Vercel to **Railway Corp. (US)**
as the compute/log processor and **Cloudflare, Inc. (US)** as the CDN/edge processor, with the same
categories (IP, user agent, timestamp, method, path, status, response time), the same lawful basis
(legitimate interest, Art. 6(1)(f)), and the platform-specific fields updated (`x-vercel-id` →
Railway deployment id and `cf-ray`).

**Residency, stated honestly.** `plan/07` §1.4 already allows "hosting compute/edge may run globally
for cached HTML (no personal data in cached pages); dynamic routes handling personal data are pinned
to an EU region where the host allows". Under ADR-0018:

- Compute runs **only** in `europe-west4` (Amsterdam). This is stronger than the Vercel arrangement
  it replaces, where only function region was pinned.
- The database (Neon, Frankfurt — ADR-0015) and object storage (R2, EU jurisdiction) are unchanged.
- **Railway Corp. is a US company** and its log storage/console is US-operated, so request metadata
  may be processed in the US under the Railway DPA (SCCs and/or DPF). That is the same class of
  transfer the Vercel row already recorded; it is not a new category of risk, and it is recorded
  rather than glossed. The EU log-drain remains the Phase 1 mitigation (`plan/08` §7), now tracked
  against Railway's log retention.
- **Cloudflare** caches only public HTML and assets. The Data Localization Suite (EU-only keys and
  regional services) is Enterprise-only and is *not* purchased; the accepted position is that no
  personal data is cached, because no cached response may carry a cookie or vary by request
  (§5.4, §6) and no PII ever appears in a URL.

**DPAs.** Both must be accepted and filed in `docs/compliance/` **before the production cutover**,
not after: `docs/compliance/dpa-railway.md` and `docs/compliance/dpa-cloudflare.md` (the Cloudflare
DPA also covers the R2 usage of ADR-0015, and the founder already owes that filing per the
TASKS.md 2026-09-15 entry). Filing them is an AC (AC-33), because "new processor → DPA recorded" is
a `plan/07` §10 reviewer-checklist item and a processor acquired by clicking "Deploy" is exactly the
failure mode that rule exists for.

**Logs and PII.** Unchanged and re-asserted: no PII in logs, URLs or analytics (`CLAUDE.md`); the
`src/lib/logger.ts` redaction list applies to the new adapter's log lines; the Cloudflare API token
and the basic-auth credential are secrets that must never reach a log, a step summary or a
screenshot (the CI steps that use them pass them as headers, as the Vercel bypass secret already
was).

**Accessibility.** One surface: the non-production basic-auth prompt is the browser's own dialog,
which is natively accessible; no custom login page is introduced, and production has no auth wall at
all.

**Security.** Full (strict) TLS, minimum TLS 1.2, HSTS on production only, a rate limit on `/api/*`
and POSTs in front of the app-level limits `plan/01` §9 requires, a scoped zone-only API token with
no account permissions, and non-root container execution.

  on `/api/health` and one locale home; alert to the founder's email and WhatsApp webhook
  (`plan/08` §7).
- **Logs.** Railway's built-in structured log stream; the existing JSON logger and its PII redaction
  are unchanged, and `request_id` still comes from `src/proxy.ts`. Retention is Railway's (US) until
  the Phase 1 EU drain — recorded in §8, not assumed away.
- **Errors.** Sentry unchanged, with `environment` = `APP_ENV` and release = Railway commit SHA
  (AC-32).
- **Cache health.** The purge adapter emits one log line per `invalidate` call with the tag names,
  the URL count and the number of API calls; a failed purge is an `error` with the same shape. The
  weekly synthetic TTFB curl set of `plan/08` §7 gains a `cf-cache-status` column, which turns "is
  the CDN actually caching?" into a number rather than an impression.
- **Drift.** `cloudflare:check` nightly (AC-29) is the alarm for somebody changing the zone in the
  dashboard; `railway:check` covers the variable key set.
- **Cost.** Railway usage alert at $50/month and a Cloudflare plan check in the same nightly job;
  `plan/08` §3.6's egress surprise is the thing being watched.

## 12. Rollout

**Order.** Every step is reversible, and the sequence is chosen so that the irreversible-looking one
(DNS) happens last and behind a proxy that can be switched back.

1. **`APP_ENV` lands first.** The abstraction, the grep gate, the `.env.example` keys and the CI
   `env-build-failure` change merge while the site still runs on Vercel, with `APP_ENV` set in the
   Vercel env store to match `VERCEL_ENV`. Nothing about hosting changes; the diff is provably
   behaviour-preserving (T-01…T-07 pin the old strings).
2. **Railway `staging`.** Dockerfile, `config/railway.json`, the `web` service, the variable set,
   the basic-auth gate. Verified by the full Playwright + LHCI suite against the staging URL,
   origin-direct (no Cloudflare yet).
3. **PR environments.** The `preview` job rewrite; the first PR that gets a Railway preview also
   drops the Vercel wait.
4. **Cloudflare settings and rules**, applied by the script against the zone while it still points
   at nothing: settings, do-not-enable list, cache rules, rate limit, `staging.` record.
5. **`worker` service** provisioned (still 0 replicas) so spec 002 TASK-024 has a seat.
6. **Production domain.** The apex/`www` records are pointed at the Railway production service and
   proxied. This is the cutover; the site is still `noindex` (ADR-0007), so the blast radius is the
   founder and the florist demos, not the index.
7. **Vercel unlinked** once §12's exit signal holds (§13 Q5 sets the timing).

**What is never done.** A production deploy on Railway before step 1 (ADR-0018 states it as a rule,
and AC-4's fail-closed behaviour is the backstop). Enabling any row of the do-not-enable table. A
second `web` replica without a shared cache handler. And — the one most likely to be attempted by
accident — **lifting `noindex`**: the indexing flip is spec 007 §12 / TASK-096, gated on the custom
domain, `NEXT_PUBLIC_SITE_URL`, a `/seo-audit` pass and the founder. It is not part of this spec, it
is not part of the cutover, and it must not be bundled into step 6 because they touch the same DNS
record on the same day.

**Feature flags.** None: environment configuration is the flag. The two runtime switches introduced
(`CLOUDFLARE_API_TOKEN` present ⇒ real purge adapter; `STAGING_BASIC_AUTH` present ⇒ auth gate) are
both absent-means-off.

**Rollback.** Per step: (1) revert the PR — `VERCEL_ENV` is still read as a fallback, so the old
behaviour returns exactly; (2)–(5) delete the Railway service/environment, no user impact; (6)
repoint the apex/`www` records back at Vercel (TTL is Cloudflare-proxied, so propagation is seconds,
not hours) — this is the reason the Vercel project stays linked until the exit signal; a bad deploy
inside Railway is a redeploy of the previous image (AC-13).

**Exit signal.** All of: staging and a PR environment green on the full suite through Cloudflare;
`cloudflare:check` and `railway:check` clean on three consecutive nightly runs; TTFB on HIT under
150 ms from four of the five `plan/01` §7 PoPs; both DPAs filed and RoPA row 2 updated; and one
successful rollback rehearsal (AC-13) recorded in `TASKS.md`. Only then is Vercel unlinked.

## 13. Open questions

Six, each with a default the implementation follows if the founder says nothing.

- **Q1 — Dockerfile or Nixpacks?** Default: **Dockerfile** (§5.3). It pins Node 24 and pnpm in the
  repository, builds identically on a laptop and on Railway, and makes `sharp`'s native dependency a
  reviewed line rather than an inference. Cost: ~40 lines to maintain and slightly slower cold
  builds. Choose Nixpacks instead if you would rather have zero build config and accept that the
  Node version lives in a dashboard.
- **Q2 — Who owns the Railway project, and who pays?** The project currently sits in the **Grovant**
  workspace (the Grovant account) and the Cloudflare zone in the **founder's** account. Default:
  **transfer the Railway project to a founder-owned workspace with Grovant added as a member, before
  the first production deploy**, so the production host, the domain and the billing all sit with the
  entity that owns the business, and a change of contractor is a membership edit rather than a
  migration. Confirm, or state the alternative (Grovant owns it and invoices) so the RoPA controller
  line and the DPA counterparty are correct.
- **Q3 — Cloudflare Free or Pro ($20)?** Default: **Free.** Free gives one rate-limit rule, which
  §5.4 spends on `/api/*` + POSTs, and the WAF managed ruleset is the main thing Pro adds. Revisit
  when there is a checkout to protect (spec 013) or when one rule is demonstrably not enough.
- **Q4 — When does the shared ISR cache handler arrive?** Default: **when the single replica is
  actually the constraint** — the trigger is p95 origin CPU above 70% for a day, or a peak-day plan
  (`plan/08` §3.6's Valentine's line). Until then one replica is correct and cheaper. It is a
  separate spec, because it re-introduces Redis or an R2-backed handler.
- **Q5 — When is Vercel unlinked?** Default: **at §12's exit signal**, and no earlier — the linked
  project is the only fast rollback for step 6. Unlinking then deletes `VERCEL_ENV`,
  `NEXT_PUBLIC_VERCEL_ENV`, `VERCEL_GIT_COMMIT_SHA` and the `vercel.live` CSP branch in one PR.
- **Q6 — Basic-auth middleware or Cloudflare Access for non-production?** Default: **basic-auth in
  `src/proxy.ts`** (§5.4): free, testable, and it protects a Railway URL even before Cloudflare is in
  front of it. Cloudflare Access is nicer for humans (Google login, no shared password) and is a
  one-setting change later if the florist demos make a shared password awkward.

**Resolution (2026-09-16, founder):** ADR-0018 accepted and all six defaults accepted without amendment. Q1 Dockerfile; Q2 **reversed by the founder later the same day: the Railway project stays in Grovant's workspace** (the Grovant account), Grovant holds the account and invoices, the founder is added as a member; the RoPA controller line names Flowers Overseas as controller and records Grovant's account as the contractual holder of the Railway relationship, and the DPA counterparty question goes on the lawyer list; Q3 Cloudflare Free; Q4 the shared ISR cache handler arrives only when p95 origin CPU exceeds 70 % for a day or a peak-day plan needs a second replica — a separate spec; Q5 Vercel is unlinked at §12's exit signal and no earlier; Q6 basic-auth in `src/proxy.ts` for non-production, Cloudflare Access revisited if shared passwords prove awkward for florist demos. **A1 — the image builds without credentials; the env gate is split in two (§5.3 "the container", AC-8; TASK-135, 2026-09-18).**
Original: AC-8 — "`pnpm build` produces a standalone server, and `docker build` from the committed

Trigger: the **Railway staging build log of 2026-09-18**, the first real build of that image.
`RUN pnpm build` failed with `EnvValidationError: Invalid environment (staging). 10 problem(s)`,
naming `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `INTERNAL_CRON_SECRET` and the seven `R2_*` keys:

Corrected (orchestrator ruling, 2026-09-18, binding):
- **AC-8 gains a clause**: the image builds **with no credential in the build environment**. No

  and `tests/unit/container.test.ts` asserts the `ARG` set *equals* the build half of the env

- Still owed by this amendment: the Railway redeploy reaching `● Active` with `/api/health` 200 and
