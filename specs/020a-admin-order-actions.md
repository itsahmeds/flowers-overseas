## 1. Problem

Spec 012 v0 gives the founder a read-only order queue and detail page (TASK-222). It deliberately ships no action control and leaves "refunds, partial refunds, cancellations, re-route, resend notifications" to spec 020 (012 §3). Specs 013 and 016 have since built the commands underneath: `cancelOrder`, `refund` and the two server actions `adminRefund` and `adminCancel` (013 §5.2, TASK-261, "spec 020 draws the page"), and `manualReroute` (016 §5.2, TASK-329, "called by spec 020's action panel"). Nothing on a screen calls any of them.

That leaves two gaps on the launch path. First, an order no florist takes sits in `no_partner_available`, the founder gets the A1 alert with a link to `/admin/orders/{id}`, and there is no button to offer it to the florist they just phoned; at the end of the grace window spec 016 cancels and refunds it, so a sale the founder could have saved is lost. Second, a buyer who phones to cancel, a missing add-on, a late delivery or a duplicate charge can only be fixed with a database edit or the Stripe dashboard, which `plan/09` Phase 1 acceptance 1 ("zero manual DB edits") and ADR-0009 forbid and which bypasses the refund invariants of spec 013. `plan/06` §6 puts "manual re-route, cancel, refund full/partial with reason, resend notifications" in Phase 1. This spec is that slice of roadmap item `020`: the buttons, who may press them, what each press records, and the screens. It adds no order logic: every effect is a call to a command specs 013 and 016 already define.

## 2. Scope

Each bullet is testable; §9 names the AC.

**2.1 One action panel on `/admin/orders/[id]`**
- An action panel on spec 012's order detail, server-rendered, showing exactly the controls the availability table (§5.3) allows for the order's status, mode and the viewer's permissions. A control that cannot act is absent, with its reason as text (spec 004 §14 A20, spec 012 §5.3).
- Four permissions added to `ADMIN_PERMISSIONS`: `orders.reroute`, `orders.cancel`, `orders.refund`, `orders.resend` (§5.2). They replace the single `orders.transition` that spec 012 §5.2 anticipated; no generic transition panel ships.
- Every action form carries an `actionId` (minted on the server when the panel renders) and the order's last event sequence number (`expectedSeq`). A second submission of one `actionId` has no second effect; a submission against an order that has moved since the page rendered is refused and changes nothing.
- Every action that takes effect writes one `admin_order_action` row and, through spec 012's audit trigger, one `audit_log` row, in the transaction of the action's first durable write. A refused action writes neither.

**2.2 Reroute** (status `no_partner_available` only)
- A dialog listing the florists `rerouteCandidates(orderId)` returns: spec 016's `eligibleCandidates` with "already offered" relaxed, ranked by `rankCandidates`, each marked when it declined or timed out on this order before.
- Confirming calls spec 016's `manualReroute(orderId, partnerId, admin:{userId})`. The panel shows the time the order is cancelled if nobody acts (`graceEnd`), in the destination's zone and the viewer's zone.

**2.3 Cancel** (set P only: the five states of E, plus `accepted` and `paid`)
- A dialog with a reason picker and an optional note, calling spec 013's `adminCancel`, which calls `cancelOrder` with actor `admin:{userId}`. From E the reasons are `buyer_cancel`, `no_partner` and `other`; from `accepted` and `paid` only `buyer_cancel` (spec 013 §5.2's rule). The refund that follows is spec 013's automatic full refund; the dialog has no amount field.

**2.4 Refund in full and refund in part**
- **Full**: in set F, a refund of exactly the remaining balance (captured minus succeeded, pending and requested refunds), with a reason. On a `cancelled` or `cancelled_refunded` order whose automatic refund failed, the same control retries the remaining balance with the cancellation's own reason. On an `abandoned` or `payment_failed` order with a captured payment (spec 013's reconcile anomaly), a full refund with reason `other`.
- **Partial**: in set F, an amount typed in the order's currency, parsed into integer minor units without floating point, strictly below the remaining balance, with a reason and optional note. Suggested amounts per `plan/06` §2.2 prefill the field and never submit themselves (§13 Q3).
- Both call spec 013's `adminRefund`, which calls `refund`. Spec 013's invariants hold unchanged: the currency equals the payment's, the amount is a positive integer, the cumulative total never exceeds the captured amount, refunds go to the original method only.
- The detail lists every refund row (status, amount, reason, who asked, when it succeeded) and the remaining balance.

**2.5 Resend an email**
- A list of the order's `notification_delivery` rows (template, audience, status, time; never an address), each with a "Resend" control when the resend table (§5.2) allows it. Resending creates a new delivery row and sends the same template through spec 016's pipeline, rendered at send time in the audience's locale to the address resolved at send time.
- At most 3 resends per order, template and recipient in 24 hours (§13 Q4).

**2.6 What the buyer sees**
- No new buyer-facing page, template, subject or message key. A buyer hears of an admin action only through spec 016's existing messages, chosen by spec 016's `notificationsFor` from the event the action causes (B5 on a cancellation, B6 on a refund, none on a reroute), and spec 018's tracking page. The admin's reason code and note never reach a buyer surface.
- One wording correction, as requests on specs 013, 016 and 018 (§12, §13 Q1): an order an admin cancels with reason `buyer_cancel` (the buyer asked us) reads "You cancelled this order", not "We could not deliver this order".

**2.7 Records**
- `docs/runbooks/admin.md` gains "Reroute an order", "Cancel an order", "Refund an order", "Resend an email"; `docs/compliance/ropa.md` gains the `admin_order_action` record; `docs/codebase-map.md` regenerated.

## 3. Non-goals

- **Any new order logic.** Rows, actors, refund invariants, the cancel handler, the reroute command, the notification pipeline and every buyer template stay with specs 002 A6, 010, 013 and 016. This spec calls them; where it needs a seam (an optional transaction handle, an `actionId`), §12 lists it as an additive request.
- **A generic transition panel** (accept or decline on a florist's behalf, rows 7 and 8; out for delivery, delivered and photo upload on a florist's behalf, rows 19, 20, 25; disputes and resolutions, rows 27 to 29) → a later slice, spec **020b**, after launch (§13 Q7).
- **Reoffering a `routed` order** to a chosen florist before its offer window ends: A6 has no row from `routed` to `manual_reroute`. It needs an A6 amendment and is not proposed here.
- **Editing recipient or delivery details** (`plan/06` §6 "edit recipient details before acceptance") → spec **020b**. Spec 013 §14 rules no buyer edits after placement; until 020b, a needed change is a cancel and a new order, arranged by phone.
- **Failed delivery, redelivery and `order.cancelled_refunded`** (rows 21, 22, 24) → spec **027a** with the florist's delivery-failed report. Until then the money remedy for a failed delivery is a refund from F, which this spec ships.
- **Order exports, the refund page as a separate list, finance reports** → spec **030a** and `plan/11` §7.
- **Fraud holds and the review queue** → spec **021**. **Payout lines and settling `payout_adjustment`** → spec **030a**.
- **Typing a message to the buyer.** Admin cannot compose buyer copy; a personal reply goes from the founder's own mailbox or WhatsApp, outside the system.
- **Changing an email address before a resend.** A resend goes to the address on the order; correcting it is part of 020b's edit.

## 4. User stories

- As the **founder at 21:40**, I get the no-partner alert, phone a Warsaw florist who agrees, open the order from the alert, pick that florist from the list and press "Offer". The florist receives the offer email in Polish, and the buyer is told nothing because nothing went wrong for them.
- As the **founder on the phone with a buyer** who wants to cancel before we start making the bouquet, I cancel with "the buyer asked", and the buyer receives "You cancelled this order. We have refunded {amount}."
- As the **founder** after a florist reports a missing vase, I refund the vase's price with reason "add-on missing"; the order stays where it is, the buyer receives the refund email and a credit note, and the next refund I try cannot take the total above what was charged.
- As the **founder**, when a buyer says the confirmation never arrived, I resend it, with the terms attached, to the address on the order.
- As the **founder**, I can see who did what to an order and when, and a double tap on a slow phone never refunds twice.
- As an **ops helper** (later), I can reroute and resend but cannot move money.

### 5.2 API / server actions / jobs / events (zod schemas named)

**Where things live** (`plan/01` §5: `app/` is thin; modules expose commands; admin composes them with the guard and the audit context):

| Where | What 020a adds |
|---|---|
| `src/modules/admin/order-actions/` | `ORDER_ACTION_AVAILABILITY` (the table below, as data), `availableActions(order, viewer) → AvailableActions`, `runOrderAction(kind, input, effect)` (the shared wrapper: permission, `withAdminContext`, order row lock, `expectedSeq` check, `admin_order_action` insert with `ON CONFLICT (id) DO NOTHING`, then the effect in the same transaction), `parseMinorUnits(text, currency)`, `suggestedRefunds(order)`, `orderActionHistory(orderId)` |
| `src/modules/payments` (spec 013) | **no new export.** `adminRefund` and `adminCancel` gain the base fields below and run through `runOrderAction` (request on TASK-261, §12) |
| `src/modules/orders/routing` (spec 016) | `rerouteCandidates(orderId) → RerouteCandidate[]` (read only: loads partners, applies `eligibleCandidates` with "already offered" relaxed, `rankCandidates`, and marks earlier declines and timeouts) and `adminReroute`, the server action wrapping `manualReroute` |
| `src/modules/notifications` (spec 016) | `RESEND_RULES` (the resend table, as data), `resendableDeliveries(orderId)`, `resendNotification(deliveryId, actor, actionId)`, the `notifications.resend` job, and `adminResendNotification`, the server action |
| `src/app/admin/orders/[id]/` | the panel and dialogs; forms post to the four server actions above; nothing else |
| `messages/admin/en.json` | namespace `admin.orderActions` |

**Shared input** `AdminOrderActionBaseSchema = z.object({ orderId: z.string().uuid(), actionId: z.string().uuid(), expectedSeq: z.number().int().positive() }).strict()`. Each action extends it:
- `AdminRerouteSchema`: `partnerId: uuid`.
- `AdminCancelSchema`: `reason: AdminCancelReasonSchema` (`'buyer_cancel' | 'no_partner' | 'other'`), `note: AdminNoteSchema.optional()`; `note` required when `reason = 'other'`.
- `AdminRefundSchema`: a discriminated union on `kind`: `{ kind: 'full', reason: AdminRefundReasonSchema, note? }` or `{ kind: 'partial', amountText: z.string().max(16), reason: AdminRefundReasonSchema, note? }`. `AdminRefundReasonSchema` is exactly `'addon_missing' | 'late_delivery' | 'substitution_complaint' | 'quality' | 'goodwill' | 'duplicate' | 'other'`; the system reasons (`buyer_cancel`, `no_partner`, `authorisation_lapsing`, `redelivery_failed`) cannot be chosen. For the cancelled-order retry and the anomaly refund, the server fixes the reason (the cancellation's, or `other`) and ignores the field.
- `AdminResendSchema`: `deliveryId: uuid`.
- `AdminNoteSchema = z.string().trim().min(1).max(280)`. The note is internal and lands only in `audit_log.reason`.

**Result** `AdminOrderActionResult = { ok: true, kind, resultRef, replayed: boolean } | { ok: false, code }`, with `code` one of `FORBIDDEN`, `ORDER_CHANGED`, `DEMO_ORDER`, `ORDER_TRANSITION_ILLEGAL`, `PARTNER_NOT_ELIGIBLE`, `CANCEL_REASON_NOT_ALLOWED`, `AMOUNT_INVALID`, `REFUND_EXCEEDS_CAPTURED`, `CURRENCY_MISMATCH`, `NOT_REFUNDABLE`, `RESEND_NOT_ALLOWED`, `RESEND_RATE_LIMITED`. Engine and command errors pass through under their own names; each code has an admin message key.

**`runOrderAction`, in order** (one transaction unless stated):
1. `requirePermission(permission of kind)`: its first statement, as for every admin action (spec 012).
2. Parse with the schema. `withAdminContext({ userId, requestId, action: 'order.action.{kind}', reason: note })`.
3. Lock the order row `FOR UPDATE`. If `admin_order_action` already has `actionId`: return its stored outcome with `replayed: true` and do nothing else. A concurrent duplicate waits on the lock and then finds the row.
4. `order.mode = 'demo'` → `DEMO_ORDER`. The order's highest `order_event.seq` ≠ `expectedSeq` → `ORDER_CHANGED`.
5. Run the effect (`manualReroute`, `cancelOrder` through `adminCancel`, `refund` through `adminRefund`, `resendNotification`) with this transaction's handle (request on specs 013 and 016, §12). A refusal rolls the whole transaction back, so no action row and no audit row exist for it.
6. Insert `admin_order_action` with the effect's `result_ref`; the trigger writes the `audit_log` row with `after` = `{ kind, reason, amount_minor, currency_code, partner_id, template_key }` (no personal data), the actor, `request_id` and the note as `reason`.
7. Commit. Then, outside the transaction and only for refunds, spec 013's provider call runs exactly as 013 §5.2 says (its idempotency key is the refund row's id; a crash here is recovered by `payments.sweep` (d)).

**Money input.** `parseMinorUnits(text, currency)` reads `currency.minor_unit_exponent` (spec 002) and accepts only `^\d{1,9}([.,]\d{1,E})?$`, where E is the exponent: "12", "12.5", "12,50" are 1200, 1250, 1250 for an exponent of 2; "12.505", "1e3", "-5", "0", "0.00", " ", "12.50 zł" are `AMOUNT_INVALID`. It works on the digit strings (integer part times 10^E plus the padded fraction) and never calls `parseFloat`, `Number()` on a decimal string, or `Math.round` (`fo/no-float-money` covers the module). The amount is then checked to be `≥ 1` and `< remaining` for a partial refund.

**Suggested partial amounts** (`suggestedRefunds(order)`, `plan/06` §2.2; defaults in §13 Q3): `addon_missing` offers one suggestion per add-on line (`qty × unit_retail_minor`); `substitution_complaint` is 30 % of the product lines' total; `late_delivery` is 20 % of the order total. Percentages are integer arithmetic on minor units, rounded half to even. A suggestion at or above the remaining balance is not shown. Choosing a suggestion fills the field and the reason; it never submits.

**Availability** (`ORDER_ACTION_AVAILABILITY`; "remaining" is captured minus succeeded, pending and requested refunds):

| Status (A6) | Reroute | Cancel (reasons) | Refund in full | Refund in part | Resend |
|---|---|---|---|---|---|
| `placed` | no | no | no | no | per resend table |
| `payment_failed`, `abandoned` | no | no | only with a captured payment and remaining > 0 (reason `other`) | no | per table |
| `authorised`, `paid_unrouted`, `routed`, `manual_reroute` | no | yes (`buyer_cancel`, `no_partner`, `other`) | no | no | per table |
| `no_partner_available` | **yes** | yes (`buyer_cancel`, `no_partner`, `other`) | no | no | per table |
| `accepted` | no | yes (`buyer_cancel` only) | no | no | per table |
| `paid` | no | yes (`buyer_cancel` only) | yes, remaining > 0 | yes, remaining ≥ 2 minor units | per table |
| `in_production`, `awaiting_buyer`, `out_for_delivery`, `delivery_failed`, `redelivery_scheduled`, `delivered`, `photo_uploaded`, `disputed`, `resolved` | no | no | yes, remaining > 0 | yes, remaining ≥ 2 minor units | per table |
| `cancelled`, `cancelled_refunded` | no | no | only when remaining > 0 and no refund is `requested` or `pending` (the cancellation's reason) | no | per table |
| `refunded_full`, `closed`, `chargeback_open`, `chargeback_won`, `chargeback_lost` | no | no | no | no | per table |

Mode: `demo` orders show no control ("Demo order: no actions"). `test` orders show every control the table allows, except buyer resends (spec 016 never sends a buyer message for `test`). Each "no" renders its reason as text, from one key per (control, cause).

**Reroute.** `rerouteCandidates` returns `{ partnerId, displayName, city, rankPosition, payoutMinor, payoutCurrency, previously: 'declined' | 'timed_out' | null }` for every partner `eligibleCandidates` admits with "already offered" relaxed; partners failing coverage, catalogue, blackout, capacity, status-for-mode or sign-in reachability are not listed. `adminReroute` calls `manualReroute(orderId, partnerId, admin:{userId})`, which writes `order.manual_reroute`, `order.routed` and `assignment.offered` (016 §5.2) and through the outbox sends V1 to the florist. `result_ref` is the `order.manual_reroute` event id. If the partner is no longer eligible at submit time, `manualReroute` refuses and nothing is written (`PARTNER_NOT_ELIGIBLE`).

**Cancel.** `adminCancel` calls `cancelOrder(orderId, admin:{userId}, reason)` (013 §5.2). Everything after is spec 013's and 016's: the `payments` target refunds the remaining balance in full; the `routing` target withdraws any open or accepted assignment and sends V4; from `accepted` or `paid` spec 016 writes one `payout_adjustment`; the `notifications` target sends B5. The confirmation dialog says, in admin words, which of these will happen for this order before the admin confirms.

**Refund.** `adminRefund` computes the amount on the server: for `full`, the remaining balance read under the order lock; for `partial`, `parseMinorUnits`. It then calls `refund({ orderId, amount, reason, actor: admin:{userId} })` (013 §5.2), whose typed refusals are returned as codes. Spec 013 then writes `order.refund_requested`, calls the provider, and on success writes row 30, 31 or 32; spec 016 sends B6 (and spec 018 issues the credit note that B8 delivers).

**Resend** (`RESEND_RULES`, data; a delivery row is resendable only when its template is listed and its condition holds now):

| Template (spec 016) | Audience | Resendable while |
|---|---|---|
| B1 `order-received` | buyer, `live` | always, once sent (the durable-medium confirmation, `plan/07` §2.1; the terms PDF of `order.terms_version`, and the issued invoice when one exists) |
| B2 `being-made` | buyer, `live` | the order's buyer projection is `being_made` |
| B3 `out-for-delivery` | buyer, `live` | the projection is `on_its_way` |
| B4 `delivered-photo`, B6 `refund`, B8 `credit-note` | buyer, `live` | always, once sent |
| B5 `cancelled` | buyer, `live` | the order is `cancelled` or `cancelled_refunded` |
| V1 `offer` | that florist member | the assignment is unanswered, not withdrawn, and its `sla_expires_at` is in the future |
| V3 `order-confirmed` | that florist member | the assignment is accepted, not withdrawn, and the order is not yet `delivered` |
| V4 `offer-withdrawn` | that florist member | the assignment is withdrawn or timed out and the delivery date has not passed in the destination's zone |
| V2, V5, A1, W | | never (reminders and the founder's own copies) |

`resendNotification` inserts a `notification_delivery` row with `source_key = admin:{actionId}`, the original's `template_key` and `recipient_ref`, `resend_of` = the original's id, status `queued`, and enqueues `notifications.resend` (`singletonKey` = the new row's id). The job renders and sends through spec 016's one path (send-time address and locale, a freshly minted one-tap link for florist templates, `Mailer.send` with `idempotencyKey = admin:{actionId}:{template_key}:{recipient_ref}`, the 409 rule, the `notifications.email` hold). The rate limit counts `admin_order_action` rows of kind `resend` for the same order, template and recipient in the last 24 hours, under the order lock.

**Events.** This spec registers no event type and writes no `order_event` row itself. Every event is written by `manualReroute`, `cancelOrder` or `refund`, through `orderService.transition` or `appendEvent`.

### 5.4 Rendering & caching (per plan/01 §3)

- Admin stays SSR `no-store`, auth-gated, `noindex`, bypassed by Cloudflare (spec 012 §5.4, spec 040). After an action the server action returns its result and the page re-renders from the database; there is no client cache to invalidate.

## 8. Compliance considerations (mandatory)

- **Data flows (RoPA)**: one new record, `admin_order_action`: actor user id, order id, action kind, reason code, amount, partner id, template key. Purpose: accountability for actions on customer orders and money (Art. 5(2)); basis Art. 6(1)(f); retention 3 years, like `audit_log`. The admin's note is free text in `audit_log.reason`: the field says "Internal note. Do not type names, addresses or phone numbers", and it is never sent to a buyer, florist, log line or analytics. No new processor: resends use the existing Resend use for transactional mail (spec 016's RoPA rows), for the same purpose, to the same address.
- **Consumer law (`plan/07` §2.1, §2.3)**: cancellation before production is free with a full refund (set P), and the cancel control offers no partial amount, so the promise in the terms cannot be undercut by a click. A resend of B1 re-delivers the contract confirmation on a durable medium with the same terms version. Refunds go to the original method only (`plan/07` §9 AML); no field takes a destination. Late-delivery and quality refunds are a remedy the buyer is told about through spec 016's B6, and spec 018's credit note follows each one.
- **Price display (`plan/07` §4)**: no consumer price is edited. A refund never exceeds what was charged, by spec 013's invariant checked under the order lock.
- **No negative framing after purchase (founder 2026-10-14)**: no admin action adds buyer wording. A reroute sends the buyer nothing. The only buyer messages an action causes are spec 016's existing B5 (on a cancellation, the order no longer happens) and B6 (on a refund), unchanged; the paid confirmation, the tracking steps and B1 to B4 carry no refund or failure sentence because of anything here. Reason codes and notes are never rendered to a buyer.
- **No relay language to buyers (founder 2026-10-14)**: buyers never see "partner", "florist accepted", "offer", "reroute" or "no florist available"; the admin copy that uses them is admin-only and exempt. The §13 Q1 correction makes the buyer's wording more accurate ("You cancelled") without adding any relay word.
- **Geo-blocking (EU 2018/302)**: no action varies by the buyer's location; nothing reads an IP (ADR-0006).
- **Accessibility (WCAG 2.2 AA, `plan/07` §8)**: dialogs are native `<dialog>` with a label, focus moved in and returned on close, Escape closes without acting; every field has a programmatic label and its error is associated with `aria-describedby`; results are announced in a polite live region; targets at least 24 × 24 CSS px; the sticky mobile bar never hides the focused element (2.4.11); no time limit.
- **Security**: permission check first in every action; server-action origin checks (Next); idempotent by `actionId`; stale-view protection by `expectedSeq`; least privilege (money actions are admin only, §13 Q2); no order id beyond the path segment spec 012 already uses; `public_token` never appears.
- **Logs and PII**: log lines carry order id, action id, kind, code and request id only. No buyer or recipient name, email, phone, street, card message, `public_token`, sign-in link or note text in any log line, Sentry event or job payload.

## 13. Open questions

Each has a recommended default; the founder may answer "all defaults".

- **Q1. When you cancel an order because the buyer asked you to, what does the buyer read?** Today specs 013, 016 and 018 choose the wording by who pressed the button, so your cancel always reads "We could not deliver this order", even when the buyer phoned to cancel. **Recommended: "You cancelled this order" when you pick "the buyer asked" (`buyer_cancel`), "We could not deliver this order" for the other reasons.** It needs the small wording change of §12 request 3 in those three specs.
- **Q2. Who may move money?** **Recommended: refunds and cancellations for the admin role only** (what spec 013 already says); rerouting and resending also for `ops`, so a helper can save an order without being able to refund it. `finance` gets no action.
- **Q3. Suggested partial refund amounts.** `plan/06` §2.2 says "add-on missing = add-on price; late delivery = delivery fee + 20 %; substitution complaint = 30 %", but our prices include delivery, so there is no delivery fee line to read. **Recommended: add-on missing = that add-on's price; substitution complaint = 30 % of the bouquet lines; late delivery = 20 % of the order total; rounded half to even; shown as a prefill only.**
- **Q4. How often may one email be resent?** **Recommended: 3 times per email per person per order in 24 hours**, enough for "it went to spam", not enough to flood anyone.
- **Q5. A free-text note on actions?** **Recommended: yes, optional, 280 characters, required only for the reason "other", seen only in admin and the audit log, with a warning not to type names or addresses; kept 3 years.**
- **Q6. How much confirmation before money moves?** **Recommended: one confirmation dialog that states the amount and what the buyer will receive; no typing of the order number.** Idempotency and the stale-page check already stop double refunds.
- **Q7. Accepting for a florist who phones, uploading the photo they send, and changing an address: now or later?** **Recommended: later, in spec 020b after launch.** Florists accept in their own inbox (spec 026a), which keeps the acceptance record theirs; until 020b an address change is a cancel and a new order.
- **Q8. Should a small goodwill refund email the buyer?** **Recommended: yes, spec 016's B6 "Refunded {amount} on {date}" as it is, with spec 018's credit note.** A refund the buyer is not told about looks like an unknown card entry and invites a chargeback.
