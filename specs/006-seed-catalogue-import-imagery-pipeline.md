## 1. Problem

`plan/10` is a decision document, not data. It fixes a six-facet taxonomy, an 84-product seed catalogue with names, price bands per country, add-ons, a demo-partner shape, an occasion calendar and an imagery approach (`plan/10` §1–§3), and it closes with "approve the taxonomy and seed shape so `006 seed catalogue import` can be specified" (`plan/10` §7). Nothing in the repository holds any of it. `plan/09` reserves 22–28 Sep 2026 for "`006` seed catalogue import + imagery pipeline (10)", in the same week as `004` (design system) and `005` (catalogue + pricing), and the week's non-code column is "Approve taxonomy + product names (10); generate imagery".

Two gaps make this urgent rather than tidy.

**The demo has no content and no pictures.** `plan/09`'s Phase 0 exit is "≥3 Warsaw florists verbally committed after seeing the demo" (16 Oct). Spec 004 delivers the approved homepage design with every photograph rendered as a `--color-photo` gradient box captioned "Photography to supply", and no `<img>` anywhere, deliberately, because `plan/10` §3's honesty rule is that the demo shows no image it does not have (spec 004 §2, TASK-045/052/053). Specs 008 and 009 render category grids and a PDP whose LCP element is *by definition* a product image (`plan/01` §6: "product imagery is the conversion lever and the LCP element on PDP and category pages"). Without this spec there is no image, no alt text, no variant, no loader and no product description — and a PDP with no description is not indexable at all (spec 002 §6: "a product with a null `description_md` must be non-indexable").

**Spec 002 is parked, so the seed has nowhere to live.** Spec 002 is `approved` but its provisioning is blocked (TASK-013): there is no Neon project, no Cloudflare account and no R2 bucket, and specs 003 and 004 were both written to be implementable, testable and demoable with no database at all. Spec 002 §2 promises seed *skeletons* (84 products with SKU, facets, tiers and `en` name/slug) and explicitly defers to this spec the seed **content** (descriptions, category and occasion copy, imagery and its prompts) and the whole **R2 implementation** (§3: "002 ships `lib/storage.ts` as an interface with a fake, the key convention, the `media_asset`/`media_variant` tables and the job declaration"). This spec therefore has to do what 003 and 004 did: build everything that does not need a server now, behind the same provider seams, and leave a short, named list of work that unblocks the day the founder provisions Neon and R2.

The consequence for the *shape* of this spec is the single most important design decision in it: the seed stops being "literals inside `seed/index.ts`" and becomes a **versioned, zod-validated, human-reviewable dataset under `seed/data/`** with its own gate (`pnpm seed:check`) and its own diff report — a build artefact that 002's importer consumes, that 005's catalogue module reads in tests, that 008/009 render, and that the founder can edit without touching TypeScript. Spec 002's seed scripts then read the files rather than restating the plan, exactly as spec 003's `toLocaleRow()` stopped the locale set from drifting between config and schema (spec 003 §5.1).

## 2. Scope

Each bullet is testable; §9 names the AC. The scope is split by the provisioning boundary, because that boundary is the whole engineering problem.

### 2.2 The seed dataset (`plan/10` §1, §2; `plan/13` A3/A4 defaults accepted in spec 002 §13 Q8)

- **`seed/data/` layout**, one file per entity family, JSON with a `$schema`-style `version` and `source: "seed"` header on every file:
  `taxonomy.json` (the six facets of `plan/10` §1.1 as canonical keys — product types, occasions, flower types, colours, price tiers, styles, substitution classes), `categories.json` (5 product-type roots + 10 occasion categories + 8 flower-type hubs = 23, `plan/10` §2.1), `occasions.json` + `occasion-country.json` (evergreen + seasonal with the `rule_type`/`rule` shapes of `plan/03` §9 and spec 002 §5.1), `products.json` (84: 40 bouquets, 14 arrangements, 8 plants, 10 funeral, 12 gift sets), `product-tiers.json` (stem/size tiers per `plan/10` §2.2), `addons.json` (6: chocolates, vase, balloon, plush, wine, card), `prices/{ISO2}.json` and `addon-prices/{ISO2}.json` (per-country retail, one file per seeded country), `media.json` (the asset manifest), `media-variants.json` (generated, committed), `alt/{locale}.json`, and `copy/{locale}/{entity}.json` (names, slugs, descriptions, SEO title/description, category and occasion intros).
- **Copy** per `plan/10` §2.2: our own text, no competitor wording; product descriptions 60–90 words in plain language stating contents, size, who it suits and what the florist may substitute, every description ending with the local-florist sentence; naming convention `{Evocative name} — {flower} {form}` with the evocative name unchanged across locales and the descriptor localised (§13 Q2). Category and occasion intros authored per locale. `en` is the source of truth (`plan/03` §6 step 1); `en-gb` ships as a thin override only where British wording differs (spec 003's catalogue precedent); `de` and `pl` copy is **absent or machine-drafted and flagged unreviewed**, never silently indexable (§7).
- **Money** is `retail_minor` (integer) + `currency` on every price row, VAT-and-delivery inclusive by definition (`CLAUDE.md`; `plan/07` §4). Price rows carry `active_from`, optional `active_to`, optional `surcharge_kind` (`sunday` | `peak_day`), and exactly one open-ended row per (product, country, tier, surcharge) — the file-level mirror of spec 002's partial unique index (spec 002 §5.1, AC-9).
- **Zero** rows in the dataset for `review`, `delivery_proof` and public partner profiles (`plan/07` §7; `plan/10` §2.1, §5; `plan/09` Phase 0 AC 6). Demo partners stay spec 002's (§3).
- **`seed/schema/*.ts`**: `SeedProductSchema`, `SeedProductTierSchema`, `SeedCategorySchema`, `SeedOccasionSchema`, `SeedOccasionCountrySchema`, `SeedAddonSchema`, `SeedPriceSchema`, `SeedCopySchema`, `MediaAssetManifestSchema`, `MediaVariantManifestSchema`, `AltManifestSchema`, plus `toProductRow()`, `toCountryPriceRow()`, `toMediaAssetRow()`, `toMediaVariantRow()`, `toProductMediaRow()`, `toProductMediaAltRow()` projections pinned by unit tests to spec 002 §5.1's column lists.

### 2.3 `pnpm seed:check` — the gate that makes the dataset trustworthy

A new script and a new CI job `seed-check` on `needs: typecheck` (spec 001 §14 A9's job-placement rule, as `i18n-check` follows it). One line per problem, naming file, entity key and rule. It fails on:

1. any file that does not parse under its schema, or whose `version` header is missing;
2. **counts and split**: not exactly 84 products in the 40/14/8/10/12 split; not 23 categories; not 6 add-ons (`plan/10` §2.1);
3. **referential integrity**: a product facet value absent from `taxonomy.json`; a `product_category`/`product_occasion` edge to an unknown key; a price row for an unknown product, tier or country; a media asset for an unknown product;
4. **slugs** (`plan/02` §4): non-ASCII, uppercase, non-hyphen, trailing-slash or duplicate within a locale; a slug that is not the ASCII fold of its name (`Kraków Spring` → `krakow-spring`); a slug colliding across `product`/`category`/`occasion` in one locale;
5. **prices**: a value outside the `plan/10` §2.3 band for its tier and currency; a non-integer minor amount; a missing currency; a psychological-ending violation (`.90`/`.99` for EUR/GBP, trailing `9` for PLN); a tier step outside +30%/+60% of the smallest by more than a stated tolerance; more than one open-ended row per (product, country, tier, surcharge);
6. **copy**: an `en` description outside 60–90 words; a description not ending with the local-florist sentence; a superlative from a small banned list (`plan/10` §2.2 "no superlatives that cannot be backed"); a duplicate description shared by two products (thin-content guard, §6); a missing `en` name or slug;
7. **media** (§2.4): an asset without complete provenance; a product with more than one `is_primary`; a referenced variant absent from the manifest or with a mismatching checksum; a rendered asset lacking alt text in a launch locale; an empty (`alt: ""`) alt on a product image;
8. **no PII and no third-party marks**: any `@`-shaped string, E.164-shaped string, postcode-shaped string, real-person-name allowlist violation or competitor brand name (list from `docs/research/competitors-*.md`) anywhere in the dataset (§8);
9. **budgets**: total committed bytes under `public/media/` above the cap; any single variant above its per-slot cap (§2.5).

### 2.4 Imagery: intake, provenance and variants (ADR-0014, ADR-0015, `plan/10` §3)

- **`content/imagery/style-guide.md`** — the file `plan/10` §3 names, written here: the locked style guide verbatim (neutral warm-grey seamless background, soft north light from the left, 4:5 with 8% margin, kraft or white wrap, **no hands, no faces, no text**, one hero + one detail + one in-home context shot per product, colour-accurate to the colour facet, plausible stem count for the tier, funeral pieces on neutral stone, plants in plain terracotta or white), the prompt template with per-product substitutions, and the human review checklist (impossible stems, melted petals, wrong flower, implausible count, visible text, any person or premises).
- **`content/imagery/prompts/{sku}.json`** — prompt text, generator, model, seed and parameters per asset, so an image can be regenerated consistently (`plan/10` §3). `prompt_hash` in the media manifest is the SHA-256 of the canonicalised prompt record; the prompt text itself is content, not code.
- **Intake is out-of-tree.** Originals (≥2000 px, `plan/01` §6) live in a git-ignored `.local/imagery/originals/` for the generation/review loop and in the founder's own store of record; **no original is ever committed** (repo weight, and they move to R2 under `originals/` in §2.6). §13 Q6 confirms the store.
- **`pnpm media:variants`** — a deterministic local CLI (`sharp`, pinned version and pinned encoder options) that, for each asset in `seed/data/media.json` whose original is present: strips all metadata except colour profile (EXIF/GPS removal is unconditional, `plan/01` §6), crops/resizes to the slot's declared aspect ratio, encodes AVIF + WebP at the width ladder of §13 Q5, writes `public/media/{assetId}/{width}.{fmt}`, and rewrites `seed/data/media-variants.json` with width, height, bytes and SHA-256 per variant. Re-running with the same inputs produces byte-identical outputs and no manifest diff (AC-13). Generation is **never** run in CI (no originals there); CI verifies manifest↔file↔checksum consistency for what is committed (AC-14).
- **Provenance is data, on every asset**: `source` (`ai` | `photo` | `partner`), `generator`, `generator_model`, `prompt_hash`, `generator_seed`, `captured_at`, `credit`, `licence`, `depicts` (`product` | `brand` | `context` | `delivery`), `review_state` (`pending` | `approved` | `rejected`), `reviewed_by`, `reviewed_at`. `seed:check` refuses `review_state: "approved"` without a reviewer and date, and refuses a `depicts: "delivery"` asset in the Phase-0 dataset entirely (real delivery photos are spec 018/027 and carry consent, `plan/07` §1.2).
- **Which assets exist in Phase 0.** Not 252. The committed set is (a) the homepage photo slots of spec 004's approved design — full-bleed hero, six occasion tiles, four "most sent" cards, the delivery-photo band (the consolidated list is TASK-053's PR body) — and (b) a **demo product set** of 12 products × 2 assets (hero + detail), one per named archetype of `plan/10` §2.2, default per §13 Q3. Every other product renders the `--color-photo` placeholder with its caption and no `<img>` (`plan/10` §3 honesty rule) until R2 exists and the rest are uploaded. The homepage delivery-photo band renders the placeholder in Phase 0 in every case, because we have no delivery photo and may not fake one (`plan/10` §3, §5).

### 2.5 Rendering: loader, `Photo`, LCP, alt text, honesty label

- **`src/modules/ui/media/loader.ts`** gains `staticVariantLoader` alongside spec 004's `placeholderLoader`, both behind the `VariantLoader` interface, selected by `resolveLoader()` inside the module. `staticVariantLoader` reads the committed variant manifest at build time (a plain typed import — no runtime fetch, no database, no `sharp` in the bundle) and returns the `/media/…` URL for a (assetId, width, format) triple.
- **`Photo` / `Media`** (spec 004 §2, `src/modules/ui/media/`) gains an `asset` path: given an asset id and the resolved locale it renders `next/image` with `sizes` from the named slot (hero 100vw, grid 50vw/33vw/25vw, thumb 96 px — `plan/01` §6), a fixed aspect-ratio box, AVIF-first `srcset` with WebP fallback, `loading="lazy"` + `decoding="async"` below the fold, and **`alt` from data, never generated at render** (`plan/01` §6). When the asset is missing, unapproved, or has no alt for the resolved locale, it renders the spec 004 placeholder box and **no `<img>`** — the honest fallback, and the reason a missing translation degrades gracefully instead of shipping an English alt on a Polish page.
- **LCP**: exactly one `priority` candidate per page (`plan/01` §6), and the `<link rel="preload" as="image" imagesrcset imagesizes>` for it is emitted from the *same* manifest lookup that produced the `srcset`, so the two cannot disagree. A page with two `priority` images fails a test (AC-19). Nothing eager above the LCP candidate.
- **Honesty label** (ADR-0014, `plan/10` §3): a `MediaProvenanceNote` component renders the visible label whenever any displayed asset on the page has `source: "ai"` — "Example arrangement · your florist hand-makes each one" as a message key, not a literal. It is rendered adjacent to the gallery, is server-rendered text (crawlable, so the structured data and the visible page agree, `plan/02` §15), and cannot be disabled by a prop. In the password-protected demo environment sample photos carry a "sample" watermark (`plan/10` §3, §5) — the watermark is baked into the variant at generation time for `depicts: "context"` assets used in the demo, not a CSS overlay.
- **Budgets** (`plan/01` §7; spec 004 AC-24): image transfer **≤ 204 800 B per page**, of which the hero LCP candidate ≤ 90 000 B at the mobile width and each grid tile ≤ 18 000 B `[agent-inferred]` split of the page budget across the approved homepage layout; total committed bytes under `public/media/` ≤ 6 MB; `next/image` optimisation is bypassed for already-derived variants (the loader returns the final URL), so `plan/08` §2's per-transformation metering is not exercised in Phase 0.
- **Cache headers**: variant URLs are content-addressed by their width and by an asset-version segment, and served `Cache-Control: public, max-age=31536000, immutable` from `next.config.ts` headers for `/media/*`. A changed image is a new asset version, never a mutated URL.

### 2.6 After 002 unparks (specified here, implemented in the tasks marked "needs 002" in §12)

- `src/lib/storage.ts` real implementation over the S3 API against R2 (`put`, `head`, `getSignedUrl`, `delete`, `objectKey`), replacing the `InMemoryStorage` fake in production paths and keeping the fake for tests (spec 002 §5.2, AC-22).
- `pnpm media:upload` — uploads originals to `originals/{assetId}` and enqueues `media.derive_variants` per asset; idempotent by checksum (an unchanged original is a no-op).

## 3. Non-goals

- **The schema, the tables and the demo skeleton rows** — spec 002 (`country`, `product`, `country_price`, `media_asset`, `media_variant`, `product_media`, `product_media_alt`, demo partners, holidays, `occasion_country`). This spec writes the *dataset* those tables are filled from and requests one amendment (§13 Q10) so 002's task 10 reads `seed/data/` instead of restating `plan/10` in TypeScript.
- **Catalogue query and pricing logic** — tier maths, FX conversion and buffer, psychological rounding at runtime, "from" prices, availability → **spec 005**. This spec ships the price *rows* and the band/ending checks; 005 ships the functions that read them.
- **Any indexable page, canonical, hreflang, JSON-LD or sitemap** → specs 007/008/009. This spec ships the `image[]` inputs (asset order, absolute URL builder, dimensions) that 009's `Product` schema builder consumes.
- **`/sitemaps/images-{n}.xml`** — `plan/02` §10 places image sitemaps in **Phase 4**. Not shipped here. What is shipped is the data that makes one a query later (asset ↔ entity ↔ locale ↔ variant), and the note in `docs/runbooks/imagery.md` that when it arrives it must obey `plan/02` §10's "nothing `noindex` ever appears in a sitemap".
- **Delivery photos and the "Real deliveries" module** — florist upload, EXIF stripping at upload, private buckets, signed URLs, consent for public use → specs 018/027/029 (`plan/07` §1.2). This spec forbids a `depicts: "delivery"` asset in the Phase-0 dataset (§2.4).
- **Corridor guide copy, blog posts, legal text** → spec 007 and the founder's content tasks (`plan/02` §5.2 requires ≥600 country-specific words per guide, human-written per locale; `plan/03` §6 gate 4 forbids machine-only corridor and legal copy even noindexed).
- **Real `de`/`pl` product copy.** Machine drafts are produced and flagged; substantive translation is founder + native-reviewer work (`plan/13` B12), and the locale stays non-indexable until reviewed (§7).
- **A brand/hero photo shoot.** ADR-0014 keeps a small real shoot as an option for brand imagery; commissioning it is a founder action, and the pipeline treats a photographed asset as `source: "photo"` with no code change.
- **Search, faceted colour pages, curated collections** → 008 and Phase 4 (`plan/02` §7).
- **Editing `CLAUDE.md`, `plan/*`, `.claude/**` or an accepted ADR.** Two bounded deviations are stated in §12 rather than silently taken.

## 4. User stories

- As the **founder preparing the 16 Oct florist demo**, the homepage and a dozen product pages show real, consistent, rights-clean imagery and honest copy, and every slot I have not yet shot still says so instead of showing a stock photo of somebody else's bouquet.
- As the **founder editing the catalogue**, I change a price or a description in a JSON file, run one command, and see a diff of exactly what would change in the database — including nothing, when nothing changed.
- As the **implementer of spec 005**, the 84 products, their tiers and their per-country prices are typed rows I can read in a unit test with no database, and the row shapes are the same ones spec 002's tables use.
- As the **implementer of spec 009**, one product image is the LCP candidate, its preload and its `srcset` come from the same manifest, its alt text is per-locale data, and the honesty label is a component I cannot forget to render.
- As **Googlebot**, every image on an indexable page has localised alt text and appears in the page's `Product.image[]` in the same order I see it, and no page claims a photograph it does not have (`plan/02` §9, §15).
- As a **buyer in Warsaw**, the picture I see is labelled as an example arrangement, so I am not misled about what a hand-made bouquet from a local florist will look like (`plan/07` §2.1; ADR-0014).
- As a **screen-reader user in Polish**, the alt text is in Polish or the image is not rendered at all — never English alt on a Polish page (`plan/07` §8; WCAG 1.1.1 + 3.1.2).
- As the **reviewer agent**, "is this dataset honest, priced in-band, PII-free and inside the image budget?" is a command that exits non-zero, not a reading exercise.
- As the **founder after provisioning R2**, one task swaps the loader and one job produces every remaining variant; no page, component or call site changes.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

**No migration and no rollback file, and no database access, in the Phase-0 half** — the same deliberate consequence of spec 002 being parked that made specs 003 and 004 implementable (spec 003 §5.1, spec 004 §5.1). `pnpm check:no-db` covers every added file (AC-1). Rollback of the Phase-0 half is `git revert` of its task commits plus deletion of `public/media/`; there is no external state except the founder's own originals folder.

The **persistence target is spec 002's, unchanged and not restated**: `product`, `product_translation`, `product_tier`, `category`, `category_translation`, `product_category`, `product_occasion`, `addon`, `addon_translation`, `addon_country_price`, `country_price`, `media_asset`, `media_variant`, `product_media`, `product_media_alt` (spec 002 §5.1). This spec's schemas project onto those columns and a unit test pins each list, so the dataset and the schema cannot drift:

| Phase 0 artefact | 002 table | Projection | Pin |
|---|---|---|---|
| `products.json` row | `product` | `toProductRow()` | AC-3 |
| `copy/{locale}/products.json` row | `product_translation` | `toProductTranslationRow()` | AC-3 |
| `prices/{ISO2}.json` row | `country_price` | `toCountryPriceRow()` | AC-3 |
| `media.json` row | `media_asset` (+ `product_media`) | `toMediaAssetRow()`, `toProductMediaRow()` | AC-3 |
| `media-variants.json` row | `media_variant` | `toMediaVariantRow()` | AC-3 |
| `alt/{locale}.json` row | `product_media_alt` | `toProductMediaAltRow()` | AC-3 |

Three **amendments to spec 002 are requested rather than taken** (§13 Q10, Q11): (a) 002's task 10 reads `seed/data/` instead of inlining `plan/10`; (b) `media_asset` gains `generator_model`, `credit`, `licence`, `depicts` and `reviewed_by`/`reviewed_at` — spec 002 §5.1 has `source`, `generator_prompt_hash`, `generator_seed`, `exif_stripped` and `review_state` but no reviewer, no licence and no `depicts`, and all four are load-bearing for §8's provenance rule; (c) `media_variant` gains `checksum_sha256` so the manifest and the row can be compared. None of the three is a behaviour change and all three are additive columns in 002's migration `0003`, which has not been written.

**Post-provisioning migration order and rollback** (the §2.6 half): no new migration if (b) and (c) land inside 002's `0003`; otherwise one additive migration `00NN_media_provenance` with its `.down.sql` dropping exactly those columns, per spec 002's rollback rule. Data rollback is `seed/index.ts --only=media --dry-run` first, then deleting `media_variant`/`media_asset` rows whose `source = 'seed'` — real rows are untouched by construction (`plan/10` §4).

### 5.2 API / server actions / jobs / events (zod schemas named)

No route handler, no server action, no public API. The surfaces are four scripts, one module extension and one job.

```
seed/
  schema/            Seed*Schema, Media*Schema, AltManifestSchema, to*Row() projections
  data/              the dataset (§2.2)
  check.ts           pnpm seed:check      — the gate of §2.3
  diff.ts            pnpm seed:diff       — SeedTarget differ (snapshotTarget | dbTarget)
  media-variants.ts  pnpm media:variants  — deterministic sharp ladder (§2.4)
  index.ts           pnpm db:seed         — 002's importer, extended to the content half (needs 002)
  upload.ts          pnpm media:upload    — originals → R2 + enqueue (needs 002/R2)
src/modules/ui/media/

```

Schemas and behavioural contracts worth pinning:

- `MediaAssetManifestSchema` — `{ id, depicts, slot, source, generator?, generatorModel?, promptHash?, generatorSeed?, capturedAt?, credit?, licence?, reviewState, reviewedBy?, reviewedAt?, productSku?, sortOrder, isPrimary }`, refined so `source: "ai"` requires `generator`, `generatorModel`, `promptHash` and `generatorSeed`; `source: "photo"` requires `credit` and `licence`; `reviewState: "approved"` requires `reviewedBy` and `reviewedAt`; `depicts: "delivery"` is rejected in Phase 0.
- `MediaVariantManifestSchema` — `{ assetId, width, height, format: "avif"|"webp", bytes, checksumSha256, objectKey }`; `bytes` is an integer; the tuple `(assetId, width, format)` is unique.
- `SeedPriceSchema` — `{ productSku, countryIso2, tierKey?, retailMinor: z.number().int(), currency, vatRateBp: z.number().int(), surchargeKind?, activeFrom, activeTo? }`. Integer minor units + currency at the boundary, so `fo/no-float-money` has nothing to catch and no float can enter a price (`CLAUDE.md`; spec 002 AC-6).
- `SeedCopySchema` — `{ entity, key, locale, name, slug, descriptionMd?, seoTitle?, seoDescription?, translationStatus: "human"|"machine", reviewed: boolean, reviewedBy?, reviewedAt?, sourceHash }` — the same review triple as `messages/*.meta.json` and `product_translation` (`plan/03` §6; spec 002 §5.1), so one rule governs UI strings and catalogue copy.
- `SeedTarget` — `{ read(table): Promise<Row[]> }` with `snapshotTarget` (a committed `seed/data/.snapshot.json`) and `dbTarget` (needs 002). `diff(dataset, target)` returns `{ table, inserts, updates, unchanged, skippedReal, conflicts }`; the printed report is stable and diffable, and `--dry-run` writes nothing anywhere.
- `variantsFor(assetId, slot)` is pure and synchronous over the manifest, so `generateMetadata`, the preload builder, the `srcset` builder and 009's schema builder all get the same answer — the same property spec 003 required of `isLocaleIndexable()`.
- `media.derive_variants` payload (declared by spec 002 §5.2): `{ assetId: z.string(), reason: z.enum(["upload","backfill","reencode"]) }`; the handler is idempotent per (asset, variant, format) and records the checksum it wrote.

### 5.3 UI (pages, components, states)

No new page. Three components change or arrive, and their states are the point:

| Surface | States | Notes |
|---|---|---|
| `Photo` (extends spec 004's) | **image** (asset approved + variants present + alt for locale) · **placeholder** (any of those missing) · **error** (variant 404 at runtime → placeholder, never a broken-image icon) | Fixed aspect box in every state, so the swap from placeholder to image costs zero CLS and no template edit (spec 004 §2's promise, discharged here) |
| Product gallery (consumed by 009) | 1 image · 2–3 images · none | Order from `sortOrder` with `isPrimary` first; the primary is the page's only `priority` candidate |
| `MediaProvenanceNote` | ai · photo · mixed · hidden (no image on the page) | Server-rendered text from a message key; visible, crawlable, not collapsible |
| Homepage photo slots (spec 004) | placeholder (Phase 0 default) · image (once the founder supplies photography) | Flipping one slot is a data edit: an asset row + variants + alt. **No template edit.** AC-20 proves it |
| Demo-environment sample | watermarked | Watermark baked into the variant, not CSS (`plan/10` §3, §5) |

### 5.4 Rendering & caching (per `plan/01` §3)

- No page's rendering strategy changes. Home stays ISR 1 h / tag `home:{locale}`; category ISR 1 h / `catalog:{country}`; product ISR 1 h / `product:{id}` (`plan/01` §3). The variant manifest is a **build-time import**, so a cached page performs zero queries and zero fetches to resolve an image — which is also the Neon compute-hour constraint of ADR-0015 restated (spec 002 §5.4).
- After 002, changing an image is a data change that must invalidate the tags of the entities it belongs to (`product:{id}`, `catalog:{country}`, `home:{locale}`); the importer records which tags a run dirtied and prints them, and the actual `invalidate()` call is made by the caller (admin flip in 012, or the seed run) — `lib/cache.ts` stays the single seam (`plan/01` §3, §11).
- `/media/*` is served `public, max-age=31536000, immutable`. Variant URLs never mutate; a new image is a new asset version. This is the only new response-header change in the spec.
- Image origin is first-party in both phases (`/media/…` now, `R2_PUBLIC_BASE_URL` later), so no third-party image origin enters the CSP beyond that one host (§8).

## 6. SEO considerations (mandatory)

Ranking is priority #1, and this spec is the first one to add bytes that compete with it. Nothing here becomes indexable — `robots.txt` still says `Disallow: /` and the blanket `noindex` stands until spec 007 lifts it by rule (ADR-0007; spec 003 §6) — so the SEO surface is entirely *the inputs later pages need in order to be indexable and fast*.

- **Indexability inputs.** Three of the gates spec 002 §6 made queryable are filled by this dataset: `product_translation.description_md` (a null description means the PDP is not indexable — this spec is where descriptions arrive, and only for locales that have them), `product_translation.reviewed` (an unreviewed `de` description keeps the German PDP out of robots-meta lifting, hreflang and sitemaps — `plan/03` §6 gate 4, `plan/02` §12), and `product_media_alt` (a primary product image with no alt row in a locale makes that locale non-indexable for that product — spec 002 §8). The dataset's Phase-0 state is therefore honest by construction: `en`/`en-gb` complete, `de`/`pl` incomplete and gated.
- **The six-product rule.** `plan/02` §6 and §4 make a country category or country occasion page exist only with ≥6 products available there. `seed:check` reports the per-(country, category) and per-(country, occasion) product counts so 008 can test both sides of the threshold, and the dataset guarantees at least the PL set passes (spec 002 §6 asked for exactly this).
- **URL pattern and localised slugs.** Slugs are dataset values, ASCII-folded, lowercase, hyphenated, unique per locale, and validated by gate rule 4 (`plan/02` §4). No slug is machine-drafted: a slug is authored or derived from an authored name and then human-checked (`plan/03` §5). Variant URLs are not page URLs: `/media/*` is a static asset space, linked only from `src`/`srcset`, and is never a crawl trap.
- **`robots.txt` must not disallow the image space.** When spec 007 opens crawling, `/media/*` (and later the R2 host) must be crawlable or Google cannot index or even fetch the images it evaluates for Core Web Vitals; blocking it is the classic own-goal. Recorded here as a requirement on 007 and in `docs/runbooks/imagery.md`.
- **Schema.org.** `Product.image[]` (`plan/02` §9) is built from the same approved, product-depicting assets in the same order as the visible gallery, as absolute URLs, with dimensions available so 009 can emit the largest variant. Assets whose `depicts` is `brand` or `context` are excluded from `image[]` because they do not depict the offered product — misleading structured data is a manual-action risk (`plan/02` §9, §15). `delivery`-depicting assets are absent from the dataset entirely (§2.4). The builder is 009's; the guarantee that it reads the same view model as the UI is this spec's (`plan/02` §15).
- **Image sitemap: Phase 4, deliberately** (`plan/02` §10 places `/sitemaps/images-{n}.xml` there). Not shipped (§3). The dataset makes it a query when it arrives.
- **Thin and duplicate content — the real risk in this spec.** 84 products × N live countries with one AI style and near-identical copy is exactly the failure `plan/02` §4.2 and §15 warn about. Five guards, four of them mechanical: (a) products are indexable only in `live` countries, so N is 1 for years (`plan/02` §4.2); (b) `seed:check` rejects a description duplicated across products and enforces the 60–90-word, contents-and-substitution shape (`plan/10` §2.2) so each description carries product-specific facts; (c) no machine-translated description is indexable (`plan/03` §6); (d) the per-country PDP block (cutoff, next date, VAT wording, local add-ons) is 009's and is server-rendered from country data, not from this dataset (`plan/02` §4.2); (e) images are *not* content — the dataset deliberately cannot make a page indexable, only fast and honest.
- **CWV budget impact — measured, not hoped.** Images are now the largest transfer on every money page. Budget: ≤ 204 800 B image transfer per page (spec 004 AC-24, already a green Lighthouse assertion), LCP < 2.0 s, CLS < 0.05 (`plan/01` §7). Mechanisms: AVIF-first with WebP fallback; one `priority` LCP candidate with a matching preload; everything else lazy with a fixed aspect box; per-slot byte caps enforced by `seed:check` **before** the bytes are committed, so a 900 KB hero fails a gate rather than a Lighthouse run; no client JavaScript added (the loader and manifest are build-time), so the Brotli script budget of spec 004 §14 A1 is untouched (AC-22).
- **Crawl efficiency.** No new URL space beyond static assets; no query parameters; no per-variant HTML page; `immutable` caching means a re-crawl is a 304 or a cache hit; and because the LCP image is preloaded from cached HTML there is no discovery round-trip for the one byte-heavy resource that matters.

## 7. i18n considerations (mandatory)

- **New message keys / namespaces.** `media.*` — the honesty label (`media.provenance.aiExample`), the placeholder caption per slot (`media.placeholder.hero`, `.occasion`, `.product`, `.delivery` — the "Photography to supply · …" strings spec 004 renders today as design copy), the demo watermark label, and `a11y.media.*` (gallery landmark, "image N of M"). `catalogue.*` — the localised descriptor patterns used in names (`plan/10` §2.2), tier labels resolved from `product_tier.label_key` (spec 002 §7), and the local-florist sentence that every description ends with, so a rewording is one catalogue edit in four locales rather than 84 description edits. No literal user-facing string in a component (`plan/03` §5; `fo/no-literal-strings`).
- **Alt text is per-locale data, required, and never generated at render** (`plan/01` §6). Four locales × every committed asset. The gate refuses a missing or empty alt for a product image (AC-8); the component refuses to render an `<img>` without one (AC-18). Alt text is written for the locale, not translated word-for-word: it describes what is in the picture in that language, with the flower and colour named (WCAG 1.1.1), and never repeats the product name verbatim (which the screen reader already announced from the heading).
- **Product names are not translated; descriptors are** (`plan/10` §2.2's convention, and §13 Q2's default). `Amber Hour` stays `Amber Hour` in all four locales; "hand-tied rose bouquet" becomes "Rosenstrauß, handgebunden" / "bukiet róż wiązany ręcznie". This keeps one brandable entity per product across locales, keeps slugs stable, and keeps the hreflang cluster a genuine translation set rather than four different products.
- **Machine drafts and the `noindex` gate.** `de` and `pl` copy is produced by `pnpm i18n:draft`'s deterministic provider extended to the catalogue dataset (spec 003 §2's `DraftProvider`, still network-free in CI), written with `translationStatus: "machine"`, `reviewed: false` and a `sourceHash`. Consequence, and it is the correct one: German and Polish PDPs are non-indexable until a native reviewer approves them (`plan/03` §6 gate 4; `plan/02` §12; spec 002 §6). `sourceHash` makes an English edit flip dependants stale (`plan/03` §6 step 5). Corridor guides and legal copy are still never machine-drafted — out of scope here (§3).
- **Formatting.** No price, date or number is formatted in the dataset: prices are integer minor units + currency, dates are ISO calendar dates, and everything user-visible goes through `src/modules/i18n/format.ts` (`fo/no-adhoc-intl`, spec 003 §2). No locale-baked string is ever stored (spec 002 §7).
- **RTL.** Photographs are **never** mirrored: `@utility mirror-in-rtl` applies to direction-carrying icons only (spec 004 §2), and a test asserts no `Photo` output carries it. Aspect-ratio boxes and `sizes` are direction-agnostic; the gallery's inline layout uses logical properties (`fo/no-physical-css`). `ar-XB` visual baselines gain the first real images, which is the first time the pseudo-RTL gate has photographic layout to mirror (spec 004 §2).
- **Collation.** Any list of products, categories or occasions ordered for display uses `collator(locale)` (spec 003), not `sortOrder`, except galleries where `sortOrder` is editorial intent.

## 8. Compliance considerations (mandatory)

- **Data flows added → RoPA: none, and this is asserted rather than assumed.** The dataset contains no personal data: no buyer, recipient, partner or staff information; demo partners are spec 002's and carry placeholder identities; there is no `email`, phone, address or name of a real person (gate rule 8, AC-9). The imagery contains **no faces, no hands, no identifiable people and no identifiable premises** by the style guide (`plan/10` §3) and by the review checklist, so it is not personal data either. `docs/compliance/ropa.md` therefore gains **no new processing row**; it gains one explicit sentence recording that spec 006 introduced imagery and catalogue data with no personal data, and a **conditional** row that must be written the moment the founder supplies photography containing an identifiable person or a named florist's shopfront (§13 Q1 option c): that would be personal data requiring a lawful basis, a model/property release ⚖️, and a retention decision. Cloudflare's row (written by spec 002 for R2) gains "product imagery" as a data category when §2.6 lands. `plan/07` §1.4's residency rule is met: the R2 bucket is EU-jurisdiction-restricted (spec 002 §8), and in Phase 0 the bytes are in the repository and on the host's CDN.
- **Content provenance and misleading-practice law — the substantive question in this spec.** Product images that a local florist will not literally reproduce are a **misleading action/omission** risk under the UCPD (2005/29) and the CRD's "main characteristics" duty (`plan/07` §2.1), and under the UK DMCC 2024's equivalent prohibitions (`plan/07` §2.2). ADR-0014 accepted AI-generated catalogue imagery **conditional on honest labelling**, and `plan/10` §3 fixes the mechanism. This spec turns both into enforced facts: every page displaying an `ai` asset renders a visible, crawlable "example arrangement · your florist hand-makes each one" note that cannot be disabled (AC-17); provenance is a required column set, not a comment (AC-8); an AI asset may never be presented as a delivery photo, and `depicts: "delivery"` is rejected outright in Phase 0 (AC-8); the demo environment's samples are watermarked in the bytes (AC-16); and the "Real deliveries" module renders only consented `delivery_proof` (out of scope, `plan/07` §1.2). Two items need the lawyer ⚖️ and are asked in §13 (Q8): whether the label wording satisfies DE/PL transposition, and whether the **EU AI Act Art. 50** transparency duty for synthetic image content reaches us. Our reading `[agent-inferred]`: Art. 50(2)'s machine-readable-marking duty falls on the *provider* of the generative system and Art. 50(4)'s disclosure duty concerns deep fakes and public-interest text, so a labelled, non-deceptive product illustration is outside it — but we keep provenance in data, preserve any C2PA metadata the generator embeds (stripping only EXIF/GPS and personal fields), and record the generator's commercial-use terms in `content/imagery/style-guide.md`, so compliance is a configuration change if the reading is wrong. ADR-0014's own condition — "check generator terms for commercial use" — is discharged as a founder action with the answer filed in `docs/compliance/` (§12).
- **No fabricated trust.** Zero reviews, zero ratings, zero testimonials, zero partner photos, zero florist counts, zero delivery-photo claims enter the dataset or the rendered pages (`plan/07` §7; `plan/09` Phase 0 AC 6; spec 004 AC-15, whose grep this spec must keep green — AC-21). The delivery-photo homepage band stays a placeholder precisely because a placeholder is honest and a stock photo is not.
- **Price display.** Every price row is VAT-and-delivery inclusive integer minor units with a currency, exactly one active per (product, country, tier, surcharge), superseded rather than updated — which is what preserves the 30-day-lowest-price history the Omnibus Directive requires and what makes "price shown = price charged = schema price" a data invariant (`plan/07` §2.1, §4; spec 002 §8). `seed:check` enforces the bands, the endings and the single-active rule (AC-6). No image or badge in this spec renders a price, a strike-through or a scarcity claim (`plan/07` §4: "no fake urgency").
- **Consumer information.** Descriptions carry the "main characteristics" the CRD Art. 6 requires — contents, size, who it suits and the substitution policy in plain words (`plan/10` §2.2; `plan/07` §2.1) — and the substitution class is a facet on the product so 009 can state it precisely. Allergen text for food add-ons is required by the FIC Regulation (`plan/07` §9) and is a required field on `chocolates` and `cake` add-on copy; `wine` copy carries the licensing note and stays flag-disabled where unlicensed.
- **Accessibility (WCAG 2.1 AA, `plan/07` §8).** WCAG 1.1.1: informative images have per-locale alt text; the component cannot render an `<img>` without it and falls back to the placeholder rather than to an empty alt (AC-18). 1.4.5 (images of text): the style guide bans text in images, so no image carries information available only visually — enforced by the review checklist. 1.4.11: the placeholder gradient and its caption meet the contrast manifest of spec 004 AC-3 (the caption pair is already in it). 2.4.4: an image inside a link never carries the link's only accessible name. 1.3.4/1.4.10: aspect-ratio boxes and `sizes` are responsive, no fixed pixel widths. axe runs on the gallery states in `/dev/components` with zero serious/critical (AC-23).
- **Logs and PII.** No object key, prompt, file path or asset id is logged at `info` in a request path; the CLIs log to stdout by design (developer tooling, no PII by construction). Spec 002 §8 added `object_key` to the logger redaction list; nothing in this spec logs one anyway. No PII can enter a URL: asset ids are opaque, derived from the SKU and role, and contain no personal data (`CLAUDE.md`).
- **Security.** `img-src` in the CSP gains `'self'` only in Phase 0 and the R2 public host in §2.6 (ADR-0016; the policy is per-environment and asserted as a whole string, spec 004 AC-23). No user-supplied image enters this pipeline (partner and florist uploads are 011/027 and go to a private bucket). `sharp` is a devDependency used by a local CLI, never at request time, so its CVE surface is not in the deployed runtime; the pinned version is recorded and covered by `pnpm audit`. R2 credentials are env-only and scoped to the media bucket (spec 002 §12 founder action 2).

## 9. Acceptance criteria

**The no-database, no-provisioning seam**
- **AC-1** `pnpm build`, `pnpm test`, `pnpm seed:check` and `pnpm media:variants --check` all succeed with `DATABASE_URL` unset and with no network access; `pnpm check:no-db` covers every file added by §2.2–§2.5 and no such file imports `src/lib/db*`, `drizzle*`, `pg` or `postgres`.

- **AC-3** Every `to*Row()` projection returns exactly the column list of its spec 002 §5.1 table, pinned by a unit test that fails if either side is edited alone: `product`, `product_translation`, `country_price`, `addon_country_price`, `media_asset`, `media_variant`, `product_media`, `product_media_alt`.

**Dataset completeness and correctness**
- **AC-4** The dataset contains exactly 84 products in the 40/14/8/10/12 split of `plan/10` §2.1, 23 categories, 6 add-ons, tiers per `plan/10` §2.2, and every product's six facet values exist in `taxonomy.json`.

## 11. Observability

- **The gate is the instrument.** `seed-check`'s GitHub step summary is the standing report on catalogue health: product counts by type, per-(country, category) and per-(country, occasion) coverage against the six-product rule, price-band outliers, description word-count distribution, copy review shares per locale (the same numbers `isLocaleIndexable()`-style gating consumes), committed image bytes, per-slot maxima and the count of products still on a placeholder. A locale or a country cannot look ready in CI and be gated in code.
- **Imagery review counters** — the imagery runbook records generated / accepted / rejected per batch and the rejection reasons (impossible stems, wrong flower, visible text, person present). That number is the honest measure of ADR-0014's main risk (`plan/10` §7 "AI imagery looks synthetic"), and it is what tells the founder whether the small real shoot is needed.
- **Diff report as the audit trail** — every `db:seed` run (post-002) prints and archives inserts / updates / unchanged / skipped-real per table plus the cache tags the run dirtied, with `request_id` and `actor = system:seed` (`plan/11` §1's actor convention, spec 002 §11). A seed run that touches more rows than the diff predicted is the signal that something drifted.
- **Runtime** — no new log line in a request path, no new metric, no new alert. The only runtime failure mode this spec introduces is a 404 on a variant, which degrades to the placeholder (AC-18's error state) and shows up as a CDN 404 rather than a broken page; `media:variants --check` in CI is what makes that failure impossible for committed assets.
- **Deliberately not instrumented yet**: per-image CWV attribution and image-search impressions (Search Console, once 007 opens crawling); R2 storage/egress usage (a Cloudflare probe alongside spec 002's Neon usage probe when §2.6 lands — recorded in `docs/runbooks/imagery.md`, `plan/13` D1).

## 12. Rollout

- **Feature flags.** None behavioural. Three data switches: `resolveLoader()`'s mode (static vs R2, env-derived from the presence of `R2_PUBLIC_BASE_URL`), the presence of an approved asset per slot (which is what makes a placeholder become an image), and `media_asset.review_state` (an unapproved asset never renders). As in spec 003 §12 and spec 004 §12, the pre-database data switches are a **bounded, stated deviation** from `CLAUDE.md`'s "go-live is a data flip in admin, never a code change": there is no database and no admin yet, each switch is read through one predicate, and spec 002 + spec 012 take over the authority with no call-site change (AC-2, AC-20 are the proofs). No ADR is proposed. The second bounded deviation: **derived image bytes are committed to the repository** in Phase 0, which is a build artefact in version control — accepted for ≤ 6 MB over four weeks, deleted in the R2-flip task (AC-27), and recorded in `docs/architecture.md` §4 as a row that closes with that task.
- **Environments.** local (originals present, CLI runnable) → PR preview (committed variants only; `media:variants --check` in CI; no originals, no generator, no network) → production alias (same bytes; still `Disallow: /` until spec 007). No founder provisioning is required for any task except the four marked "needs 002/R2".
- **Migration order.** None in Phase 0. Post-provisioning: spec 002's `0003` (with the three additive columns of §5.1) → `pnpm db:seed --only=catalogue,copy,prices` → `media:upload` → `media.derive_variants` → loader flip. Each step is idempotent and re-runnable; the rollback of each is in §5.1.
- **Rollback plan.** Phase 0: `git revert` per task plus deleting `public/media/`; there is no external state. Post-002: revert the loader flip first (it is the only user-visible step), then `seed`-level rollback by deleting `source='seed'` media rows, then the additive migration's `.down.sql`. The hazard to state: reverting the loader flip **after** `public/media/` has been deleted leaves no image origin, so those two must be one commit or reverted together (the same pairing hazard spec 004 §12 recorded for its budget/CSP tasks).

**Resolved 2026-09-09 (founder: "accept defaults"; Q1 answered explicitly):** Q1 imagery is **AI-generated under the locked style guide or free-licence stock** (CC0 / public-domain / Unsplash-licence class — no paid stock; every asset records `generator_model` or `licence` + `credit` in provenance and the AI honesty label applies to generated assets; the hero and delivery band may use free stock where AI output reads as synthetic, and a real photograph replaces them when the founder has one); Q2 names stay English, descriptors localise; Q3 12 products × 2 assets plus the homepage slots; Q4 ≤6 MB derived bytes committed until R2, deleted in the R2-flip task; Q5 AVIF + WebP at the seven widths, one JPEG per asset for OG/email; Q6 originals in the founder's store + git-ignored local folder; Q7 `fo-media` / `fo-media-preview` / `fo-backups`, `media.flowersoverseas.com`; Q8 both questions go on the October legal-drafts list, label shipped now; Q9 founder signs off against the §2.4 checklist; Q10 spec 002 task 10 reads `seed/data/` (spec 002 §14 A1); Q11 the seven media columns fold into migration `0003` (spec 002 §14 A1); Q12 watermark mechanism kept, no watermarked asset in Phase 0. Original questions kept below for the record.

Each has a recommended default. The spec is `draft` until they are answered and the founder marks it `approved`.

- **Q1 — Where do the pictures come from, and how is each kind labelled?** Three options, and they can be mixed. (a) **AI-generated under the locked style guide** — ADR-0014's accepted decision, ~€50–150, very consistent, rights-clean, and labelled "Example arrangement · your florist hand-makes each one" on every page that shows one. (b) **Licensed stock** — €300–800, inconsistent, and the same images competitors use; ADR-0014 rejected it and nothing has changed. (c) **Commissioned/own photography** — the honest ideal, and the only option for the homepage's full-bleed hero and delivery band, where AI output reads as synthetic; costs money and calendar, and if a person or a named shopfront is identifiable it needs a model/property release ⚖️ and a RoPA row (§8). **Recommendation: (a) for all 84 catalogue products, (c) for the homepage photo slots and the brand band, (b) never.** Whatever is chosen, provenance is per-asset data and the label follows the asset, so a later swap is a data edit.
- **Q2 — Are product names translated, or does the evocative name stay English in every locale?** `plan/10` §2.2's convention is that the name stays and the descriptor localises. **Recommendation: keep the name, localise the descriptor** (`Amber Hour` + "Rosenstrauß, handgebunden"). It keeps one brandable entity per product, keeps slugs and hreflang clusters stable, and halves the translation surface. The alternative — fully localised names — gives better keyword coverage in `de`/`pl` slugs at the cost of four different product identities and a re-slug of every locale. Answer gates T2.
- **Q3 — How many products carry imagery for the 16 Oct demo?** All 84 exist as *data* regardless. **Recommendation: 12 products × 2 assets (hero + detail), one per named archetype of `plan/10` §2.2, plus the homepage slots** — enough that a category grid and a PDP look real to a florist, small enough to generate, review and commit inside the week and inside the 6 MB budget. Alternatives: 24 products (better-looking grid, roughly double the generation and review time) or all 84 (252 assets; not reviewable in a week and not committable to the repository — it needs R2 first).
- **Q4 — Is committing derived image bytes to the repository acceptable until R2 exists?** **Recommendation: yes, capped at 6 MB, only for slots actually rendered, deleted in the R2-flip task.** The alternative is waiting for provisioning, which would leave the demo with no pictures at all and make the whole imagery half of this spec unimplementable this week. Cost: a few MB of git history that a later `git gc` will not reclaim.
- **Q5 — Variant widths, formats and quality.** **Recommendation: AVIF (quality 50, effort 4) + WebP (quality 72) at widths 384 / 640 / 828 / 1080 / 1200 / 1600 / 1920, aspect ratios 4:5 (product), 1:1 (occasion tile), 16:9 desktop / 4:3 mobile (hero band), 3:2 (context).** No JPEG in the page ladder (every target browser has WebP), one JPEG at 1200 px per asset for OG/email/social where AVIF and WebP are still unreliable. Trade-off accepted: two formats × seven widths is 14 files per asset; dropping to five widths saves storage and loses a little transfer efficiency on mid-size viewports.
- **Q6 — Where do the originals live before R2 exists?** **Recommendation: the founder's own store (Drive or local) plus a git-ignored `.local/imagery/originals/` for the generation loop; never committed; moved to R2 `originals/{assetId}` when §2.6 lands.** The alternative — Git LFS — is a new dependency, a new quota and a new failure mode for a four-week window.
- **Q7 — R2 bucket and CDN domain naming.** **Recommendation: buckets `fo-media` (public, EU jurisdiction), `fo-media-preview`, `fo-backups` (private, spec 002's); public origin `https://media.flowersoverseas.com` as a Cloudflare custom domain on the media bucket** — first-party origin (one CSP entry, no third-party host in `img-src`), zero egress (ADR-0015's whole point), and a name that survives the Hetzner move because it is a DNS record rather than a vendor URL. Confirm, because the name enters `.env.example`, both CSP strings and every image URL.
- **Q8 — Two lawyer questions ⚖️ on imagery honesty.** (i) Does "Example arrangement · your florist hand-makes each one" satisfy the UCPD/CRD and DE/PL transposition for AI-generated product illustrations, and should it also appear in the checkout summary and the confirmation email?
