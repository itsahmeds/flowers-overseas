## 1. Problem

Spec 008 gives a buyer a grid of bouquets and a card that, deliberately, does nothing: "while the spec 009 product link id is unpublished, every card renders as a non-interactive tile with no `<a>`" (008 AC-12, §13 Q8). This spec publishes that link id and builds the page behind it. It is the last page of the Phase 0 browsable site and the only one that has to answer the question the whole business turns on — **when will it arrive, and how do you know?** — which is also the one question four specs have so far been forbidden from answering. Spec 006 §14 A4 banned every lead-time, cutoff and "same day" phrase from catalogue *copy* and named this spec as the owner of the computed replacement. Spec 007 AC-19 banned the same claims from the corridor page's guide state and shipped the `ActivePartnersProvider` that decides when they may appear. Spec 005 declared `CutoffEvaluator` as a seam with a test-grade implementation that "computes nothing" and wrote in the file that "there is no date arithmetic, no holiday evaluation, no time-zone conversion and no occasion-date rule in this file, because `plan/03` §9/§10 and spec 005 §3 put every one of them in spec 009". Four specs have pointed here. This is the implementation.

Two things make it harder than the four pages before it. The first is **honesty under zero operational data**. `plan/04` §7 draws the PDP with a date list, a fee on every chip and a live countdown; `docs/design/benchmarks/01-product-page.md` §2 makes "the fee printed on every selectable date" and "the cutoff in the recipient's time zone" the two things we take from the field. But in Phase 0 `hasActivePartners(iso2)` is `false` for every country (007 §2, founder ruling 2026-09-15) and `countries.ts` carries no `operations` block for any of them (007 §5.1). A picker that offers Thursday to a country with no florist is the single most damaging sentence this site could render, and it would be rendered by a template, at scale, in four locales. So the first half of this spec is the rule that decides **what the picker is allowed to say**, keyed on data, with no per-country branch.

The second is that the date picker is **the first interactive element on a page type that is meant to be indexed**. Specs 003, 004, 007 and 008 all hold the line "zero new client islands" (007 AC-24, 008 AC-23), and it has cost nothing so far because a FAQ is text and a sort control is a `GET` form. A date grid whose selection changes a price is the first place where that line has a price of its own. So the second half of this spec is a contract: the page is complete, correct and fully operable with JavaScript disabled; every number the buyer can reach is in the server-rendered HTML before any script runs; and the enhancement that makes selection feel instant is one island with a hard byte budget and no network access of any kind.

## 2. Scope

Each bullet is testable; §9 names the AC. This spec **consumes** spec 005's `modules/catalog` read and pricing API, spec 006's media loader and honesty label, spec 007's `modules/seo` engine and `ActivePartnersProvider`, and spec 008's `ProductCard`, `slugs.ts`, breadcrumb and `localePath()`. It re-specifies none of them. Nothing here requires a database, a partner, a payment provider or an image we do not have.

**The URL and its existence rule (`plan/02` §4.1, §4.2; 008 §2's reserved pattern)**

- `/{locale}/{countrySlug}/{product}/{productSlug}` — `product` is the localised path segment already authored in `locales.data.ts` (`product` / `produkt` / `produkt`), `countrySlug` comes from `countries.ts`, `productSlug` from spec 008's `slugs.ts`, and the whole URL is composed only by 008's `productPath()`, which is `localePath()` underneath (spec 003 §6). `plan/02` §4.1's row and its §4.2 recommendation ("country in every shop URL") are followed verbatim.
- **A PDP exists iff** the country is published (`status === 'live' || guidePublished`), **and** the product is `status: 'active'`, **and** an active `country_price` row exists for that (product, country) — i.e. spec 005's `hasActivePrice()` — **and** the product has a slug in that locale (§13 Q1). Everything else is a hard **404**: an unknown slug, a product not deliverable to that country, an unpublished country, a segment belonging to another locale, an uppercase or trailing-slash variant. No redirect (ADR-0006), no soft-404, no "similar products" page standing in for one.
- `productPageExists()` is a pure synchronous predicate over the providers and is the **only** answer to that question — the route, `generateStaticParams`, the sitemap builder, 008's card-link renderer and the e2e crawl all call it, so they cannot disagree (007's `corridorPageExists` rule, applied again).
- **Prebuild is a performance choice, not an existence choice.** 84 products × 7 published countries × 4 locales is 2 352 URLs, and `plan/01` §3 already answers it: "`generateStaticParams` prebuilds only the live country corridors and the **top 50 products per live locale**, so builds stay under 3 minutes; everything else is generated on demand." The PDP is therefore the one route in the Phase 0 site with `dynamicParams = true` — prebuilding `topProductsForPrebuild(country, locale, N)` (default **N = 24**) and generating the rest on first hit — with the 404 guarantee preserved by `productPageExists()` inside the route rather than by the params set. AC-3 asserts that (prebuilt ∪ on-demand) equals the existence set exactly and that a URL outside it 404s on first request.

**Page anatomy (`plan/04` §7; the `product-{desktop,mobile}` artboards; `docs/design/benchmarks/01-product-page.md`)**

Block order, top to bottom, exactly as §12's artboards fix it: breadcrumb → destination line ("Where is it going? Poland — changing it reloads the country-scoped URL") → gallery → `<h1>` product name → description and care copy (spec 006) → **tier selector** → **delivery date picker** → **delivery facts** → add-on price list → **price summary** (all-in, "includes delivery and VAT") → trust/promise block → related products in this country.

- **Gallery.** Spec 006's `Photo` + `resolveLoader()` with a new named `hero` slot; the hero is the page's single `priority` image with a `<link rel="preload" as="image" imagesrcset imagesizes>` built from the same manifest lookup that produced its `srcset` (006 §2.5, 008 AC-24). Alt text is per-locale data from spec 006 and never derived from the product name; the honesty/provenance label renders wherever an `ai` asset is shown. **72 of the 84 products have no imagery in Phase 0**, so the *no-photo* state is the common case, not an edge case: a captioned placeholder box, no `<img>`, no honesty label (there is no generated image to be honest about), and the same fixed box in every state so CLS across the swap is 0.
- **Tier selector.** A radio group inside the page's one `<form method="get">`, one radio per `product_tier` ordered by `sort`, each printing its label (`catalog.tier.stems` ICU plural / `size.{s,m,l}` / `single`, spec 005 §7) and its own all-in price through `formatMoney`. The preselected tier is `is_default` data (005 §13 Q6), never a code constant. Stem counts, never adjectives (`docs/design/benchmarks/01-product-page.md` §2.4).
- **All-in price.** One amount from `priceProjection().displayPrice` in the **locale's default currency** (005 §7; the 2026-09-16 orchestrator ruling that settled the same point for 008), with the authored per-locale `catalog.price.inclusive` formula beside it and the VAT rate and "delivery included" named as rows in the summary. There is no "from" on a PDP (`plan/04` §7). Where the FX rate is stale the projection falls back to the destination currency and the page says which currency it is quoting (005 §14 A3 / §14 A2's stale-FX rule).
- **Add-ons in Phase 0 are a priced list, not a control** (§13 Q6): name, per-country price, its own VAT rate, and the "what the price does not include" sentence. There is no checkbox, because there is no basket to add one to (spec 010), and a checkbox that changes nothing is a worse lie than no checkbox. CRD Art. 22 is unbreakable here by construction and stays so when 010 adds the inputs, because spec 005's add-on type has no `defaultSelected` field to set (005 AC-19).
- **Trust block — only the claims whose backing exists.** The substitution sentence renders (it is a statement about how we work, true today). The delivery-photograph promise does **not** (gated on spec 027 shipping; founder ruling 2026-09-15, spec 004 §14 A15). The "our florist in the recipient's town" claim does **not** while `hasActivePartners` is false (007 AC-19's rule, applied to the PDP). The withdrawal-right notice does **not** (lawyer-gated, `plan/13` B4; placement is spec 010's and the legal set's — §3, §13 Q7). A block whose backing is missing renders **nothing** — no heading, no placeholder (spec 004 §5.3, 007 §5.2).
- **Related products**: up to 6, same country, from spec 005's deterministic ordering, rendered with spec 008's `ProductCard` unchanged.

**The date picker and the cutoff/holiday engine — the core**

- **`src/modules/geo/delivery/`** implements spec 005's declared `CutoffEvaluator` (`nextAvailableDate`, `isDateAvailable`, `cutoffFor`) for real, plus `deliveryWindow({ countryIso, from, days })` → the ordered grid the page renders. Every answer is computed in the **destination country's IANA zone** (`plan/03` §10), from four data inputs and nothing else: the country's `operations` block (`ianaZone`, `sameDayCutoffLocal`, `deliveryDays`, `sundayDelivery` — the optional object spec 007 §5.1 added to `countries.ts`), the destination's public holidays (`country_holiday` in spec 002; in Phase 0 the committed `seed/data/occasion-country.json` + a new `holidays.json`, §5.1), the occasion rules of `modules/geo/occasions`, and — later, without a call-site change — `CapacityProvider` and partner blackout dates (`plan/06` §5.1, §5.2; Phase 1/2, §3).
- **Each date in the grid is a value, not a rendering decision**: `{ date, selectable, reasonKey?, surcharge?: Money, occasionKeys: string[] }`. A date is unselectable because it is before the first possible day, past the cutoff, a non-delivery weekday, a Sunday where `sundayDelivery` is false, or a public holiday in the destination — and the **reason is rendered in words next to the date before it is chosen**, never by colour or opacity alone (WCAG 1.4.1). A surcharge (Sunday, peak day) is spec 005's `dateSurcharges()` row and prints its exact amount **on the chip before selection**, which is `plan/07` §4's requirement and the one thing the whole competitor field gets wrong (`docs/design/benchmarks/01-product-page.md` §2.1, §3.3).
- **Occasion dates are highlighted, not invented**: a date carrying an occasion observed in that country (from `upcomingOccasions`, TASK-089's typed seam) gets a labelled marker through `formatDate`, with the occasion name from its message key. No date literal exists in any component or message string (007 AC-22's rule, inherited).
- **No relative day labels and no countdown in cached HTML** (§13 Q4 — a deviation from `plan/04` §5/§7 and from the current artboard, stated rather than silently taken). "Today", "Tomorrow" and "Order within 3 h 20 m" are all functions of `now`, and an ISR page is served for up to an hour after it is rendered: a cached "Today" is wrong after destination-midnight and a cached countdown is wrong after sixty seconds. The page therefore renders **absolute dates** ("Thu 10 Sep", weekday + month name per `plan/03` §7) and an **absolute cutoff** ("Order by 14:00 in Warsaw — the recipient's time, not yours", through `formatTimeInZone` with the zone named, `plan/03` §7/§10). A live PDP additionally drops to `revalidate` 300 s and carries a `cutoff:{iso2}` tag that a Phase 1 scheduled job purges at destination-midnight and at the cutoff minute (declared here, implemented with the partner data that makes it meaningful).
- **Three states, chosen by data, no per-country branch** (§13 Q2):

| State | Condition | What the picker renders |
|---|---|---|
| `unavailable` | the country has no complete `operations` block | **No dates at all.** A disabled `<fieldset>` with one honest sentence ("We are still choosing florists in Poland, so we cannot offer delivery dates yet") and a link to the corridor page. No cutoff, no calendar, no "next available". |
| `preview` | a complete `operations` block **and** `hasActivePartners === false` | The full computed grid, **every date unselectable**, under a heading that says plainly what it is: "This is how delivery dates will work in {country}. We are not taking orders yet." Surcharges, holiday reasons and occasion markers all render, because they are facts about the destination's calendar rather than promises about us. |
| `live` | a complete `operations` block **and** `hasActivePartners === true` (007's `corridorState(iso2) === 'live'`) | The grid with real selectable dates, the earliest preselected, the cutoff line, and the selected date's surcharge folded into the one all-in total. Phase 1, PL first. |

  In Phase 0 the default is `unavailable` for all seven destinations, becoming `preview` for Poland the moment the founder authors PL's `operations` block (§13 Q3) — which is the state the 16 October demo shows, and which is a **data flip, not a template edit** (AC-8).

- **Server-rendered grid + one small island.** The whole picker is a radio group in a `<form method="get">` with a real submit button: with JavaScript disabled, choosing a date and submitting reloads to `?date=YYYY-MM-DD` and the server re-renders the summary with that date's surcharge. Every selectable date's all-in total is **already in the HTML** (an embedded table in the shape and with the byte discipline of spec 005's `priceTable`, §5.2), so the island — `DateAndTierEnhancer`, **≤2 048 B Brotli**, no `fetch`, no `XMLHttpRequest`, no dynamic import, no timer — only swaps the summary total from numbers already present and announces the change on an `aria-live="polite"` region. AC-13 asserts that the JS-on and JS-off totals are byte-identical for every date and tier of a fixture product. This is the **first client island on an indexable page** and it is a stated, bounded amendment to spec 007 AC-24 / 008 AC-23 rather than a quiet exception (§5.4, §12, §13 Q5).
- **Parameters.** `?tier=` and `?date=` are parsed by a strict zod schema; an unknown parameter, an out-of-window date, a malformed date or a date that is not selectable falls back to the default rendering rather than erroring. Every parameterised URL is `noindex,follow` with a canonical to the bare URL, appears in no sitemap and is never an `<a href>` — the same policy 008 §6 set for `?sort=`, with the same edge-cache resolution (008 §5.4, §13 Q2).

**The seventh occasion rule type (`plan/13` B15; 007 §13 Q7's assignment)**

- `modules/geo/occasions` gains **`orthodox_easter_offset(days)`** — Orthodox Easter computed by the Julian computus and converted to the Gregorian calendar, plus a day offset — as an additive rule type beside the six of `plan/03` §9. The existing six are untouched, `occasionDate(rule, year)` keeps its signature, and the 100% branch-coverage gate on the module (`plan/12` §4) extends to the new branch.
- Fixtures: Romanian Orthodox Easter and its dependent observances for **2026–2030**, verified against the Romanian Orthodox Church calendar by the implementer before the fixture is committed (the `plan/13` D6 pattern — a date we have not checked is not a fixture). The RO rows currently carried as `rule_type: "none", observed: true` in `seed/data/occasion-country.json` (TASK-072) are migrated to the new type in the same PR.
- Two further seed rows queued to this spec by the founder on 2026-09-15 (PR 60 note (a)): **Andrzejki (30 Nov)** and **Wigilia (24 Dec)** as `fixed` PL rows, so the homepage occasion strip stops carrying two occasions the calendar cannot date. Polish **name days stay a category, never a dated occasion** (B15, unchanged).

**Indexability, schema, sitemap, links**

- The PDP registers a `PageDescriptor` with 007's `indexability()`. **No new `noindex` branch is written in this spec.** Indexable iff the page exists **and** `corridorState(iso2) === 'live'` **and** spec 005's `isProductIndexable(product, locale, iso2)` (active price, non-null reviewed description in that locale) **and** `isLocaleIndexable(locale)` **and** `isIndexingEnvironment()`. In Phase 0 the partner predicate is false everywhere, so **every PDP in every locale is `noindex,follow` and in no sitemap** (ADR-0007).
- **Schema**: `BreadcrumbList`, mirroring the visible breadcrumb exactly. **No `Product` and no `Offer` in Phase 0** (§13 Q8): a `Product` node without an `Offer` earns no rich result and adds a "missing field offers" warning, and an `Offer` on a page with no purchase path advertises a transaction we cannot perform (`plan/02` §9's "never emit `Offer` for a country that is not live", 008 §13 Q5, `plan/07` §4). The typed `Product` + **single** `Offer` builder is nevertheless written and tested here, fed by spec 005's `offerProjection()` so `Offer.price === renderedDisplayPrice` by construction (005 AC-11), and is emitted only when the page is indexable **and** a purchase path exists — which is a data flip the day spec 010 ships into a live country. `aggregateRating` and `review` are forbidden and asserted absent, always.
- **Sitemap**: a new child `/sitemaps/{loc}/products.xml` with 007's contract, listed in the per-locale index **only when non-empty** — so in Phase 0 it is empty and therefore absent.
- **Links**: `site-links.ts` publishes the `product` link id 008 reserved. Publishing it turns every 008 product card from a tile into a link **with no markup change other than the element** (008 AC-12, re-run green here). Out: breadcrumb (home → country shop → category → product), the country shop root, the category, related products, the corridor page. Crawl depth from any locale home to any PDP is ≤4, and **zero links to a non-200 URL** survives (004 AC-14, 007 AC-17, 008 AC-21).

**Gates, docs, artboards**

Lighthouse URL set gains one PDP per locale; axe gains the picker in all three states plus keyboard-only traversal; visual baselines gain PDP desktop/mobile in all three picker states, the no-photo state and `/ar-XB`; the crawl test is extended; `seo:validate` gains the `products.xml` child and a PDP schema fixture; `docs/runbooks/delivery-calendar.md` is new (how a country's `operations` block is authored, how a holiday is added, how to read a picker state, what a DST failure looks like); `docs/architecture.md` §2/§3, `docs/codebase-map.md`, `messages/*.json` and the artboards of §12 follow.

## 3. Non-goals

- **Basket, add-to-basket, "Continue", checkout, the quote issue, add-on *selection* and the withdrawal-right notice** → spec 010 (`plan/04` §8, §9). Phase 0's PDP has **no purchase affordance at all**; where the artboard draws "Continue" it renders the honest demo sentence instead (§13 Q6, Q7).
- **Reviews, ratings, stars, review counts, "most sent", bestseller badges** → real data only, specs 022/023/027 (`plan/07` §7, `plan/09` Phase 0 AC 6). The section is not rendered at all — not as an empty state, not as "be the first".
- **The delivery-photograph promise** → gated on spec 027 (founder ruling 2026-09-15, spec 004 §14 A15).
- **Partner capacity, blackout dates, city-level availability, the `capacity:{city}:{date}` tag and real-time greying** (`plan/06` §5.2 item 5) → Phase 1/2, specs 016/024/031. The `CapacityProvider` seam spec 005 declared is consumed here in its "unmodelled" form (`null` ≠ `0`) and nothing more.
- **Delivery windows (morning / afternoon / any)** (`plan/04` §7) → Phase 1; they need partner data that does not exist.
- **A live cutoff countdown and relative day labels** → §13 Q4; Phase 1, together with the shorter revalidate window and the scheduled cutoff purge.
- **The currency menu, the `fo_currency` cookie and a currency repaint island** → 008 §13 Q9's ruling holds unchanged on the PDP in Phase 0; the price renders in the locale's default currency.
- **City-scoped PDPs, a `/{locale}/{country}/{product}` flat form, or any second URL for the same product in the same country** → not created, so they cannot leak into a sitemap.
- **The database and migrations** → spec 002 / spec 012. This spec adds no migration and requests three spec amendments instead (§5.1).
- **Editing `CLAUDE.md`, `plan/*` or an accepted ADR.** Two bounded, stated deviations are carried (§12): the config-file publish flags (the 003/004/007/008 precedent) and the single-island amendment to 007 AC-24.

## 4. User stories

- As a **buyer choosing a bouquet for my mother in Warsaw**, the page shows me one price that already includes VAT and delivery, tells me plainly that we are still choosing florists there, and does not offer me a Thursday it cannot honour.
- As the same buyer **after Poland goes live**, I can see every date for the next two weeks, what each one costs, which ones are closed and why ("public holiday in Poland", "Sundays are not delivered"), and that the cutoff is 14:00 **in Warsaw**, not in my own time zone.
- As a **buyer on a slow phone with a script blocker**, the whole page — price, tiers, dates, reasons, totals — is already in the HTML, and choosing a date works with a button.
- As a **screen-reader user**, the date grid is a labelled radio group, every unselectable date states its reason in words, and the total is announced when it changes.
- As a **buyer on `/pl/`**, the date reads "czw., 10 wrz", the plural reads "12 łodyg", the price reads in złoty and no English string appears.
- As **Googlebot**, every PDP is complete server-rendered HTML with one self-canonical, a reciprocal hreflang cluster, a `BreadcrumbList` that matches the visible trail, **no `Offer` for a country I cannot buy from**, and no `?date=` variant claiming to be a separate page.
- As the **founder demoing on 16 October**, Poland's picker shows a real calendar with real holidays and real surcharges and says in one sentence that we are not taking orders yet — and going live is authoring a partner row, not editing a template.
- As the **implementer of spec 010**, the tier, the date, the surcharge and the total are already one view model with one price, so checkout is a form over a value I do not have to re-derive.

## 5. Design

**Rollback of this spec** is `git revert` of its task commits plus setting the `site-links.ts` `product` row back to `published: false` (cards return to tiles) and clearing any `operations` block: no state, no migration, no external resource. Because no PDP URL is announced before the indexing flip (§12), a revert cannot orphan an indexed URL.

Zod schemas, parsed at module load (authored data) or at the route boundary (`plan/12` §2):

- **`ProductParamsSchema`** — locale, country slug, the `product` path segment, product slug. Any failure → `notFound()`. Never a redirect, never a case-fixing rewrite.
- **`ProductSearchParamsSchema`** — `{ tier?: TierKey, date?: IsoDate }`, **strict**. An unknown parameter is dropped and contributes only `indexable: false`; an unknown tier, a malformed date, a date outside the rendered window or a date that is not selectable falls back to the default rendering (never a 404, never an error page — a stale link from a chat message must still show the product).
- **`CountryOperationsSchema`** — spec 007's, reused unchanged: `{ ianaZone, sameDayCutoffLocal: "HH:mm", deliveryDays: Weekday[], sundayDelivery: boolean }`. A partial block is a parse error, so a cutoff cannot be rendered unless every field it depends on was authored.
- **`CountryHolidaySchema`** — `{ iso2, date: IsoDate, nameKey, source }`; dates are authored per year, never derived from "the usual date".
- **`DeliveryDateSchema`** — `{ date, selectable, reasonKey?, surcharge?: Money, occasionKeys: string[] }`; `selectable: false` **requires** a `reasonKey` (the spec 004 `CompanySchema` pattern: a state cannot be set without its explanation).
- **`DeliveryWindowSchema`** — `{ state: "unavailable" | "preview" | "live", timeZone?, cutoffLocal?, dates: DeliveryDate[], noticeKey }`; `state: "unavailable"` **requires** `dates: []`, so an unavailable picker is structurally incapable of listing a day.
- **`ProductViewSchema`** — `{ locale, country, product, h1, description, care, gallery, tiers: TierOption[], selectedTierKey, price: PriceProjection, addons: AddonLine[], delivery: DeliveryWindow, facts, totals: DateTotals, breadcrumb[], related: ProductCardView[], trust: TrustClaim[], indexability }`. The single view model. There is **no** `rating`, `reviewCount`, `badge`, `countdownSeconds`, `relativeDayLabel` or `ctaAddToBasket` field: §8's honesty rules are enforced by the type, not by review.
- **`DateTotalsSchema`** — `Record<TierKey, Record<IsoDate, integer>>` with a size refinement in spec 005 §14 A2's style (**≤ 4 096 B** serialised UTF-8, ≤ 5 tiers × ≤ 21 dates), because this is the table the island reads and the page pays for in bytes.

Behavioural contracts worth pinning:

- `productView()` is the **only** source for the page, the JSON-LD builders and the sitemap row (007's `corridorView()` rule, extended).
- `pickerState()` is a pure function of (`operations` present, `hasActivePartners`) and is the **single** place the three states are decided.
- Every money value comes from `priceProjection()` / `dateSurcharges()`; no component receives a number and no component constructs an `Intl` object (`fo/no-adhoc-intl`, `fo/no-float-money`).
- All date arithmetic happens in `modules/geo/delivery` in the destination zone; **no component computes a date**, and no component compares a date to `Date.now()`.
- A block whose data is missing renders nothing (004 §5.3, 007 §5.2, 008 §5.2).

### 5.4 Rendering & caching (SSG/ISR/SSR, tags invalidated, per plan/01 §3)

- **Server components everywhere except one island.** The gallery, tiers, prices, date grid, reasons, surcharges, facts, breadcrumb and related products all render with JavaScript disabled, and the page is complete without the island (AC-13).
- **The one island**, `DateAndTierEnhancer`: **≤2 048 B Brotli**, counted inside the page's 131 072 B budget, with a test that asserts it performs **no** `fetch`/`XHR`/`WebSocket`/dynamic import and reads only from the embedded `DateTotals` table and the form's own DOM. It never removes the form's submit button and never changes the URL's meaning; the enhanced and unenhanced paths produce byte-identical totals. This is the amendment to 007 AC-24 recorded in §5.1.
- **The bare URL is ISR**: `revalidate` **3600** (`plan/01` §3's "product 1 h + tag `product:{id}`"), tags `product:{sku}`, `catalog:{iso2}`, `catalog:{iso2}:{locale}` and `sitemap` through `src/lib/cache.ts` as the only invalidation seam. A **live** PDP drops to `revalidate` **300** and adds the `cutoff:{iso2}` tag (§2).
- `generateStaticParams` prebuilds the top 24 products per (locale, published country); `dynamicParams = true`; `productPageExists()` enforces the 404 (§2, AC-3). This is the only route in the site with dynamic params, and the reason is `plan/01` §3's build-time budget, stated.
- **Parameterised requests** (`?tier=`, `?date=`) follow 008 §5.4's resolution unchanged: rendered per request and cached at the edge by full URL (`public, s-maxage=3600, stale-while-revalidate=86400`) with every data read wrapped in the same tag-keyed cache, under ADR-0018's single Railway replica behind Cloudflare.
- **No response varies by request header and no cached response sets or reads a cookie**: no `Vary`, no `Set-Cookie`, byte-identical bodies with and without `fo_locale`, `fo_currency` and `fo_consent` (`plan/02` §14; 001 AC-15, 003 AC-12, 004 §5.4, 007 AC-23, 008 AC-22).
- **Images**: exactly one `priority` LCP candidate — the gallery hero — with its preload built from the same manifest lookup as its `srcset`; everything else `loading="lazy" decoding="async"`; initial image transfer ≤204 800 B (006's budget), which the no-photo majority makes comfortable.
- **Budgets**: ≤131 072 B Brotli first-load **including the island**, no route regressing >5 KB against the committed baseline (004 §14 A1); the embedded `DateTotals` table ≤4 096 B serialised.

## 6. SEO considerations (mandatory)

- **Indexability — one engine, one descriptor.** Through 007's `indexability()`; this spec writes no `noindex` branch (asserted by a grep for robots-directive literals outside `modules/seo`). `index,follow` iff the page exists **and** `corridorState(iso2) === 'live'` **and** `isProductIndexable(product, locale, iso2)` (005 §6: active price, non-null **reviewed** description in that locale) **and** `isLocaleIndexable(locale)` **and** `isIndexingEnvironment()`. In Phase 0 every PDP in every locale is `noindex,follow` and in no sitemap (ADR-0007), because no country has an active partner. A table-driven test covers every combination.
- **Canonical.** Self-canonical per (locale, country, product): absolute, lowercase, no trailing slash, parameter-free. No cross-locale canonical is expressible (003 §6). `?tier=` and `?date=` canonical to the bare URL and are `noindex,follow`.
- **Canonical policy across countries — the real duplication risk** (`plan/02` §4.2). The same bouquet exists at up to seven country URLs per locale with the same photograph and description. We take `plan/02` §4.2's own answer and make each mitigation checkable: (a) products are indexable **only in live countries**, so N is 1 for a long time and the 2 352-URL Phase 0 set is entirely `noindex`; (b) every PDP carries a **server-rendered country block that genuinely differs** — the destination's currency and VAT wording, its price column, its delivery calendar with its own holidays, its cutoff in its own zone, its occasion markers and its corridor link — which is exactly the "country block" §4.2 names, and which the picker makes substantive rather than decorative; (c) the money pages are the corridor and category pages, so PDP consolidation by Google costs little; (d) GSC's "Duplicate, Google chose different canonical" above **10% of PDPs** is the monitored trigger to reconsider country-scoped PDP indexing (§11). **No cross-country canonical is emitted** — it would be a lie about which page serves which destination, and `plan/02` §4.2 explicitly keeps one canonical per (locale, country, product).
- **hreflang.** 007's `alternatesFor()` in `<head>` and in the sitemap, reciprocal, complete over indexable locales, `x-default → /en`, `en-150` never emitted, and no alternate for a locale in which the product has no slug or no reviewed description — which in Phase 0 is `de` and `pl` for every product (005 §7: the dataset ships `en` only), so a PDP's cluster is `en` + `en-gb` until the catalogue is translated.
- **URL pattern and localised slugs.** `plan/02` §4.1's row verbatim. Slugs are ASCII, lowercase, hyphenated, unique per locale per namespace, human-authored and gated by `seed:check`; §13 Q1 rules how a product slug behaves in a locale with no product translation. No price, no date, no tier and no session identifier ever appears in a path.
- **Schema types.** `BreadcrumbList` only, in Phase 0. `Product` + one `Offer` is built and tested here and gated (§2, §13 Q8); `AggregateOffer`, `aggregateRating`, `review`, `Event`, `LocalBusiness` and `FloristShop` are forbidden and asserted absent on every PDP in every locale. When the `Offer` does emit, `price` is the visible all-in amount to the cent, `priceCurrency` is the currency in the HTML, `eligibleRegion` is the destination ISO, `shippingRate` is 0 because delivery is in the price, `deliveryTime.cutoffTime` is the rendered cutoff, and `hasMerchantReturnPolicy` is `MerchantReturnNotPermitted` so the structured data agrees with the perishability disclosure (005 §6, `plan/02` §9).
- **Sitemap membership.** `/sitemaps/{loc}/products.xml` with 007's contract (valid XML, real `<lastmod>` = max `updatedAt` across product, translation, media and price data — never "now"; full `xhtml:link` set; ≤10 000 URLs; ≤10 MB; `Cache-Control: public, max-age=3600`), listed in the per-locale index only when non-empty. Nothing `noindex` can appear, because membership and the robots directive come from one predicate. In Phase 0 the child is empty and therefore absent.
- **Internal links.** In: the country shop root, the country category, the country occasion, related products on sibling PDPs, and the corridor page once the shop is live. Out: breadcrumb, category, shop root, corridor, ≤6 related products. Crawl depth from any locale home to any PDP ≤4 (`plan/02` §11). Zero links to a non-200 URL.
- **Thin content and duplication.** (a) *Country duplication* — above. (b) *Parameter duplication* — `?tier=`/`?date=` are `noindex` + canonicalised, never in a sitemap, never a crawlable `<a>` (they are produced by a form submission), and `robots.txt` gains their parameter shapes to the existing `plan/02` §7 list without blocking them, so their `noindex` can be seen. (c) *Description thinness* — a product with no description in a locale is **non-indexable by construction** (005 §6) rather than filled with generated copy; the description is 60–90 authored words ending in the substitution sentence (spec 006). (d) *Machine-translated catalogue copy* — structurally impossible: unreviewed translations fail `isProductIndexable` and `isLocaleIndexable('de'|'pl')` is false.
- **CWV budget impact.** The LCP element is the gallery hero (preloaded, sized from 006's manifest) on the 12 imaged products and server-rendered text on the other 72. One island of ≤2 048 B is the only script delta. Budgets unchanged: performance/accessibility/best-practices ≥0.95, LCP <2.0 s, CLS <0.05, script ≤131 072 B Brotli, image transfer ≤204 800 B. `categories:seo` ≥0.95 is asserted only on indexable URLs (007 AC-25's rule), which in Phase 0 is none of these, with the reason recorded in `lighthouserc.json`.
- **Crawl efficiency.** No calendar URLs (the date is a query parameter with a strict schema and a bounded window, never a path), no infinite parameter space, no redirect chains, no soft-404, and no URL a crawler can reach that `indexability()` has not ruled on.

## 7. i18n considerations (mandatory)

- **New message keys / namespaces.** `product.*` (section headings, the destination line, the "what the price does not include" sentence, the demo sentence that replaces the CTA, the related-products heading), `delivery.*` (the picker legend, the three state notices, the cutoff line with `{time}` and `{zone}` as parameters, the "more dates" control, the reason strings — `closedSunday`, `publicHoliday`, `pastCutoff`, `notDeliveryDay`, `beforeEarliest`), `surcharge.*` (reusing spec 005's `catalog.surcharge.*` keys, not duplicating them), plus `a11y.*` additions (date group label, tier group label, the live-region label). All ICU, namespaced, typed, zero literals. `en-gb` overrides only where British wording differs; `de`/`pl` chrome re-drafted by `pnpm i18n:draft` and therefore unreviewed, which correctly keeps `isLocaleIndexable('de'|'pl')` false.
- **Dates and times are the acid test here.** Every date goes through `formatDate` with **weekday and month name** ("Thu 10 Sep", "Do., 10. Sep.", "czw., 10 wrz" — `plan/03` §7's rule against ambiguous numeric dates); every time goes through `formatTimeInZone` with an **explicit IANA zone that is named in the copy** ("14:00 Warsaw time" — `plan/03` §7, §10; there is no "local time" overload, and the PDP is the second surface that rule was written for). The date grid uses the locale's **week start** (Monday for all four launch locales, `plan/03` §7) and `Intl` is constructed only in `format.ts`. **No date literal exists in any component or message string** — asserted by repo grep (007 AC-22, extended).

- **Currency.** The locale's default (005 §7; the 2026-09-16 ruling), because cached HTML must be byte-identical for every visitor. The destination currency appears only in the stale-FX fallback, with the page stating which currency it quotes. The `fo_currency` cookie is not read (008 §13 Q9).
- **Product names are not translated** (`plan/10` §2.2, 005 §7): "Amber Hour" stays, the descriptor localises — which is the basis of §13 Q1's slug rule.
- **RTL.** No physical CSS; the date grid, tier row and summary are logical-property layouts; the name/price pair and every date chip's label/amount pair are wrapped in `<bdi>`; `/ar-XB` visual baselines gain the PDP.
- **Address/phone formats.** Not rendered here (no address form until 010). Unchanged.
- **Translation review plan and `noindex` gating.** Per-product: the translation's `reviewed` flag and a non-null description (005 §6). Per-locale: `isLocaleIndexable()`. Both feed the one `indexability()` decision, so a product whose `de` copy is drafted but unreviewed has a page that renders and is `noindex,follow` until a native reviewer signs it. Delivery, cutoff and holiday vocabulary goes into `content/i18n/glossary.{locale}.md` in the same PR — the reviewers translate legal-adjacent phrasing against it.

## 8. Compliance considerations (mandatory)

- **Data flows added → RoPA: none.** The PDP renders public catalogue and calendar content, accepts no personal data, sets no cookie, reads no cookie and adds no processor. The only inputs are a tier key and a date in a query string; neither is personal data, neither identifies anyone, and no address, postcode or recipient field exists on this page (that is 010's, with its own RoPA row). `docs/compliance/ropa.md` gains an explicit "no new processing" note for 009, as 006, 007 and 008 did.
- **Price display (`plan/07` §4, `CLAUDE.md`) — the core.** One all-in amount from `priceProjection()`: integer minor units, VAT included, delivery included, equal to what checkout will charge, rendered by `formatMoney` with the authored per-locale VAT-and-delivery formula. Every date's surcharge is printed **on the chip before selection**, with its exact amount, so nothing is added after a choice — which is precisely the drip-pricing pattern the UK DMCC and the Price Indication Directive prohibit and which `docs/design/benchmarks/01-product-page.md` §3.3 catalogues at three competitors. No "was/now", no strike-through, no reference price, no urgency claim, no countdown (§13 Q4 removes the only countdown the design carried, and `plan/07` §4 permits one only from real cutoff data in any case). The one thing excluded from the price — the vase — is **named in words** rather than left for the photograph to imply.
- **No delivery promise without operational data — the rule this page exists to keep.** `pickerState()` is the gate: with no `operations` block the picker states no date, no cutoff and no calendar; with an `operations` block but no active partner it states a calendar **explicitly labelled as not yet orderable**, with every date unselectable; only an active partner unlocks a selectable date. There is no code path by which a country without a partner renders a selectable date, and AC-8 asserts it across all seven destinations in all four locales. Spec 006 §14 A4's line is drawn precisely: **authored copy** (descriptions, intros, SEO fields) may state no lead time, cutoff or "same/next day" claim at all, and the only permitted form in copy is a pointer to this block; **this block** is computed from authored operational data and renders only what that data supports.
- **No purchase affordance, therefore no pre-contractual offer.** No add-to-basket, no "Continue", no add-on checkbox, no pre-ticked anything (CRD Art. 22 is unbreakable because there is nothing to tick), no contract formed. The demo sentence says plainly that ordering is not open. The **withdrawal-right notice for perishables** (CRD Art. 16(d) / UK CCRs reg. 28(1)(c)) is a legal disclosure, is lawyer-gated (`plan/13` B4) and belongs to spec 010 and the legal page set — it is **not** rendered here in Phase 0 (§13 Q7), and the current artboard's version of it is removed in §12.
- **Reviews and trust (`plan/07` §7, `plan/09` Phase 0 AC 6).** Zero reviews, ratings, stars, review counts, testimonials, Trustpilot marks, florist names, florist photos, florist counts, delivery photographs and "X sold" counters on the page or in its JSON-LD — asserted in all four locales and unexpressible in `ProductViewSchema`. The delivery-photograph promise is gated on spec 027 and the florist claim on an active partner (§2).
- **Ranking transparency.** The related-products row is spec 005's deterministic founder-set order, labelled for what it is, never "bestsellers" or "recommended for you" (008 §8's rule, inherited). Nothing on the page depends on anything about the visitor.
- **Geo-blocking (EU 2018/302, ADR-0006).** Every PDP is reachable from anywhere, identical for everyone, never redirected and never varied by IP or buyer country. Price and calendar are keyed on the **destination** only; spec 005's signature test already fails on a buyer/IP/geo parameter (005 AC-18) and this spec adds none. A destination we do not serve gets an honest "not yet", which Art. 3 permits.
- **Accessibility (EAA / WCAG 2.1 AA).** Radio groups with `<fieldset>`/`<legend>`; an unselectable date carries both the `disabled` attribute and a visible worded reason (never colour or opacity alone, WCAG 1.4.1); the total is announced on a polite live region when it changes; keyboard-only operation of tier, date, "more dates" and the form submit; visible focus on every control; 200% reflow at 390 px; per-locale alt text with no `<img>` at all where no alt exists (006 AC-18); axe zero serious/critical with no exception list on all three picker states in all four locales, plus a manual VoiceOver pass on the picker recorded in the runbook.
- **Logs / PII.** No new request-scoped field. The tier key and the date may appear in a log line and in an analytics URL; neither can identify a person, and no recipient, address or name exists on this page. Structured data contains no personal data and no fabricated entity.
- **Security.** No new dependency, no new origin, no inline script. The island is a normal bundled module under ADR-0016's existing `script-src` policy — **no inline script and no `unsafe-inline` is introduced**, which is the specific risk a "small enhancement" usually smuggles in. `img-src` already allows the static `/media/` variants (006).

## 9. Acceptance criteria

**Existence, routing, prebuild**

- **AC-1** For each launch locale, `/{locale}/{country}/{product}/{slug}` returns 200 for exactly the (locale, country, product) triples the §2 existence rule defines, and **404** for every other: unknown slug, product with no active price in that country, unpublished country, another locale's `product` segment, uppercase variant, trailing slash, unknown locale. No redirect, no soft-404, no substitute page.
- **AC-2** `pnpm seed:check` fails, naming file, entity and rule, on each of: a published country with no holiday rows for a year inside the rendered window; a holiday row with no `nameKey`; an occasion row whose `rule_type` the evaluator cannot date; a product slug missing where §13 Q1's rule requires one. It passes on the committed corpus.
- **AC-3** `generateStaticParams` emits the top 24 products per (locale, published country) by spec 005's deterministic ordering, `dynamicParams === true`, and the union of prebuilt and on-demand 200s equals the existence set exactly; a URL outside it 404s on **first** request; the per-locale counts print to the CI step summary.
- **AC-4** `productPageExists()` is the single existence answer: the route, `generateStaticParams`, the sitemap builder, 008's card-link renderer and the e2e crawl all call it, and a fixture change moves all five together with no file outside `src/modules/catalog` participating.

**The date picker and the calendar engine**

- **AC-5** `deliveryWindow()` computes every date in the **destination's IANA zone**: the grid, the cutoff comparison and "the earliest possible date" are identical whatever the server's own zone, asserted with `TZ=UTC`, `TZ=America/New_York` and `TZ=Pacific/Auckland`.
- **AC-6** DST correctness: across the last Sundays of March and October in 2026 and 2027, for `Europe/Warsaw` and `Europe/London`, the grid contains each calendar day exactly once, no day is skipped or duplicated, and a cutoff evaluated at 00:30, 02:30 and 14:00 local on the transition day returns the authored wall-clock time and not an hour-shifted one.
- **AC-7** A date is unselectable for exactly one of the enumerated reasons — before earliest, past cutoff, not a delivery weekday, Sunday where `sundayDelivery` is false, public holiday in the destination — and `DeliveryDateSchema` rejects `selectable: false` without a `reasonKey`; the reason is rendered as **visible words** beside the date and is present in the accessible name, not conveyed by colour or opacity alone.
- **AC-8** Honesty gate, all seven destinations × four locales: with no `operations` block the picker renders **zero dates**, no cutoff and the `unavailable` notice; with an `operations` block and `hasActivePartners === false` it renders the full grid with **every date unselectable** and the `preview` notice; with a fixture `ActivePartnersProvider` returning true the **same route** renders selectable dates, the cutoff line and the preselected earliest date — with **zero template edits** between the three.
- **AC-9** Every selectable date prints its own money before selection: "included" where there is no surcharge, the exact amount from `dateSurcharges()` where there is; selecting a surcharged date changes the single all-in total and no second charge appears anywhere on the page.
- **AC-10** No relative day label ("today", "tomorrow", "in N hours") and no countdown appears in any rendered PDP in any locale, and no such key exists in any message file (repo grep); the cutoff is rendered as an absolute local time with its zone named.
- **AC-11** Occasion-marked dates equal `occasionDate`/`upcomingOccasions` for that country and year, formatted by `formatDate`; no date literal exists in any component or message string (repo grep); a `rule_type: none` occasion never marks a date.
- **AC-12** `occasionDate(rule, year)` supports **seven** rule types; `orthodox_easter_offset` is correct for RO for 2026–2030 against a fixture verified against the Romanian Orthodox Church calendar; `modules/geo/occasions` keeps **100% branch coverage**; the Andrzejki and Wigilia PL rows date correctly; Polish name days remain undated.

**The no-JS contract and the island**

- **AC-13** With JavaScript disabled, the whole page renders and the form works: choosing a tier or a date and submitting reloads to the parameterised URL and the server-rendered total equals, **byte for byte**, the total the island produces for the same selection — asserted over every tier × every date of a fixture product.
- **AC-14** The island is ≤**2 048 B** Brotli, is the only client island the PDP adds, performs **no** network access of any kind (`fetch`, `XHR`, `WebSocket`, `EventSource`, dynamic import — asserted by a route-level network-request assertion and a static check), introduces no inline script, and first-load script on a PDP is ≤131 072 B Brotli with no route regressing >5 KB against the committed baseline.

## 13. Open questions

Each carries the default this spec is written against; the spec stays `draft` until the founder rules.

- **Q1 — What is a product's slug in a locale with no product translation?** The Phase 0 dataset ships `en` only (005 §7) and product **names are deliberately untranslated** ("Amber Hour" stays; the descriptor localises — `plan/10` §2.2). `plan/02` §4.1's example nevertheless shows a localised German slug. **Default: one authored ASCII slug per product, shared by all four locales** (`/de/polen/produkt/amber-hour`), with an optional per-locale override honoured the moment a translation authors one — so PDPs exist in all four locales for the demo and a future localised slug is additive. Alternative: require a per-locale slug, which is tidier but leaves `/de/` and `/pl/` with **no product pages at all** on 16 October. The rule differs from the category/occasion slugs of 008 §13 Q10 for a reason worth stating: a category name is a common noun that must be translated; a bouquet name is a proper noun that must not.
- **Q2 — What does the date picker do in Phase 0: hidden, empty, or a labelled preview?** **Default: the three data-driven states of §2** — `unavailable` (no `operations` block: no dates at all, one honest sentence) everywhere on day one, and `preview` (the full computed calendar with **every date unselectable** under the heading "This is how delivery dates will work in Poland. We are not taking orders yet") for any country whose `operations` block is authored. This shows the demo a real calendar without promising anything, keeps the engine visually testable, and never renders a selectable date without a partner. Alternative A: `unavailable` everywhere until a partner exists — safest, and it means the 16 October demo's PDP has an empty box where its most important element goes. Alternative B: hide the picker entirely in Phase 0 — rejected: an invisible component is an untested component, and the block order would change when it appears.
- **Q3 — What are Poland's operational values, and what is the default cutoff per country?** The chrome copy already says "Order by 14:00 in Warsaw". **Default: PL = `{ ianaZone: "Europe/Warsaw", sameDayCutoffLocal: "14:00", deliveryDays: Mon–Sat, sundayDelivery: false }`, authored by the founder, and no other country gets an `operations` block until it has a florist.** There is deliberately **no global default cutoff**: a missing block yields the `unavailable` state, never an assumed 14:00, because an assumed cutoff is exactly the kind of plausible invention this project's gates exist to prevent. Alternative: author plausible blocks for all seven so the demo shows seven calendars — rejected unless you rule otherwise, because six of them would be fiction.
- **Q4 — Do we drop the countdown and the "today"/"tomorrow" labels?** `plan/04` §5/§7 and the current artboard both carry them; the benchmark study makes the cutoff one of the two things we take from the field. **Default: yes, drop both from cached HTML** and render an absolute cutoff ("Order by 14:00 in Warsaw — the recipient's time, not yours") and absolute dates. A countdown on a page cached for an hour is wrong within a minute, and a cached "Today" is wrong after destination-midnight; both would be *false statements rendered by us*, which is a worse failure than a less urgent page. They return in Phase 1 with the shorter revalidate window and the scheduled cutoff purge. Alternative: render them client-side in the island — rejected here because it doubles the island's size and its risk, and because the no-JS page would then say something different from the JS page.
- **Q5 — Is one client island acceptable on an indexable page, and at what budget?** **Default: yes, exactly one, ≤2 048 B Brotli, no network access of any kind, PDP only**, recorded as an amendment to spec 007 AC-24 (§5.1). The page is complete and correct without it (AC-13), so the island is an ergonomics improvement over a working form, not a dependency. Alternative: zero islands — every tier or date change is a full page reload, which is honest and slow, and is one fewer thing to review. Say which; the whole of task 9 hangs on it.
- **Q6 — Do add-ons get checkboxes in Phase 0?** **Default: no — a priced, read-only list.** There is no basket to add one to, and a checkbox that changes a total the buyer cannot act on is a worse experience than a clear price list. The inputs, and the recomputation with them, are spec 010's. Alternative: checkboxes that update the displayed total — one more parameter, one more island behaviour, and a "total" that nothing can charge.
- **Q7 — Where does the withdrawal-right notice live, and what else does the trust block claim?** **Default: not on the Phase 0 PDP.** The perishable-goods withdrawal disclosure is a legal statement, is lawyer-gated (`plan/13` B4) and belongs to spec 010 and the legal page set; the delivery-photograph promise is gated on spec 027 (founder ruling 2026-09-15); the "our florist in the recipient's town" claim is gated on an active partner. What renders in Phase 0 is the substitution sentence and the honest demo sentence — and the artboard loses the other three. Alternative: keep an informational perishability sentence with no legal effect — cheap, but it is the kind of sentence a regulator reads as a disclosure, so it should go through the same lawyer pass as the rest.
