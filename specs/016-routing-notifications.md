## 1. Problem

A paid order today goes nowhere after the money is secured. Spec 013 (draft) takes the payment and writes the outbox rows; spec 010 owns the engine that moves the order; spec 011 gives a florist an inbox where they can accept, decline, deliver and add the photo. Nothing picks the florist, nothing re-offers when one declines or does not answer, nothing tells the florist an order is waiting, nothing tells the buyer what is happening, and nobody notices when no florist takes an order. `plan/09` Phase 1 AC 1 asks for one real order "routed automatically, accepted by a florist via magic link, delivered, photo uploaded, buyer notified … zero manual DB edits", and AC 7 asks for alerts on SLA cascade exhaustion, webhook failure and "`paid` without `routed`" for more than 5 minutes. Without this spec the product, trust plus routing (`plan/00` §1), has no routing.

`plan/09` reserved two numbers: `016` (routing job, assignment SLA, timeouts, no-partner path) and `017` (notifications: Resend set, React Email, WhatsApp procedure, vendor magic-link flows). They are one flow (an offer is a notification, an exhaustion is an alert), so they are one spec. Number `017` is folded in here and stays unused; references to "spec 017" in specs 010, 011, 012 and ADR-0019 resolve to this file. ADR-0019 replaced the "vendor magic-link flows" with the one florist sign-in, so the florist half of `017` is now "order emails that sign the florist in and open the order in one tap" (spec 011 §12, ADR-0019 consequences).

## 2. Scope

Each bullet is testable; §9 names the AC.

**Routing (`src/modules/orders/routing/`; `plan/06` §5.2)**
- Routing starts when a `live` or `test` order reaches **payment secured**: `order.authorised` (row 1 of spec 002 A6.3, to `authorised`) or `order.captured` from `placed` (row 2, to `paid_unrouted`). This is A6.1's reading of `plan/01` §8's "paid", and the spec 013 draft's Q1. `demo` orders keep spec 010's `demoRoute` and spec 011's demo effect; this spec never routes them.
- A pure, unit-tested ranking picks one florist over **coverage**, **catalogue**, **blackout**, **capacity** on the delivery date, **sign-in reachability**, then rating, acceptance rate, payout and round-robin (§5.2).
- Each offer has an **SLA** (`plan/06` §5.2 rule 3): 60 minutes 08:00–20:00 destination local time, 30 minutes for same-day orders; orders secured at night are offered at 07:30 with the SLA ending 09:00.
- A reminder at half the SLA; on decline or timeout the next candidate is offered (the **cascade**), up to 5 offers or the routing deadline.
- **No-partner path**: exhaustion moves the order to `no_partner_available` and alerts the founder; the founder reroutes through spec 020's admin action (which calls this spec's `manualReroute`), or, after a grace window, the order is cancelled with `order.cancelled` and spec 013's cancel handler voids or refunds it.
- **After capture**: `order.in_production` is written at once, as spec 011's demo effect already does, so the florist's "Out for delivery" action (row 19) becomes available.
- **Withdrawal**: when an order leaves fulfilment before delivery (cancelled, refused capture, full refund, chargeback), the open or accepted assignment is withdrawn and the florist is told to stop.
- **Checkout coverage predicate** `canServe(...)`, the postcode coverage check spec 010 §3 assigned to this spec, for spec 010's checkout to call (wiring by a spec 010 amendment, §12, §13 Q13).

**Notifications (`src/modules/notifications/`, `emails/`; ADR-0013, `plan/11` §5)**
- An outbox handler for the `notifications` target: picks templates from `(event, from_status, mode)`, resolves addresses at send time, renders React Email in the audience's language, sends through spec 012's one `Mailer`, and records each send in `notification_delivery`.
- The Phase 1 set (§5.2 table): buyer messages (order received, florist has it and the contract confirmation, on its way, delivered with photo, cancelled, refund, payment refused after acceptance), florist messages (offer, reminder, order confirmed, withdrawn, photo reminder), the founder's no-partner alert and WhatsApp copies.
- **Every florist email signs the florist in and opens the order in one tap** (ADR-0019; spec 011 §12), through spec 012's sign-in core.
- The **Phase 1 WhatsApp procedure**: the founder receives a ready-to-paste message for each florist who chose WhatsApp; email always goes in parallel.
- **Resend webhooks**: signature-verified, stored before processing, idempotent, order-independent, with contract tests (`plan/09` AC 3).

**Alerts (`plan/09` AC 7, this spec's share)**
- Cascade exhausted (`order.no_partner_available`); an offer past its SLA with no timeout processed; a Resend webhook row dead; a florist email bounced. The "secured but not routed for 5 minutes" check and the Stripe webhook alerts are the spec 013 draft's (`sla.watch`, §11); this spec supplies the expected first-offer time that check needs (§5.2). Ownership against spec 012 §11's pointer to spec 025 is §13 Q10.

## 4. User stories

- As a **buyer**, I get an email when my order is in, another when a florist near the recipient has taken it (and I have been charged), one when it is on its way and one with the photo when it has arrived.
- As a **buyer whose order no florist could take**, I am told promptly that I have not been charged (or that my refund is on its way), so I can still send something else in time.
- As a **florist**, I get a short email (and, if I chose it, a WhatsApp message from the founder) with the product, date, town, postcode and what I receive; one tap opens the order already signed in, and I accept or decline there.
- As a **florist who accepted**, I am told the moment the order is confirmed, and told at once to stop if it is cancelled before delivery.
- As the **founder**, I am alerted when no florist takes an order, when an offer is stuck past its time, or when Resend webhooks fail, and I can reroute or cancel from admin without a database edit.
- As a **recipient**, my address and phone never appear in an email or a WhatsApp message.

### 5.2 Jobs, commands, contracts

**Contracts consumed** (named so their owners are written to match):
- `orderService.transition(orderId, event, actor, payload)` and `appendEvent(...)` — spec 010, with its A1 guards (`allowed_actors`, the transaction-local event setting, `ORDER_EVENT_NEEDS_TRANSITION`). Actors follow spec 010's `ActorSchema`: this spec's are `system:order.route`, `system:assignment.timeout`, `system:routing.no_partner_expiry`, `system:fulfilment.start`; spec 020's admin actions pass `admin:{uuid}`.
- `outboxTargets(event, mode)` — spec 010; this spec fills the `routing` and `notifications` targets for the events in the tables below. The dispatcher, its backoff and its `dead` state are the spec 013 draft's; this spec adds no retry policy of its own.
- `AcceptedOrderEffect.afterDecline(orderId)` — spec 011's seam; this spec registers the effect for `test` and `live` orders.
- `Mailer.send(MailMessage)` and the sign-in core's link minting — spec 012 (two additive requests in §12).
- `order.cancelled` with payload `reason` including `no_partner`, and the cancel handler that voids or refunds — spec 013 draft.

**Routing functions**
- `eligibleCandidates(order, partners, now)` — pure. Eligible when: the partner's status matches the order's mode (`live` → `active`, `test` → `demo`; spec 010's trigger enforces the same pair); a `partner_coverage` row matches the order's postcode zone or city; `partner_catalog_mapping.can_fulfil` is true for every product line and tier; no `partner_blackout` on the delivery date; accepted plus open offers on that date are below `min(fulfillment_partner.capacity_per_day, partner_coverage.capacity_per_day)`; it has not been offered this order; and it has at least one `partner_member` whose sign-in spec 011's `signInPolicy(environment)` allows (a florist who cannot sign in cannot act on the offer).
- `rankCandidates(candidates)` — pure, deterministic. Key in order: inside the best-rating band (rating ≥ 95 % of the best candidate's, `plan/06` §5.2 rule 2c) before outside it, then rating descending; acceptance rate descending; payout for this order ascending; last offer time ascending (round-robin); partner id. A null rating counts as 4.50 and fewer than 5 offers in 90 days as 100 % acceptance (§13 Q1).
- `offerWindow(now, deliveryDate, zone)` — pure, in the destination's IANA zone with spec 009's zone helpers. Same-day: offer now, SLA 30 min. 08:00–20:00: offer now, SLA 60 min. 07:30–08:00: offer now, SLA to 09:00. 20:00–07:30: offer at the next 07:30, SLA to 09:00. The SLA never passes the **routing deadline**: the delivery date at the country's same-day cutoff plus 2 hours (§13 Q2). Absolute instants are stored; DST is the zone's job, never added hours.
- `expectedFirstOfferAt(order)` — `offerWindow(...)`'s offer time from the moment the payment was secured; exported for spec 013's unrouted check so a night-deferred order does not alert at 23:00 (§12).
- `canServe({ countryIso2, postcode, cityId, deliveryDate, lines, mode })` → `{ ok: true } | { ok: false, reason: 'no_coverage' | 'no_capacity' }` — the same rules as `eligibleCandidates` minus "already offered", read under the system context on `no-store` routes only; never called while rendering a cached page.

**Jobs** (pg-boss on the Railway worker, ADR-0018; payloads are zod schemas; `order.route` is a job name, not an event):
- `order.route` (`{ orderId }`, `singletonKey = orderId`): enqueued by the `routing` outbox handler on payment secured, by `afterDecline`, and by `assignment.timeout`. In one transaction: lock the order and the chosen partner row `FOR UPDATE` (two routes cannot double-book capacity); pick the top candidate; insert `order_assignment` (`attempt` + 1, `offered_at`, `sla_expires_at`); write the events of the table above; schedule `assignment.remind` at half the SLA and `assignment.timeout` at `sla_expires_at` (both keyed by assignment id). A deferred offer reschedules the job with `startAfter` and writes nothing else. No candidate, 5 attempts made, or the deadline passed: `order.no_partner_available` and schedule `order.no_partner_expire`.
- `assignment.remind`: if still unanswered and not withdrawn, send V2. Otherwise nothing.
- `assignment.timeout`: if still unanswered, set `response = 'timeout'`, write `assignment.timed_out`, send V4 to that florist, enqueue `order.route`. An answered or withdrawn assignment makes it a no-op. Accept and timeout racing on one assignment: both lock the assignment row; the first wins, the second finds it answered.
- `order.no_partner_expire`: at `min(exhausted_at + 2 h, routing deadline)`; if the order is still `no_partner_available`, write `order.cancelled` (`reason: no_partner`). Spec 013's cancel handler voids or refunds; B5 goes to the buyer. If the order has moved on (rerouted, or cancelled by the buyer), nothing.
- `routing.sla_watch` (added to spec 013's `sla.watch` if it exists, else its own minute job): an assignment unanswered 5 minutes past `sla_expires_at` raises `alert=routing.sla_overdue` (the timeout job did not run).
- `assignment.photo_remind`: scheduled on `order.delivered`, fires 1 h later; sends V5 if the order is still `delivered`.

**The `routing` outbox handler** (idempotent on the outbox row):
- `order.authorised`; `order.captured` from `placed` → enqueue `order.route` (or, with `routing.auto` off for the destination, write `order.no_partner_available` at once).
- `order.captured` from `accepted` → write `order.in_production`.
- **Withdrawal**: `order.cancelled`, `order.payment_failed` from `accepted`, `order.refunded_full`, `order.chargeback_opened` and `order.cancelled_refunded`, each when the event's `from_status` is not `delivered`, `photo_uploaded`, `closed`, `disputed` or `resolved`: set `withdrawn_at` and `withdrawn_reason` on the order's open or accepted assignment, and send V4 to its florist. Pending remind, timeout and photo-reminder jobs then find it withdrawn and do nothing.
- `order.delivered` → schedule `assignment.photo_remind`.

**`manualReroute(orderId, partnerId, actor)`** (`src/modules/orders/routing/`, called by spec 020's action panel with `admin:{uuid}`): from `no_partner_available`, writes `order.manual_reroute`, then the first-offer steps to the named partner, which must pass `eligibleCandidates` with "already offered" relaxed (the founder may have phoned a florist who declined earlier). From `routed`, `manual_reroute` or any other state it refuses with `ORDER_TRANSITION_ILLEGAL` and writes nothing. Until spec 020 ships, nothing calls it, and an exhausted order is cancelled at the end of the grace window (§13 Q4).

**Notifications**
- `notificationsFor(event, fromStatus, mode)` — pure; the table below as data. `demo` → nothing. `test` → florist and ops rows only, never a buyer row (spec 010 AC-24; §13 Q11). `live` → every row.
- The `notifications` outbox handler, and the jobs above for V2 and V5: for each row, resolve the address at send time (buyer → `order.buyer_snapshot` email, spec 010; florist → `users.email` of each `partner_member` of the assignment's partner; ops → `OPS_ALERT_EMAIL`), render in the audience's locale (buyer → `order.locale_code`; florist → that member's `partner_member.locale_code`; ops → `en`), insert `notification_delivery` as `queued` (the unique key makes a repeat a no-op), call `Mailer.send` with `idempotencyKey = {source_key}:{template_key}:{recipient_ref}` (request on spec 012, §12), and record `provider_message_id` and `sent`. A send error throws, so the dispatcher's retry and `dead` handling apply.
- **One-tap florist link** (ADR-0019; spec 011 §12): each florist email carries a link minted per member through spec 012's core with the callback `{FLORIST_BASE_PATH}/orders/{assignmentId}` stored server-side with the token. The URL is the core's `{base}/sign-in/confirm?t={token}`: no email address and no personal data; its `GET` uses nothing up; the one tap is the confirm step's "Continue"; a member already signed in lands on the order directly; an expired or used token shows the core's expired page with "send me a new link". Tokens keep the core's single use and one hour, so each email (offer, reminder, confirmed, photo reminder) mints a fresh one.
- **WhatsApp copy** (W): for a partner with `notification_channel = 'whatsapp'`, each V1, V2, V4 and V5 also sends the founder an email holding the florist's message, in the locale of the partner's earliest owner member, ready to paste. It carries the inbox address `{FLORIST_BASE_PATH}/orders/{assignmentId}` and **no sign-in token**, so no bearer credential passes through the founder's inbox or Meta.
- **The refund line** (spec 002 A6.4, advisor F4): B6, and any buyer email sent after a `refund` row with `status = 'succeeded'` exists, shows "Refunded {amount} on {date}" (refund minor units and currency through `Intl` in the buyer's locale; the refund's success date). One formatter is shared with spec 018's tracking page; whichever task lands first puts it in `src/modules/orders/` and the other imports it. A `refunded_full` order is never called "cancelled" in an email (D5).
- Feature flag `notifications.email`: off → handler rows wait as `pending` (held, never dropped).

| B5 `cancelled` | `order.cancelled` (any reason) | buyer | by reason: no florist (apology), the buyer's own cancellation, a lapsed hold; "you have not been charged" for a voided hold or "your refund of {amount} is on its way" for a charged payment |
| B6 `refund` | `order.refunded_partial`; `order.refunded_full` (rows 30–32) | buyer | "Refunded {amount} on {date}", method, timing; the order's buyer status beside it (A6.4) |
| B7 `payment-refused` | `order.payment_failed` from `accepted` (row 15, D2) | buyer | we could not take the payment, so the order is cancelled and nothing was charged; how to order again |
| V1 `offer` | `assignment.offered` | florist | product, tier, add-ons, date, window, town and postcode, payout in the florist's currency, answer-by time, one-tap link. **No recipient name, street, phone or card message** |
| V2 `offer-reminder` | `assignment.remind` job | florist | answer-by time, one-tap link |
| V3 `order-confirmed` | `order.captured` from `accepted` | florist | "confirmed, open the order for the delivery details", one-tap link |
| V4 `offer-withdrawn` | `assignment.timed_out` (that florist); the withdrawal events of the routing handler | florist | "this order is no longer yours, please do not make it" |
| V5 `photo-reminder` | `assignment.photo_remind` job | florist | one-tap link |
| A1 `alert-no-partner` | `order.no_partner_available` | ops (email + Sentry `alert=routing.no_partner`) | reference, destination city, date, attempts and decline reasons, link to `/admin/orders/{id}` (spec 012) |
| W `whatsapp-copy` | each V1, V2, V4, V5 for a WhatsApp partner | ops | the florist's message in the florist's language, inbox address, no token |

Subject lines never contain a person's name, an address or a phone number. Open and click tracking are **off** on the Resend domain: click tracking would rewrite the sign-in links through a third party.

**Resend webhooks (`src/app/api/webhooks/resend/route.ts`, thin; logic in the notifications module)**
- Verify the Svix signature (`svix-id`, `svix-timestamp`, `svix-signature`) with `RESEND_WEBHOOK_SECRET`; reject a timestamp more than 5 minutes off with 401, store nothing, log a counter and send a Sentry event fingerprinted `webhook-signature:resend`.
- Store the raw body in `webhook_inbox` (`provider = 'resend'`, `event_id = svix-id`) before anything else; a duplicate `svix-id` answers 200 and does nothing. Answer 200, then process in `webhook.resend.process`.
- Processing updates `notification_delivery` by `provider_message_id` with a precedence order (`queued < sent < delivery_delayed < delivered`; `bounced`, `complained`, `failed` are final), so out-of-order events never move a status backwards. A bounce on a florist address raises `alert=notifications.florist_bounce` (the florist cannot be reached by email). `email.opened` and `email.clicked` are ignored.
- A Resend inbox row that reaches `dead` raises spec 013's `webhook.dead` alert with `provider=resend`.

### 5.3 UI

- **No new page.** Florist screens are spec 011's inbox; admin screens are spec 012's order detail and spec 020's action panel; buyer pages are spec 018's.
- **One additive inbox stage** (request on spec 011, §12): an assignment with `withdrawn_at` set renders "This order is no longer yours. Please do not make it." with no recipient field, in the inbox list's in-progress group until the order's delivery date passes.
- **Email templates** (React Email, `emails/`): one layout (logo, body, footer with trader identity and support contact), the keys of §5.2, HTML plus plain text, `lang` and `dir` per locale, logical spacing only.

Email always reaches the florist in parallel, so a late paste never blocks an offer.
- **Design**: the email layout, each template's frame per audience, and the inbox "withdrawn" stage get artboards in `docs/design/` (`/design`) before `/plan-tasks` (`CLAUDE.md`).

### 5.4 Rendering & caching

No route that renders HTML is added. `/api/webhooks/resend` is dynamic, `POST` only, `Cache-Control: no-store`, under `/api/` (already disallowed in `robots.txt`), and bypasses the Cloudflare cache like spec 013's Stripe endpoint. Emails render on the worker at send time. `canServe` runs only from spec 010's `no-store` checkout actions (`plan/01` §3), so no cached page reads the database and no cache tag changes.

## 8. Compliance considerations (mandatory)

- **Data flows (RoPA, `docs/compliance/ropa.md`)**: (1) **Resend**, already a processor for sign-in (spec 012 adds the row; spec 011 adds two uses). This spec adds three uses: buyer transactional email (buyer email, order reference, recipient name and city in B1, the delivery photo in B4); florist order email (member email, order facts without recipient contact); ops alerts (no personal data). Basis: Art. 6(1)(b) for buyers and florists. Resend's message retention is noted on the row. (2) **WhatsApp (Meta)** through the founder's Business app: the florist's business phone and the minimised order facts, no recipient data. (3) **Delivery photo** copied to Resend as the B4 attachment (stored in R2 private under spec 011; 2-year retention by spec 002's sweep).
- **Lawful basis**: buyer messages, contract; florist messages, contract; recipient name and city to the buyer who typed them, legitimate interest with minimisation (`plan/07` §1.2). No message here is marketing; none carries an unsubscribe link, and none may be added without consent gating (`plan/11` §5.3 template rule).
- **Minimisation**: recipient name, street, phone and card message never appear in an email or WhatsApp message (they are shown only in spec 011's inbox, from acceptance until the photo, and not at all after withdrawal); ops alerts carry ids, city and date only; `notification_delivery` stores no address or subject.
- **Consumer law**: B1 carries the `plan/07` §2.1 items listed in §5.2. B2 is the confirmation on a durable medium (CRD Art. 8(7); UK CCR 2013 reg. 16) and attaches the terms version the buyer accepted; the contract is formed on capture after acceptance (`plan/07` §2.3), which is when B2 is sent. A no-partner order is never charged, or is refunded in full by spec 013's cancel handler (`plan/06` §2.2). B7 tells the buyer of a refused capture (D2). Spec 010's `legalReadiness()` term "the confirmation email is registered" reads this spec's B1 and B2 registration.
- **Price display**: every amount in a buyer email equals the amount authorised, charged or refunded, in that currency, read from the order or the refund row, never recomputed.
- **Accessibility**: emails use semantic headings, a plain-text part, alt text per locale on the photo, sufficient contrast, and links with descriptive text. The inbox "withdrawn" stage meets spec 011's WCAG 2.2 AA rules.
- **Logs and PII**: no address, name, phone, card message, email address, subject line or sign-in token in any log, Sentry event or analytics event. The logger's redaction list gains `svix-signature`; Sentry's `beforeSend` scrubs the webhook body. Decline notes are free text and never logged.
- **Security**: no new bearer-token scheme (ADR-0019); florist links are spec 012's single-use, one-hour tokens; the WhatsApp copy carries no token; the Resend webhook signature and timestamp are checked before the body is trusted.
- **`CLAUDE.md` non-negotiable rules, checked**: status only through `orderService.transition` (every row in §5.2 cites A6.3); no new indexable page; no IP redirect; no literal strings, no physical CSS, `Intl` for formatting; zod at every boundary (job payloads, webhook body, `canServe` input); a versioned migration with its rollback; money in integer minor units with a currency; price shown equals price charged; partner and country go-live stay data flips; no PII in logs or URLs; secrets only in env; design artboards before `/plan-tasks`. No rule is broken; no ADR is needed.

## 9. Acceptance criteria

**Routing**
- **AC-1** For a `live` or `test` order, `order.authorised`, or `order.captured` from `placed`, leads to exactly one `order.route` job run and one first offer, even when the outbox row is handled twice; for a `demo` order no job is enqueued.
- **AC-2** `eligibleCandidates` excludes, each on its own, a partner whose status does not match the order's mode, with no coverage for the order's postcode zone or city, unable to fulfil one product line, with a blackout on the date, at capacity on the date, already offered this order, or with no member `signInPolicy` allows.
- **AC-3** `rankCandidates` orders a fixture of five candidates exactly as §5.2's key says, including the 95 % rating band, the null-rating default of 4.50 and the under-5-offers default of 100 %.
- **AC-4** `offerWindow` returns the offer time and SLA end of §5.2 for same-day, daytime, 07:30–08:00 and night cases in Europe/Warsaw and Europe/London, including the nights of 25 Oct 2026 and 28 Mar 2027, and never an SLA end after the routing deadline.
- **AC-5** A first offer on an `authorised` or `paid_unrouted` order writes, in one transaction, `order.routed` (actor `system:order.route`) and then `assignment.offered`, inserts one `order_assignment` with `attempt = 1`, `offered_at` and `sla_expires_at`, and queues V1 to each member of the partner (and W for a WhatsApp partner).
- **AC-6** A re-offer on a `routed` order writes `assignment.offered` and no `order.routed`, inserts the next `attempt`, and leaves the status `routed`.
- **AC-7** With no answer, V2 is sent at half the SLA; at `sla_expires_at` the assignment gets `response = 'timeout'`, `assignment.timed_out` is written by `system:assignment.timeout`, V4 goes to that florist and the next candidate is offered. A timeout on an answered or withdrawn assignment writes nothing.
- **AC-8** A decline through spec 011's `respondToOffer` on a `test` or `live` order leads to the next offer within one `order.route` run; the declining florist receives no V4.
- **AC-9** Two concurrent routes for orders on the same date cannot take a partner past its capacity (two workers).
- **AC-10** On a `routed` order, no candidate left, 5 offers made, or the deadline passed each lead to `order.no_partner_available` and A1 (an ops email with the admin order link and a Sentry event tagged `alert=routing.no_partner`).
- **AC-11** On an `authorised` or `paid_unrouted` order with no candidate at the first attempt, and on any paid order in a country with `routing.auto` off, the order moves to `no_partner_available` with A1. (This AC depends on the spec 002 amendment of §12; until the founder approves it, the AC is blocked, not waived.)
- **AC-12** At the end of the grace window an order still `no_partner_available` receives one `order.cancelled` with `reason: no_partner` from `system:routing.no_partner_expiry`, and B5; an order rerouted or cancelled first receives nothing.
- **AC-13** `manualReroute` with an admin actor on a `no_partner_available` order writes `order.manual_reroute`, `order.routed` and `assignment.offered` in that order and offers the named partner (allowed even if it declined earlier); on any other status, or for a partner failing another rule, it writes nothing and returns the refusal.
- **AC-14** `order.captured` from `accepted` leads to one `order.in_production` by `system:fulfilment.start`, B2 to the buyer and V3 to the florist's members.
- **AC-15** For each of `order.cancelled`, `order.payment_failed` from `accepted`, `order.refunded_full`, `order.chargeback_opened` and `order.cancelled_refunded` from a state before delivery, the open or accepted assignment gets `withdrawn_at` and the matching `withdrawn_reason`, V4 is sent, the florist's order view renders the withdrawn stage with no recipient field, and later remind, timeout and photo-reminder jobs write nothing; from `delivered` or later, nothing is withdrawn and no V4 is sent.
- **AC-16** An accept and a timeout fired together on one assignment end with exactly one outcome and one event.
- **AC-17** An order `delivered` without a photo sends V5 one hour later; a photo uploaded before then means no V5.

**Notifications**
- **AC-18** `notificationsFor(event, fromStatus, mode)` returns exactly the §5.2 table's rows for `live`, only florist and ops rows for `test`, nothing for `demo`, and nothing for an event the table does not list; `order.captured` from `placed` and from `accepted` select different templates.
- **AC-19** Handling one outbox row twice, or re-running a job after success, calls `Mailer.send` once per `(source_key, template_key, recipient_ref)` with the same idempotency key; a send error leaves the row for the dispatcher to retry.
- **AC-20** The address is resolved at send time; `notification_delivery` has no column holding an address, a name or a subject (schema assertion), and its rows for a fixture order contain none of the fixture's values.
- **AC-21** Every template renders in each of its locales with an HTML and a plain-text part, no missing message key, money and dates through `Intl`, and a visual snapshot per locale.
- **AC-22** V1, V2, V3, V4, V5 and every W copy contain no recipient name, street, phone or card message; no subject line contains a name, address or phone; no W copy contains a sign-in token.
- **AC-23** Each florist email's link contains no email address or other personal data; two `GET`s and a `POST` sign the member in and land on `{FLORIST_BASE_PATH}/orders/{assignmentId}`; a member already signed in lands on that page directly; a used or expired token shows the core's expired page.
- **AC-24** B1 contains each `plan/07` §2.1 item of §5.2's row; B2 attaches the terms PDF of `order.terms_version`.
- **AC-25** B6 shows "Refunded {amount} on {date}" built from the succeeded `refund` row's minor units, currency and date through `Intl` in the buyer's locale, for a partial and a full refund; no email for a `refunded_full` order says "cancelled".
- **AC-26** With `notifications.email` off, rows stay `pending`; when it is turned on they are all sent once.
- **AC-27** `canServe` returns `no_coverage` for a postcode no eligible partner covers, `no_capacity` when every covering partner is full that date, and `ok` otherwise, for a `live` and a `test` fixture.

**Webhooks and alerts**
- **AC-28** The Resend webhook rejects a bad signature or a timestamp more than 5 minutes off with 401 and stores nothing; stores a valid event in `webhook_inbox` before processing; answers a duplicate `svix-id` with 200 and no second processing.
- **AC-29** Resend events applied in any order leave `notification_delivery.status` at the highest-precedence status received; a bounce on a florist address raises `alert=notifications.florist_bounce`.
- **AC-30** A Resend inbox row whose processing exhausts its retries raises `webhook.dead` with `provider=resend`, once.
- **AC-31** An assignment unanswered 5 minutes past `sla_expires_at` (timeout job disabled by fault injection) raises `alert=routing.sla_overdue`; `expectedFirstOfferAt` for an order secured at 23:00 Warsaw time returns 07:30 the next morning.

**Engine discipline and logs**
- **AC-32** Every event this spec writes is one of A6.6's 36 names, by an actor whose class is in the row's `allowed_actors` (spec 010 A1.5); a source scan finds no arrow label (`route`, `accept`, `decline`, `timeout`, `exhausted`, `capture`, `start`, `refund`) passed as an event, and no status write outside `transition`.
- **AC-33** Across the integration suite, no log line or Sentry event contains an email address, a phone, a recipient name, a sign-in token, or a Svix signature.

**End to end**
- **AC-34** In a PR environment (capturing mailer, Stripe test mode from spec 013), a `test` order to Warsaw with two demo partners, where the first florist lets the offer time out and the second opens the order through the one-tap link in the captured email, accepts, marks out for delivery and delivers with a photo, writes exactly this event sequence: `order.placed`, `order.authorised`, `order.routed`, `assignment.offered`, `assignment.timed_out`, `assignment.offered`, `assignment.accepted`, `order.captured`, `order.in_production`, `order.out_for_delivery`, `order.delivered`, `order.photo_uploaded`; the florist emails render in `pl`; no buyer email is captured; zero manual database edits.

## 13. Open questions

Each has a recommended answer the founder can approve with one word.

- **Q1 — How do we rank florists with no history?** At launch none has a rating. **Recommendation: count a missing rating as 4.50 and fewer than 5 offers as 100 % acceptance,** so round-robin shares work fairly among new florists. Approve: "yes".
- **Q2 — Until when on the delivery day do we keep offering, and how long do we wait before cancelling?** **Recommendation: no new offer after the same-day cutoff plus 2 hours (16:00 in Poland), and a 2-hour grace window (never past that deadline) before an untaken order is cancelled and released.** Approve: "yes".
- **Q3 — Should recipient address, phone and card message appear in florist emails?** **Recommendation: no;** only in the inbox after acceptance (spec 011), so nothing personal sits in inboxes or WhatsApp chats. Approve: "yes".
- **Q4 — How do you reroute an order no florist took?** ADR-0019 rules out a separate link scheme, and spec 012 puts reroute and cancel in spec 020's admin panel. **Recommendation: the alert links to the admin order page; the reroute button is spec 020's and calls this spec's command; spec 020's reroute and cancel are part of the set needed before the first real order. Until then an untaken order is cancelled and released automatically at the end of the grace window.** Approve: "yes".
- **Q5 — Is the Phase 1 WhatsApp procedure right?** **Recommendation: yes:** for florists who chose WhatsApp you receive a ready-to-paste message for every offer, reminder, withdrawal and photo reminder, with no sign-in link in it (the florist signs in from the email); florists always get the email too; buyers get email only until spec 028. Start Meta Business Verification once the OÜ exists (`plan/13` B10). Approve: "yes".
- **Q6 — Is it right to leave substitutions, failed deliveries, review requests, payout statements and the 72-hour closing timer out of this spec?** **Recommendation: yes;** they belong to specs 027, 022 and the payouts spec. In Phase 1 a florist with a substitution or failed delivery phones you. Approve: "yes".
- **Q7 — Where does the terms PDF attached to the confirmation come from?** **Recommendation: one static PDF per terms version and variant (EU, UK; per locale), uploaded to R2 when the legal text is final; a missing PDF for a live country's terms version blocks the go-live flip, not this build.** Approve: "yes".
- **Q8 — Does the delivery photo reach the buyer attached or as a link?** **Recommendation: attached, as a 1200 px JPEG,** so it is still there next month; a signed link would expire. Approve: "yes".
- **Q9 — May the order go straight to "no florist available" when no florist covers it at all?** The approved order machine (spec 002 A6) only allows that after at least one offer. **Recommendation: yes; ask for two more rows in spec 002 (`authorised` and `paid_unrouted` to `no_partner_available`, system only),** so the alert fires at once and the buyer is not left waiting. Without them such an order sits as "confirmed" until spec 013's 5-minute alert. Approve: "yes".
- **Q10 — Which spec builds the Phase 1 alerts?** Spec 012 §11 says order alerts belong to spec 025, which `plan/09` schedules for the last weeks before launch; `plan/09` Phase 1 AC 7 needs them for the first real order. **Recommendation: this spec builds the routing alerts and spec 013 the payment and unrouted alerts now; spec 025 keeps the runbook set and any later alerts.** Approve: "yes".
- **Q11 — Do test orders (Stripe test mode, demo florists) send emails?** Spec 010 forbids buyer and recipient messages for test orders and says this spec "skips" them. **Recommendation: florist and founder messages go out for test orders, buyer messages never,** so the florist emails can be tried on staging before launch. Approve: "yes".
- **Q12 — What happens when we stop an order a florist already accepted (refused payment, full refund, chargeback)?** **Recommendation: we tell the florist at once to stop, and record when; whether they are paid for a bouquet already made is set by the florist agreement and the payouts spec, not here.** Approve: "yes".
- **Q13 — Should checkout refuse a postcode no florist covers?** Spec 010 assigned this check to this spec. **Recommendation: yes,** at step 1 and again at placement, for real and test orders, through a spec 010 amendment; the buyer is told before paying instead of being refunded later. Approve: "yes".
