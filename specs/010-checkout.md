## 1. Problem

Phase 0's fourth acceptance criterion is the one the florist pitch rests on: "pick Poland → PDP → date → checkout → 'place order' (no charge) → order appears in `/demo/vendor-inbox` and admin queue within 5 s" (`plan/09` Phase 0, AC 4). Today the journey stops at the product page. Spec 009 built that page with **no purchase affordance at all** (009 §3, §8) and handed "basket, Continue, checkout, the quote issue, add-on selection and the withdrawal-right notice" to this spec. Spec 005 left the price lock to us ("30-minute signed quote, secret lands in spec 010", 005 §13 Q5). Spec 003 left phone validation and the address *forms* to us (003 §3). Spec 002 built the tables for customers, recipients and orders, and its §13 Q3 noted that "nothing places orders until spec 010, and that is behind a demo guard". Spec 041 left `order.terms_version` for us to write. Five specs point here.

Three things make this harder than "build a form". **First, nothing can be sold yet.** No country is live, the company is not registered, the terms and the privacy notice do not exist (041 §2, §13 Q1), no lawyer has read a word (`plan/13` B4) and no payment account exists. So the checkout must be complete, real and testable while being structurally unable to take money, and the switch from demo to real must be a set of preconditions the code checks, not a promise in a document. **Second, the product page cannot hand over a date.** In Phase 0 every PDP date is unselectable on purpose (009 AC-8: the `preview` state shows the calendar and offers nothing). The demo needs a date; the honesty rule says the PDP may not offer one. **Third, an order is the first thing in this codebase that changes status.** ADR-0009 says only `orderService.transition` may do that, and spec 015, which owns the service, is Phase 1. The demo order needs a state machine now.

The founder's instruction of 2026-10-04 sets the bar: "site will be live on railway not vercel … get everything ready for prod and launch whole site … order management … whole backend". The checkout is where the site stops being a brochure. It has to work on the live site, in four locales, on a phone, with JavaScript off, and it has to be impossible to mistake for the real thing while it is a demo.

## 2. Scope

Each bullet is testable; §9 names the AC.

**One decision decides what the checkout may do (`checkoutMode`)**

- `checkoutMode()` in `src/modules/checkout/mode.ts` is a pure function and the **only** place that decides whether a checkout is `closed`, `demo`, `test` or `live` (table in §5.2). Its inputs are data: the country's checkout flag, spec 009's `pickerState()`, the `checkout.demo_guard` flag, the `payments.stripe` flag, the kind of Stripe key in the environment, `APP_ENV`, the legal-readiness predicate, and whether spec 013 has registered a test or a live payment step. No other file branches on any of these.
- **The demo guard.** While `checkout.demo_guard` is on (spec 002 seeds it on), the mode is `demo` or `test`, never `live`. In `demo`, placing an order calls no payment provider, makes no outbound request and writes no `payment` row. `test` is reachable only once spec 013 registers its Stripe test payment step (test keys only, never where `APP_ENV = production`); this spec registers none, so in Phase 0 the guard yields `demo`.
- **Turning the guard off does not open the shop.** With the guard off, the mode is `live` only when every precondition holds: the country is live (`pickerState = live`), the company is registered, the terms and withdrawal documents for the buyer's regime are in force and lawyer-reviewed, the privacy notice exists, the confirmation email exists (spec 017), and spec 013 has registered a live payment step. In Phase 0 the last of these is always false, so the mode is `closed`. Taking money needs spec 013 merged; it cannot happen by flipping a flag.

**The entry from the product page (an amendment to spec 009, §5.3)**

- In the `preview` picker state, the PDP's demo price summary keeps its sentence and gains one control: **"Try a demo order"**, a submit button inside the PDP's existing form with `formaction` pointing at the start route and `formmethod="post"`. In the `live` state the same control reads "Continue — {total}". In `unavailable` there is no control. The button submits the tier (and, when live, the date) already selected in the form, so it needs no JavaScript and changes no island.
- `POST /api/checkout/start` (route handler, `no-store`, Origin-checked) parses the posted selection, resolves the price through spec 005, creates a server-side draft, issues the signed quote, sets the `fo_checkout` cookie and answers **303** to `/{locale}/checkout`. A GET answers 405. Nothing personal travels in a URL.

**The checkout: three steps on one URL (`plan/04` §9)**

- `/{locale}/checkout`, server-rendered, `no-store`, `noindex`. Three steps, each a `<form>` posting to a server action that validates with zod and saves the draft; the next step renders after a successful save. Everything works with JavaScript disabled. `?step=recipient|card|review` only selects a step already reachable; an incomplete step is never skipped.
- **Step 1, "Who are the flowers for?"**: the delivery date (§2 "The date"), the recipient's full name, the recipient's phone (required, validated for the destination), the address in the **destination country's** format from `src/config/address-formats.ts` (field order, required fields, label keys, postcode pattern and normaliser), the kind of place (home, work, hospital, funeral home, hotel, cemetery, church — spec 002's `place_kind`) with one delivery note of at most 120 characters whose hint changes with the place. At most eight inputs.
- **Step 2, "Your card and your details"**: the card message (at most 200 characters counted as graphemes; blank means no card), "sign as" (at most 40), a printed-card preview, the add-ons on offer for the destination as one-tap rows (none preselected), then the buyer's email, full name, optional phone and country of residence (defaulted from the locale, freely changeable, never used in a price). At most eight inputs.
- **Step 3, "Check and place your order"**: the summary (product, tier, date, place, recipient, card, add-ons), the all-in total with its lines and its VAT split by rate, the currency line, and the place-order control for the mode. In `demo` the control is **"Place demo order — nothing is charged"**. In `test` and `live` (both built by spec 013) it is "Pay {amount} and place order" with the pre-contract block directly above it, nothing between the two (§8; §14 A4.1). The card is charged when the order is placed (§14 A4.2).
- **An order summary panel** on every step (sticky total bar on mobile, except on step 3 in `test` and `live`, which has none: §14 A4.1), editable inline: changing the tier or an add-on is a submit, recomputed on the server.

**Money: price shown = price charged**

- The draft carries one signed quote (spec 005's `quote()` / `verifyQuote()`, 30 minutes, `QUOTE_SIGNING_SECRET` added to `lib/env.ts` here, as 005 §13 Q5 decided). Every amount on every step is read from the draft's current quote, which is built from the same `priceProjection()` the PDP renders. The checkout re-derives nothing in a component.
- Every amount comes through spec 005's price provider, whichever one is wired in (the committed dataset today; a database provider after a later cutover swaps it for the PDP and the checkout in one deploy). Nothing in `modules/checkout` or `modules/orders` reads `country_price` directly.
- The posted selection carries the total the PDP displayed. If the server's total differs (a redeploy changed the FX snapshot under a cached page, or the provider's price changed), step 1 opens with a notice naming the old and the new amount and asks the buyer to confirm. The same notice appears whenever a quote is re-derived to a different amount. Nothing is ever recorded at an amount the buyer did not see last.
- Currency: the one the PDP showed for that locale (the locale default, or the destination currency when FX is stale — 005 §14 A3). No currency switch in Phase 0. No approximate-equivalents line in checkout (004 §14 A21 clause 6(c) lists where it appears; checkout is not among them, because the checkout shows the one currency that is charged).
- Add-on prices are projected into the display currency by the same FX rule as the bouquet (a requested addition to spec 005, §5.2), which ends spec 009 design-round Q4's interim "add-on prices in the destination currency".

**The date**

- `live`: the date comes from the PDP and stays editable in step 1, drawn by the same `deliveryWindow()` grid with the same fee on every chip.
- `demo` and `test`: the PDP offers no date (009 AC-8), so step 1 shows the destination's real calendar from `deliveryWindow()`, computed **as if** the country's demo florists were active, under the heading "Pick any date to see how it works. In the demo, nothing is delivered." Holidays, closed Sundays, surcharges and reasons render exactly as on the PDP. This calendar exists only inside the checkout and only in these two modes; the PDP is unchanged.
- At placement the date is checked again at `now` in the destination's time zone (009 §14 A10's requirement on this spec). If it can no longer be met, step 1 reopens with the reason and the next possible date, and nothing is placed.

**Placing the order: the shared order engine, owned by this spec**

- This spec **owns the one order engine** of ADR-0009 and `plan/11` §2, for itself and for specs 011, 012, 015 and 020. `src/modules/orders/service/` gains `orderService.place(draft)`, `orderService.transition(orderId, event, actor, payload)`, `appendEvent` (status-preserving events), the event-schema registry and the outbox writer. `transition` reads legality from spec 002's `order_transition` rows, sets `app.allow_status_write`, updates `order.status` and appends `order_event` with the next `seq`, all in one transaction. It writes an `outbox` row in that transaction **only when `outboxTargets(event, mode)` returns at least one target**. An event absent from `order_transition` for the current status raises `ORDER_TRANSITION_ILLEGAL`, the name spec 002's trigger already uses, and writes nothing. The engine is its own task (§12 task 3), which waits only for TASK-019, TASK-020, TASK-021 and TASK-023.
- **Event names are the `plan/11` §2 catalogue's**, never the diagram's arrow labels: pay → `order.authorised`, route → `order.routed`, accept → `assignment.accepted`, decline → `assignment.declined`, exhausted → `order.no_partner_available`, capture → `order.captured`, start → `order.in_production`, dispatch → `order.out_for_delivery`, deliver → `order.delivered`, photo → `order.photo_uploaded`, and so on for every arrow. Spec 002's `order_transition.event` holds the same names (a requirement on TASK-019's brief, §12). Versioned zod schemas ship here for the four events this spec emits: `order.placed`, `order.authorised`, `order.routed`, `assignment.offered`.
- **Actors** match one `ActorSchema`: `buyer`, `partner:{uuid}`, `admin:{uuid}` or `system:{name}`, where the name uses lowercase letters, `_` and `.` only, with no hyphen. This spec's system actors are `system:demo_guard` and `system:demo_router`.
- **Specs 011 and 012 only call `transition`.** Neither builds an engine. Spec 011 adds its florist commands and the versioned schemas of the events it writes to this registry, and its `placeDemoOrder` is a thin wrapper over `place` plus `demoRoute`. Spec 012's queue reads; its action buttons arrive with spec 020, through this engine. Spec 015 adds every other command, timeout, event and payment coupling to the same code (§13 Q4).
- **A demo order walks the real arrows.** One request, after the buyer clicks: `place` (status `placed`, actor `buyer`) → `transition('order.authorised', 'system:demo_guard', { mode: 'demo' })` with no payment row → `transition('order.routed', 'system:demo_router')` with exactly one `order_assignment` offered to a **demo** florist covering the destination (first by postcode zone, else the first demo florist in the country by code), with the 60-minute answer window of `plan/06` §5.2, and `assignment.offered` appended through `appendEvent` as a status-preserving event (`from_status = to_status = 'routed'`, so spec 002's status trigger is not involved). All of it is committed before the confirmation responds, so the order is in the florist inbox and the admin list as soon as either page loads. Accepting or declining it is spec 011's.
- **The demo marker is `order.mode`** (`demo` | `test` | `live`), written on every order and on every event payload. Nothing marks a demo order through `source`, which spec 002 keeps for telling seed rows from real ones. Demo and test orders route only to `demo` florists; live orders only to `active` ones; the database enforces it (§5.1).
- Idempotent: one draft yields at most one order, whatever the double-clicks, refreshes or races.
- `src/modules/orders` exports two read projections for the screens of 011 and 012: `listOrdersForPartner(partnerId)` and `listOrdersForAdmin(filter)`, each under the right RLS context, carrying reference, buyer-visible status, mode, delivery date, city, product and tier, and no contact data.
- A daily cap on demo orders (default 200 per UTC day, `src/config/checkout.ts`) protects the database's free compute allowance from a public demo being spammed.

**Confirmation**

- `/{locale}/checkout/done`, `no-store`, `noindex`, read from the draft cookie (no token in the URL): the order reference (`FO-XXXX-XXXX`, derived from the order id), the demo statement in demo mode, the recipient recap, the date, the card, the total and what happens next in the real service. Without a valid cookie it renders "This confirmation is no longer available" and no order data.

**Compliance and honesty in the demo**

- A non-dismissible demo banner on every step and on the confirmation, a "Use sample details" button that fills obviously sample data for the destination, and an inline privacy notice at the point of collection (the controller line spec 041 already uses, the purpose, the retention period, how to ask questions).
- **Retention (the only copy of these two rules; specs 011 and 012 do not repeat them):** personal data of demo and test orders is cleared (pseudonymised) **24 hours** after placement in production and **7 days** after placement on staging and PR environments; unfinished checkouts (drafts) are deleted **24 hours** after the last activity in every environment.
- In production, demo orders show only in spec 012's admin queue; the florist inbox runs on staging (spec 011), so a stranger's typed details never reach a florist.
- In `demo` there is no pre-contract block, no withdrawal sentence and no terms link: no contract is formed, and spec 009 §13 Q7 kept those lawyer-gated sentences off the site until they can be true. In `test` (spec 013) they render with the "draft, not in force" label from spec 041; in `live` they are a precondition.

**Gates, docs, artboards**

- e2e for the full journey in `en-gb` and `pl`, JS-on and JS-off; axe on every step, its error state and the confirmation in four locales; visual baselines desktop and mobile per step; the client-JS budget; robots and header assertions; a runbook `docs/runbooks/checkout.md`; RoPA rows; the cookie register; artboards listed in §12 drawn before `/plan-tasks`.

## 3. Non-goals

- **The coverage rule itself** ("we do not deliver to this postcode yet": which florist covers which postcode, and capacity) → spec **016**'s `canServe`. *(Amended by §14 A3: this spec calls it, in `test` and `live`, at step 1 and at placement. Phase 0 `demo` validates the postcode's format only.)*

- **Country-specific address rules** (Polish hospitals take flowers at reception) as rendered copy → Phase 1 country content. Step 1 shows the place-kind hint only.

## 4. User stories

- As a **Polish florist watching the founder's demo**, I see an order placed on the website appear in my inbox seconds later, with the recipient, the address, the date and the card, and I can tell from every screen that it is a rehearsal.
- As the **founder on the live site**, I can click from a bouquet to a placed demo order in under a minute on my phone and see it in the admin list, and nothing I do can charge anyone.
- As a **buyer in Manchester sending flowers to my mother in Kraków**, I see one total that includes VAT and delivery, the same total I saw on the product page, and the form asks for her address the Polish way.
- As a **buyer who stops halfway to find the address**, I come back, refresh, press back, and nothing I typed is lost.
- As a **buyer with a screen reader**, every field has a label, every error tells me how to fix it and takes my focus there, and the progress through the three steps is announced.
- As a **buyer on `/pl/`**, every date reads with a weekday and a month name, the price reads in złoty, and my grandmother's name keeps its "ł".
- As a **visitor who finds the demo by accident**, I am told plainly that it is a demo before I type anything, asked to use sample details, and offered a button that fills them for me.
- As **Googlebot**, I never see a checkout page: no link points at one, `robots.txt` disallows it, and every response says `noindex`.
- As the **implementer of spec 013**, the order exists, the quote is signed, the mode is decided in one function, and I add a live payment step behind an interface without touching the form.
- As the **implementer of spec 015**, `orderService.transition` already reads its guards from data and writes events and outbox rows; I add commands, not a rewrite.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

**A. Requested amendment to spec 002 (A6), folded into its unbuilt migrations.** Spec 002's order tables are TASK-019 (migration `0007`) and its triggers TASK-020 (`0008`); both are `todo`. **B. This spec's migration: `NNNN_checkout_draft`** (the next free number after spec 002's last migration), with `NNNN_checkout_draft.down.sql`.

`checkout_draft(id uuid PK DEFAULT gen_random_uuid(), token_sha256 text NOT NULL UNIQUE, locale_code FK locale, destination_country_id FK country, product_id FK product, tier_key text NOT NULL, delivery_date date NULL, addon_keys text[] NOT NULL DEFAULT '{}', recipient jsonb NULL, buyer jsonb NULL, card jsonb NULL, quote jsonb NULL, expected_total_minor bigint NULL, expected_currency_code char(3) NULL FK currency, confirmed_total_minor bigint NULL, confirmed_currency_code char(3) NULL FK currency, mode text NOT NULL CHECK (mode IN ('demo','test','live')), steps_completed smallint NOT NULL DEFAULT 0 CHECK (steps_completed BETWEEN 0 AND 3), order_id uuid NULL UNIQUE FK "order", last_activity_at timestamptz NOT NULL DEFAULT now(), expires_at timestamptz NOT NULL, created_at, updated_at)`.

- The cookie holds a 256-bit random token; the database holds only its SHA-256, so a database leak does not yield a usable cookie.
- `order_id UNIQUE` is the idempotency key: placement locks the draft row `FOR UPDATE`, returns the existing order when `order_id` is set, and sets it in the same transaction as `orderService.place`.
- On placement, `recipient`, `buyer` and `card` are set to `NULL` in the same transaction (the data now lives in the order's snapshots and lines); the draft keeps `order_id` so the confirmation page can find the order.
- Money pairs follow spec 002's rule (`*_minor bigint` beside a currency column with an FK), so `db:check`'s money-pair gate passes unchanged.
- RLS enabled; one policy, for `app.role = 'system'` only. No public, customer or partner policy. `db:check`'s RLS-coverage gate passes.
- Rollback: `DROP TABLE checkout_draft` (no other object references it; `order` has no FK to it).

**C. Data the checkout reads but does not own.** Products and **every amount** through spec 005's price provider, whichever one is wired in (today the same committed dataset the PDP renders, so the identity in AC-15 holds by construction; a later cutover swaps the provider for the PDP, its structured data and the checkout in one deploy). The checkout never reads `country_price` directly. `order_line.product_id` is resolved by SKU from the seeded `product` table (spec 002 TASK-026 seeds from the same dataset; production is seeded insert-only from it before the first production demo order, §12). Countries, calendars and holidays through `modules/geo` (spec 009). Demo florists, their coverage and postcode zones from spec 002's seed.

`legalReadiness(locale, buyerCountry)` is true only when: `isCompanyRegistered()`; `infoPageExists('privacy', locale)`; the `terms` and `cancellation` documents for the buyer's regime (`uk` for a GB buyer, `eu` otherwise — spec 041 §2) have `inForce && lawyerReviewed`; the `checkout.legal.*` message keys are `reviewed` in that locale; and spec 017's confirmation email is registered. `checkoutEntryFor(pickerState, deployment)` is the pure, database-free predicate the PDP calls (§5.3); the authoritative check is `checkoutMode()` at the start route and on every action.

**Zod schemas** (parsed at every boundary, `plan/12` §2):

- `CheckoutStartSchema` — `{ locale, countryIso, sku, tierKey, date?: IsoDate, expectedTotalMinor: int ≥ 0, expectedCurrency }`, strict. From the PDP form body.
- `RecipientStepSchema(countryIso)` — built from `addressFormModel()`: `{ deliveryDate, fullName (1–120 graphemes, NFC), phone (E.164 after parsing for the destination), address fields per format (postcode normalised then matched), placeKind ∈ spec 002's list, deliveryNote ≤ 120 graphemes }`.
- `CardAndBuyerStepSchema` — `{ cardMessage ≤ 200 graphemes | "", signAs ≤ 40 graphemes | "", addonKeys: AddonKey[] (only those priced for the destination), email, buyerName, buyerPhone? (E.164, any country), residenceCountry: ISO2 }`. There is no field for a default-selected add-on; the schema cannot express one (CRD Art. 22).
- `ReviewStepSchema` — `{ confirmedTotalMinor, confirmedCurrency, quoteDigest }`; the server compares all three with the draft before placing.
- `DraftSchema` — the row above as a type; `DraftQuoteSchema` = spec 005's `QuoteSchema`.
- `OrderPlacedV1`, `OrderAuthorisedV1`, `OrderRoutedV1`, `AssignmentOfferedV1` — event payloads, registered in `events.ts` under their catalogue names; every one carries `mode`; none carries a name, phone, email, address or card message (those live in the order's snapshots, never in events or outbox payloads). Spec 011 registers its own events' schemas in the same registry.
- `ActorSchema` — `z.string().regex(/^(buyer|partner:[0-9a-f-]{36}|admin:[0-9a-f-]{36}|system:[a-z_.]+)$/)`; `transition` and `appendEvent` parse the actor before any write.
- `OrderListItemSchema` — `{ orderId, reference, mode, buyerStatus, deliveryDate, cityName, productName, tierKey, placedAt }`, returned by `listOrdersForPartner`. `listOrdersForAdmin` returns spec 012's `AdminOrderListItemSchema`, which extends it with the internal status, the total and the assigned partner; the partner projection never carries those.

**Server actions and the route** (Next server actions keep their built-in Origin check; the route handler checks `Origin` itself):

- `POST /api/checkout/start` → 303 to `/{locale}/checkout` and `Set-Cookie: fo_checkout=…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400`. Errors: 405 (GET), 403 (foreign Origin), 303 back to the PDP for an unknown product, tier or country, with no query string.
- `saveRecipientStep`, `saveCardAndBuyerStep`, `updateSelection` (tier, add-on, date), `placeOrderAction` — each loads the draft by cookie, re-runs `checkoutMode()`, parses its schema, verifies the quote, saves, and redirects (303) to the next step or re-renders the same step with errors.
- `placeOrderAction` in `demo`: re-check the date and the quote → check the daily cap → `orderService.place()` → `transition('order.authorised')` → `demoRoute()` → 303 to `/checkout/done`. All in one database transaction, so a failure leaves no half-placed order.

**`orderService`** (signatures only):

- `place(input: PlaceOrderInput): Promise<{ orderId: string }>` — inserts `order` (status `placed`, `mode`, snapshots, FX, `vat_breakdown`, `supply_model` from the country, `terms_version` only when live), `order_line` rows, `order_event` seq 1, and an outbox row only when `outboxTargets('order.placed', mode)` is non-empty.
- `transition(orderId: string, event: OrderEventType, actor: Actor, payload: unknown): Promise<TransitionResult>` — locks the order row; rejects an event absent from `order_transition` for the current status with `ORDER_TRANSITION_ILLEGAL` (and an unknown order with `ORDER_NOT_FOUND`), writes nothing on rejection.
- `appendEvent(orderId: string, event: OrderEventType, actor: Actor, payload: unknown): Promise<{ seq: number }>` — status-preserving events through the same writer, so `seq` stays monotonic and the outbox rule is the same.
- `demoRoute(orderId: string, opts?: { partnerId?: string }): Promise<{ assignmentId: string }>` — demo and test orders only; refuses a live one. Applies `order.routed` through `transition`, inserts the `order_assignment` (to `opts.partnerId` when spec 011's `placeDemoOrder` names a demo partner, else by the rule in §2), and appends `assignment.offered` through `appendEvent`.
- Outbox targets come from `outboxTargets(event, mode)`; an empty list means no outbox row. In Phase 0 every list is empty (spec 015 and spec 017 fill them). For `demo` and `test` no target that messages a buyer or a recipient is ever produced (spec 017 consumes the outbox later and must not email a stranger about a demo).

**The payment seam handed to spec 013:** `interface CheckoutPaymentStep { readonly mode: CheckoutMode; prepare(draftId: string, quote: Quote): Promise<PaymentPreparation>; confirm(orderId: string, input: unknown): Promise<PaymentOutcome> }`. This spec ships `demoPaymentStep` (prepares nothing, confirms with no request) and the registry. Spec 013 registers the Stripe test step and the live step; until it does, `checkoutMode()` returns neither `test` nor `live`.

**Customers and recipients:** `upsertGuestCustomer` matches on the normalised email and never overwrites an existing row's name, phone or country from an unauthenticated checkout (the order's `buyer_snapshot` keeps what was typed). `createRecipient` deduplicates on `(customer_id, normalised full name, phone)` per `plan/11` §3 and writes the `recipient_address`; the order's `recipient_snapshot` is the history-preserving copy.

**Jobs:** none new. Spec 002's `retention.sweep` gains handlers for the two retention rows of §5.1 A. Demo routing is synchronous in the request, so the 5-second promise does not depend on the worker (spec 040: `worker` has 0 replicas until TASK-024).

**Requested amendment to spec 005 (§14):** `addonPriceProjection(addonKey, countryIso, locale)` mirroring `priceProjection()` (same FX snapshot, buffer and rounding, integer minor units, own VAT rate), so an add-on's displayed and quoted price share one path. Additive inside `modules/catalog`; rollback deletes the function.

### 5.4 Rendering & caching (SSG/ISR/SSR, tags invalidated, per plan/01 §3)

- Checkout and confirmation are **SSR `no-store`** (`plan/01` §3: "Cart, checkout, order confirmation: SSR no-store, noindex"). They read the draft cookie and the database; they are never prerendered and never cached. Served from Railway Amsterdam (spec 040), which keeps personal-data processing in the EU (`plan/07` §1.4).
- Cloudflare's rule 1 (spec 040 §5.4) already bypasses `/checkout` with and without the locale prefix and `/api/`; rule 3 rate-limits POSTs at 60 per minute per IP. This spec adds no cache rule and verifies the bypass on staging (AC-31).
- The PDP stays ISR with its tags (spec 009 §5.4). The amendment adds a button whose presence depends only on `pickerState()` and the build-time deployment descriptor, so the cached HTML is still byte-identical for every visitor, sets no cookie, reads none and adds no `Vary`. Turning `checkout.open` off in the database does not change cached PDP HTML; the button then leads to the honest `closed` state, and spec 012's flag flip may call `invalidate(['catalog:{iso}'])` to remove it sooner.
- No `revalidateTag` is called by the checkout. Placing an order changes no public page.
- Client JavaScript on the checkout: the card counter and preview island, the on-blur validation island and `useFormStatus`, **4 096 B Brotli in total**, no network access. No Stripe.js loads from this spec (spec 013 adds it for its test and live steps). The route stays inside spec 004 §14 A1's 131 072 B first-load ceiling.
- CSP (ADR-0016): checkout routes are dynamic, so they get a per-request nonce. This spec adds no origin; spec 013 adds Stripe's for its steps. No other route's policy changes.

## 6. SEO considerations (mandatory)

- **Indexability.** Every checkout and confirmation response is `noindex, nofollow`, in the header (`X-Robots-Tag`) and in `<meta name="robots">`, in every environment. Registered as `SeoPageType`s `checkout` and `checkoutDone` in `modules/seo/indexability.ts` with a constant `noindex` rule, so no robots literal is written outside `modules/seo` (spec 009's grep rule).
- **robots.txt.** `DISALLOWED_PATHS` in `src/modules/seo/robots.ts` gains `/*/checkout`, closing the "known gap" its header records ("the locale-prefixed forms are added by the spec that creates the segment"). `/api/` is already disallowed.
- **Canonical and hreflang.** None. A `noindex` page with a canonical or an alternate set would send Google mixed signals; the locale switcher still links to `/{other}/checkout` for the human, and the draft survives the switch (the quote's currency does not change with the UI language).
- **URL pattern.** `/{locale}/checkout` and `/{locale}/checkout/done`, the same English word in every locale (§13 Q10): `plan/02` §4.1 gives only the English form, the page is never indexed, and one spelling keeps the robots, Cloudflare and test patterns to one line each. No query string other than `?step=`; no product, price, date, token or personal value in any URL (AC-34).
- **Schema types.** None on checkout or confirmation. On the PDP the amendment changes nothing: `Product` + `Offer` stays unemitted in Phase 0, because `hasPurchasePath()` is true only in `live` mode, and a demo checkout is not a purchase path.
- **Sitemap membership.** None, and none possible: no sitemap builder can reach a checkout URL, asserted by spec 007's sitemap validator over the built set.
- **Internal links.** In: the PDP's submit button (a form control, not an `<a>`; crawlers do not submit POST forms). Out: the product page, the home, and the footer as on every page. Zero `<a href>` to a checkout URL anywhere on an indexable page (asserted by the spec 004 AC-14 crawl).
- **Thin content.** Not applicable to a `noindex` transactional page; the risk is the reverse, a checkout URL leaking into the index, and the four mechanisms above (header, meta, robots, no link) close it.
- **CWV budget impact.** Indexable pages: the PDP gains one server-rendered button and no script, so its LCP, CLS and JS budget are unchanged (009 AC-26 re-run). The checkout is not in the Lighthouse set (it is `noindex` and needs a draft), but it carries the client-JS budget of §5.4 and its own visual baselines, because conversion is priority 2 and a slow checkout loses orders.

- **Locale formatting.** Every amount through `formatMoney` from integer minor units; VAT rates through `formatPercentFromBasisPoints`; the add-on list through the list formatter; dates through `formatDate` with weekday and month name; the cutoff and the "no longer available" reason through `formatTimeInZone` with the destination's zone named (`plan/03` §7, §10). `countGraphemes` joins `format.ts` so `Intl.Segmenter` is constructed only there (`fo/no-adhoc-intl`). Phones are stored in E.164 and shown in the destination's national format by `libphonenumber-js`, which is phone metadata, not `Intl`.
- **Addresses and names.** The recipient address follows the **destination's** format (`plan/03` §8): PL `ul. Marszałkowska 10/5`, `00-001`, apartment folded into the street line; DE house number after the street; GB postcode after the town. The recipient is one `full_name` (`plan/03` §7). Diacritics are preserved and stored in NFC; postcodes are normalised before matching. The recipient phone validates against the destination's numbering plan and accepts a valid non-local number with the warning `plan/03` §8 specifies. A destination reaches checkout only when it has a non-generic address format (AC-8): adding a country is a row in `address-formats.ts` plus its label keys.
- **RTL.** Logical properties only (`fo/no-physical-css`); names, addresses, the card message and "sign as" are wrapped in `<bdi>` wherever they render beside other text; `/ar-XB` gets visual baselines for every step.
- **Translation review plan and `noindex` gating.** Checkout pages are always `noindex`, so review does not gate indexing here; it gates **live mode**. The `checkout.legal.*` keys and the button wording ("Pay {amount} and place order"; the German "zahlungspflichtig bestellen" form) are legal formulas: `legalReadiness()` requires them `reviewed` in the buyer's locale, after the native reviewer and the lawyer (`plan/13` B4, B12). A demo in `de` or `pl` runs on drafts and says so with spec 041's "not yet checked" line. The glossary (`content/i18n/glossary.{locale}.md`) gains "demo order", "printed card", "sign as", "place of delivery" and "order reference".

## 8. Compliance considerations (mandatory)

- **Data flows added → RoPA** (`docs/compliance/ropa.md`, rows added by the task that first writes the data):
  1. **Checkout drafts.** Subjects: buyers and recipients. Categories: buyer name, email, optional phone, country; recipient name, phone, delivery address, place kind, delivery note; card message and signature. Purpose: keep a checkout in progress across steps. Basis: Art. 6(1)(b) steps prior to a contract in `live`; Art. 6(1)(f) in `demo` and `test`. Retention: deleted 24 hours after the last activity; personal fields cleared at placement. Processors: Neon (Frankfurt), Railway (Amsterdam), Cloudflare.
  2. **Demo and test orders.** Same categories. Purpose: demonstrating and testing how an order reaches a florist. Basis: Art. 6(1)(f), balanced by the inline notice, the sample-details button and short retention ⚖️ (the lawyer confirms). Retention: personal data pseudonymised 24 hours after placement in production and 7 days after placement on staging; the anonymised order stays as demo history (spec 011's 30-day deletion of whole demo orders and their photos applies on staging only). Recipients of the data: in production the founder only, in spec 012's admin queue; on staging also demo florist accounts (§13 Q1).
  3. **Live orders** (the flow `plan/07` §1.2 already lists): the row is marked "starts with spec 013"; nothing writes it in Phase 0.
  The Stripe test-mode row (test card data to Stripe, staging only) is spec 013's.
- **Transparency at collection (GDPR Art. 13).** The privacy notice does not exist until the company is registered (041 §13 Q1), so step 1 carries an inline notice: who runs the site (spec 041's `company.controller` line), why the details are asked for, how long they are kept (24 hours on the live site, 7 days on staging), and that questions and requests go to the phone/WhatsApp number. In `live`, the notice is a link to the privacy page, which `legalReadiness()` requires to exist.
- **Recipient data minimised (`plan/07` §1.3).** No recipient email field exists in any schema here (spec 002's `db:check` gate already forbids one on `recipient`). The phone is required and its reason is stated next to it. Recipient data never enters an event, an outbox payload, a log, a URL or an analytics call; the partner list projection carries no contact data. In `live` mode step 1 carries the light-touch sentence that the buyer may share these details with us for the delivery; in demo the request to use sample details replaces it.
- **Consent gating.** No consent-requiring script loads on checkout. `fo_checkout` is an essential first-party cookie (the visitor asked for the function) and joins `src/config/cookies.ts` as `status: "set"`, so spec 041's cookie page lists it. The `fo_csrf` row (declared for this spec) is removed: server actions' Origin check, the route handler's Origin check and `SameSite=Lax` cover the risk it was declared for. Stripe's cookies stay declared and unset; spec 013 sets them in its test mode on staging and confirms their classification (the `cookies.ts` note says so).
- **Price display (`plan/07` §4, `CLAUDE.md`).** One all-in total, VAT and delivery included, equal to the PDP's for the same selection (AC-15); every line visible from step 1; a date surcharge visible on the chip before selection; nothing added at step 3; the VAT split by rate on the review; the currency line ("You pay in GBP."; it no longer names what anyone else is paid, §14 A4.3). Any price change between pages is named and confirmed, never silent. No countdown for the quote, no "only N left", no pre-ticked anything.
- **Consumer information (CRD Art. 6, 8; UK CCRs 2013).** In `demo` no contract is formed, so the review carries no pre-contract block and no withdrawal sentence (009 §13 Q7's reasoning: a regulator reads such a sentence as a disclosure). Spec 013 builds the block: in `test` it renders labelled "draft, not in force"; in `live` it is mandatory and server-rendered above the button: main characteristics, the total, the delivery date, the free cancellation and the perishable-goods exemption (Art. 16(d); CCRs reg. 28(1)(c)) together, gain first, as `checkout.legal.cancellation`: "You can cancel for free until we start preparing your order. Flowers are fresh, so the 14-day cancellation right does not apply after that." (`proposed`, lawyer-gated; the founder's "1 ok" of 2026-10-14, §14 A-founder-2026-10-14b; "until we start preparing" means until 06:00 destination-local on the delivery date, spec 002 §14 A10; the card is charged at order, §14 A4.2), the trader's identity and links to the terms and the withdrawal page. The button names the obligation to pay and the amount (Art. 8(2); the German wording). The durable-medium confirmation (Art. 8(7)) is spec 017's email, which is why `legalReadiness()` requires it.
- **Geo-blocking (EU 2018/302, ADR-0006).** The checkout is reachable from anywhere, never redirected by IP, and the buyer's country of residence is a free choice that changes nothing in the price (prices are keyed on the destination only; spec 005 AC-18's signature test covers the new `addonPriceProjection`). Any country may be chosen.
- **Honesty (spec 004 AC-15, A5, A22; spec 041).** Present tense for how our florists work, prefixed "In the real service" wherever a demo screen describes what happens next; no florist name, count, rating or photo; the card is "printed", never "handwritten"; the guarantee is the "fresh-flower promise" and **no number of days of freshness appears anywhere** (041 §2); ~~no "photo of your delivery" promise until spec 027~~ *(withdrawn by §14 A-founder-2026-10-14b: every order closes only with a delivery photo, spec 002 §14 A6.11 D6, so the photo is promised for every order; a checkout string that says so carries an `honestyAllow` entry citing D6, as spec 041 A.3 does)*; none of the nine banned words in any string.
- **Accessibility (WCAG 2.2 AA, `plan/07` §8, spec 004).** §5.3's rules; axe zero serious or critical on every step, in its error state, and on the confirmation, in four locales; keyboard-only completion of the whole flow; a manual VoiceOver pass recorded in the runbook.
- **Logs and PII.** Logged: `request_id`, `order_id`, `draft_id` (never the token), `mode`, `step`, `locale`, `country_iso`, `duration_ms`, error codes. Never: names, email, phones, address lines, postcode, card message, signature, delivery note, quote digest, cookie value. The logger's redaction list gains `email`, `sign_as`, `delivery_note`, `token` and `*_snapshot` (it already has `*name`, `card_message`, `phone_e164`, `postal_code`). Sentry's `beforeSend` scrubs request bodies on checkout routes. Browser Sentry stays off (decisions-log, 2026-09-08: it returns on checkout in spec 013).
- **Security.** 256-bit draft token, hashed at rest; `HttpOnly; Secure; SameSite=Lax`; Origin checks on every POST; zod on every input; one order per draft under a row lock; the daily cap and Cloudflare's rate limit; React's escaping for every user string; no `dangerouslySetInnerHTML`; `QUOTE_SIGNING_SECRET` only through `lib/env.ts`, in `.env.example`, constant-time digest comparison (spec 005).

**1. The decisions (each with its default; the founder's question is in §13 where one is open).**

- **D1. A basket holds bouquets for different recipients, dates and destination countries (Q18).** One basket line is one bouquet for one recipient on one date in one destination, with its own add-ons and card. **Each line becomes its own order**, routed to its own florist by spec 016's per-order rules, with its own `delivery_date`, `recipient_snapshot`, VAT breakdown, events and reference (`FO-XXXX-XXXX`). The lines are bought together: **one buyer, one payment, one confirmation**. The new internal record that groups them is a **`purchase`** (item 2). Buyer-facing copy never says "purchase"; it says "your order" and "delivery {n} of {total}".
- **D2. Quantity is always one.** There is no quantity stepper. Two bouquets are two lines, even for the same person on the same day (two orders, two deliveries; merging is Q23).
- **D3. At most five lines per basket** (`BASKET_MAX_LINES = 5` in `src/config/checkout.ts`; Q21). A sixth add is refused with a notice and writes nothing.
- **D4. Add-ons belong to a line.** They are chosen per line on that line's step 2 (as today, AC-11: only add-ons priced for that line's destination, none preselected, CRD Art. 22) and listed per line in the basket and the summary. The florist of that order delivers them with that bouquet. A line's price is its tier, its date surcharge where present, and its add-ons.
- **D5. Price shown = price charged, per line and in total.** Every line shows one all-in amount (VAT and delivery to that address included, the same integer as that line's quote); the basket total is the integer sum of the line amounts; no delivery, service or basket fee is added anywhere. Delivery is charged per order because it is already inside each line's price (spec 005), and a date surcharge is a line of that order only. Each line carries **its own signed quote** (spec 005 `QuoteSchema` has one `ratePpm` and one `fxAsOf`, and two destinations have two FX rates); the review confirms the sum.
- **D6. One mode and one currency per basket.** The basket's `mode` (`demo`, `test`, `live`) is set by its first line; a line whose destination's `checkoutMode()` differs is refused with a notice (a demo order and a real order can never share one payment). The basket's currency is the one its first line was priced in (§2 "Currency"). A later line is **priced in the basket's currency** by the same provider; when the PDP showed another currency (the buyer switched language between products), the price-changed notice names both amounts, as AC-6 does today. A line that cannot be priced in the basket's currency (stale FX, spec 005 §14 A3, where only the destination currency is offered) is refused with a notice. Changing the UI language never changes the basket's currency (§6 already says so for the draft). There is still no currency menu (spec 008 §13 Q9); if one ever ships, it re-prices every line at once on the server and shows the price-changed notice; a basket never holds two currencies.
- **D7. Persistence: server side, behind the existing hashed cookie, no personal data in any cookie (Q20).** The basket **is** the checkout draft: `checkout_draft` keeps the basket-level fields and gains `checkout_draft_line` rows (item 2). `fo_checkout` keeps its 256-bit token (SHA-256 at rest, `HttpOnly; Secure; SameSite=Lax; Path=/`) and its lifetime becomes **30 days** after the last change (`Max-Age=2592000`). Recipient, card and buyer details stay **server-side only** and are cleared **24 hours** after the last activity, as today; the lines themselves (product, tier, destination, date, add-ons) stay for 30 days. A second cookie, `fo_basket`, holds **only the number of unplaced lines** (digits, nothing else) so the header can show a count without a request (D10).
- **D8. A line that becomes unavailable, or whose date passes, while it waits (Q22).** On every render and every action the server re-derives each line: product active, tier priced, destination's mode unchanged and not `closed`, date still deliverable at `now` in the destination's zone, price unchanged. A line that fails is **marked, kept visible and excluded from the total**, and the buyer cannot reach step 3 or place the order until they act: **Remove** (any failure) or **Use {next date}** (date failure). A changed price shows the price-changed notice and blocks placement until confirmed (AC-17, per line). Nothing is dropped silently, because a dropped line may be someone's birthday.
- **D9. One charge, so no partial payment; routing stays per order.** Placement writes the purchase and all its orders in **one transaction**: any line failing a re-check (date, coverage in `test` and `live`, quote, SKU or price, availability, the daily cap) writes nothing at all and returns the buyer to that line's step with the reason. In `test` and `live` the purchase is paid by one charge (spec 013, item 13), so the orders are paid together or not at all. After payment each order is routed on its own (spec 016). If one order later cannot be served, spec 016 and spec 013 handle **that order alone**: `order.no_partner_available`, then at `graceEnd` `cancelOrder` with actor `system:routing.no_partner_expiry`, a refund of **that order's amount only** against the shared charge, and spec 016's B5 for that delivery; the other orders continue untouched. Nothing on the confirmation page anticipates that case (founder 2026-10-14, no negative framing post-purchase).
- **D10. The header basket link and its count.** Every page's server HTML carries the same Basket link (`<a href="/{locale}/basket" rel="nofollow">`, label `nav.basket`, an icon and an **empty badge slot of fixed size**), identical for every visitor, so cached HTML stays byte-identical and gains no `Vary` or `Set-Cookie` (spec 008 AC-22; spec 009 AC-5). A tiny client island, loaded **after the LCP paint** by the deferral TASK-244 merged, reads `fo_basket` and writes the count into the reserved slot. It makes **no network request**, so it costs no server time and leaks nothing. With no `fo_basket` cookie the slot stays empty. Phone placement is Q26.
- **D11. Guest checkout stays; accounts are optional and spec 018's.** No step asks for an account or a password (AC-12 unchanged). The basket belongs to the browser through the cookie. When spec 018's account ships, attaching a basket to a signed-in buyer is its requirement (item 15).
- **D12. Entry points.** The PDP form keeps its one entry control and gains **"Add to basket"** beside it, both submits in the existing form, posting to the start route (item 4). "Try a demo order" (`preview`) and the live continue label (`live`) **add the line and open checkout** for the whole basket (`plan/04` §8: the basket is never a required step); "Add to basket" adds the line and opens `/{locale}/basket`. When the basket already held other lines, step 1 opens with a notice naming how many, so nobody pays for a forgotten line by surprise (Q24). Listing cards still carry no add-to-basket (`plan/04` §6: the date comes first; spec 008 AC-6 unchanged).

**16. Open questions (§13; each has the default this entry is written against).**
- **Q18. Can one basket send to different people, on different dates, in different countries?** Default: **yes**; each bouquet becomes its own order with its own florist, paid once, confirmed once. Alternative: one recipient and one date per basket (simpler, but the common "Mum and Grandma" order needs two checkouts).
- **Q19. How spec 013 records one charge for several orders.** Default: **the payment belongs to the purchase, and each refund names its order** (a refund can never exceed that order's own amount; a dispute covers every order of the purchase). Alternative: one payment row per order, all pointing at one Stripe payment (keeps spec 013's per-order tables, but a dispute then fits no single row).
- **Q20. How long a basket is kept.** Default: **30 days after the last change**; anything typed about recipients, cards and the buyer is deleted after **24 hours**, as today. Alternatives: 7 days, or 24 hours for everything.
- **Q21. Most bouquets in one basket.** Default: **5**. Alternative: 10 (corporate gifting, more fraud exposure until spec 021).
- **Q22. A bouquet in the basket stops being available, or its date passes.** Default: **keep it visible, leave it out of the total, and ask the buyer to remove it (or pick the next date) before paying**. Alternative: drop it automatically with a notice.
- **Q23. Two bouquets for the same person on the same day.** Default: **two orders, two deliveries**, each price including its delivery. Alternative (later amendment): merge them into one order with one delivery, which needs a delivery fee that is not inside the bouquet price.
- **Q24. "Continue" on a product page when the basket already has bouquets.** Default: **checkout covers the whole basket** and step 1 says how many other bouquets are in it, with Remove in the summary. Alternative: "Continue" buys only this bouquet and leaves the rest in the basket.
- **Q25. One confirmation email for the whole basket.** Default: **yes**, listing every delivery, with one invoice per order attached (each order carries its destination's VAT). Alternative: one email per delivery.
- **Q26. Where the basket sits on a phone.** Default: **an icon with the count beside Menu** in the 65 px header. Alternative: inside the Menu only (no count visible until it opens).
- **Q27. Keep the basket out of Google by blocking it in `robots.txt`** (`plan/02` says so) **plus `noindex` and a `nofollow` header link.** Default: **yes**. Alternative: allow crawling so Google reads the `noindex` (a deviation from `plan/02` §4 that needs your word).

**E3 When the panel appears.** Only when all of these hold: the product page's picker state is `live` (a date can be picked); the flag `checkout.express_wallet` is on for the destination (country scope) and for the page's locale (locale scope), both default off and both a data flip in admin (spec 002's `feature_flag_scope`); `checkoutMode()` for the selection is `demo`, `test` or `live` (read by the options endpoint of E6, never in cached HTML); and either the device has a wallet that Stripe's element reports as ready (in `test` and `live`), or the mode is `demo` and the demo wallet of E7 is used. In every other case, including `closed`, the panel never renders and the page is exactly as before. `preview` product pages, which offer no date (spec 009 AC-8), keep "Try a demo order" and get no panel.

**E4 The price in the wallet sheet equals the page price.**
- The options endpoint (E6) computes the amount from the same `priceProjection()` the page rendered, issues spec 005's signed quote for it, and returns the total, the currency and the sheet's lines: the bouquet and size, and the date surcharge when there is one. Delivery is shown as one delivery option named "Delivery on {date}" at the surcharge amount (zero when there is none). The sheet's total is the quote's total, in integer minor units, in the currency the page showed for that locale (the stale-FX rule of AC-18 included).
- Changing the size or the date asks the endpoint again and updates the element's amount before the button can be used again.
- At placement the server verifies the quote and compares the amount the sheet showed with its own total. If they differ (an hourly regeneration changed the price under the open page), nothing is placed, the sheet closes with a failure, and the panel shows spec 010's price-changed notice naming both amounts (`checkout.price.changed`); the buyer taps again at the new amount. No order is ever written, and no payment ever created, at an amount the sheet did not show.
- No approximate-equivalents line, no discount and no strike-through in the sheet or the panel.

**E6 Server side.** Three thin route handlers under `src/app/api/checkout/express/`, each POST only, `no-store`, `X-Robots-Tag: noindex`, Origin-checked like the start route (AC-6), each calling `src/modules/checkout/express.ts`:
- `options/route.ts`: body `ExpressOptionsRequestSchema` `{ locale, countryIso, sku, tierKey, date }` (no personal data); answers `ExpressOptionsSchema` `{ mode: 'demo'|'test'|'live'|'closed', wallet: 'fake'|'stripe'|'none', publishableKey?, amountMinor, currency, lines: { labelKey, labelArgs, amountMinor }[], quoteToken, preContract: boolean, legalRegime: 'uk'|'eu' }`. Sets no cookie.
- `address/route.ts`: body `ExpressAddressCheckSchema` `{ countryIso, postcode, city?, date, sku, tierKey, mode }` from the sheet's partial address; answers ok or a reason (`bad_postcode`, `no_coverage`, `no_capacity`) so the sheet can refuse it in place. Coverage only in `test` and `live` (A3.2's rule). The postcode is never logged (A3's AC-50 rule).
- `place/route.ts`: body `ExpressPlaceSchema` `{ attemptId (uuid from the island, one per sheet), quoteToken, expectedTotalMinor, expectedCurrency, locale, countryIso, sku, tierKey, date, cardMessage, recipientPhone, delivery: { name, addressLines[], postalCode, city, countryIso }, payer: { name, email, phone?, billingCountryIso? } }`. It runs, in order: `checkoutMode()`; the flag; the quote and the amount (E4); the date re-check at now in the destination's zone (AC-19); the recipient schema, the phone and the card-message limits (AC-8 to AC-10); the coverage check in `test` and `live` (A3.2); the daily demo cap in `demo` (AC-27). Then it creates a `checkout_draft` with `steps_completed = 3` and `entry = 'express'`, and calls the same placement path as `placeOrderAction` (one transaction, `orderService.place`, then in `demo` `transition('order.authorised')` and `demoRoute()`, AC-20). In `test` and `live` it then calls spec 013's registered payment step `confirm(orderId)` and answers `{ outcome: 'pay', clientSecret }`; in `demo` it answers `{ outcome: 'placed' }`. Any refusal answers `{ outcome: 'refused', reason }` with nothing written. It sets `fo_checkout` exactly as the start route does, so the confirmation page (AC-29, A2.4) works unchanged. `attemptId` is the idempotency key: a repeated `place` with the same `attemptId` returns the same order and the same intent (AC-21's rule, AC-91). The island keeps one `attemptId` until the payment succeeds or the buyer changes the size, the date, the card message or the phone, so a retry after a decline pays the same placed order; a changed selection starts a new attempt, and the earlier unpaid order is closed by spec 013's sweep (its 2-hour rule), never charged.
- In `test` and `live` the island then calls Stripe's `confirmPayment` with the element and the client secret (`redirect: 'if_required'`, `return_url` spec 013's return route); success navigates to `/{locale}/checkout/done`; a decline closes the sheet with the failure and the panel shows spec 013's decline message for its code, and the buyer may tap again (the same placed order and intent, spec 013's retry rule). Spec 013's reconcile writes `order.captured`; nothing here touches status.
- **Data model.** One migration, `NNNN_express_entry.sql` with `NNNN_express_entry.down.sql`: `checkout_draft.entry text NOT NULL DEFAULT 'checkout' CHECK (entry IN ('checkout','express'))` and `"order".checkout_channel text NOT NULL DEFAULT 'checkout' CHECK (checkout_channel IN ('checkout','express'))`, written by `place` from the draft. Rollback: drop both columns. Nothing else changes; the order is an ordinary order with `place_kind = 'home'` and no note.

**E8 Performance: the product page's budgets do not move.**
- **Nothing in the first load.** The panel, the adapters and Stripe.js load only after the buyer's first interaction with the product page's purchase form (a `pointerdown`, `keydown`, `focusin` or `change` inside the form), scheduled after that interaction's next paint so the interaction itself stays fast (INP). The raise is never used for this: if the listener does not fit under the restored budget, the task trims elsewhere first; it never raises a budget.

- **No layout shift.** The panel appears without moving anything already on screen (a reserved place in the sticky mobile bar, or below content that is out of view; the designer chooses in the artboard), so CLS stays 0 (an e2e layout-shift observer after the interaction, AC-95).

**E10 No JavaScript, unsupported browsers, and failures.**
