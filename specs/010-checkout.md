## 1. Problem

The product page (spec 009) ends with one all-in price for a tier and a date, and then stops: in
Phase 0 it has "no purchase affordance at all" (009 §3). The 16 October demo has to show a florist
the whole buyer journey — "pick Poland → PDP → date → checkout → place order (no charge)"
(`plan/09` Phase 0 AC 4) — and Phase 1 has to take a real buyer's money for a real delivery
(`plan/09` Phase 1 AC 1–2). Both need the same pages. Nothing in the repository collects a
recipient, a buyer or a card message, and the `(checkout)` route group is empty.

Checkout is where three of our five priorities meet. Conversion: guest-first, mobile-first, at most
eight fields per step (`plan/04` §9). Compliance: the price shown must be the price charged, the
pre-contract information and the perishable-goods exception must appear before the pay button, and
the recipient's data must be minimised (`plan/07` §1.3, §2, §4). Honesty: while no florist is
signed, nothing on these pages may take money or pretend an order exists. This spec builds the
flow once, with a **demo guard** that decides — from data, in one function — whether a given
checkout may charge anyone. In Phase 0 the answer is always no.

## 2. Scope

Each bullet is testable; §9 names the AC.

**The guard (one function, one answer)**

- `checkoutMode(iso2, locale)` returns `closed`, `demo` or `live`, with the list of reasons.
  `live` needs **all** of: `APP_ENV === "production"`; `pickerState(iso2) === "live"` (009); the
  flag `checkout.demo_guard` explicitly off (an absent flag counts as on); `company.registered`
  (spec 004's `company.ts`); the locale's `checkout.legal.*` keys reviewed; and every Phase 1 port
  bound (§5.2). `closed` when the picker is `unavailable`, or `preview` in production. Everything
  else is `demo`. In Phase 0 no country can reach `live`. (AC-1, AC-2)
- **Demo mode charges nothing.** No processor call, no order row, no `consent_log` row. "Placing"
  a demo order marks the draft `placed_demo` and shows the demo confirmation. A banner that cannot
  be dismissed says so on every step and on the confirmation. If spec 013's Stripe hand-off is
  bound while the mode is `demo`, it is told `test` and the key check refuses a live key. (AC-3, AC-4)
- `purchasePathExists(iso2)` is published for spec 009's gated `Offer`: it is true only when
  `checkoutMode` is `live`. (AC-26)

**Entry from the product page (an amendment to spec 009, §5.1)**

- The PDP's one form gains a second submit button, posting to `/{locale}/checkout/start`. It
  renders in the `live` picker state ("Continue to checkout"), and in the `preview` state outside
  production only ("Try the demo checkout — no order, no charge", §13 Q1). In production `preview`
  and in `unavailable`, the PDP is unchanged. It is a button, never an `<a>`, so no crawler can
  follow it. (AC-5)
- The start handler validates the product, tier and date on the server, creates a draft, issues a
  quote, sets the `fo_checkout` cookie and redirects to the checkout. (AC-6, AC-10)

**The flow: three steps on one path (`plan/04` §9)**

- **Step 1 — Recipient.** Name, phone (required), address in the destination's format, place kind
  (home, office, hospital, hotel, funeral home) with one details field, delivery note, the date
  (carried from the PDP, editable, same surcharge on each chip), add-ons (unticked), card message
  and "sign as". (AC-11–AC-14)
- **Step 2 — You.** Email, name, optional phone, country of residence, one unticked marketing
  checkbox. (AC-15, AC-16)
- **Step 3 — Review and pay.** The itemised summary, VAT by rate, the pre-contract block, the
  payment-method slot, and the place button that names the amount. (AC-8, AC-17–AC-19)
- **Confirmation** at `/{locale}/checkout/confirmation/{token}`: the demo state is built here; the
  live state is spec 018's (§3). (AC-20, AC-21)

**Money**

- The checkout total with no add-ons is **the same integer in the same currency** as the PDP's
  total for that tier and date (009's `dateTotals`, 005's `priceProjection`). Add-ons and the date
  surcharge are the only other lines, each visible before it is chosen. (AC-7, AC-8)
- The price is locked by 005's 30-minute signed quote, re-issued whenever a line changes and
  verified at place. An expired quote at the same total is re-issued; a different total is shown
  and needs a new click. (AC-9)
- The date is re-checked against `now` in the destination's time zone at every step and at place.
  (AC-12)

**Payment-method slots (interfaces only)**

- An express-wallet slot above step 1's first field and a method slot on step 3, both filled from
  `methodsForBuyerCountry(country)` (GB: Apple Pay, Google Pay, card, PayPal, Klarna; PL: BLIK,
  Przelewy24, card, Apple Pay, Google Pay, PayPal; `plan/04` §10). Only methods marked `available`
  render, so in Phase 0 both slots render nothing. Specs 013 and 014 fill them. (AC-19)

**Cross-cutting**

- Works with JavaScript off; server-side Zod is the only validator; no PII in URLs, logs or
  analytics; `no-store`, `noindex`, `no-referrer` on every response; en-gb and pl flows tested end
  to end; WCAG 2.1 AA. (AC-22–AC-31)

## 3. Non-goals

- **Payment processing** — Payment Intents, the Payment Element, 3DS, manual capture, webhooks,
  Apple Pay and BLIK themselves → spec 013 (Stripe), 014 (Mollie). 010 defines the hand-off port and
  the slots; it never imports a processor SDK.
- **Creating the order, the customer and the recipient rows, and `orderService.transition`** →
  spec 015 (ADR-0009). 010 hands a `PlacementRequest` to a port; it never writes `"order"`,
  `order_event`, `customer`, `recipient` or `consent_log`.
- **Postcode coverage by florist, capacity, routing** → spec 016 (`plan/06` §5.1–§5.2). 010 asks
  a `CoveragePort`; there is no live mode without one.
- **The live confirmation content, the tracking page, the invoice PDF, `.ics`, share-to-WhatsApp**
  → spec 018. **The confirmation email (durable medium)** → spec 017, which reuses 010's
  `PreContractInfo` view model.
- **The demo vendor inbox and the admin queue** → specs 011 and 012. They read demo placements
  through `listDemoPlacements()` (§5.2); 010 renders neither.
- **Fraud pre-checks and the review queue** (card-message patterns, velocity, €300 review) →
  spec 021. **GA4 events** → spec 023 (010 emits server log events only, §11).
- **A basket page, more than one product per order, quantities above one** → later (`plan/04` §8).
- **Accounts, "create a password", magic-link login** → spec 019. **WhatsApp/SMS delivery
  updates opt-in** → spec 017 (§13 Q10). **"Pay in PLN instead"**, the currency menu → later (005
  AC-9 forbids a currency override today). **Address autocomplete** → Phase 4 (`plan/04` §9).
- **The terms, privacy and withdrawal pages themselves** → the legal set (spec 007 template, lawyer
  review, `plan/13` B4). 010 links to them and records their versions.

## 4. User stories

- As a **buyer in London sending to Warsaw**, I go from the product page to a paid order in three
  short steps, the total never changes from the number I saw, and I am told why each field is asked.
- As the **same buyer on a phone with scripts blocked**, every step still works and the back
  button does not lose what I typed.
- As a **buyer on `/pl/`**, the address form is Polish (`00-001 Warszawa`), the phone takes `+48`,
  the total is in złoty, and no English appears.
- As a **screen-reader user**, errors are listed at the top with links to the fields, and the
  total is announced when it changes.
- As a **florist watching the 16 October demo on staging**, I see the full flow and a banner on
  every screen telling me nothing is real; I then see the order land in the demo inbox (spec 011).
- As the **founder**, flipping a country from demo to live is a florist row, a flag and a
  reviewed legal text — not a code change — and nothing can charge a card before all of them exist.
- As the **implementer of spec 013**, I receive one quote, one draft reference and one mode, and
  the amount I charge is the number on the review step.
- As **Googlebot**, I never see a checkout URL: no link, no sitemap row, `Disallow` in `robots.txt`.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

**One new table, `checkout_draft`**, in the next free migration number at merge time, with its
`.down.sql` (`DROP TABLE checkout_draft;`). It is the server-side state `plan/04` §9 asks for
("state saved server-side per step so refresh and back never lose data") and the `abandoned (draft
expiry)` edge of `plan/11` §2.

```
checkout_draft(
  id uuid PK, token_hash bytea UNIQUE NOT NULL,          -- SHA-256 of the cookie value; the value is never stored
  locale_code, destination_iso2, sku, tier_key, delivery_date date,
  addon_keys text[] NOT NULL DEFAULT '{}',
  recipient jsonb NULL, buyer jsonb NULL, consents jsonb NULL,   -- each Zod-parsed on write and read
  quote jsonb NOT NULL, price_version text NOT NULL,
  step smallint NOT NULL, mode text CHECK IN ('demo','live'),
  status text CHECK IN ('open','placed_demo','handed_off') NOT NULL DEFAULT 'open',
  confirmation_token_hash bytea NULL UNIQUE,
  created_at, updated_at, expires_at timestamptz NOT NULL       -- updated_at + 24 h (§13 Q3)
)
```

RLS on, deny by default; read and written only through `withSystemContext` (spec 002 §5). No
foreign key to `customer` or `"order"`: a draft is not yet either. Money lives only inside the
signed `quote` (integer minor units plus ISO currency, spec 005). `db:check`'s money-pair and
no-recipient-email rules apply: the `recipient` jsonb schema has no email key (AC-13).

**Four amendment requests** (the founder rules on them with this spec):

1. **Spec 002 §14** — add `checkout_draft` above to the schema of record, owned by 010.
2. **Spec 005 §14** — `QuoteLineInput` gains `kind: "product" | "surcharge" | "addon"` and an
   optional `addonKey` / `date`; `QUOTE_PAYLOAD_VERSION` increments, so an old quote verifies as
   `tampered`, never as `ok`. `signingSecret()` reads `QUOTE_SIGNING_SECRET` from `lib/env.ts`
   (005 §13 Q5 put the secret here). Rollback: revert both.
3. **Spec 009 §14** — the CTA slot of §2 (live state, and non-production preview), and the
   `purchasePathExists` input to the `Offer` gate. The island, the totals table and the GET form
   are unchanged. Rollback: remove the button; the PDP returns to 009's demo sentence.
4. **Spec 004 §14** — the cookie register replaces the declared `fo_basket` row (cart-less: there
   is no basket) with `fo_checkout`: essential, first party, written by the **server**, `HttpOnly;
   Secure; SameSite=Lax; Path=/; Max-Age=86400`, set only on `no-store` checkout responses. The
   register's "no server writer" refinement is relaxed for rows flagged `noStoreOnly`, and AC-22 of
   spec 004 still forbids `Set-Cookie` on any cached response. `payment-methods.ts` gains the
   additive `methodsForBuyerCountry()` ordering. Rollback: restore the rows.

**Rollback of this spec:** `git revert` of its task commits, the down migration, and the PDP button
removed. No order, payment or consent row exists to orphan, because 010 writes none.

### 5.2 API / server actions / jobs / events (zod schemas named)

Code lives in **`src/modules/orders/checkout/`**, exported through the `orders` barrel (`plan/01`
§5 has no `checkout` module; a draft is the step before an order, and spec 015 adds the state
machine beside it). Routes are thin, in `src/app/[locale]/(checkout)/checkout/`.

```
src/modules/orders/checkout/
  mode.ts          checkoutMode, purchasePathExists, paymentModeFor, assertProcessorKeyMatchesMode
  schemas.ts       the Zod schemas below
  draft.ts         DraftStore interface; drizzle and in-memory implementations; sweep
  lines.ts         checkoutLines (product, surcharge, add-ons) → quote inputs; reviewSummary
  validate.ts      recipient phone and postcode per destination; card-message grapheme rule
  ports.ts         PlacementPort, PaymentHandoff, CoveragePort, ConfirmationPort + demo implementations
  precontract.ts   preContractInfo(draft, regime) → the view model 010 renders and 017 emails
  demo.ts          placeDemo, listDemoPlacements
  rate-limit.ts    RateLimiter interface; in-memory implementation (single replica, ADR-0018)
src/app/[locale]/(checkout)/checkout/
  start/route.ts                 POST only
  page.tsx                       the three steps (server actions per step)
  confirmation/[token]/page.tsx
```

**Zod schemas** (parsed at every boundary — form post, draft read, port call):

- `CheckoutStartSchema` — `{ sku, country, tier, date: IsoDate, pv: string }`; `pv` is the
  `priceVersion` + `fxAsOf` the PDP was rendered with. Strict: unknown keys are refused.
- `RecipientStepSchema` — `{ fullName (1–120), phone (E.164 after parse, destination plan),
  address: AddressFor<iso2> (fields, order, postcode pattern and normaliser from
  `config/address-formats.ts`), placeKind: home|work|hospital|hotel|funeral_home (default home),
  placeDetails? (≤120), deliveryNote? (≤120), date: IsoDate, addonKeys: AddonKey[] (unique),
  cardMessage? (≤200 graphemes), signAs? (≤40 graphemes) }`. **No email key.**
- `BuyerStepSchema` — `{ email, fullName (1–120), phone? (E.164), countryOfResidence: Iso2,
  marketingConsent: boolean }`.
- `PlaceSchema` — `{ quoteId, confirmPriceChange?: true, confirmDateChange?: true }`.
- `CheckoutDraftSchema` — the row, with `recipient`, `buyer` and `consents` parsed on read, so a
  corrupt row fails closed (the explanation page), never renders.
- `PlacementRequestSchema` — what the port receives: draft id, quote, recipient snapshot
  (`plan/11` §3), buyer, consents `{ marketing, policyVersion, termsVersion, privacyVersion }`,
  regime, mode.

**Ports** (§2, AC-1). Each has a demo implementation in 010 and a Phase 1 implementation owned
elsewhere. `checkoutMode` treats a port as bound only when a non-demo implementation is registered.

| Port | Shape | Phase 0 (010) | Phase 1 owner |
|---|---|---|---|
| `PlacementPort` | `place(PlacementRequest) → { orderToken }` | `placeDemo`: draft → `placed_demo`, token minted | 015 (customer, recipient, `"order"` via `orderService`) |
| `PaymentHandoff` | `start({ orderToken, quote, methodId, mode: "test" \| "live" }) → { kind: "client_secret" \| "redirect" \| "none", … }` | none bound | 013 / 014 |
| `CoveragePort` | `covers(iso2, postcode, date) → boolean \| null` (`null` = unmodelled) | `null` | 016 |
| `ConfirmationPort` | `view(token) → ConfirmationView` | demo view from the draft | 018 |

**Behaviour worth pinning**

- `checkoutMode()` is the only place the mode is decided; every route and component asks it.
- Every money value comes from 005 (`priceProjection`, `dateSurcharges`, `listAddons`,
  `vatBreakdown`, `quote`, `verifyQuote`); no checkout file does arithmetic on prices other than
  005's `sumMoney`.
- Every date decision comes from 009's calendar (`isDateAvailable` in the destination's IANA zone).
  In `demo` mode for a `preview` country, the calendar facts (cutoff, weekdays, holidays) apply; the
  picker's "nothing selectable" display rule does not, because a demo order promises nothing.
- Writes are post-redirect-get: a valid step saves the draft and answers 303 to the next step; an
  invalid step answers 200 with the errors and the typed values. Step server actions check the
  `Origin` header (Next's built-in check plus an explicit test); `start/route.ts` checks it itself.
- **Sweep**: `checkout.draft_sweep` deletes rows with `expires_at < now()` — as a pg-boss job once
  spec 002's TASK-024 lands, and until then as a bounded delete (≤100 rows) inside every draft
  write. Demo placements expire the same way.

### 5.4 Rendering & caching (SSG/ISR/SSR, tags invalidated, per plan/01 §3)

- Every checkout and confirmation response is SSR with `Cache-Control: private, no-store`,
  `X-Robots-Tag: noindex, nofollow`, the robots meta, and `Referrer-Policy: no-referrer` (the
  confirmation token must not leak to a third party). `plan/01` §3 row "Cart, checkout, order
  confirmation".
- These are the only routes that set a cookie (`fo_checkout`), and only on `no-store` responses.
- CSP: the route may use a per-request nonce (ADR-0016's `no-store` branch). In demo mode it loads
  no third-party script; spec 013 adds the processor origins when it binds.
- The PDP stays ISR. The CTA is server-rendered HTML in the existing form; it adds no script, no
  cookie and no `Vary` to the cached page. No tag is invalidated by checkout.
- Budget: ≤131 072 B Brotli first-load JS on each checkout page (`plan/01` §7, 009 §5.4).

## 6. SEO considerations (mandatory)

- **Indexability**: never. `noindex, nofollow` by header and meta on every checkout and
  confirmation response, `Disallow: /*/checkout` in `robots.txt` for every locale, and no checkout
  URL in any sitemap (`plan/02` §4.1 row "Cart, checkout, confirmation", §7).
- **No crawl path**: the PDP's entry is a form button posting to a route that refuses `GET`; there
  is no `<a href>` to a checkout URL anywhere on the site (asserted by the crawl test).
- **Canonical / hreflang**: none emitted on these pages; they are not part of any cluster.
- **URL pattern**: `/{locale}/checkout` and `/{locale}/checkout/confirmation/{token}`; the segment
  is not localised because the pages are never indexed. `?step=` carries only a step name.
- **Schema**: none on checkout pages. On the PDP, 010 publishes `purchasePathExists(iso2)`; 009
  emits its `Product` + `Offer` only when that is true. In every Phase 0 configuration it is
  false, so no `Offer` appears for a country nobody can buy from (`plan/02` §9; 009 §6).
- **PDP impact**: the CTA is one button inside the existing form. No change to the PDP's
  indexability, canonical, LCP element or script budget (009's budgets re-run green).
- **Thin content / duplication / CWV**: not applicable to non-indexed pages; the checkout keeps the
  site's performance budgets because it is the conversion path (`plan/04` §15).

## 7. i18n considerations (mandatory)

- **New namespaces**: `checkout.*` (steps, field labels where 003's `address.*` keys do not exist,
  the "why we ask" lines, errors, states, the demo banner, button labels), `checkout.legal.*` (the
  pre-contract block in `eu` and `uk` variants, the withdrawal-exception sentence, the
  recipient-data sentence, the cancellation sentence), `confirmation.*`. All ICU, typed, no
  literals. English copy goes to the founder in one batch (decisions log, 2026-10-03).
- **Live needs reviewed legal copy**: `checkoutMode` returns `live` only for a locale whose
  `checkout.legal.*` keys are all `reviewed` (founder for `en`/`en-gb`, native reviewer plus lawyer
  for `pl`, `plan/13` B4, B12). In Phase 1 that is `en-gb` and `pl`; `en` and `de` render with
  drafted keys and stay `demo`.
- **Polish register**: informal in the UI, formal in `checkout.legal.*` (`plan/13` A5's default).
- **Formatting**: money by `formatMoney`; the delivery date by `formatDate` with weekday and month
  name; the cutoff by `formatTimeInZone` with the destination zone named (`plan/03` §7, §10). The
  grapheme counter is a new `countGraphemes()` in `modules/i18n/format.ts`, the only place `Intl`
  objects are built (`fo/no-adhoc-intl`).
- **Addresses and phones**: the recipient form follows the **destination's** row in
  `config/address-formats.ts` (field order, required fields, postcode pattern, normaliser,
  placeholder); PL is required for Phase 1, GB and DE rows already exist. Phones are parsed to
  E.164 against the destination's numbering plan for the recipient and the buyer's country for the
  buyer, and shown in national format. Diacritics are accepted and preserved (NFC).
- **Plurals**: the counter ("12 of 200 characters") and stem counts are ICU plurals, Polish
  one/few/many tested.
- **RTL**: logical properties only; names, the card message and every label/amount pair are in
  `<bdi>`; the `/ar-XB` pseudo-locale renders each step for the visual baseline.
- **Buyer country default**: `en-gb` → GB, `pl` → PL, `de` → DE, `en` → no default (the buyer
  picks). Never inferred from IP (ADR-0006).

## 8. Compliance considerations (mandatory)

- **Data flows added → RoPA** (`docs/compliance/ropa.md`, two rows):
  1. *Checkout draft* — buyer (name, email, phone, country) on contract basis (Art. 6(1)(b));
     recipient (name, phone, address, place details, note, card message) on legitimate interest
     (Art. 6(1)(f)), minimised per `plan/07` §1.3; marketing consent choice. Stored in Neon (EU);
     deleted 24 h after the last change; no processor beyond the existing host and database.
  2. *Demo placements* — the same fields, typed on staging or preview by the founder or a florist
     during a demo; same 24 h deletion; never sent anywhere.
  Phase 1's order, payment and consent rows are recorded by specs 013, 015 and 019.
- **Lawful basis and consent**: one marketing checkbox, unticked, separate from the place button,
  never a condition of ordering (`plan/07` §1.2: explicit consent everywhere). Its value and the
  policy version travel in `PlacementRequest`; spec 015/019 writes `consent_log`. The recipient
  acknowledgment is a sentence beside the button, not a checkbox (`plan/07` §1.3 "light-touch";
  §13 Q5).
- **Recipient minimisation**: no recipient email field exists anywhere (schema, HTML, draft).
  Phone is required and the reason is printed (`plan/03` §8, `plan/07` §1.3). The confirmation
  page shows the recipient's city only.
- **Price display**: the total includes VAT and delivery; the date surcharge is on the chip before
  it is chosen; add-ons start unticked (CRD Art. 22); the total is identical for every payment
  method (CRD Art. 19, no surcharge) and every buyer country (Geo-blocking Regulation Art. 4); the
  review step shows VAT by rate and, when currencies differ, "you pay in GBP; the florist is paid
  in złoty" (`plan/07` §4). The amount charged is the quoted amount on the review step.
- **Pre-contract information** (CRD Art. 6; UK CCRs Sch. 2): main characteristics, trader identity
  and address (from `company.ts`, placeholders while `registered` is false — which also keeps the
  mode `demo`), total price, payment and delivery arrangements, complaints route, the withdrawal
  position, links to terms and privacy, all server-rendered above the button. The regime follows
  the buyer's **country of residence**: GB → UK wording (CCRs reg. 28(1)(c)); anywhere else → EU
  wording (CRD Art. 16(d)). Non-perishable add-ons are disclosed as part of one gift pending
  `plan/13` B6. `terms_version` and `privacy_version` are recorded.
- **Button solution** (CRD Art. 8(2)): live "Pay {amount} and place order" (de: "Zahlungspflichtig
  bestellen · {amount}"); demo "Place demo order — no charge".
- **Cancellation promise**: "You can cancel free of charge until our florist accepts your order"
  (`plan/07` §2.3; §13 Q6). The contract is formed on capture after acceptance (spec 013/015).
- **Geo-blocking**: country of residence is self-declared, defaulted from the locale, freely
  changeable; it changes the method order and the legal wording, never the price or access
  (`plan/07` §3). No IP lookup anywhere.
- **Accessibility** (EAA, WCAG 2.1 AA, `plan/07` §8): labels, `fieldset`/`legend`, error summary
  with links, `aria-describedby`, no colour-only signals, keyboard-only completion, 200% reflow at
  390 px, no time limit except the 30-minute quote — and its expiry loses nothing (the draft
  survives; the buyer confirms a new total only if it changed). axe in CI on every step and state.
- **Logs and PII**: logs carry `draft_ref` (first 8 hex of the token hash), step, locale,
  destination, mode, outcome and duration — never a name, email, phone, address, card message,
  token or IP. Validation failures log field names, not values. URLs carry no submitted value. The
  rate limiter keys on a salted hash of the IP held in memory only.
- **Security**: `Origin` check on every POST; HttpOnly cookie; only the token's hash is stored;
  ≥128-bit random tokens; rate limits on start and place; no processor key is read by 010 except
  through `assertProcessorKeyMatchesMode` in 013's boot path.

## 9. Acceptance criteria

**The guard**

- **AC-1** `checkoutMode(iso2, locale)` returns `live` only when all six conditions of §2 hold. A
  table test flips each condition alone from an all-true fixture and gets `demo` every time; an
  absent `checkout.demo_guard` flag counts as on.
- **AC-2** `checkoutMode` is `closed` for an `unavailable` country in every environment and for a
  `preview` country in production; then `POST /{locale}/checkout/start` answers 303 to the bare PDP
  and the PDP renders no checkout button.
- **AC-3** In `demo` mode, placing an order makes no request to any host outside the app (asserted
  with the network blocked), writes no `"order"` or `consent_log` row, sets the draft to
  `placed_demo`, and renders the demo banner on all three steps and the confirmation in all four
  locales, with no control that hides it.
- **AC-4** `paymentModeFor("demo")` is `test` and `paymentModeFor("live")` is `live`; a fake
  `PaymentHandoff` bound in demo mode never receives `live`; `assertProcessorKeyMatchesMode`
  refuses a `sk_live_`/`pk_live_` key in `test` mode and a `sk_test_`/`pk_test_` key in `live`.

**Entry from the product page**

- **AC-5** The PDP renders the checkout button (a `<button>` with `formaction` and
  `formmethod="post"`, no `<a>`) in the `live` picker state, the demo button in `preview` outside
  production, and neither in production `preview` or `unavailable`. The PDP sets no cookie, sends
  no `Vary`, and its island, totals table and script budget are unchanged (009's tests re-run green).
- **AC-6** `POST /{locale}/checkout/start` with a valid body creates a draft, sets `fo_checkout`
  with exactly the §5.1 attributes, and answers 303 to `/{locale}/checkout`. A body failing
  `CheckoutStartSchema`, a product page that does not exist, or a date not open in the destination
  zone at `now` answers 303 to the bare PDP and creates nothing. `GET` answers 405.

**Money**

- **AC-7** For every tier of three fixture products × every open date in a 14-day window × `en-gb`
  and `pl`, the checkout total with no add-ons equals `productView().totals[tier][date]`: the same
  integer and the same currency.
- **AC-8** The review step's lines (product and tier, the date surcharge when there is one, each
  add-on, the card at zero) sum exactly to the total; the VAT lines equal 005's `vatBreakdown`; and
  the total is identical for buyer countries GB, PL and DE and for every method in the slot fixture.
- **AC-9** Each change of tier, date or add-ons re-issues the quote. At place: a tampered quote is
  refused; an expired quote whose re-derived total is unchanged is re-issued and the place goes
  through; a changed total renders the price-changed state with both totals and places nothing until
  the buyer confirms. No path places or hands off an amount not shown on the review step.
- **AC-10** When the `pv` posted from the PDP differs from the current price version, step 1 shows
  the price-updated notice with the current total above the first field.
- **AC-11** Step 1 offers the destination's add-ons from `listAddons()` (wine absent for PL, flags
  respected), each with its price and VAT rate, none with a `checked` attribute in the HTML; a body
  repeating an add-on key is refused.

**Dates and data**

- **AC-12** Step 1's date chips show the same surcharge amounts as the PDP for the same date. At
  every step submit and at place, a date no longer open at `now` in the destination zone renders the
  date-unavailable state naming the next open date and its total; nothing is placed until the buyer
  confirms a date.
- **AC-13** The recipient step collects exactly the `RecipientStepSchema` fields, in the
  destination's address order, with the destination's postcode pattern and normaliser; phone is
  required and stored as E.164. No `email` key exists in the schema, the draft row's `recipient`
  value or the step's HTML (key-set test plus a grep).
- **AC-14** The card message accepts 200 graphemes and refuses 201 on the server even with the
  client check bypassed; a Polish diacritic, a Cyrillic letter, a flag emoji and a ZWJ family emoji
  each count as one; control characters are stripped and the text is stored NFC. `signAs` refuses
  41 graphemes.
- **AC-15** The buyer step requires email and name, takes an optional phone, and requires a
  country of residence defaulted per §7. Changing the country changes the method order and the
  legal wording on step 3 and leaves every money value unchanged.
- **AC-16** Apart from the add-on group, the only checkbox in the flow is the marketing one:
  unticked in the HTML, not required, and its value plus the policy version present in the `PlacementRequest`. The
  recipient-data sentence renders beside the place button.

**Review, pay and confirmation**

- **AC-17** Step 3 renders, server-side and above the button, every item of §8's pre-contract list;
  the withdrawal sentence is the UK variant for a GB resident and the EU variant otherwise; the
  draft records `terms_version` and `privacy_version`.
- **AC-18** The place button names the amount through `formatMoney`: "Pay {amount} and place
  order" in `live` (the `de` variant per §8), "Place demo order — no charge" in `demo`. No button in
  the flow reads "Confirm" or "Submit" alone.
- **AC-19** With a fixture marking Apple Pay and BLIK `available`, a GB buyer sees Apple Pay first
  in the express slot and a PL buyer sees BLIK first on step 3, in `plan/04` §10's order. With
  nothing `available` (the committed config), neither slot renders any method name or logo.
- **AC-20** A demo place answers 303 to `/{locale}/checkout/confirmation/{token}` with a random
  token of at least 128 bits, clears `fo_checkout`, and the page shows the demo banner, the order
  summary, the recipient's city only and the buyer's email masked — no street, phone, recipient
  name or card message — and every link that would open a real order is inert. An unknown or
  expired token returns 404 with the localised `lang` document.
- **AC-21** A live confirmation renders only through a bound `ConfirmationPort`; with the demo
  implementation, AC-1 keeps the mode `demo`, so no live confirmation can render.

**Flow mechanics**

- **AC-22** With JavaScript disabled, en-gb and pl buyers complete all three steps and a demo place;
  the browser back and forward buttons and a reload restore every typed value from the draft; a
  `?step=` beyond the first incomplete step redirects to it.
- **AC-23** An invalid step answers 200 with an error summary linking to each failing field, a
  message under each field linked by `aria-describedby`, and every typed value kept.
- **AC-24** A draft expires 24 h after its last write: an expired cookie gets the explanation page
  and no data; the sweep (clock fixture) deletes expired drafts and demo placements and nothing
  else; the table holds the token hash, never the token.

**Rendering, SEO, privacy, budgets**

- **AC-25** Every checkout and confirmation response carries `Cache-Control: private, no-store`,
  `X-Robots-Tag: noindex, nofollow`, the robots meta and `Referrer-Policy: no-referrer`;
  `robots.txt` disallows `/*/checkout`; no sitemap lists a checkout URL; the crawl finds no `<a>`
  to one.
- **AC-26** `purchasePathExists(iso2)` is false for every destination in every committed
  configuration, and 009's `Offer`-absence test stays green; flipping a fixture to `live` mode makes
  it true for that country only.
- **AC-27** The e2e suite completes the flow in `en-gb` (GB buyer to Warsaw) and `pl` (PL buyer,
  `00-001`, `+48`) with JavaScript on and off; `pl` shows no English string (missing-key check);
  `en` and `de` render every step.
- **AC-28** axe reports zero serious or critical issues on each step and each state of §5.3 in
  `en-gb` and `pl` at 390 and 1440 px; the flow completes by keyboard alone; every field has its
  `autocomplete` token and a font size of at least 16 px.
- **AC-29** Over one full e2e run, no request URL contains any submitted value, and a capturing
  logger shows only allow-listed keys and none of the submitted values; a validation failure logs
  field names only.
- **AC-30** A cross-origin `POST` to start, a step or place answers 403; more than 20 starts or 10
  places per hour from one client answers 429 with the localised page; no IP is logged or written.
- **AC-31** Each checkout page's first-load JS is at most 131 072 B Brotli, and in `demo` mode no
  third-party script loads.

- **Flags and data**: `checkout.demo_guard` (spec 002 seeds it on; absent counts as on), read
  through one `checkoutFlags()` reader with a static Phase 0 provider, so spec 002's
  `feature_flag` table and spec 012's admin take over with no call-site change (the 005/009
  pattern). Going live in a country is data: a florist row (007's `ActivePartnersProvider`), the
  flag off, `company.registered`, reviewed legal keys, and the Phase 1 ports bound. No code change.
- **Environments**: local and CI (in-memory draft store when `DATABASE_URL` is unset, Postgres in
  integration tests) → preview and staging (Postgres, `demo` mode, the 16 October demo runs on

  migration drops the table. It depends only on spec 002's migration runner (TASK-014, done).
  Integration tests need spec 002's PG16 CI service (TASK-027); if it has not landed, task 1 below
  runs its integration cases against the in-memory store and carries the Postgres cases as `todo`
  until it does.
- **Design first**: `/design` updates the two checkout and two confirmation artboards, the PDP
  artboards' CTA slot, and `flows/buyer-journey.dc.html`, with every state in §5.3, before

## 13. Open questions

Each has a recommended default; "yes to all" approves every default.

- **Q1 — How does the 16 October demo reach checkout?** Poland's picker is `preview`, which by
  spec 009 has no selectable date and no button. **Recommended:** outside production only, the
  `preview` PDP shows "Try the demo checkout — no order, no charge", and checkout uses the calendar
  facts for dates. Production keeps 009's honest sentence. *Alternative:* count demo florists as
  active on staging, so the PDP is `live` there (contradicts 009's demo story and prints cutoff
  promises on staging).
- **Q2 — Where are add-ons chosen?** **Recommended:** on checkout step 1 only, for Phase 1. The PDP
  keeps its priced list, so 009's island and totals table do not change. *Alternative:* checkboxes
  on the PDP too (`plan/04` §8), which multiplies 009's totals table and island work.
- **Q3 — Where does the draft live, and for how long?** **Recommended:** a Postgres
  `checkout_draft` row, deleted 24 h after the last change, found by an HttpOnly `fo_checkout`
  cookie that replaces the declared `fo_basket`. *Alternative:* an encrypted cookie holding the
  whole draft (no table, but personal data in the browser and a 4 KB ceiling).
- **Q4 — Does the demo use Stripe test mode?** **Recommended:** not for 16 October: the demo place
  calls no processor. Once spec 013 lands, staging can bind Stripe in test mode behind a
  `payments.stripe_test` flag, and the key check refuses any live key there. *Alternative:* build a
  Stripe test-mode Payment Element into 010 now (pulls spec 013's work forward).
- **Q5 — Legal copy and checkboxes.** **Recommended:** ship `plan/07` §2.1's wording as drafts for
  the demo; live mode needs the lawyer-reviewed keys (`plan/13` B4, B6). No "I accept the terms"
  checkbox (the button and the link suffice), and the recipient-data acknowledgment is a sentence,
  not a checkbox. *Alternative:* add either checkbox.
- **Q6 — Which cancellation promise?** **Recommended:** `plan/07` §2.3's "cancel free of charge
  until our florist accepts your order". *Alternative:* the artboard's "change free until 14:00 the
  day before delivery", which is an operations promise no florist has agreed to.
- **Q7 — Is the recipient's phone required?** **Recommended:** yes (`plan/07` §1.3, and
  `address-formats.ts` already records it as required). The artboard's "I don't have it" option is
  removed. *Alternative:* optional, with a warning that a missed door cannot be rescued.
- **Q8 — Collect marketing consent now?** **Recommended:** yes: one unticked box, recorded with the
  policy version, used only once spec 033 exists. *Alternative:* no box until spec 033.
- **Q9 — An expired quote with the same total: ask again?** **Recommended:** no: re-issue it
  silently; ask only when the total changed (005 §5.2's rule is about a new price). *Alternative:*
  always ask after 30 minutes.
- **Q10 — WhatsApp/SMS delivery updates and account creation in checkout?** **Recommended:** not in
  010; email only, guest only (specs 017 and 019 add them). *Alternative:* add the opt-in now with
  nothing yet able to send.
