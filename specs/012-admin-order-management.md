## 1. Problem

Every switch that turns the demo into a business still lives in code. Whether Poland takes orders is `status` in `src/config/countries.ts`; whether a locale launches is `isLaunch` in `src/config/locales.ts`; whether a link renders is `published` in `src/config/site-links.ts`; a price is a row in `src/config/catalogue/prices.data.ts`. Specs 003, 004, 005, 007, 008 and 009 each record this as a "bounded, stated deviation" from `CLAUDE.md`'s rule that **country and partner go-live is a data flip in admin, never a code change**, and each names spec 012 as the place the authority moves to (spec 003 §12, spec 004 §12, spec 007 §12, `plan/10` §4). There are also no florists in the system to route to, and nowhere to see an order. The founder set "website and CMS first" on 2026-09-14 (`docs/decisions-log.md`), and `plan/09` reserves `012` for 6–12 Oct: partners, catalogue, countries, flags, translations queue.

Phase 1 then needs the operator side of an order: a queue, a timeline, and the handful of actions a solo founder takes when an order goes wrong (re-route, cancel, refund, resend, note) — `plan/06` §6's Phase 1 rows and `plan/09`'s `020`. They belong in the same admin, behind the same sign-in and the same audit log, so this spec takes both and keeps them boring: server-rendered pages, plain tables, one server action per form, every change audited. The CRM is bought, not built (ADR-0010); nothing here is a CRM.

## 2. Scope

Each bullet is testable; the AC that covers it is in §9.

**Shell, sign-in, roles, audit**
- `/admin/**` (no locale prefix, `plan/02` §4) is server-rendered, `no-store`, `noindex`, and reachable only with a valid admin session.
- Sign-in is Auth.js v5 (ADR-0015, spec 002 §13 Q1) with an email magic link sent through Resend (ADR-0013). Only an email that already holds a `user_role` row can get a link; there is no sign-up. The first admin is granted by a founder-run CLI, `pnpm admin:grant`.
- One permission check, `can(role, capability)`, read on every page and inside every server action. v0 ships the `admin` role; the `support` role is designed in §5.2 and granted later (§13 Q2).
- Every admin mutation and every sign-in writes one `audit_log` row in the same transaction as the change. `/admin/audit` lists them with filters.

**Orders (Phase 1; the read half works as soon as spec 002's order tables exist)**
- `/admin/orders`: a queue with filters (status, needs-attention, delivery date range, destination, partner) carried in the URL, keyset-paginated.
- `/admin/orders/[id]`: lines, totals, payment summary, recipient snapshot, buyer, the `order_event` timeline, assignment offers, outbox deliveries, internal notes.
- Actions: change status **only** through `orderService.transition` (ADR-0009) and only to events the `order_transition` data allows for actor `admin`; assign or re-route a florist through spec 016's routing; full or partial refund through spec 013's payments, in integer minor units; resend a notification through spec 017; add an internal note. Each action that depends on an unwritten spec renders **disabled** with the reason until that spec ships.

**Partners**
- Partner list, create and edit; status changes (`demo → onboarding → active → paused → offboarded`) with guards; coverage (cities and postcode zones, capacity per day); blackout dates; catalogue mapping with a payout per product in minor units; a "set payouts from a share" bulk action; a margin column.
- Partner applications from spec 011's form: list, change status, convert into a partner draft.
- The corridor's active-partners seam (`src/modules/geo/partners.ts`) gets its database implementation.

**Countries and go-live flags**
- Country list and detail: status `demo | live | disabled`, the two publish flags, the operations block. Going live is blocked until a computed checklist passes (§5.3).
- `/admin/flags`: toggle the registered feature flags (locale launch, site-link `published`, payment method, `checkout.demo_guard`).
- The database becomes the runtime authority for these values, with the config files as seed defaults, behind the predicates each earlier spec already funnels reads through. A flip purges the affected pages (§5.4).

**Catalogue and prices**
- Product list and detail through `modules/catalog`; product status `draft | active | retired`.
- New retail prices, surcharge rows and add-on prices are **superseding rows** (`active_to` set on the old row, never an update), validated by the same rules as `pnpm catalogue:check`.
- A margin view: net-of-VAT retail minus partner payout, per product and country, where currencies match.

**Translations review queue**
- `/admin/translations`: per locale, every reviewable entry that is machine-drafted or stale, side by side with English. Only the founder marks entries reviewed (`docs/decisions-log.md`, 2026-10-03, "nothing is marked reviewed by anyone else").
- A mark is stored as data; `pnpm i18n:pull-reviews` writes the marks into the repository's review metadata in a PR, so the existing gates stay the source of truth (§5.1, §13 Q3).

**Fit**
- Every page is usable on a 390 px phone with no horizontal page scroll; every form works without JavaScript.

## 3. Non-goals

- **CRM features** (contact timelines, segments, campaigns, deal pipelines, marketing consent management, customer notes as a relationship log) → Phase 3, bought not built (ADR-0010; specs 032–039). Internal order notes are an operations log, not a contact record.
- **The order state machine, the outbox writer and the events** → spec 015. **Payment calls, refund rows and webhook handling** → spec 013. **Routing, candidate ranking and SLA timers** → spec 016. **Templates and sending** → spec 017. 012 calls their public functions and never writes `order.status`, `order_event`, `refund`, `order_assignment` or `outbox` rows itself.
- **Editing recipient details before acceptance** (`plan/06` §6 Phase 1) → a follow-up once spec 015 defines the edit event; it changes `recipient_snapshot` and needs its own review.
- **Editing long copy in admin** (product descriptions, category and occasion intros, corridor guides) → stays file-authored and reviewed in PRs in v0 (ADR-0017, spec 006, spec 007; §13 Q6).
- **Holidays and the occasion calendar** → stay in `seed/data/holidays.json` and the occasion data (spec 009) until a later admin amendment.
- **Exports** (orders CSV, Wise payout CSV, accounting export) → spec 030 (payouts) and the reporting spec 039.
- **Review moderation, delivery-photo approval for public use** → specs 022 and 029. **Fraud review queue** → spec 021, which adds a filter to this queue. **DSAR tracking** → spec 019.
- **Capacity greying on the product page, peak-day dashboards, automated re-routing rules, partner scorecards, analytics dashboards** → specs 024, 031 and `plan/11` §7 (Phase 4).
- **Passkeys or a second factor** → later; v0 relies on the magic link plus a short session (§8).
- **The rest of `plan/09`'s `020`.** Its admin half (queue, refunds UI) moves here; the automatic refund on cancellation or `no_partner_available` belongs to 013/015. The orchestrator retires or narrows `020` when it plans those specs.

## 4. User stories

- As the **founder**, I open `/admin/orders` on my phone, tap "needs attention", and see the one order with no florist, so that I can call a florist and assign it before the SLA runs out.
- As the **founder**, I refund £6 for a missing add-on in two taps, see the exact amount and currency before I confirm, and cannot refund more than was captured.
- As the **founder**, I add my first Warsaw florist, her coverage and her payouts, flip her to `active`, and then flip Poland to `live`; the corridor and shop pages change and the sitemap gains the shop URLs without a deploy.
- As the **founder**, I review the Polish product copy a native reviewer checked, mark it reviewed, and the next deploy makes those pages indexable.
- As the **founder**, I can answer "who changed this price, and when?" from the audit log.
- As a **buyer**, the price I see is still the price I am charged after an admin price change, because prices are superseded, never edited.
- As **Googlebot**, I never see an admin URL, and a country that goes back to `demo` leaves the sitemap and becomes `noindex` again.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

Most of what admin needs already exists in spec 002 §5.1 and is **not** restated: `country`, `feature_flag`, `feature_flag_scope`, `fulfillment_partner`, `partner_coverage`, `partner_blackout`, `partner_catalog_mapping`, `partner_application`, `product`, `country_price`, `addon_country_price`, `"order"`, `order_line`, `order_event`, `order_transition`, `order_assignment`, `payment`, `refund`, `outbox`, `audit_log`, `retention_policy`, `users`, `sessions`, `verification_tokens`, `user_role`.

**Amendment requests to spec 002** (additive; fold into TASK-021's unimplemented migration `0009`, or ship in 012's migration if `0009` has merged first):
- **R1** `audit_log.entity_id` is `text`, not `uuid`: flag keys (`checkout.demo_guard`) and ISO codes (`PL`) are entity ids too.
- **R2** `audit_log` is append-only: a `BEFORE UPDATE OR DELETE` trigger raises `AUDIT_LOG_IMMUTABLE`, except deletes by the retention sweep (`app.role = 'system'`). Plus indexes `(at DESC)` and `(entity_table, entity_id, at DESC)`.

**012's own migration `NNNN_admin_v0`** (number assigned when spec 002's migrations have landed; with `NNNN_admin_v0.down.sql`):
- `order_note(id uuid PK, order_id FK "order" ON DELETE RESTRICT, author_user_id FK users, body text NOT NULL CHECK (char_length(body) BETWEEN 1 AND 2000), redacted bool NOT NULL DEFAULT false, created_at timestamptz NOT NULL DEFAULT now())`. Append-only by trigger; the one allowed update is a redaction (`body → ''`, `redacted → true`) under `app.role = 'system'` (DSAR and retention sweep, spec 002 TASK-025). RLS: `admin` only.
- `translation_review(id uuid PK, locale_code FK locale, entry_kind text CHECK IN ('message','product','category','occasion','addon','corridor'), entry_ref text NOT NULL, source_hash text NOT NULL, reviewed_by FK users, reviewed_at timestamptz NOT NULL DEFAULT now(), UNIQUE (locale_code, entry_kind, entry_ref, source_hash))`. RLS: `admin` only. A mark is valid only for the source text whose hash it names; when the English changes, the mark no longer matches and the entry is stale again (`plan/03` §6.5).
- Indexes, each only if spec 002 has not created it: `"order" (status, delivery_date)`, `"order" (destination_country_id, delivery_date)`, `order_assignment (partner_id, offered_at DESC)`, `outbox (order_id)`.
- `retention_policy` rows: `order_note` pseudonymised with the buyer's personal fields (3 years, `plan/07` §1.2) and on DSAR erasure; `audit_log` deleted after 5 years (it holds no personal values, §8).
- Rollback drops the two tables, the indexes it created and the two retention rows, in reverse order.

**Seeded rows become real when admin edits them.** Any admin write to a row with `source = 'seed'` sets `source = 'real'`, so re-running the seed (which never touches `source = 'real'`, spec 002 §5.1) cannot undo a go-live flip, a price or a partner edit (`plan/10` §4).

### 5.2 API / server actions / jobs / events (zod schemas named)

**Module layout.** `src/modules/admin/` holds the auth glue, the permission matrix, the action wrapper, queries and actions; `src/app/admin/**` holds routes only (`plan/01` §5). Database-backed implementations of the existing read seams live in `src/modules/<module>/db/` (`geo/db/`, `i18n/db/`, `catalog/db/` from spec 005 TASK-070); `pnpm check:no-db` keeps scanning everything else and exempts exactly those directories.

**Auth** (`src/modules/admin/auth.ts`, `src/app/admin/api/auth/[...nextauth]/route.ts`)
- Auth.js v5, Drizzle adapter on spec 002's tables, database sessions, Resend email provider. Session cookie `__Secure-`-prefixed, `HttpOnly`, `Secure`, `SameSite=Lax`; session lifetime 12 h, link lifetime 10 minutes, at most 5 link requests per email per hour.
- `signIn` callback refuses any email with no `user_role` row; the page answers the same "check your email" either way (no account enumeration).
- `AdminSession = z.object({ userId: z.string().uuid(), role: z.enum(["admin"]), requestId: z.string() })`; `requireAdmin(capability)` for pages; never trusted from the proxy alone — every page and every action re-checks.
- `pnpm admin:grant --email <e> --role admin` (founder-run, direct URL): creates the `users` row if absent, inserts `user_role`, writes `audit_log` with actor `system:cli`. `--revoke` deletes the role and the user's sessions.
- New env keys, validated by `lib/env.ts` and listed in `.env.example`: `AUTH_SECRET`, `RESEND_API_KEY` (shared with spec 017), `AUTH_EMAIL_FROM`.

**Permissions** (`src/modules/admin/permissions.ts`) — one closed list of capabilities and one matrix. v0 grants `admin` everything; the `support` column is the design for when a helper joins and is not grantable until §13 Q2 is answered "now" (it needs a `user_role` value and an RLS policy).

| Capability | admin | support (later) |
|---|---|---|
| `orders.read`, `orders.note`, `orders.resend` | yes | yes |
| `orders.reroute` | yes | yes |
| `orders.transition`, `orders.refund` | yes | no |
| `partners.read` / `partners.write` | yes / yes | yes / no |
| `catalogue.read` / `catalogue.write` | yes / yes | yes / no |
| `countries.write`, `flags.write` | yes | no |
| `translations.review` | yes (the founder is the only `admin`) | no |
| `audit.read` | yes | no |

**The action wrapper** (`src/modules/admin/action.ts`): `adminAction(capability, InputSchema, handler)` → a server action that (1) resolves the session and checks `can()`, (2) parses `FormData` with the zod schema, (3) opens `withDbContext({ role: "admin", userId, requestId })`, (4) runs the handler, (5) writes the `audit_log` row in the same transaction, (6) after commit, calls `invalidate()` with the tags the handler returned. A handler cannot skip the audit row: the wrapper writes it from the handler's returned `{ entityTable, entityId, before, after }`, where `before`/`after` pass through a per-entity field allowlist that drops personal values and keeps only field names for them (§8). Next's server-action origin check plus `SameSite=Lax` cover CSRF.

**Input schemas** (`src/modules/admin/schemas.ts`). Money is entered as a decimal string and parsed to integer minor units by `parseMinor(text, currencyCode)` in `modules/catalog` (string arithmetic on the currency's exponent, never a float; added there if spec 005 has no parser), and carried as `Minor` (spec 005, TASK-163).
- Orders: `OrderQueueQuery` (URL params; no personal data in the URL), `OrderLookupInput { email }` (POST only, see §8), `OrderNoteInput { orderId, body }`, `OrderTransitionInput { orderId, event, expectedSeq, reason }`, `OrderRerouteInput { orderId, partnerId, expectedSeq, reason, override }`, `OrderRefundInput { orderId, paymentId, amount, currencyCode, reasonCode, note?, expectedSeq, idempotencyKey: uuid }`, `NotificationResendInput { orderId, outboxId }`.
- Partners: `PartnerInput`, `PartnerStatusChangeInput { partnerId, to, reason }`, `PartnerCoverageInput`, `PartnerBlackoutInput { partnerId, date, reason }`, `PartnerCatalogMappingInput { partnerId, productId, tierKey?, canFulfil, payout, currencyCode }`, `PayoutFromShareInput { partnerId, countryIso, shareBp: int 1..10000 }`, `ApplicationStatusInput`, `ApplicationConvertInput`.
- Countries and flags: `CountryStatusChangeInput { iso2, to, confirmIso2 }` (type the code to confirm), `CountryOperationsInput`, `CountryPublishInput`, `FlagToggleInput { flagKey, scope, scopeRef, enabled }`.
- Catalogue: `ProductStatusChangeInput`, `PriceSupersedeInput { productId, countryIso, tierKey?, surchargeKind?, retail, currencyCode, vatRateBp, activeFrom, activeTo? }`, `AddonPriceSupersedeInput`.
- Translations: `TranslationReviewInput { locale, entries: [{ kind, ref, sourceHash }] (1..200) }`.

**Ports to unwritten specs** (`src/modules/admin/ports.ts`). 012 declares what it needs; the owning spec implements it; until then an `unavailable` implementation makes the UI render the action disabled with "available when spec NNN ships". Tests use fakes.

| Port | Owner | What 012 calls |
|---|---|---|
| `OrderCommands.transition({ orderId, event, actor: "admin:{userId}", expectedSeq, payload: { reason } })` | spec 015 | status changes; the signature is 015's, this is the shape 012 needs |
| `RoutingCommands.candidates(orderId)`, `offerTo({ orderId, partnerId, actor, reason, override })` | spec 016 | assign and re-route |
| `PaymentCommands.summary(orderId)`, `refund({ paymentId, amount, currencyCode, reasonCode, idempotencyKey, actor })` | spec 013 | refunds; the order event follows from 013/015's contract |
| `NotificationCommands.resend({ outboxId, actor })` | spec 017 | resend |

**Optimistic concurrency.** Every order action carries the highest `order_event.seq` the page showed. If the order has moved on, the action is refused with "this order changed; reload" and nothing is called — two tabs cannot double-refund or race a transition.

**Which transitions admin may offer** is data: the `order_transition` rows whose `from_status` is the order's status and whose `requires_actor` is `admin` or `any` (spec 002 §5.1). No list of events is written in 012's code.

**Refund rules.** `amount ≤ captured − (succeeded + pending refunds)` on that payment, in the payment's currency; full refund = the remainder. Reason codes: `add_on_missing`, `late_delivery`, `substitution_complaint`, `quality_complaint`, `not_delivered`, `goodwill`, `cancellation`, `other` (`other` needs a note). Suggested amounts, shown and editable (`plan/06` §2.2; §13 Q5): add-on missing = that add-on line's retail; substitution complaint = 30% of product lines; late delivery = 20% of the order total. Percentages are basis points on integers, rounded half-up to the minor unit. Before capture there is no refund: the action offered is a cancel transition, and 013 voids the authorisation.

**Countries, flags and the go-live checklist** (`src/modules/admin/golive.ts`). `goLiveChecklist(iso2)` returns named items, each pass or fail, computed from the same inputs as spec 007's `corridorState()`: (1) the operations block is complete; (2) at least one `active` partner has coverage in the country and at least one `can_fulfil` mapping; (3) at least one `active` product has an active price in the country; (4) a reviewed `en` live-state corridor file exists for the country; (5) `country.supply_model` is set (the accountant's VAT sign-off, `plan/06` §4). `demo → live` is refused while any item fails (§13 Q4). `live → demo` and any `→ disabled` are always allowed, after typing the ISO code. Each flip writes `country.status_changed` (and partner flips `partner.status_changed`) to the outbox through the notifications module's writer, `plan/11` §2's event catalogue.

**Runtime authority.** `src/modules/geo/db/` implements the country registry reads (status, the two publish flags, operations) and the active-partners seam over `country`, `fulfillment_partner` and `partner_coverage`; `src/modules/i18n/db/` implements the locale launch flag over `feature_flag_scope` (scope `locale`); site-link `published` reads `feature_flag_scope` (scope `site_link`). Each reads through the single predicate or provider the earlier spec already funnels callers through (spec 003 AC-5, spec 004 AC-11, spec 007 `getActivePartnersProvider()`), so no caller changes. The config files stay the seed defaults. Reads are cached in-process for 60 s (spec 002's flag rule) and the cache is cleared by any admin write to those tables. With no database (CI, local, `DATABASE_URL` a placeholder) the config answers; a production or staging build or render that cannot reach the database **fails** rather than falling back to config, so ISR keeps serving the last good page and nothing goes live or dark by accident.

**Disabled countries.** Spec 005 §14 left `country.status = 'disabled'` sharing the `demo` availability state and asked 012 to add the sixth reason key. 012 adds `catalog.availability.countryDisabled` (en) and the §7 note; a disabled country also answers `false` from the corridor and shop publish predicates, so its URLs 404 and leave the sitemaps.

**Translations queue and the pull script.** In Phase 0 every reviewable text is repository-authored: UI strings in `messages/*.json` + `*.meta.json` (spec 003), product, category, add-on and occasion copy in spec 006's seed copy files, corridor guides in `content/corridors/**` (spec 007). The queue reads them through the loaders that already exist (no second copy of any text) and lists entries per locale whose meta says `machine` and not reviewed, or whose `sourceHash` no longer matches the English. "Mark reviewed" writes `translation_review` rows. `pnpm i18n:pull-reviews` (run by an implementer, reads the database, writes files) sets `reviewed: true`, `reviewedBy`, `reviewedAt` in the matching meta or front matter for every mark whose `source_hash` still matches, and nothing else; its output lands in a normal PR, so `i18n:check`, `corridor:check` and `seed:check` keep reading one truth and indexability changes on the next deploy (§13 Q3).

**Jobs and events.** No new job. Events written: `country.status_changed`, `partner.status_changed` (both already in `plan/11` §2's catalogue). Order events are written by spec 015 only.

### 5.4 Rendering & caching (per plan/01 §3)

- Every `/admin/**` route is dynamic: `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` and a robots meta, a nonce-based CSP with `'strict-dynamic'` (ADR-0016 reserves that mode for `no-store` routes). Cloudflare already bypasses `/admin*` (spec 040 rule 1). `robots.txt` already disallows `/admin/` (`src/modules/seo/robots.ts`). The proxy leaves `/admin` alone (no locale handling).
- The admin bundle is route-isolated: no admin code reaches a public route's chunks, and the public JS budgets (spec 001 `client-js-budget`) are unchanged.
- **Purging public pages.** The handler of each mutation returns its tags; the wrapper calls `invalidate()` after commit.

| Mutation | Tags (built only by the existing builders in `src/lib/cache.ts` and `cacheTagsFor()`) |
|---|---|
| Country status, publish flags, operations | `country:{iso}`, `catalog:{iso}`, the country's corridor tags for every locale, `sitemap` |
| Partner status or coverage (changes the active-partners answer) | the country's corridor tags, `country:{iso}` |
| Price or surcharge superseded | `cacheTagsFor({ kind: "price", productId, countryIso })` (`docs/runbooks/pricing.md` §6) |
| Product status | `product:{id}`, `catalog:{iso}` for every priced country, `sitemap` |
| Locale launch flag | every tag of that locale, `sitemap` |
| Site-link `published` | the home, hub and corridor tags of every locale, `sitemap` |
| Blackouts, payouts, orders, notes, translation marks | none (no public page reads them in Phase 0; marks act on deploy) |

- **Origin first, then edge.** Today `invalidate()` purges Cloudflare by URL, but Next's own ISR cache on the Railway origin would keep serving the old page until its time window ends, and the purge would just refetch it. 012 extends the seam so that `invalidate()` first revalidates each URL `urlsForTag()` resolves on the origin (`revalidatePath`), then purges the edge. Single replica (ADR-0018) makes the origin step complete.

## 6. SEO considerations (mandatory)

- **Admin itself:** not indexable (header, meta, robots disallow), in no sitemap, linked from no public page, no hreflang, no canonical needed. A crawl of the public site finds zero `/admin` links (AC-34).
- **What admin changes for SEO is the point of the spec.** A `demo → live` flip makes the country's shop, category, occasion and product pages indexable and adds them to the sitemaps within one request after the flip (no deploy); `live → demo` or `→ disabled` reverses it (`noindex` or 404, sitemap rows removed). ADR-0007's "index only true pages" holds because the checklist refuses a flip without an active florist, prices and a reviewed live corridor (thin-content guard).
- **Canonical and hreflang** do not change shape: they are computed by spec 007's generators from the same predicates admin now feeds, so they cannot disagree with the sitemap.
- **Prices in schema:** a superseded price changes the visible price and the `Offer` price together because both read the same row, and the purge covers both (`plan/02` §9).
- **Translations:** a review mark lifts `noindex` only after `i18n:pull-reviews` lands and deploys, so the hard gate of `plan/03` §6.4 stays in CI where `seo-auditor` and the validators see it.
- **CWV:** no effect on public pages; admin JavaScript is route-isolated (AC-34).

## 7. i18n considerations (mandatory)

- **Admin UI language:** English only (one user). Its strings are message keys in a separate catalogue, `messages/admin.en.json`, loaded only under `/admin`. It is not part of the locale catalogues, so it is never machine-drafted into `de`/`pl` and never counts toward a locale's unreviewed share or the 5% gate. `i18n:check` validates it (ICU parse, unused keys). The literal-string and physical-CSS lint rules apply to admin code like any other.
- **New public key:** `catalog.availability.countryDisabled` in `en` (spec 005 §14), with `de`/`pl` drafts flagged unreviewed through the normal flow. Its exact English text goes to the founder for batch approval (`docs/decisions-log.md` 2026-10-03).
- **Formatting:** all money through `formatMoney` with the record's currency; dates and times through `Intl` in the destination's zone with the zone named; numbers and percentages through `Intl`. Admin uses the `en-GB` format locale.
- **Data in other languages** (Polish product names, German copy in the queue) renders with the right `lang` attribute; `dir` follows the locale registry, so RTL needs nothing extra. All layout uses logical properties.
- **Addresses and phones** render with spec 003's per-country formatters, as the florist will read them.
- **Translation review plan and `noindex` gating:** this spec is the queue `plan/03` §6.3 calls for. The founder is the only reviewer; a native reviewer's checked text reaches the founder outside admin and the founder marks it. Stale entries (English changed) reappear automatically because the mark is tied to the source hash.

## 8. Compliance considerations (mandatory)

- **Data flows added (→ RoPA update):** (1) admin access to buyer and recipient data for order fulfilment and customer service — same controller, same purposes and bases as `plan/07` §1.2 (contract; legitimate interest for recipients); (2) admin identity data (email, sessions) for security — legitimate interest; (3) Resend sends the sign-in email — Resend is a processor (EU region, DPA), recorded in the RoPA with this spec if spec 017 has not recorded it first; (4) partner applicant contact data shown to the founder — pre-contract steps. `docs/compliance/ropa.md` gains these rows in the shell task.
- **No personal data in logs, URLs or analytics.** Queue filters carry no names, emails or phones; email lookup is a POST whose result renders in the response and never in the URL. Logs carry request id, action, entity uuid and outcome only. `audit_log.before/after` keep field **names** for personal fields (`contact_phone changed`) and never their values. No analytics tag loads on `/admin`.
- **Minimisation in the UI:** the queue shows city, not names; outbox recipient addresses are masked; the full recipient snapshot appears only on the order page. Redacted orders and notes show "redacted" and never the old value. Each order page view writes an `order.viewed` audit row (who looked at whose data, without the data).
- **Retention:** `order_note` follows the buyer's personal fields (3 years) and DSAR erasure; `audit_log` 5 years; sessions expire at 12 h and expired rows are deleted by Auth.js. The notes form tells the founder not to write card, bank or health details.
- **Price display:** prices change only by superseding rows, so the 30-day lowest-price history the Omnibus Directive needs is preserved (`plan/07` §2.1, §4); a price cannot be backdated (`activeFrom` ≥ today in the country's zone); price shown = price charged is untouched because the site reads the same rows.
- **Consumer information and refunds:** refunds go only to the original payment method through spec 013 (`plan/07` §9 AML row); every refund carries a reason code for the record.
- **Accessibility:** WCAG 2.1 AA for admin too (`plan/07` §8; UK Equality Act duties to staff): semantic tables with headers, labelled inputs, error summaries linked to fields, visible focus, axe clean.
- **Security:** sign-in only for granted emails; no account enumeration; link and request limits; short sessions; permission re-checked inside every action (not only in the proxy); CSRF covered by origin checks and `SameSite`; RLS applies (`app.role = 'admin'` through `withDbContext`, never a second connection string, spec 002 §13 Q4); go-live, refunds and status changes need a confirmation step.

## 9. Acceptance criteria

**Shell, sign-in, roles, audit**

- **AC-1** Every `/admin/**` response is `Cache-Control: private, no-store` with `X-Robots-Tag: noindex, nofollow` and a robots meta; with no session every admin page other than sign-in answers a redirect to `/admin/sign-in` and every admin server action answers 401 and changes nothing.

- **AC-5** Every admin server action writes exactly one `audit_log` row in the same transaction as its change: when the change rolls back, no row exists; when the audit insert fails, the change rolls back. Asserted for one action of each area.
- **AC-6** `audit_log` rows cannot be updated or deleted by `app_web` outside the retention sweep (`AUDIT_LOG_IMMUTABLE`); `entity_id` accepts `PL` and `checkout.demo_guard`.
- **AC-7** For a partner edit changing `contact_phone` and `contact_email`, the audit row's `before`/`after` contain the field names and none of the old or new values; a scan of the audit rows written by the whole integration suite finds no email address or E.164 number.
- **AC-8** `/admin/audit` lists rows newest first, 50 per page with keyset pagination, filtered by actor, action, entity and date range.

**Orders**

- **AC-9** `/admin/orders` filters by status, needs-attention, delivery date range, destination and partner, with every filter in the URL; no URL the queue produces contains an email, phone or name; email lookup is POST-only and leaves the URL unchanged.

- **AC-11** An order placed through spec 010's demo checkout appears in the queue on the next request (no cache), meeting `plan/09` Phase 0 AC 4's "within 5 s".

- **AC-13** The action panel offers exactly the events whose `order_transition` row has the order's status as `from_status` and `requires_actor` in (`admin`, `any`); adding or removing such a row in fixture data changes the offered set with no code change.
- **AC-14** A transition calls `OrderCommands.transition` once with actor `admin:{userId}`, the reason and the shown `expectedSeq`; no code path in `src/modules/admin` or `src/app/admin` writes `order.status` or inserts into `order_event` (the existing `fo/no-direct-order-status-write` lint and the database trigger both hold).

- **AC-16** Re-route lists `RoutingCommands.candidates` first; choosing a partner outside the list requires `override` and a reason, both passed to `offerTo` and audited.

- **AC-19** The confirmation step shows the refund as `formatMoney(amount, currency)` and the payment it hits; an `other` reason without a note is refused.
- **AC-20** Resend lists the order's outbox deliveries with masked addresses and calls `NotificationCommands.resend` once per click, at most 3 times per delivery per hour.

- **AC-22** With the `unavailable` port implementations, each dependent action renders disabled with its "available when spec NNN ships" reason and its server action refuses; with fakes, each works.

**Partners**

- **AC-23** A partner can be created and edited; `→ active` is refused without at least one coverage row and one `can_fulfil` mapping; each status change is audited and writes `partner.status_changed` to the outbox; the edited seeded row becomes `source = 'real'`.

- **AC-28** `goLiveChecklist` reports each of the five items separately; `demo → live` is refused while any fails and names the failing items; with all passing and the ISO code typed, the flip commits, sets `source = 'real'`, writes `country.status_changed` to the outbox and is audited.

## 13. Open questions

Each has a recommended default. The spec is `draft` until they are answered and the founder marks it `approved`.

- **Q1 — How do you sign in to admin?** **Recommendation: an email magic link sent through Resend.** It is `plan/11` §1's flow, needs no password, and Resend is the email provider we already chose (ADR-0013) and need for order emails anyway; the cost is a Resend account and its DNS records on Cloudflare before the first sign-in. Alternative: "Sign in with Google" for your Workspace address — no email setup, but a Google Cloud OAuth client to create and a second identity provider to keep.
- **Q2 — Build the `support` role now or later?** **Recommendation: later.** v0 has one admin (you). The permission table in §5.2 already says what a helper could and could not do (no refunds, no go-live, no prices, no copy approval), so adding the role later is one role value, one database policy and a test, not a redesign. Build it now only if someone will help with orders before the MVP.
- **Q3 — When does "mark reviewed" take effect?** **Recommendation: on the next deploy.** Your mark is saved at once; a script copies the marks into the repository's review files in a PR, and the pages become indexable when that deploys. Everything public is still written in repository files in Phase 0, so this keeps one source of truth and keeps the checks that stop unreviewed pages being indexed. Alternative: the site reads marks from the database immediately — faster, but then the repository and the live site disagree about what is reviewed, and the CI checks stop seeing the truth.
- **Q4 — What must be true before a country can go live, and is it a hard block?** **Recommendation: a hard block on five items** — complete delivery facts (cutoff, delivery days), at least one active florist with coverage and products, at least one priced product, a reviewed English live corridor page, and the VAT model set after the accountant's sign-off. One florist is the minimum the system can route to; `plan/06` §5.1's target of three for Warsaw stays your judgement, not a gate. Alternative: warnings only, which makes a mistaken flip one click away from indexing an unbuyable shop.
- **Q5 — Refund suggestions: which amounts?** **Recommendation:** missing add-on = that add-on's price; substitution complaint = 30% of the flowers; late delivery = **20% of the order total**. `plan/06` §2.2 says "delivery fee + 20%", but our prices include delivery, so there is no separate delivery fee to refund. They are suggestions only; you can type any amount up to what was paid. No extra approval step above a threshold, since you are the only person refunding.
- **Q6 — Do you edit long copy in admin in v0?** **Recommendation: no.** Product descriptions, category and occasion intros and corridor guides stay in repository files written and reviewed in PRs, as today (ADR-0017). Admin v0 edits the operational switches (status, prices, payouts, flags, florists) and approves copy. An in-admin editor for long copy is a later amendment once the database becomes the source for that text; building it now would mean two places to edit the same words.
