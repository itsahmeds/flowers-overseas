## 1. Problem

**This one spec covers two roadmap items: `013` (payments module) and `015` (order state machine, events, outbox).** `plan/09` Phase 1 lists them separately and then, under "core-touching risks", says they must be designed together because capture happens on florist acceptance: the payment cannot be captured until the order reaches `accepted`, and the order cannot reach `paid` until the payment is captured. Two specs written apart would each assume the other's half. So spec number `015` is folded into this one and stays unused, and `/plan-tasks` breaks this spec into tasks that cover both halves.

Today nothing can take money or move an order. `src/modules/payments/index.ts` and `src/modules/orders/index.ts` are empty barrels. Spec 002 designed the tables (`order`, `order_event`, `order_transition`, `payment`, `refund`, `webhook_inbox`, `outbox`) and the database triggers that refuse a status write outside the service, but those migrations (TASK-019, TASK-020, TASK-021) are still `todo`. Spec 005 ships `quote()` / `verifyQuote()`, so a price the buyer saw can be proven at payment time. Spec 010 (checkout UI, not yet written) needs something to hand the buyer to after step 3. Spec 016 (routing) needs an event that says "the money is safe, find a florist". Phase 1's first acceptance criterion — one real paid order, real card, 3DS, routed, accepted, captured, zero manual database edits — is impossible without this spec, and the first real order is due mid-December (stretch) or mid-January (committed).

The cost of getting this wrong is direct: a buyer charged twice, a buyer charged a different amount from the one on the page (illegal under `plan/07` §4), a florist who makes a bouquet we cannot charge for, or a forged webhook that marks an order paid. Every design choice below is aimed at making those impossible rather than unlikely.

## 2. Scope

**Order state machine (the `015` half; ADR-0009, `plan/11` §2)**
- `orderService.placeOrder(input)` — the only way an order row is created. It verifies spec 005's quote, writes the order, its lines and its recipient snapshot with status `placed`, and appends `order.placed` as event 1.
- `orderService.transition(orderId, event, actor, payload, { idempotencyKey })` — the only way `order.status` changes. One database transaction: lock the order row, check `(from_status, event)` and `requires_actor` against the `order_transition` table, update the status under `app.allow_status_write`, append the `order_event` row with the next `seq`, and write one outbox row per target. All of it commits or none of it does.
- A versioned zod schema for every event type in `plan/11` §2's catalogue, in `src/modules/orders/events.ts`.
- The outbox dispatcher: a pg-boss job that hands each outbox row to its target's handler, retries with backoff, and marks a row `dead` after 8 attempts. Handlers are registered per target; a target with no handler is a compile error, not a silent backlog.
- `sla.watch` (the job `plan/08` §7 names): the "payment secured but not routed for more than 5 minutes" alert. Spec 016 adds the "routed past SLA" check to the same job.

**Payments (the `013` half; ADR-0005, `plan/06` §2.2)**
- A `PaymentProvider` interface with two implementations in this spec: the Stripe adapter and an in-memory fake used by tests and local development. Spec 014's Mollie adapter must pass the same contract suite.
- The Stripe adapter: PaymentIntents with **manual capture** for cards and wallets (Apple Pay, Google Pay), **automatic capture** for methods that cannot hold an authorisation (BLIK and the others in the capability table), 3DS/SCA, Radar metadata, idempotency keys on every write, a pinned API version, and a restricted API key.
- The payment lifecycle: start a payment for a placed order; reconcile the order with the PaymentIntent; capture on florist acceptance; void on cancellation before acceptance; expire unpaid drafts; guard authorisations that are about to lapse; handle a capture that fails.
- **Price charged = price shown**: the PaymentIntent amount and currency are read from the order, which was written from the verified quote, and no function in this module accepts an amount from a caller.
- A **webhook inbox**: signature verification, store-before-process, idempotency by event id, correct results when events arrive out of order, and a replay command.
- **Refunds and partial refunds** as a service with money invariants, plus chargeback (dispute) handling.
- The **demo guard**: a country that is not `live` pays in Stripe **test mode** on every environment; live keys exist only in production and are used only for a `live` country.
- Alerts: secured-but-unrouted over 5 minutes, dead webhooks, webhook error rate, webhook silence, amount mismatch, dispute opened, authorisation about to lapse (`plan/09` Phase 1 acceptance 7, `plan/08` §7).
- Contract tests on recorded Stripe payloads (`plan/09` Phase 1 acceptance 3), and the payment e2e paths of acceptance 2 once spec 010's pay step exists.

## 3. Non-goals

- **Checkout UI** (steps 1–3, the Payment Element on the page, the confirmation page layout, the pay-button wording) → **spec 010**. The hand-off is §5.2's `placeOrder` → `startPayment` → `syncFromProvider`.
- **Routing, offers, florist accept/decline, SLA timeouts, the no-partner path** → **spec 016**. The hand-off is the order reaching a *payment-secured* state (`authorised` or `paid_unrouted`, see §13 Q1); 016 subscribes to the `routing` outbox target and calls `transition(…, 'route' | 'accept' | …)`.
- **Mollie adapter** → **spec 014** (same interface, same contract suite).
- **Buyer and florist emails/WhatsApp** (confirmation, "your florist has it", refund confirmation, admin alert emails) → **spec 017**, as the `notifications` outbox target. This spec writes the outbox rows; it sends nothing.
- **Invoice PDF, tracking page, buyer self-service cancel button** → **specs 018 and 019**. They call the commands defined here.
- **Admin order queue and refund UI** (filters, timeline, the suggested partial-refund amounts of `plan/06` §2.2) → **spec 020**. This spec ships the refund service and the admin server actions it calls, with no page.
- **Our own fraud pre-checks and the manual-review queue** (disposable email list, velocity, >€300 review) → **spec 021**. This spec ships the Radar side only: metadata on every PaymentIntent and the documented rule set.
- **Chargeback evidence packs** (delivery photo, acceptance record, 3DS result bundled for Stripe) → **spec 021**; this spec records the dispute and moves the order.
- **Runbooks top 10 and the remaining alerts** (SLA cascade exhaustion, photo missing) → **specs 016 and 025**.
- **Florist payouts** (`payout_line`, Wise) → **spec 030** / `plan/06` §5.4.
- **GA4 server-side `purchase` event** → **spec 023**, as the `analytics` outbox target.

## 4. User stories

- As a **buyer in the UK sending to Poland**, I pay with a card or Apple Pay, pass 3DS once, and see exactly the amount I saw on the product page and in step 3, so I trust the site.
- As a **buyer**, I can cancel for free until a florist accepts, because my card was only held, never charged (`plan/07` §2.1).
- As a **buyer paying with BLIK**, I am charged at once (BLIK cannot hold money), and if no florist can take the order I get my money back automatically without asking.
- As a **florist**, when I accept an order the money is already captured before I am told to start, so I never make a bouquet that is not paid for.
- As the **founder**, I get one alert when an order has been paid for five minutes and nobody is finding it a florist, and one when Stripe's webhooks stop or fail, so I find out before the buyer does.
- As the **founder**, I can refund all or part of an order from admin and the system refuses to refund more than was captured.
- As the **implementer of spec 016**, I subscribe to one outbox target and call `transition`; I never touch `order.status` or Stripe.
- As the **implementer of spec 014**, my Mollie adapter is accepted when it passes the same provider contract suite as Stripe's.
- As a **reviewer**, I can prove that a forged, replayed, duplicated or out-of-order webhook cannot move an order to the wrong state.
- As **Googlebot**, I see nothing new: no indexable page loads Stripe.js, and the budgets of `plan/01` §7 hold.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

All tables are spec 002's. This spec adds **no new module of tables**; it asks for the columns, rows and one table below. Because TASK-019, TASK-020 and TASK-021 have not been built, the cheapest path is to fold these into their migrations (`0007`, `0008`, `0009`) before they are written. If any of them merges first, task 1 of §12 ships the same changes as one new migration `00NN_payments_state_machine` with a `.down.sql`.

**Amendment request A to spec 002** (the orchestrator records it as spec 002 §14 A6 when this spec is approved):

1. **`order_transition` rows** added to the `plan/11` §2 transcription, each with its `requires_actor`:
   - `(authorised, buyer_cancel) → cancelled`, `(routed, buyer_cancel) → cancelled`, `(paid_unrouted, buyer_cancel) → cancelled` — actor `buyer` or `admin`. `plan/07` §2.1 promises "cancel free until your florist accepts it", and the diagram has no arrow for it.
   - `(placed, payment_attempt_failed) → placed` — actor `system`. A declined attempt is not the end: the buyer can retry on the same PaymentIntent.
   - `(placed, payment_failed) → payment_failed` — actor `system`, used only by the draft-expiry job after at least one failed attempt (otherwise `(placed, expire) → abandoned`).
   - `(accepted, capture_failed) → payment_failed` — actor `system`. The florist is told to stop; see AC-15.
   - `(paid_unrouted, route) → routed` exists in the diagram; `(routed, accept) → accepted` and `(accepted, capture) → paid` apply to both capture styles (for an automatic-capture payment the capture command makes no provider call).
   - **Partial refunds do not change the fulfilment status.** For every state from `paid` onward (`paid`, `in_production`, `awaiting_buyer`, `out_for_delivery`, `delivered`, `delivery_failed`, `redelivery_scheduled`, `photo_uploaded`, `disputed`, `resolved`), a self-loop row `(s, refund_partial) → s`. The `plan/11` §2 state `refunded_partial` is dropped: an order whose add-on was missing still has to be delivered, and a status of `refunded_partial` would hide that. `(s, refund_full) → refunded_full` stays for the same states. On `cancelled`, a self-loop `(cancelled, refund_full) → cancelled` records the refund that completes a cancellation of a captured payment without leaving `cancelled`.
   - **Chargebacks from any captured state**, not only from `disputed`: `(s, chargeback) → chargeback_open` for every state from `paid` onward plus `refunded_full` and `closed`. A bank dispute can arrive for an order nobody complained to us about.
   - `(chargeback_open, chargeback_won) → chargeback_won`, `(chargeback_open, chargeback_lost) → chargeback_lost`, as in the diagram.
   - Spec 002 AC-14's fixture list becomes "`plan/11` §2 plus Amendment A"; set equality both ways still holds.
2. **`order`**: `source CHECK IN ('web','admin','demo')` (the column exists; the values are new). A `BEFORE INSERT` trigger rejects any status other than `placed` (`ORDER_INITIAL_STATUS`), so the only way to start an order elsewhere in the machine is through transitions.
3. **`order_event`**: `idempotency_key text NULL` with `UNIQUE (order_id, idempotency_key)`. A Stripe event id, a capture key or a job key goes here, so a retried command cannot append twice.
4. **`payment`**: `livemode bool NOT NULL`; `status CHECK IN ('creating','requires_action','processing','authorised','captured','cancelled','failed')`; `capture_method CHECK IN ('manual','automatic') NULL` (known once the buyer picks a method); `amount_captured_minor bigint NOT NULL DEFAULT 0`; `amount_refunded_minor bigint NOT NULL DEFAULT 0`; `authorised_at`, `auth_expires_at`, `failed_at` (all `timestamptz NULL`); `attempts integer NOT NULL DEFAULT 0`; `last_decline_code text NULL` (a Stripe code such as `insufficient_funds`, never the bank's free text); `card_brand text NULL`, `card_last4 char(4) NULL` (`plan/07` §1.2 keeps token, last4, brand); `UNIQUE (order_id) WHERE status <> 'cancelled'` — one live payment per order. Checks: `amount_captured_minor BETWEEN 0 AND amount_minor`, `amount_refunded_minor BETWEEN 0 AND amount_captured_minor`.
5. **`refund`**: `order_id` (denormalised for locking), `status CHECK IN ('requested','pending','succeeded','failed','cancelled')`, `reason CHECK IN ('buyer_cancel','no_partner','capture_failed','addon_missing','late_delivery','substitution_complaint','quality','goodwill','duplicate','other')`, `requested_by text NOT NULL` (the `plan/11` §1 actor string), `provider_ref` nullable until the provider answers (it stays `UNIQUE`). The row's own `id` is the provider idempotency key.
6. **`payment_dispute`** (new, `payments` module): `id, payment_id FK, provider_ref UNIQUE, amount_minor bigint, currency_code, reason text, status CHECK IN ('open','won','lost','closed'), evidence_due_by timestamptz NULL, opened_at, closed_at NULL`. Partner-invisible under RLS; admin and system only.
7. **`webhook_inbox`**: `livemode bool NOT NULL`, `event_type text NOT NULL`, `object_ref text NULL` (the PaymentIntent, refund or dispute id), `status CHECK IN ('received','processed','ignored','failed','dead') NOT NULL DEFAULT 'received'`, `ignore_reason text NULL`, `last_error text NULL` (an error class and message, never a payload excerpt). `raw` stays, under the existing 12-month retention row.
8. **`outbox`**: one row per **(event, target)** instead of one row with `targets text[]`: `target text NOT NULL` replaces `targets`, with `UNIQUE (event_id, target)`. A target that fails must not hold up, or be re-run with, a target that succeeded.

Every item has a one-line rollback in the matching `.down.sql` (drop the column, the table, the trigger, or delete the added `order_transition` rows after re-typing any order that sits in a dropped state — none can exist before Phase 1). Money columns follow spec 002's pair rule; `payment_dispute.amount_minor` pairs with `currency_code`.

### 5.2 API / server actions / jobs / events (zod schemas named)

Module layout follows `plan/01` §5. Callers outside a module use its `index.ts` only.

```
src/modules/orders/
  index.ts            placeOrder, transition, getOrderStatus, OrderError types
  service.ts          the transaction (lock → guard → update → event → outbox)
  events.ts           OrderEventSchemas: one versioned zod schema per event type
  outbox.ts           OUTBOX_ROUTES (event type → targets), OutboxTarget union, dispatcher
  watch.ts            sla.watch: the secured-not-routed check
src/modules/payments/
  index.ts            startPayment, syncFromProvider, cancelPayment, refund, paymentMode, declineMessageKey
  provider.ts         PaymentProvider interface + provider contract suite (exported for 014)
  mode.ts             paymentMode(): live | test
  lifecycle.ts        reconcile(), capture handler, void, draft expiry, auth-expiry sweep
  refunds.ts          refund service + invariants
  methods.ts          method capability table (manual capture yes/no, currencies)
  stripe/             adapter, amount mapping, version.ts (pinned API version), webhook parsing
  fake/               FakePaymentProvider (in memory, deterministic)
  webhooks/           ingest (verify → store), process job, replay
src/app/api/webhooks/stripe/route.ts   thin: raw body → payments.ingestStripeWebhook()
```

**Order commands (`modules/orders`)**
- `PlaceOrderInput = z.object({ quote: QuoteSchema, destination: …, deliveryDate, deliveryWindow, recipient: RecipientSnapshotSchema, buyer: BuyerRefSchema, buyerCountryDeclared: Iso2, locale, termsVersion, source: z.enum(['web','admin','demo']) })` — the recipient and buyer fields are the ones spec 010 collects; their exact shapes are 010's and are referenced, not redefined.
- `placeOrder(input) → { orderId, publicToken } | QuoteExpired | QuoteTampered`. `verifyQuote` (spec 005) runs first. `expired` → nothing written, 010 shows the new price for re-confirmation (005 §5.2). `tampered` → nothing written, one `warn` log without the quote. `ok` → order + lines + snapshot + event 1, one transaction. `buyer_total_minor` and `buyer_currency_code` are copied from the quote; the line amounts are the quote's lines, and their sum equals the total or the insert is refused.
- `transition(orderId, event, actor, payload, opts) → OrderEvent | IllegalTransition | ActorNotAllowed | PayloadInvalid`. `IllegalTransition` carries the current status so the caller can show it. `opts.idempotencyKey` returns the existing event when the key was used before.
- `OrderEventSchemas`: `order.placed`, `order.authorised`, `order.payment_attempt_failed`, `order.payment_failed`, `order.abandoned`, `order.cancelled`, `order.routed`, `assignment.offered`, `assignment.accepted`, `assignment.declined`, `assignment.timed_out`, `order.no_partner_available`, `order.captured`, `order.refunded` (`kind: 'partial' | 'full'`), `order.chargeback_opened`, `order.chargeback_won`, `order.chargeback_lost`, and the fulfilment events of `plan/11` §2 (declared here, emitted by 016/017/027). Each is `{ version: 1, … }`; adding a field is additive, renaming means a new version (`plan/11` §2). Payloads carry ids, amounts, currencies, codes and reasons; **never** a name, email, phone, address or card message.
- `OUTBOX_ROUTES`: data, not code paths — e.g. `order.authorised → ['routing','notifications','analytics']`, `order.captured` with `from = placed` (automatic capture) → `['routing','notifications','analytics']`, `assignment.accepted → ['payments']`, `order.cancelled → ['payments','notifications']`, `order.refunded → ['notifications','analytics']`. `OutboxTarget = 'payments' | 'routing' | 'notifications' | 'analytics' | 'crm'`. The handler registry is typed `Record<OutboxTarget, Handler>`; targets whose spec has not shipped register the explicit `deferredHandler`, which marks the row `sent` with `last_error = 'deferred:<spec>'` so the backlog is visible and replayable later (`plan/11` §4.3: "switching is a replay of the outbox").

**Payment functions (`modules/payments`)**
- `PaymentProvider` interface: `createIntent(CreateIntentInput) → ProviderIntent`, `retrieveIntent(ref)`, `capture(ref, idempotencyKey)`, `cancel(ref, idempotencyKey)`, `refund(ref, Money, idempotencyKey, metadata)`, `verifyAndParseWebhook(rawBody, headers) → ProviderEvent | SignatureInvalid`, `listEventsSince(date)`. `ProviderIntent = { ref, status: 'requires_payment_method'|'requires_action'|'processing'|'requires_capture'|'succeeded'|'canceled', amount: Money, captureMethod, methodType, cardBrand?, cardLast4?, threeDsOutcome?, riskScore?, livemode, lastDeclineCode? }`. Provider types never leave the module.
- `startPayment(orderId) → { clientSecret, publishableKey, mode: 'live'|'test', methodTypes: string[] } | PaymentsDisabled | OrderNotPayable`. It takes **no amount and no currency**: both are read from the order. It inserts the `payment` row as `creating` *before* calling the provider, so a webhook that races the response can still be matched by `metadata.payment_id`. The client secret is returned to 010's pay step and nowhere else.
- `CreateIntentInput` sent to Stripe: `amount`, `currency` (from the order through `toStripeAmount`), `capture_method: 'automatic'` with `payment_method_options.card.capture_method: 'manual'` (and the same per-method override for every other method the capability table marks as holdable), `payment_method_types` = `methodsFor(buyerCountryDeclared, currency)` ∩ registry `available` ∩ `payments.method.{id}` flags — never `automatic_payment_methods`, so the list is ours, deterministic and testable; `payment_method_options.card.request_three_d_secure` per §13 Q2; `metadata` = exactly `{ order_id, payment_id, destination_country, buyer_country_declared, is_first_order, amount_eur_minor }` for Radar rules (`::destination_country::` etc.); `description` = the order's public number, no product or person; no `receipt_email` (our own confirmation is 017's, `plan/06` §2.2); no `shipping` (recipient data never goes to Stripe, §8).
- `toStripeAmount(Money)` — an explicit table for **GBP, EUR, PLN** (all exponent 2, identity mapping). Any other currency throws `UnsupportedCurrency`; adding one is a reviewed table row with a test, because Stripe's rules for some currencies (HUF, for example) differ from ISO 4217.
- `paymentMode(destinationIso2) → 'live' | 'test'`: `live` only when the environment is `production` (spec 040's `appEnvironment()`), the country's `status` is `live`, `corridorState(iso2) === 'live'` (spec 007), and the `checkout.demo_guard` flag is **off** for that country. Everything else is `test`: staging, PR previews, local, and every `demo`/`preview`/`guide` country in production. A `test` order is written with `source = 'demo'` and `payment.livemode = false`.
- `syncFromProvider(orderId)` — retrieves the PaymentIntent and runs the same `reconcile()` the webhook processor runs. Spec 010's return page calls it so the buyer sees "confirmed" without waiting for a webhook, and the e2e suite does not need a webhook tunnel.
- `reconcile(payment, intent)` — the one place a PaymentIntent's state becomes an order transition. It always works from the **retrieved** intent, not from the event body ("fetch, don't trust"), so the order of events cannot matter:

| Intent status (retrieved) | Order now | Transition (idempotency key = `pi:{ref}:{status}`) |
|---|---|---|
| `requires_capture` | `placed` | `pay` → `authorised` (payment `authorised`, `auth_expires_at` = Stripe's `capture_before` or authorised_at + 7 days) |
| `succeeded`, captured automatically | `placed` | `pay` (automatic) → `paid_unrouted` |
| `succeeded`, after our capture | `accepted` | `capture` → `paid` (normally already done by the capture handler) |
| `requires_payment_method` with a new decline | `placed` | `payment_attempt_failed` self-loop (payment `attempts + 1`, `last_decline_code`) |
| `canceled` | any | none — cancellation is always initiated by our own command, which already moved the order; a cancellation we did not start raises `payment.unexpected_cancel` |
| `processing`, `requires_action` | `placed` | none (wait) |
| anything that would move the order backwards | — | none; inbox row `ignored`, reason `stale` |

  Before any transition, `reconcile` checks `intent.amount` against the order's total and currency. A mismatch makes no transition, cancels the intent, sets payment `failed`, and raises `payment.amount_mismatch`.
- **Capture handler** (outbox target `payments`, on `assignment.accepted`): for a manual-capture payment, `provider.capture(ref, 'capture:{paymentId}')` for the full authorised amount (never a partial capture, never more), then `transition(…, 'capture')` → `paid`. For an automatic-capture payment, the same transition with no provider call. A provider refusal (expired or declined authorisation) → `transition(…, 'capture_failed')` → `payment_failed`, which routes `notifications` (buyer: payment failed; florist: do not make it) and raises `payment.capture_failed`.
- **Cancel handler** (outbox target `payments`, on `order.cancelled`): from a manual-capture authorisation → `provider.cancel` (void, nothing charged); from a captured payment → a full refund through `refunds.ts` with reason `buyer_cancel` or `no_partner`. This is `plan/06` §2.2's "the buyer is never charged for an undeliverable order" and "refund automatically on `no_partner_available`" once the order is cancelled.
- `refund({ orderId, amount: Money, reason, actor, idempotencyKey })` → `Refund | RefundExceedsCaptured | CurrencyMismatch | NotRefundable`. Under the order row lock: `amount.currency` equals the payment's; `amount.amountMinor` is a positive integer; captured − (succeeded + pending + requested refunds) ≥ amount. It inserts the `refund` row as `requested`, calls the provider with the row id as the idempotency key, and records `provider_ref` and `pending`. Refunds always go to the original payment method — the function has no destination parameter (`plan/07` §9, AML). On success: the cumulative refund equals the captured amount → `transition(…, 'refund_full')` → `refunded_full` (on a `cancelled` order, the `cancelled` self-loop); otherwise the `refund_partial` self-loop appending `order.refunded { kind: 'partial' }`.
- Admin server actions `adminRefund` and `adminCancel` (zod-parsed, role `admin`, audit-logged through spec 002's `audit_log`) wrap the services for spec 020's page. No page ships here.
- `declineMessageKey(code) → MessageKey` maps Stripe decline codes to buyer-friendly keys in the `payments` namespace (§7); an unknown code maps to `payments.error.generic`. The provider's own message text is never shown.

**Webhook inbox (`modules/payments/webhooks`; `plan/01` §9)**
- `POST /api/webhooks/stripe` (Node runtime, `dynamic = 'force-dynamic'`): reads the **raw** body (≤ 1 MB, else 413), verifies `Stripe-Signature` against the live secret and then the test secret with Stripe's 300-second timestamp tolerance, and rejects (400, nothing stored, one counter log line) on a missing header, a bad signature or a stale timestamp. A verified event whose `livemode` disagrees with the secret that verified it is stored as `ignored` (`livemode_mismatch`).
- Store before process: `INSERT … ON CONFLICT (provider, event_id) DO NOTHING`, then enqueue `webhook.process` with `singletonKey = inbox id`, then answer **200**. A database failure answers 500 so Stripe retries. Processing never happens inside the request.
- `webhook.process` job: locks the inbox row `FOR UPDATE SKIP LOCKED`, parses it with `StripeEventSchema` (zod over the fields we read), routes by type, and marks it `processed`, `ignored` (unknown type, stale, unknown object after retries) or `failed`; pg-boss retries `failed` with backoff and marks it `dead` after 8 attempts.
- Event types subscribed (and nothing else, to keep personal data out of `raw`): `payment_intent.requires_action`, `payment_intent.amount_capturable_updated`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `payment_intent.processing`, `charge.refunded`, `refund.created`, `refund.updated`, `refund.failed`, `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`.
- `pnpm jobs:replay-webhooks --since <ISO> [--inbox-id <id>] [--dry-run]` (the name `docs/runbooks/payment-webhook-down.md` already uses): pulls `events.list` from Stripe (30-day window) and feeds each through the same ingest path, so a replay is idempotent; `--inbox-id` resets one stored row to `received` and re-enqueues it.

**Jobs (registered in `src/jobs/index.ts` with versioned payload schemas)**
- `outbox.dispatch` — every tick; batches pending rows with `FOR UPDATE SKIP LOCKED`.
- `webhook.process` — per inbox row.
- `payments.sweep` — every 15 minutes: (a) authorisations within 24 h of `auth_expires_at` (capture now if the order is `accepted`; otherwise `cancel` → `cancelled` + void + `payment.auth_expiring` alert — see §13 Q4); (b) `placed` orders older than **2 hours** → `expire` → `abandoned`, or `payment_failed` if an attempt failed, with the intent cancelled; (c) `creating` payments older than 15 minutes with no provider ref → `failed`; (d) `requested` refunds older than 5 minutes → retried with the same idempotency key.
- `sla.watch` — every minute (§11).

**Errors and logs**: every exported function returns typed results for expected outcomes and throws only on bugs. Allowed log fields are listed in §11.

### 5.3 UI (pages, components, states: loading / empty / error / demo / disabled)

No page and no component ships in this spec. What it gives spec 010's pay step, and the states 010 must draw:
- `startPayment` result: `mode` (`test` must render 010's demo notice: "This is a demonstration. No real payment will be taken."), `methodTypes` (the order of methods comes from `plan/04` §10 via the buyer's declared country), `clientSecret`, `publishableKey`.
- `PaymentsDisabled` (the `payments.stripe` flag is off) — 010's existing no-charge demo path.
- Decline and retry: `declineMessageKey()` gives the message; the order stays `placed`; the buyer retries on the same intent with the same or another method.
- `QuoteExpired` from `placeOrder` — 010 re-shows the new price and asks for confirmation (spec 005 §5.2).
- Return from 3DS or a bank redirect: 010's return route calls `syncFromProvider`, then answers 303 to the confirmation URL **without** Stripe's query parameters (`payment_intent`, `payment_intent_client_secret`, `redirect_status`), which are never read for state.

### 5.4 Rendering & caching (SSG/ISR/SSR, tags invalidated, per plan/01 §3)

- `/api/webhooks/stripe` and the internal job routes: dynamic, Node runtime, `Cache-Control: no-store`, `X-Robots-Tag: noindex`, disallowed in `robots.txt` (`/api/` already is). Cloudflare: cache bypass on `/api/*` (spec 040) plus a WAF skip rule so bot protection never challenges Stripe's POSTs (founder action, §12).
- Checkout and confirmation routes stay SSR `no-store` (`plan/01` §3, spec 010). Stripe.js is loaded **only** on the pay step, with the CSP additions for `js.stripe.com`, `*.js.stripe.com`, `hooks.stripe.com` (frames) and `api.stripe.com` (connect) scoped to the checkout routes, using the nonce path ADR-0016 reserves for `no-store` routes. No indexable route's CSP or HTML changes.
- No cache tags are invalidated by payments. Capacity tags (`capacity:{city}:{date}`) belong to 016/024.

## 6. SEO considerations (mandatory)

- **Indexability**: nothing in this spec renders an indexable page. The webhook route is under `/api/`, already disallowed in `robots.txt` and sent with `X-Robots-Tag: noindex`; the checkout and confirmation pages remain `noindex` and SSR `no-store` (spec 010, `plan/01` §3). No canonical, hreflang set, sitemap or schema type changes.
- **Core Web Vitals and bytes**: Stripe.js (~40 KB+ gzipped plus its iframes) and its fraud-signal requests are the heaviest third party this project will add. They load only on the pay step, never on home, corridor, category or product pages, so the Lighthouse budgets of `plan/01` §7 and spec 004 are untouched — which is exactly `plan/09` Phase 1 acceptance 8 ("budgets still met with payments … present"). AC-33 pins it by scanning every indexable route's HTML and CSP.
- **Schema identity**: `Offer.price` = visible price = charged amount. The first two are spec 005's identity (`offerProjection()`); this spec closes the chain by charging only the order total copied from the verified quote (AC-10). A price shown in schema that differs from the charge is both a Merchant Center policy problem and a consumer-law one (`plan/02` §15, `plan/07` §4).
- **Internal links, thin content, URL patterns**: none added. The 303 after a payment return strips third-party query parameters, so no parameterised confirmation URL can be crawled or shared.

## 7. i18n considerations (mandatory)

- **New message keys** (namespace `payments`, in `en`, `en-gb`, `de`, `pl`): `payments.error.cardDeclined`, `.insufficientFunds`, `.authenticationFailed`, `.expiredCard`, `.incorrectCvc`, `.processingError`, `.tryAnotherMethod`, `.generic`, `.amountChanged` (quote expired), `.paymentsUnavailable`; `payments.demo.notice`; `payments.status.*` for the buyer projection labels if 010 needs them (they reuse spec 002's `buyer_projection` values). `pnpm i18n:check` covers them. `de` and `pl` go to the native reviewers before the PL flip, as every buyer-facing string does (`plan/03`); until reviewed they ship with the English fallback and the pages stay `noindex` anyway.
- **Formatting**: amounts in messages go through spec 003's `formatMoney`; this spec adds no `Intl` call. The 3DS challenge and the Payment Element are Stripe's UI; their language follows the `locale` option passed at mount (`en-gb` → `en-GB`, `de` → `de`, `pl` → `pl`, `en` → `en`), mapped in one table with a test.
- **Decline messages are ours**, not the bank's: the provider's English `message` is never shown in a `de` or `pl` page.
- **RTL**: no layout ships; the pay step's RTL behaviour is 010's (Stripe's iframe supports `dir` via its locale).
- **Address and phone formats**: untouched. Recipient data never reaches Stripe; billing details are collected by the Payment Element only where a method needs them (`plan/04` §9).
- **Currency**: the charge is in the order's buyer currency (GBP, EUR or PLN in Phase 1), which is the currency the buyer saw — never re-derived from a cookie at payment time (spec 005 AC-9's rule carried to money movement).

## 8. Compliance considerations (mandatory)

- **Data flows added → RoPA** (`docs/compliance/ropa.md`, new row; task 6): **Stripe Payments Europe Ltd (Ireland)** as processor for payment processing and independent controller for its own fraud and regulatory purposes (`plan/07` §1.1, §1.4). Subjects: buyers. Categories sent: amount, currency, buyer email and billing details collected by the Payment Element, card data (entered into Stripe's iframe only), device and IP signals gathered by Stripe.js, and the six non-personal metadata fields of §5.2. **Not sent**: recipient name, address, phone, the card message, or any free text. Basis: contract (Art. 6(1)(b)) for payment; legitimate interest (Art. 6(1)(f), Recital 47) for fraud prevention. Stored by us: `payment` (provider ref, status, amounts, method type, brand, last4, 3DS outcome, risk score, decline code) as part of the order's accounting record (10 years with the invoice archive, `plan/07` §10, accountant to confirm under B1); `webhook_inbox.raw` 12 months (spec 002's retention row). DPA: Stripe's DPA is part of its services agreement; recorded in `docs/compliance/` when the account is opened.
- **Lawful basis and minimisation**: recipient data is the most sensitive data we hold (`plan/07` §1.3); it stays out of Stripe entirely, at the cost of Radar not seeing the delivery address (§13 Q7). Subscribed webhook types are limited (§5.2) so `raw` holds as little personal data as possible.
- **Contract formation and withdrawal** (`plan/07` §2.1, §2.3): the contract is concluded when payment is captured after florist acceptance; until then the buyer can cancel free and the authorisation is voided (AC-16). For immediate-charge methods, cancellation before acceptance is a full automatic refund. This is what makes the perishable-goods withdrawal exemption (Art. 16(d); UK CCR reg. 28(1)(c)) fair to rely on.
- **Price display** (`plan/07` §4, `CLAUDE.md`): the charged amount is the order total, copied from the verified quote the buyer saw, in the currency they saw; no function accepts a different amount; a mismatch with the provider cancels the payment (AC-10). No payment-method surcharge exists (CRD Art. 19).
- **Geo-blocking** (EU 2018/302, `plan/07` §3): payment methods are chosen from the buyer's **declared** country and the order currency, which the buyer can change freely; never from IP (AC-12, ADR-0006). Cards are accepted from every country.
- **PCI DSS**: card data is entered only in Stripe's iframe and never touches our servers or logs, which keeps us at SAQ A. The pay step's CSP allows only Stripe's origins.
- **Security**: webhooks verified before storage; replayed and stale signatures refused; test-mode events cannot move live payments and vice versa; a restricted Stripe key with only the permissions listed in the runbook (PaymentIntents write, Refunds write, Events read, Disputes read); live keys refused by `lib/env.ts` outside production; idempotency on every provider write; no amount accepted from the client.
- **Logs and PII** (`CLAUDE.md`): §11's allow-list only. `client_secret`, the `Stripe-Signature` header, the raw body and billing details are never logged; the logger's redaction list gains `client_secret`/`clientSecret` and `stripe-signature`. The client secret never appears in our URLs: the return route strips Stripe's query parameters with a 303 and sends `Referrer-Policy: no-referrer` (AC-19).
- **Cookies**: Stripe.js sets `__stripe_mid` and `__stripe_sid` for fraud prevention; `plan/07` §5 classifies them as essential. They are set only on the pay step; `docs/compliance/cookie-register.md` gains the two rows (task 6).
- **Accessibility**: 010 announces decline and retry messages in an `aria-live` region; the messages here are short, plain and say what to do next. The Payment Element and 3DS frames are Stripe's and are WCAG-tested by Stripe; we pass the locale.
- **Consumer information on durable medium** (CRD Art. 8(7)): the confirmation email is 017's, triggered by this spec's outbox rows.
- **AML**: refunds go only to the original payment method (`plan/07` §9).

## 9. Acceptance criteria

**Order state machine**
- **AC-1** `orderService.transition` is the only code that writes `order.status`. In one transaction it locks the order row, reads `(from_status, event)` from `order_transition`, checks `requires_actor`, updates the status with `app.allow_status_write` set locally, appends `order_event` with `seq` = previous + 1, and inserts one `outbox` row per target from `OUTBOX_ROUTES`. Forcing a failure at each step in turn (fault injection) leaves no status change, no event and no outbox row.
- **AC-2** For every row of `order_transition`, a transition from `from_status` with `event` and an allowed actor succeeds and lands in `to_status`; for every state, every event without a row from that state returns `IllegalTransition` carrying the current status and writes nothing; a disallowed actor returns `ActorNotAllowed` and writes nothing.
- **AC-3** Calling `transition` twice with the same `idempotencyKey` returns the first event both times and writes exactly one event and one set of outbox rows.
- **AC-4** Two concurrent commands on one `routed` order — `buyer_cancel` and `accept` — run 50 times: each time exactly one succeeds, the other returns `IllegalTransition`, and the order's `seq` values are 1…n with no gap or duplicate.
- **AC-5** Every event type in §5.2's catalogue has a versioned zod schema; `transition` returns `PayloadInvalid` (writing nothing) for a payload that fails it; and no schema declares a key that the logger's redaction list would redact (a test walks every schema's keys).
- **AC-6** `placeOrder` with an `expired` quote returns `QuoteExpired` and writes nothing; with a `tampered` quote returns `QuoteTampered` and writes nothing; with an `ok` quote writes an order whose `buyer_total_minor` and `buyer_currency_code` equal the quote's, lines equal to the quote's lines whose sum equals the total, status `placed`, and event `seq = 1` of type `order.placed`. A raw `INSERT` of an order with any other status is rejected by the database with `ORDER_INITIAL_STATUS`.
- **AC-7** The outbox dispatcher delivers each pending row to its target's handler once and marks it `sent`; a throwing handler is retried with backoff, each attempt is recorded in `outbox_attempt`, and the 8th failure marks the row `dead` and raises `outbox.dead`. The handler registry's type requires a handler for every `OutboxTarget` (a type test fails if one is missing), and a row redelivered after `sent` causes no second side effect.
- **AC-8** `order_transition` contains every Amendment A row of §5.1 and no `refunded_partial` state; spec 002 AC-14's fixture is updated to "`plan/11` §2 + Amendment A" and passes with set equality both ways.

**Payments**
- **AC-9** The Stripe adapter (against recorded responses) and `FakePaymentProvider` both pass one exported provider contract suite covering create, retrieve, capture, cancel, refund, webhook verify/parse and event listing; the suite is importable by spec 014.
- **AC-10** `startPayment(orderId)` creates an intent whose amount and currency equal the order's `buyer_total_minor` and `buyer_currency_code` for every total in spec 005's fixture matrix in GBP, EUR and PLN, and no exported function of `modules/payments` has a parameter that sets a charge amount for a payment (a type-level test over the barrel). When `reconcile` sees an intent whose amount or currency differs from the order, it makes no transition, cancels the intent, sets the payment `failed` and raises `payment.amount_mismatch`.
- **AC-11** `toStripeAmount` returns the exact integer for GBP, EUR and PLN and throws `UnsupportedCurrency` for every other currency in `src/config/currencies.ts`; `fo/no-float-money` passes on `modules/payments` and `modules/orders`.
- **AC-12** An intent is created with `capture_method: 'automatic'`, a `manual` capture override for every method the capability table marks holdable (cards, Apple Pay, Google Pay), and `payment_method_types` equal to the configured methods for (declared buyer country, currency) that are `available` and flag-enabled. A `requires_capture` intent moves a `placed` order to `authorised`; a BLIK intent that `succeeded` moves it to `paid_unrouted`. Two requests that differ only in an IP-country header produce identical method lists.
- **AC-13** Every card intent carries the `request_three_d_secure` value §13 Q2 settles (default `any`), and every intent's `metadata` has exactly the keys `order_id`, `payment_id`, `destination_country`, `buyer_country_declared`, `is_first_order`, `amount_eur_minor`, with no `receipt_email` and no `shipping`.
- **AC-14** When an order reaches `accepted`, the `payments` handler captures the full authorised amount once with idempotency key `capture:{paymentId}` and moves the order to `paid`; for an automatic-capture payment it moves the order to `paid` with zero provider calls; delivering the same outbox row twice makes exactly one capture call.
- **AC-15** A capture the provider refuses moves the order `accepted` → `payment_failed`, sets the payment `failed`, writes `notifications` outbox rows for the buyer and the florist, and raises `payment.capture_failed` (fault-injection test).
- **AC-16** Cancellation: a `placed` order older than 2 hours becomes `abandoned` (or `payment_failed` if an attempt failed) and its intent is cancelled; `buyer_cancel` from `authorised` or `routed` → `cancelled` with the authorisation voided and nothing captured; `buyer_cancel` from `paid_unrouted` → `cancelled` with one full refund; `buyer_cancel` from `accepted` or later returns `IllegalTransition`.
- **AC-17** With a clock fixture, a manual-capture payment 24 h before `auth_expires_at` is captured by `payments.sweep` if its order is `accepted`, and otherwise its order is cancelled with the authorisation voided and `payment.auth_expiring` raised; at 25 h before, nothing happens.
- **AC-18** `paymentMode` returns `live` only for production + country `live` + `corridorState` `live` + `checkout.demo_guard` off for that country, and `test` for each of the other combinations (table test). `lib/env.ts` refuses a `sk_live_`, `rk_live_` or `pk_live_` value in any non-production environment. A `test` order is written with `source = 'demo'` and `payment.livemode = false`, and a test-mode event can never transition a live payment, nor a live event a test payment.
- **AC-19** The return route ignores Stripe's query parameters for state, calls `syncFromProvider`, and answers 303 to a URL with no query string, with `Cache-Control: no-store`, `X-Robots-Tag: noindex` and `Referrer-Policy: no-referrer`. A capturing logger, the analytics payloads and the rendered HTML outside the Payment Element bootstrap contain no `client_secret` value across the whole e2e and integration run.
- **AC-20** `declineMessageKey` maps every decline code in the recorded fixture list to a key that exists in `en`, `en-gb`, `de` and `pl`, maps an unknown code to `payments.error.generic`, and the provider's own message string never reaches a rendered page or an outbox payload.

**Webhook inbox**
- **AC-21** A body signed with the live or the test secret gets 200 and exactly one inbox row; a missing header, a wrong signature, or a timestamp more than 300 s old gets 400 and no row; a body over 1 MB gets 413 and no row.
- **AC-22** The 200 is sent after the inbox insert commits and before processing starts; a processing failure does not change the response; a database failure during the insert answers 500.
- **AC-23** The same event delivered twice in sequence, or twice concurrently, yields one inbox row, one processing run and at most one order transition.
- **AC-24** For each recorded out-of-order sequence — `succeeded` before `amount_capturable_updated`; `payment_failed` after `succeeded`; `refund.updated` before `charge.refunded`; `charge.dispute.closed` before `charge.dispute.created` — the final order, payment, refund and dispute rows equal those of in-order delivery, and every stale event is marked `ignored` with reason `stale`.
- **AC-25** An unknown event type gets 200 and is marked `ignored`; a `livemode` mismatch is marked `ignored` with reason `livemode_mismatch` and logs one `warn`; an event that fails `StripeEventSchema` is marked `failed`, retried, and after 8 attempts `dead` with `webhook.dead` raised.
- **AC-26** `pnpm jobs:replay-webhooks --since <ISO>` ingests the listed events through the same path, and a second run changes nothing; `--inbox-id` re-processes one stored row; `--dry-run` writes nothing and prints counts only.
- **AC-27** Contract fixtures live under `tests/contract/fixtures/stripe/<api-version>/`, the version directory equals the adapter's pinned `apiVersion` (a test fails if they differ), and a scan finds no email address or phone number in them other than Stripe's documented test values.

**Refunds and disputes**
- **AC-28** `refund` refuses (typed error, no provider call, no row) a non-integer or non-positive amount, a currency different from the payment's, and any amount that would make succeeded + pending + requested refunds exceed the captured amount — including two concurrent refunds that each fit alone but not together. Its signature has no destination parameter.
- **AC-29** A partial refund appends `order.refunded { kind: 'partial' }` and leaves the order's status unchanged; the refund that brings the cumulative total to the captured amount moves the order to `refunded_full` (or, on a `cancelled` order, appends `order.refunded { kind: 'full' }` and leaves it `cancelled`). A crash between the `requested` insert and the provider call is recovered by `payments.sweep` with the same idempotency key, producing exactly one provider refund.
- **AC-30** `charge.dispute.created` writes a `payment_dispute` row, moves the order to `chargeback_open` from any captured state, and raises `payment.dispute_opened`; `charge.dispute.closed` with `won` or `lost` moves it to `chargeback_won` or `chargeback_lost`.

**Alerts, gates, docs**
- **AC-31** With the `routing` handler disabled and an injected clock, an order that has been `authorised` or `paid_unrouted` for 5 min 1 s with no `order.routed` event raises exactly one Sentry error-level event tagged `alert=order.unrouted` and `order_id`; at 4 min 59 s none is raised; re-running `sla.watch` does not raise a second one for the same order.
- **AC-32** Fault injection raises `webhook.error_rate` when more than 2 % of inbox rows in 10 minutes end `failed` or `dead`, and `webhook.silent` when no Stripe event has arrived for 24 h while any payment is `authorised`, `processing` or `creating` (`plan/08` §7).
- **AC-33** No indexable route's HTML or `Content-Security-Policy` header references a Stripe origin (crawl of the spec 007/008/009 page sets), and the checkout pay step's CSP contains exactly the Stripe origins listed in §5.4.
- **AC-34** Driving every path of this spec with a capturing logger, every emitted key is in §11's allow-list; no line contains a client secret, a `Stripe-Signature` value, a raw webhook body, an email address or billing details.
- **AC-35** Against a PR preview in test mode, once spec 010's pay step exists: `en-gb` with Stripe's 3DS-challenge test card → order `authorised`; `en-gb` with a declining test card → the decline message key renders and the order stays `placed`; `pl` with the BLIK test flow → order `paid_unrouted`.
- **AC-36** Docs are current in the PR that finishes the spec: `docs/compliance/ropa.md` Stripe row; `docs/compliance/cookie-register.md` `__stripe_mid`/`__stripe_sid`; `docs/runbooks/payments.md` (keys and their permissions, webhook endpoints and subscribed types, the Radar rule set verbatim, the Apple Pay domain step, the capture/void/refund recovery steps); `docs/runbooks/payment-webhook-down.md` updated to the real commands; `.env.example`; `docs/codebase-map.md`.

## 13. Open questions

Each question has the default this spec is written against. The spec stays `draft` until the founder decides.

- **Q1 — What does "paid" mean for routing and the 5-minute alert?** `plan/01` §8 says routing runs "on `paid`" and `plan/09` Phase 1 acceptance 7 says "`paid` without `routed` > 5 min", but in `plan/11` §2 — the canonical machine — `paid` comes *after* the florist accepts (capture on accept), so routing cannot wait for it. **Default: "paid" in those two places means payment secured — the order is `authorised` (card held) or `paid_unrouted` (BLIK and other immediate methods).** Routing (016) starts there, and the alert measures from there. Alternative: rename the internal states; that changes `plan/11`, spec 002's seed and every later spec, for no gain.
- **Q2 — When do we ask for 3DS?** `plan/06` gives two thresholds (§2.2: first-time cards and orders over €150; §2.3: first-time cards over €120) and relies on exemptions for repeat buyers. In Phase 1 every buyer is new. **Default: request 3DS on every card payment (`request_three_d_secure: 'any'`) for Phase 1**, and revisit after 100 orders. It shifts fraud liability to the card issuer on every order — the main chargeback defence for a gift sent to someone else — and most banks complete it without a challenge. Alternative: the €120/€150 thresholds, with slightly less friction and more chargeback risk.
- **Q3 — In production, does a `preview` country pay in Stripe test mode, or make no Stripe call at all?** `plan/10` §5 says the Phase 0 demo guard makes no Stripe call. **Default: test mode.** While a country is not `live`, checkout runs the real flow against Stripe's test keys (real 3DS screens, test cards), labelled as a demonstration; a real card is rejected by Stripe in test mode, so no money can move. This lets the founder demo the true flow to florists and lets us test the production code path before the flip. Alternative: no Stripe call (an instant fake authorisation), which is simpler but demos a flow that does not exist.
- **Q4 — What happens to an order for a date more than a week away?** A card authorisation lapses after about 7 days. **Default: spec 016 offers every order to a florist immediately, whatever the delivery date, so acceptance — and capture — normally happens within hours.** If an authorisation is 24 hours from lapsing and no florist has accepted, the order is cancelled, the hold is released, and the founder is alerted. Alternative: for delivery dates more than 6 days ahead, capture at once at order time; the buyer is charged earlier and "free cancellation until acceptance" becomes a refund rather than a released hold.
- **Q5 — Do we pay for Radar for Fraud Teams?** Custom Radar rules (block high-risk card-country/destination pairs, force review on three-way country mismatches, `plan/06` §2.3) need Stripe's paid add-on, charged per screened payment (a few cents; check the current price). Built-in Radar is free. **Default: yes, from the first live order.** At Phase 1 volume it costs a few euros a month, and `plan/09` Phase 1 acceptance 5 requires "Radar rules active". Alternative: built-in Radar only, plus spec 021's own pre-checks.
- **Q6 — Do you accept Amendment A to the state machine (§5.1)?** Four behavioural changes to `plan/11` §2 (the rest of Amendment A is columns and self-loops that follow from them): (a) buyers can cancel free before acceptance (the diagram had no arrow for the promise `plan/07` makes); (b) a refused capture after acceptance moves the order to `payment_failed`; (c) a partial refund no longer changes the order's status, and the `refunded_partial` state is dropped, so an order with a refunded add-on still gets delivered; (d) a chargeback can arrive from any paid state, not only after a complaint. **Default: accept all four**; they are data rows in a table nobody has built yet, so they cost nothing now.
- **Q7 — What do we send Stripe about the people in an order?** **Default: the buyer's email and the billing details the payment method needs (Radar uses them); about the recipient, only the destination country — no name, address, phone or card message.** This keeps recipient data minimised (`plan/07` §1.3) at the cost of Radar not seeing the delivery address. Alternative: send the delivery address as Stripe's `shipping` field, which improves fraud scoring and makes Stripe a recipient of recipient data (RoPA and privacy-policy change).
