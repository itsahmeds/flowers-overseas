## 1. Problem

**This spec covers two roadmap items, `013` (payments) and `015` (order state machine, events, outbox).** `plan/09` lists them apart and then, under core-touching risk (a), says they must be designed together because capture happens on florist acceptance. **The founder's ruling of 2026-10-14 (§14) replaces that model: every payment is captured when the order is placed, and the machine's authorise-then-capture path is not used at launch**; the two halves still meet, at the hand-off to routing and at the start of production. Since then most of `015` has been decided elsewhere. Spec 002 §14 A6 (approved 2026-10-12, rulings D1–D6) fixed the machine as data: 26 states, 73 rows, 28 transition events and 8 status-preserving events, with `allowed_actors` per row. Spec 010 (approved) owns the one order engine: `orderService.place`, `transition`, `appendEvent`, `ActorSchema`, the event-schema registry, the outbox writer and `outboxTargets(event, mode)`, plus `checkoutMode()` and the `CheckoutPaymentStep` seam; its §14 A1 (proposed, PR 213) binds the engine to A6. Spec 011 (approved) owns the florist commands and the `AcceptedOrderEffect` seam. What remains of `015` is the money half: the events that move money, the routes that hand them to their consumers, and the dispatcher that delivers them. That is small enough to sit here, so number `015` stays unused (§13 Q6, approved). Wherever specs 010, 011 and 012 say "spec 015", this spec is meant.

Today nothing can take money. Spec 010's checkout places demo orders and stops: its `checkoutMode()` can return `test` or `live` only once this spec registers a Stripe payment step (010 §2, AC-2, AC-4), and it handed this spec the Stripe test mode, the Payment Element, the pre-contract block and the test-mode records (010 §12, §13 Q5). Spec 011's florist can accept an order, but for a `live` order nothing starts production (`unconfiguredOrderEffect`, 011 §5.2). `plan/09` Phase 1 acceptance 1 (one real paid order, real card, 3DS, routed, accepted, captured, zero manual database edits; under the ruling the capture comes first) cannot happen without this spec, and the founder wants the site ready for real paid orders.

Getting it wrong costs money or trust directly: a buyer charged twice, charged an amount other than the one on the page (`plan/07` §4), charged for an order we then cannot deliver and not refunded, told how our fulfilment works behind the brand (§14), a florist who makes a bouquet that is not paid for, or a forged webhook that marks an order paid. Each design choice below aims to make these impossible, not unlikely.

## 2. Scope

**A. The pay step in spec 010's checkout (010 §12 "Requirements on spec 013" (a) and (b))**
- `stripeTestPaymentStep` (mode `test`) and `stripeLivePaymentStep` (mode `live`), registered in spec 010's `CheckoutPaymentStep` registry. `checkoutMode()` stays the only place that decides the mode (010 AC-1); this spec adds no mode logic.
- Step 3 in `test` and `live`: the Stripe Payment Element (a client island, deferred intent), the server-rendered pre-contract block, and the pay button that names the amount. Step 3 also renders a placed but unpaid order so the buyer can retry after a decline.
- A return route for 3DS and bank redirects, which reconciles and then 303s to spec 010's confirmation page. **This spec owns the confirmation page's `test` and `live` states** (spec 010 §14 A2 fixes 010's §5.3 rows so that one spec owns them). The post-purchase block spec 018 designs (masked email, tracking link, invoice state, the free-cancel control) is content that 018 supplies through `getConfirmationBlock` and this spec's page renders inside those states; 018 owns the block's content and view model, this spec owns the page, the state per A6.4 projection and the payment copy.
- **Launch methods (§13 Q5): card, Apple Pay and Google Pay, each charged at once** (automatic capture, the founder's ruling of 2026-10-14, §14). No method is put on hold. BLIK and the other bank methods are a later task (§12 task 9), not a launch criterion.
- Stripe.js, the Stripe CSP origins, the Stripe cookies and browser Sentry load on step 3 in `test` and `live` only.

**B. The provider**
- A `PaymentProvider` interface, the Stripe adapter (PaymentIntents, automatic capture for every method, 3DS, Radar metadata, idempotency keys, pinned API version, restricted live key) and an in-memory `FakePaymentProvider`. One exported contract suite that both pass and spec 014's Mollie adapter must pass.

**C. The payment lifecycle, written in A6's event names only**
- Start a payment for a placed order and capture it at once, reconcile the order with the provider's state (row 2, `placed → paid_unrouted`), mark the order paid when a florist accepts (row 14, no provider call), start production on the morning of the delivery date (row 16, 06:00 destination-local, §14 A-founder-2026-10-14b; spec 002 §14 A10), refund in full on cancellation before production, and expire unpaid orders. **Not used at launch (§14):** the authorisation hold (row 1), capture on acceptance and its refusal (rows 14 with a provider call, and 15, D2), and the D4 "cancel before a card hold lapses" job, which is removed. A6's rows stay as they are; no code of this spec writes rows 1 or 15.
- **Price charged = price shown:** every amount sent to the provider is read from the order, which spec 010 wrote from the verified quote. No exported function takes a charge amount.

**D. The webhook inbox:** signature check, store before process, idempotency by event id, correct results out of order, replay command.

**E. Refunds and disputes:** a refund service with money invariants and A6's refund rules (D1, F2), the refund data spec 018 needs for advisor F4, and dispute handling inside and outside A6's set C (D3).

**F. The order-machine half (former `015`)**
- Versioned schemas, in spec 010's registry, for every event this spec writes.
- The rows of spec 010's `outboxTargets(event, mode)` for the `payments` and `routing` targets.
- The outbox dispatcher and its typed handler registry, with per-target delivery.
- `cancelOrder` (A6 row 13), the one command for buyer, admin and system cancellation.

**G. Alerts** (§11): the alerts that fire at the point of failure inside this spec's code, **and two monitors built here (§13 Q8): "paid but not routed for 5 minutes" and "no Stripe webhook for 24 hours"**; and **spec 002 §14 A7** (§5.1, one migration with its rollback).

## 4. User stories

- As a **buyer in the UK sending to Poland**, I pay by card or Apple Pay, pass 3DS once, and see the amount I saw on the product page and at step 3, so I trust the site.
- As a **buyer**, I am charged once, when I place the order, and the page tells me plainly that you have my order and my payment. I can cancel for free until you start preparing my order, and I get the full amount back (`plan/07` §2.1, A6 row 13 then row 32).
- As a **buyer whose order you cannot deliver**, I am told plainly that you could not deliver it and that you have refunded me in full, without being told why in terms of who makes the flowers.
- As a **buyer paying in złoty**, I pay by card, Apple Pay or Google Pay at launch, charged at once like everyone else. *(Later task, not launch: BLIK.)*
- As a **buyer whose card is declined**, I stay on step 3, read what went wrong in my language, and try again without retyping anything.
- As a **florist**, the money is captured before I am even offered the order, so I never make a bouquet that is not paid for.
- As the **founder**, I get an alert when a payment behaves unexpectedly, a webhook dies, a dispute opens or an amount does not match, so I find out before the buyer does. I also get one when a paid order has not been routed within 5 minutes, and one when Stripe has been silent for 24 hours, so a broken endpoint or router is caught before the first real order is lost.
- As the **founder**, I can refund all or part of an order from admin, and the system refuses to refund more than was captured or to refund a closed order.
- As the **implementer of spec 016**, I register one routing handler and call `transition`; I never touch `order.status` or Stripe.
- As the **implementer of spec 018**, I read succeeded refunds from one function and render them beside the status.
- As a **reviewer**, I can show that a forged, replayed, duplicated or out-of-order webhook cannot move an order to the wrong state.
- As **Googlebot**, I see nothing new: no indexable page loads Stripe.js, and the budgets of `plan/01` §7 hold.

### 5.1 Data model changes (tables, columns, migrations + rollback)

The tables are spec 002's, as built by TASK-019 to TASK-023 in PR 210 (`0007_orders_payments`, `0008_order_integrity`, `0009_notifications_ops`, `0011_rls_policies`). PR 210 is being finished now, so this spec does not fold anything into it. Everything below ships as **one migration of this spec**, `NNNN_payments_a7.sql` (the next free number when it merges) with `NNNN_payments_a7.down.sql`. Nothing in it touches `order_status` or `order_transition`.

**Spec 002 §14 A7** (approved by the founder 2026-10-14, §13 Q7; A6.10 (vi) reserved the number for it). It is written into spec 002 by its own amendment PR, as a **later migration** that leaves PR 210's tables (migrations 0007 to 0011, on main) unchanged, and **this spec's migration ships it**. Where this section and spec 002 §14 A7 differ, spec 002 §14 A7 governs and this section is corrected. It replaces the draft's "Amendment request A". Spec 002 §14 A8 (spec 016's two `no_partner_available` rows and spec 018's `sessions.created_at`) is a separate migration, shipped by the earliest of spec 016's and 018's first migrations; A7 and A8 do not depend on each other.

1. **Catalogue: one status-preserving event, `order.payment_attempt_failed`.** A6.10 (iii) says the draft's `(placed, payment_attempt_failed) → placed` self-loop may enter only through this spec's own amendment. A7 takes it in as a **status-preserving** event, not a self-loop row. A declined attempt never changes a status and never has to be refused: a decline reported for an order that has already moved on is still a true fact about the payment. Under A6.1 that makes it status-preserving, written only by `appendEvent`. The catalogue is **37 names after A7**: 28 transition events and 9 status-preserving (spec 002 §14 A8 adds rows, not names, so it stays 37). A7 adds no `order_transition` row (the fixture's count is 73 on main, and 75 once spec 002 §14 A8 merges), and spec 010 AC-22's set of 28 transition events is unchanged. Spec 002 AC-14's fixture (`tests/fixtures/order-machine.ts`) adds the name to its status-preserving list.
2. **`payment`** (0007 today: `provider_ref NOT NULL`, `method NOT NULL`, status `pending | requires_action | authorised | captured | failed | cancelled`):
   - `provider_ref` and `method` become nullable, with `CHECK (provider_ref IS NOT NULL OR status IN ('pending','failed'))`. The row is written as `pending` **before** the provider call, so a webhook that races the response is matched by `metadata.payment_id`.
   - Status gains `processing` (bank-redirect methods in flight).
   - New: `livemode bool NOT NULL`; `capture_method text NULL CHECK IN ('manual','automatic')`; `amount_captured_minor bigint NOT NULL DEFAULT 0`; `amount_refunded_minor bigint NOT NULL DEFAULT 0`; `authorised_at`, `auth_expires_at`, `failed_at` (`timestamptz NULL`); `attempts integer NOT NULL DEFAULT 0`; `last_decline_code text NULL` (a Stripe code such as `insufficient_funds`, never the bank's text); `last_decline_ref text NULL` (the failed charge's id, so one decline writes one event); `card_brand text NULL`; `card_last4 char(4) NULL` (`plan/07` §1.2 keeps token, last4, brand).
   - Checks: `amount_captured_minor BETWEEN 0 AND amount_minor`; `amount_refunded_minor BETWEEN 0 AND amount_captured_minor`. Partial unique index: one live payment per order, `UNIQUE (order_id) WHERE status NOT IN ('cancelled','failed')`.
   - The existing `(order_id, currency_code) → order(id, buyer_currency_code)` key already forces the payment currency to equal the order's. This spec relies on it.
   - **Under the ruling of 2026-10-14 (§14) A7 ships unchanged.** The hold-only parts stay in the schema and are left empty at launch: status `authorised`, `capture_method = 'manual'`, `authorised_at` and `auth_expires_at`. Every launch payment row is written with `capture_method = 'automatic'`. Removing them would be a new amendment to an approved, unbuilt migration for no gain, so this spec does not ask for one.
3. **`refund`** (0007 today: `provider_ref NOT NULL`, free-text `reason`, status `pending | succeeded | failed | cancelled`):
   - `provider_ref` nullable, with `CHECK (provider_ref IS NOT NULL OR status IN ('requested','failed'))`. The row's own `id` is the provider idempotency key.
   - Status gains `requested`.
   - `reason CHECK IN ('buyer_cancel','no_partner','authorisation_lapsing','redelivery_failed','addon_missing','late_delivery','substitution_complaint','quality','goodwill','duplicate','other')`. `authorisation_lapsing` is never written at launch (the lapse job is removed, §14); it stays in the check with A7. The reason is internal: no buyer surface renders it (§5.3).
   - New: `requested_by text NOT NULL` (the `ActorSchema` value of whoever asked); `succeeded_at timestamptz NULL` with `CHECK ((status = 'succeeded') = (succeeded_at IS NOT NULL))`, which is the `{date}` of advisor F4; `failure_code text NULL`.
4. **`payment_dispute`** (new, `payments` module): `id, payment_id, currency_code, provider_ref UNIQUE, amount_minor bigint, reason text, status CHECK IN ('open','won','lost','closed'), evidence_due_by timestamptz NULL, opened_at, closed_at NULL`, with `(payment_id, currency_code) → payment(id, currency_code)` so the money pair holds. RLS on, policies for `system` and `admin` only: partners never see it.
5. **`webhook_inbox`** (0007 today: no status column): `livemode bool NULL` and `event_type text NULL`, with `CHECK (provider <> 'stripe' OR (livemode IS NOT NULL AND event_type IS NOT NULL))`, so spec 016's email-provider rows (016 §5.1 widens `provider` to `resend`) are admitted while every Stripe row carries both; `object_ref text NULL` (the PaymentIntent, refund or dispute id), `status text NOT NULL DEFAULT 'received' CHECK IN ('received','processed','ignored','failed','dead')`, `ignore_reason text NULL`, `last_error text NULL` (error class and message, never a payload excerpt). `raw` stays, under the existing 12-month retention row.
6. **Per-target outbox delivery.** Spec 010's writer keeps writing one `outbox` row per event with `targets text[]` (0009, `UNIQUE (event_id)`); this spec does not change it. A7 adds `outbox_delivery(id, outbox_id FK, target text NOT NULL, status CHECK IN ('pending','sent','dead') DEFAULT 'pending', attempts integer NOT NULL DEFAULT 0, last_error text NULL, sent_at timestamptz NULL, UNIQUE (outbox_id, target))`, filled by an `AFTER INSERT ON outbox` trigger with one row per element of `targets`, and `outbox_attempt.target text NULL`. A target that fails then never holds up, or re-runs, a target that succeeded. `outbox.status` becomes `sent` when every delivery is `sent`, and `dead` when any delivery is `dead`. RLS on, `system` only.

**Rollback** (`NNNN_payments_a7.down.sql`, reverse order). First a guard: if any `payment` row has `livemode = true`, the down file **raises** `A7_ROLLBACK_LIVE_PAYMENTS` and changes nothing. A real payment, its refunds and its disputes are part of the accounting record (§8) and are never deleted by a rollback; after the first live payment, rollback is flags first (§12). With no live payment: drop the outbox trigger, its function and `outbox_delivery`; drop `outbox_attempt.target`; drop the new `webhook_inbox` columns; drop `payment_dispute`; restore `refund`'s and `payment`'s original checks after deleting rows in the added statuses (`requested`, `processing`) and rows with a null `provider_ref` or `method`, all of them test-mode rows (the guard has proved there is no live one); drop the added columns. The catalogue item is data in the fixture and the registry, with no database object. The migrate, rollback, migrate round trip of spec 002 runs over it.

**What the draft asked and A7 drops:** `order.source` values (spec 010 uses `order.mode`; `source` stays `seed | real`); the `ORDER_INITIAL_STATUS` insert trigger (spec 010 §5.1 A, built in 0008); `order_event.idempotency_key` (§5.2 gets one money fact, one event, from the money row's own state change instead, so spec 010's `transition` signature stays as written); every `order_transition` row (A6 has them all).

**How a paid order flows (test and live)**

1. Step 3 renders. `prepare(draftId, quote)` returns the Payment Element options for a **deferred intent**: amount and currency from the quote, `methodTypes`, the Stripe locale, the publishable key. No intent exists yet.
2. The buyer presses "Pay". The island calls `elements.submit()`, then spec 010's `placeOrderAction`, which verifies the quote and places the order (010 AC-17, AC-21; status `placed`, `order.placed` seq 1) and commits.
3. Outside that transaction, `confirm(orderId)` runs `startPayment(orderId)`. It inserts the `payment` row as `pending` and creates the PaymentIntent from the **order** with idempotency key `pi:create:{paymentId}`. It returns the client secret to the island only. A second call for the same order (010 AC-21's double click) returns the same intent.
4. The island calls `stripe.confirmPayment` with `return_url = /{locale}/checkout/return`. A decline comes back to the island: step 3 stays, the message key is shown, and the buyer retries on the same intent. A 3DS or bank redirect returns through the return route.
5. The return route, or a webhook, whichever comes first, runs `reconcile`, which writes A6 row 2 (`placed → paid_unrouted`, `order.captured`): the money is taken. The outbox then routes the order (below). Row 1 (`authorised`) is not written at launch (§14).

A refresh while the draft's order is `placed` renders step 3 from the order's snapshots and lines, with the Payment Element on the existing intent. This is how this spec reads 010 §12 (a)'s "a declined test card keeps step 3 and the draft intact": nothing the buyer typed is lost, and 010's placement transaction still clears the draft's personal fields as 010 §5.1 B says.

**Payment step and provider**
- `CheckoutPaymentStep` implementations (010's interface, unchanged): `prepare(draftId, quote) → PaymentPreparation` (`{ elementOptions: { mode: 'payment', amountMinor, currency, methodTypes, captureMethod: 'automatic' }, publishableKey, stripeLocale }`) and `confirm(orderId, input) → PaymentOutcome` (`{ clientSecret } | PaymentsUnavailable | OrderNotPayable`). `stripeTestPaymentStep` and `stripeLivePaymentStep` each register only when the `routing` handler of spec 016 is registered (below), so neither "payment step registered" precondition of spec 010 can be true while a `test` or `live` order would have no router. This spec's own tests inject a stub `routing` handler (AC-12), so they do not wait for spec 016.
- **Capture is `'automatic'` everywhere, the founder's ruling of 2026-10-14 (§14).** The Element's `captureMethod` and the intent's top-level `capture_method` are both `'automatic'`, which Stripe requires to match, and the intent carries no per-method `capture_method` override. `CreateIntentInput.captureMethod` is typed as the literal `'automatic'`, so a hold cannot be asked for without changing a type (AC-14). Task 2 proves on Stripe test mode that a 3DS-challenged card ends `succeeded`, never `requires_capture` (AC-38).
- `PaymentProvider`: `createIntent(CreateIntentInput) → ProviderIntent`, `retrieveIntent(ref)`, `capture(ref, idempotencyKey)`, `cancel(ref, idempotencyKey)`, `refund(ref, Money, idempotencyKey, metadata)`, `verifyAndParseWebhook(rawBody, headers) → ProviderEvent | SignatureInvalid`, `listEventsSince(date)`. `ProviderIntent = { ref, status: 'requires_payment_method'|'requires_action'|'processing'|'requires_capture'|'succeeded'|'canceled', amount: Money, captureMethod, methodType, cardBrand?, cardLast4?, threeDsOutcome?, riskScore?, livemode, captureBefore?, lastDecline?: { code, ref } }`. Provider types never leave the module.
- `CreateIntentInput` sent to Stripe: `amount` and `currency` from the order through `toStripeAmount`; `capture_method: 'automatic'` and no `payment_method_options.*.capture_method` for any method; `payment_method_types` = `methodsFor(buyerCountryDeclared, currency)` ∩ `src/config/payment-methods.ts` `available` ∩ the `payments.method.{id}` flags, never `automatic_payment_methods`, so the list is ours and testable (at launch `available` is true for card, Apple Pay and Google Pay only; Apple Pay and Google Pay travel as the `card` type); `payment_method_options.card.request_three_d_secure` = `'any'` (§13 Q1); `metadata` = exactly `{ order_id, payment_id, destination_country, buyer_country_declared, is_first_order, order_mode }`, all non-personal, for Radar rules; `description` = the order reference (`FO-XXXX-XXXX`); no `receipt_email` (our confirmation is spec 016's); no `shipping` (recipient data never goes to Stripe, §8, §13 Q4).
- `toStripeAmount(Money)`: an explicit table for **GBP, EUR, PLN** (exponent 2, identity). Any other currency throws `UnsupportedCurrency`; adding one is a reviewed table row with a test.
- **Methods at launch (§13 Q5):** the capability table lists card (with Apple Pay and Google Pay) as `available`, with no capture column: every method is captured automatically. BLIK (PLN, Polish banks) is a table row with `available: false` and no flag set, so no code path offers it. Stripe documents BLIK as "not supported when collecting payment details before creating a PaymentIntent", and step 3 is built that way (deferred intent), so BLIK needs its own task (§12 task 9). Every live order reaches `paid_unrouted` through reconcile row 2; the same lifecycle serves BLIK later, so its task adds a method row and a step 3 change, not new lifecycle logic.
- `declineMessageKey(code) → MessageKey` maps Stripe decline codes to keys in the `payments` namespace (§7); an unknown code maps to `payments.error.generic`. The provider's own message never reaches a page.
- Keys and environments: production holds only the live restricted key (`rk_live_`), the live publishable key and the live webhook secret; staging and PR environments only test keys (`sk_test_`, which spec 010's `checkoutMode()` table reads) and the test webhook secret. `validateEnv` (010 AC-2) additionally rejects `rk_live_` outside production.

**Reconcile** (`reconcile(payment, intent)`, the one place a provider state becomes an order transition). It always works from the **retrieved** intent, never from the event body, so the order of events cannot matter. Actor `system:payments`. Before any transition it compares `intent.amount` with the order's total and currency; a mismatch makes no transition, cancels the intent, sets the payment `failed` and raises `payment.amount_mismatch`.

| Intent (retrieved) | Order now | What happens (A6.3 row) |
|---|---|---|
| `succeeded` | `placed` | `transition('order.captured')` → `paid_unrouted` (row 2); payment `captured`, `capture_method = 'automatic'`, `amount_captured_minor` = amount, **`captured_at` = now**. The only way a launch order is paid |
| `succeeded` | `abandoned` or `payment_failed` | no transition (A6 has no row); payment `captured`, `captured_at` = now; `refund` of the full captured amount at once (reason `other`, actor `system:payments`, the narrow case of § Refunds); `payment.captured_after_close`. Reachable only by a provider-side anomaly, because the sweep closes an unpaid order only after the provider confirms the intent cancelled (sweep (b)) |
| `requires_capture` | `placed` | **not expected at launch** (no intent asks for a hold): `provider.capture(ref, 'capture:{paymentId}')` at once and `payment.unexpected_hold`; the `succeeded` that follows writes row 2. Row 1 is never written |
| `requires_payment_method`, decline ref ≠ `last_decline_ref` | `placed` | `appendEvent('order.payment_attempt_failed')` (A7) in the same transaction as `attempts + 1`, `last_decline_code`, `last_decline_ref` |
| `canceled`, cancelled by us | any | nothing: our own command already moved the order |

`syncFromProvider(orderId)` retrieves the intent and runs `reconcile`. The return route calls it, so the buyer sees the result without waiting for a webhook and the e2e suite needs no webhook tunnel.

**Routing hand-off (the `routing` target).** For `test` and `live`, this spec's rows of `outboxTargets` send `order.authorised` and `order.captured` to `routing`. The handler acts only when the event's `to_status` is `authorised` or `paid_unrouted`, so row 14's second `order.captured` (A6.3 note F3) routes nothing. At launch only `paid_unrouted` occurs; the `order.authorised` route stays so the machine's row 1 keeps a consumer if a hold ever returns. **`test` and `live` orders are both routed by spec 016's router** (the founder's 16-11: test orders send florist messages, never buyer messages). Spec 016 registers the one `routing` handler; this spec only hands off after authorisation or capture and writes no routing transition (rows 5, 6, 8 to 12 are spec 016's, written by its `system:order.route`, `system:assignment.timeout` and admin actors). Spec 010's `demoRoute(orderId)` serves `demo` mode only, in the request, and never an order that reached this hand-off. With no `routing` handler registered, the delivery throws `ROUTING_NOT_CONFIGURED`, retries and goes `dead` with `outbox.dead`. `demo` orders get no row: spec 010 routes them in the request, and 010 AC-20's "zero outbox rows" stays true.

**Production start on acceptance (the `payments` target and 011's seam).** Spec 011's `respondToOffer` writes `assignment.accepted` (row 7). For `test` and `live`, this spec's `outboxTargets` row sends it to `payments` in the same transaction. This spec registers `paymentAcceptedOrderEffect` in 011's `AcceptedOrderEffect` for `test` and `live` (011 §2 anticipates it: "Spec 013 replaces the effect for test orders"); its `afterAccept` only asks the dispatcher to run that order's pending deliveries now, so the outbox row stays the guarantee. `demoOrderEffect` keeps `demo` orders. The handler (`paymentAcceptedOrderEffect`'s outbox side):
- checks the order is `accepted` and its payment is `captured` (it was captured at placement, row 2). It makes **no provider call**: under the ruling nothing is held, so nothing is captured here (§14). An order that is no longer `accepted` when the delivery runs (the buyer cancelled it in between, spec 002 §14 A10 row 39) makes the handler write nothing and mark the delivery `sent`.
- In one transaction: `transition('order.captured')` → `paid` (row 14, the second `order.captured` of A6.3 note F3, `provider_call: false`) by `system:payments`. `captured_at` is not touched: row 2 set it. **Then, only if the order's production-start instant has already passed**, `transition('order.in_production')` → `in_production` (row 16) in the same transaction, by the same actor. Otherwise the order stays `paid` ("We have your order", spec 002 A9.1) and the production-start job writes row 16 on the delivery morning (below; §14 A-founder-2026-10-14b; spec 002 §14 A10.1). "Paid before the florist is told to start" holds trivially. **This spec is the only writer of `order.in_production` for `test` and `live` orders; spec 016 does not write it** (016 only reacts to the row 16 event with its messages, so spec 016's table row for row 16 and its AC-14 are corrected to match).

**Production start on the delivery morning (spec 002 §14 A10.1; the founder's "2 B", 2026-10-14).**
- `productionStartAt(order) → Date`: 06:00 local on `order.delivery_date` in the destination's zone (`city.iana_zone`, else `country.iana_zone`), the time read from `PRODUCTION_START_LOCAL_TIME` in `src/config/orders.ts` (one constant, `'06:00'`). Pure and DST-safe; exported for specs 016 and 018.
- `payments.production_start` (pg-boss, every minute, actor `system:payments.production_start`): selects `test` and `live` orders in `paid` whose `productionStartAt` is at or before now, locks each `FOR UPDATE SKIP LOCKED`, re-reads the status under the lock, and writes row 16 for each still `paid`. An order in any other status (cancelled by the buyer, charged back) is skipped. Idempotent: a second tick finds the order `in_production`. `demo` orders are untouched (spec 011's demo effect keeps them).
- `startProduction(orderId, actor)`: the same write for one order, refused with `PRODUCTION_NOT_DUE` before the delivery date begins in the destination's zone. Spec 011's dispatch command calls it, in the dispatch's transaction and before row 19, when a florist marks a `paid` order "out for delivery" on its delivery date before the job has written row 16 (for example at 05:45, or between two ticks), so row 19 always finds `in_production` (requirement on spec 011, §12). The florist has then really started, so the buyer's window closing then is still true.
- Cancel and start race on a `paid` order at its instant: both lock the order row; the first wins and the second is refused by the engine (`ORDER_TRANSITION_ILLEGAL`), so an order is never both cancelled and in production (AC-45).
- A payment that is not `captured` cannot reach here at launch. If one does, the handler throws `PAYMENT_NOT_CAPTURED`, writes nothing, and the delivery retries and ends `dead` with `outbox.dead`; the founder resolves it by the runbook. Row 15 (`order.payment_failed` from `accepted`, D2) is never written at launch, and `payment.capture_failed` is retired with it.

**Cancellation.** `cancelOrder(orderId, actor, reason) → OrderEvent | OrderError` applies `order.cancelled` (row 13, and rows 39 and 40 of spec 002 §14 A10). It is legal from the five states of A6's set E for `buyer`, `admin` and `system`, and from `accepted` and `paid` for `buyer` and `admin` with reason `buyer_cancel` only (set P, the buyer's free-cancellation window, spec 002 §14 A10.2; any other reason there returns `CANCEL_REASON_NOT_ALLOWED` and writes nothing; spec 010 A1.5 checks the class). From `in_production` or any later state it returns spec 010's `ORDER_TRANSITION_ILLEGAL` and calls no provider. It is the **only** way any actor cancels an order before production; nobody writes `order.cancelled` through `transition` directly. Callers: spec 018's buyer cancel line (actor `buyer`, reason `buyer_cancel`), `adminCancel` (spec 020 draws the page; reason chosen by the admin from the refund reasons), and spec 016's no-partner expiry (actor `system:routing.no_partner_expiry`, reason `no_partner`), which runs at spec 016's `graceEnd` for every order still `no_partner_available`, **including when `routing.auto` is off** for the destination (the orchestrator's ruling on spec 016 O-3, 2026-10-14): if the founder has not rerouted or cancelled the order by then, it is cancelled here and refunded in full through the refund path below, and spec 016 sends the buyer B5's plain cancellation. So no charged order can wait without an end. The sweep no longer cancels paid orders: the D4 lapse branch is removed (§14). The job `payments.monitor` and the actors `system:payments` and `system:payments.sweep` are this spec's; `system:routing.*` actors are spec 016's. `order.cancelled` and `order.cancelled_refunded` (row 24, written by spec 020) route to `payments`, whose cancel handler calls `refund` for the remaining captured balance with the cancellation's reason (`buyer_cancel`, `no_partner`, `redelivery_failed` or the admin's). Under the ruling the money was taken at placement, so **every cancellation of a paid order is a full refund**, through the refund path below; its success writes row 32. A hold to void exists only for a `requires_capture` intent, which launch never creates; the handler voids one (`provider.cancel`, key `void:{paymentId}`) if it ever meets one, and raises `payment.unexpected_hold`. The reason is stored on the refund row and in the event; **no buyer surface renders the reason**, and the buyer's view distinguishes only "you cancelled" from "we could not deliver" (§5.3). This is `plan/06` §2.2's "the buyer is never charged for an undeliverable order", kept by refund instead of by void.

**Refunds.** `refund({ orderId, amount: Money, reason, actor }) → Refund | RefundExceedsCaptured | CurrencyMismatch | NotRefundable`.
- Under the order row lock: `amount.currency` equals the payment's; `amountMinor` is a positive integer; captured − (succeeded + pending + requested refunds) ≥ amount.
- The order must be in A6's set F (`paid` … `resolved`, rows 30 and 31) or in `cancelled` / `cancelled_refunded` (row 32), where the amount must equal the remaining balance exactly. One narrow case is added by the ruling (§14): an order in `abandoned` or `payment_failed` whose payment is `captured` (the anomaly of the reconcile table), where the amount must equal the full captured amount, the actor is `system:payments` or `admin:{id}`, the reason is `other`, and no order event is written on success because A6 has no row for it (the money fact stays on the refund row, as for `payment.refund_state_mismatch`). Anything else, `closed` included (advisor F2, declined by the founder), returns `NotRefundable` with no provider call. A complaint after closing goes through `order.disputed` (row 27), as A6.3 says.
- It inserts the `refund` row as `requested` (`requested_by` = the actor), appends `order.refund_requested` (status-preserving) with that actor, calls the provider with the row id as the idempotency key, and records `provider_ref` and `pending`. There is no destination parameter: refunds go to the original method only (`plan/07` §9).
- **One money fact, one event.** When the provider confirms success (synchronously, by `refund.updated` or by `charge.refunded`), one transaction locks the refund row, and only if it is not yet `succeeded`: sets `succeeded`, `succeeded_at`, adds to `payment.amount_refunded_minor`, and applies the order event by `system:payments` (A6.2: money rows are `system` only). In F: cumulative < captured → `order.refunded_partial` (row 30, status unchanged, D1); cumulative = captured → `order.refunded_full` (row 31) → `refunded_full`. In `cancelled` or `cancelled_refunded` → `order.refunded_full` (row 32, status unchanged). A second notification finds the row `succeeded` and writes nothing.
- A refund that settles after the order has left the allowed set keeps the money fact on the refund row, writes no order event, and raises `payment.refund_state_mismatch`. `refund.failed` sets the row `failed` with `failure_code` and raises `payment.refund_failed`.
- `succeededRefunds(orderId) → { amount: Money; succeededAt: Date }[]`: the data spec 018 renders as "Refunded {amount} on {date}" beside the status (advisor F4, A6.4). Succeeded rows only. It is the **one source** of `{date}`: 018 reads the date from here, never from an event's `occurred_at`.
- `adminRefund` and `adminCancel`: server actions, zod-parsed, role `admin`, audit-logged in spec 002's `audit_log`, actor `admin:{userId}`. They call the services above; spec 020 draws the page. Spec 020's generic transition panel cannot offer rows 30–32 (`system` only), so refunds always go through `refund`.

**Disputes.** `charge.dispute.created` writes a `payment_dispute` row and raises `payment.dispute_opened`. If the order is in A6's set C as amended by spec 002 §14 A9.7 (F plus `paid_unrouted`, `routed`, `no_partner_available`, `manual_reroute`, `closed`, `refunded_full`: 16 states), `transition('order.chargeback_opened')` → `chargeback_open` (row 34; fulfilment stops and, from the three routing states, routing stops, D3, with the founder's conditions declined). Outside C (for example `cancelled`, `cancelled_refunded`, or `accepted` in the instant before row 14), the dispute is recorded on the payment, `payment.dispute_outside_machine` is raised and the order status stays as it is (A6.3, "a requirement on spec 013"). `charge.dispute.closed` with `won` or `lost` applies row 35 or 36 when the order is `chargeback_open`; otherwise it updates the dispute row only and raises the same outside-machine alert.

- Transition events, written only through `transition`: `order.payment_failed`, `order.abandoned`, `order.cancelled`, `order.refunded_partial`, `order.refunded_full`, `order.chargeback_opened`, `order.chargeback_won`, `order.chargeback_lost`. `OrderRefundedPartialV1` and `OrderRefundedFullV1` carry exactly `refund_id`, `amount_minor`, `currency_code`, `reason` and `mode` (the fields spec 018 §12 asks for); `order.refund_requested` carries the same five fields. `OrderCancelledV1` carries exactly `reason` and `mode` (the actor is the event's own column); the confirmation reads the actor class to choose its wording (§5.3), and no buyer surface renders `reason`.

**The dispatcher.** `outbox.dispatch` (pg-boss, every tick) takes `pending` `outbox_delivery` rows `FOR UPDATE SKIP LOCKED` and hands each to its target's handler with `{ eventId, orderId, type, fromStatus, toStatus, mode }` read from `order_event`. Success → `sent`. A throw → `outbox_attempt` (with `target`), backoff, and after 8 attempts `dead` and `outbox.dead`. `HandlerRegistry` is typed `Record<OutboxTarget, OutboxHandler>`, so a target added to the union without a handler fails `tsc`. Handlers are idempotent: a redelivered row causes no second side effect (production start and refunds by status check and idempotency key; routing by status check).

**Webhook inbox (`plan/01` §9)**
- `POST /api/webhooks/stripe` (Node runtime, `force-dynamic`): reads the **raw** body (over 1 MB → 413), verifies `Stripe-Signature` against the environment's one secret with Stripe's 300-second tolerance, and answers 400 with nothing stored for a missing header, a bad signature or a stale timestamp. A verified event whose `livemode` differs from the environment's is stored `ignored` (`livemode_mismatch`).
- Store before process: `INSERT … ON CONFLICT (provider, event_id) DO NOTHING`, enqueue `webhook.process` with `singletonKey` = the inbox id, then **200**. A database failure answers 500 so Stripe retries. Nothing is processed inside the request.
- `webhook.process`: locks the row `FOR UPDATE SKIP LOCKED`, parses it with `StripeEventSchema` (zod over the fields we read), routes by type to `reconcile`, the refund path or the dispute path, and marks it `processed`, `ignored` (unknown type, stale) or `failed`; `failed` retries with backoff and becomes `dead` after 8 attempts with `webhook.dead`.
- Subscribed types (only these, to keep personal data out of `raw`): `payment_intent.requires_action`, `.amount_capturable_updated`, `.succeeded`, `.payment_failed`, `.canceled`, `.processing`; `charge.refunded`; `refund.created`, `refund.updated`, `refund.failed`; `charge.dispute.created`, `.updated`, `.closed`.
- `pnpm jobs:replay-webhooks --since <ISO> [--inbox-id <id>] [--dry-run]` (the name `docs/runbooks/payment-webhook-down.md` already uses): feeds Stripe's `events.list` (30-day window) through the same ingest path, so a replay is idempotent; `--inbox-id` resets one row to `received`.
- PR environments share staging's database (010 §12), so staging's endpoint processes their test events too.

**Jobs** (registered in `src/jobs/index.ts` with versioned payload schemas; needs TASK-024)
- `outbox.dispatch`, `webhook.process` (above).
- `payments.monitor`, every minute, read-only: the two monitors of AC-39 and AC-40. It writes no table and calls no provider; it raises Sentry alerts (§11).
- `payments.production_start`, every minute, actor `system:payments.production_start`: writes row 16 for each `paid` order whose `productionStartAt` has passed (above; AC-44).
- `payments.sweep`, every 15 minutes, actor `system:payments.sweep`:
  (a) *removed by the ruling (§14):* the D4 branch that captured or cancelled a card hold near `auth_expires_at`. No hold exists, so nothing lapses; `payment.auth_expiring` is retired;
  (b) a `placed` order older than **2 hours** (`src/config/payments.ts`, §13 Q9): the sweep first retrieves the intent and runs `reconcile`. `succeeded` → row 2, as any payment. `processing` → skipped until the next run (money may be moving). Otherwise it cancels the intent (`provider.cancel`, key `void:{paymentId}`), and only once the provider confirms `canceled` writes `order.abandoned` (row 4), or `order.payment_failed` (row 3) if at least one attempt failed. A provider that refuses the cancel because the intent moved on leaves the order `placed` for reconcile. So the sweep never closes an order whose money has moved; a capture the provider reports after a confirmed cancel is the reconcile table's `payment.captured_after_close` anomaly, refunded at once;
  (c) a `pending` payment older than 15 minutes with no `provider_ref` → `failed`;
  (d) a `requested` refund older than 5 minutes → retried with the same idempotency key.

**Errors and logs:** every exported function returns typed results for expected outcomes and throws only on bugs. Spec 010's engine errors (`ORDER_TRANSITION_ILLEGAL`, `ORDER_ACTOR_NOT_ALLOWED`, `ORDER_EVENT_NEEDS_TRANSITION`) pass through unchanged.

- **What the confirmation says (the founder's rulings of 2026-10-14, §14 A-founder-2026-10-14 and A-founder-2026-10-14b).** The buyer is charged at placement and is never told how the order is fulfilled. In the paid states the page thanks the buyer and says where and when the flowers arrive: "Thank you. We have your order." and "Your flowers arrive in {city} on {date}." (`{city}` the destination city's name in the page locale, `{date}` the delivery date through `formatDate` with the weekday, day and month and no year). The `notCompleted` heading may wrap to two lines on a phone; that is a design note for the artboard, not copy.

### 5.4 Rendering & caching (SSG/ISR/SSR, tags invalidated, per plan/01 §3)

This is spec 010 §12's list plus `*.js.stripe.com`, which Stripe's current CSP guidance adds. No other route's policy changes.

- No cache tag is invalidated. Placing or paying for an order changes no public page.

## 6. SEO considerations (mandatory)

- **Indexability:** nothing here renders an indexable page. The return route lives under `/{locale}/checkout/`, which spec 010 disallows (`/*/checkout`) and sends with `noindex, nofollow` (010 AC-30); the webhook is under `/api/`. No canonical, hreflang set, sitemap or schema type changes.
- **URL pattern** (`plan/02` §4.1): one new transactional path, `/{locale}/checkout/return`, the same English word in every locale (spec 010 §13 Q10). - **Core Web Vitals and bytes:** Stripe.js and its fraud-signal requests are the heaviest third party this project adds. They load on step 3 in `test` and `live` only, never on home, corridor, category or product pages, so the budgets of `plan/01` §7 and spec 004 hold. That is `plan/09` Phase 1 acceptance 8 ("budgets still met with payments … present"); AC-2 pins it with a crawl.
- **Schema identity:** `Offer.price` = visible price = charged amount. Spec 005's `offerProjection()` and spec 010's AC-15 give the first two; this spec closes the chain by charging only the order total written from the verified quote (AC-1, AC-9). A schema price that differs from the charge is a Merchant Center policy breach and a consumer-law one (`plan/02` §15, `plan/07` §4).
- **Internal links, thin content:** none added. No `<a href>` to a checkout URL on any indexable page (010 AC-30's crawl).

## 8. Compliance considerations (mandatory)

- **Data flows → RoPA** (`docs/compliance/ropa.md`):
  1. **Stripe, live** (activates spec 010 §8's row 3 "Live orders"): Stripe Payments Europe Ltd (Ireland) as processor for payment processing and independent controller for its own fraud and regulatory duties (`plan/07` §1.1, §1.4). Subjects: buyers. Sent: amount, currency, the buyer's email and the billing details the Element collects, card data (entered only in Stripe's iframe), device and IP signals gathered by Stripe.js, and the six non-personal metadata fields of §5.2. **Not sent:** recipient name, address, phone, card message or any free text (§13 Q4). Basis: Art. 6(1)(b) for payment; Art. 6(1)(f) and Recital 47 for fraud prevention. Kept by us: the `payment` row (provider ref, status, amounts, method, brand, last4, 3DS outcome, risk score, decline code) as part of the accounting record (10 years with the invoice archive, `plan/07` §10; accountant to confirm, `plan/13` B1); `webhook_inbox.raw` 12 months (spec 002's retention row); `payment_dispute` with the accounting record.
  2. **Stripe, test mode** (staging and PR environments only; 010 §8 hands this row here): the same categories, typed by testers and demo users, with Stripe's test cards only. Basis: Art. 6(1)(f). Retention follows spec 010's demo and test order rule.
  Stripe's DPA is part of its services agreement; it is filed in `docs/compliance/` when the account opens (founder action).
- **Minimisation:** recipient data, the most sensitive we hold (`plan/07` §1.3), stays out of Stripe entirely, at the cost of Radar not seeing the delivery address. Subscribed webhook types are limited so `raw` holds as little personal data as possible.
- **Contract formation and withdrawal** (`plan/07` §2.1–§2.3), **changed by the founder's ruling of 2026-10-14 (§14) and sent to the lawyer (§13 Q11):** the buyer pays at placement. The proposed reading is that the contract is concluded when we take the payment and confirm the order, and that the buyer may cancel free, with a full refund to the original method, until we start preparing the order (A6 row 13 from set E, and spec 002 §14 A10's rows 39 and 40 from `accepted` and `paid`, then row 32; the wording of spec 010 §14 A-founder-2026-10-14b and spec 041). "Being made" (`in_production`, row 16) begins at 06:00 destination-local on the delivery date, or at acceptance when that comes later (§5.2; the founder's "2 B", §13 Q11), so the window lasts until the delivery morning and the promise and the machine agree. If we cannot deliver, the buyer gets an automatic full refund (`plan/06` §2.2). This is what makes reliance on the perishable-goods exemption (CRD Art. 16(d); UK CCRs reg. 28(1)(c)) fair. The buyer-facing promise no longer names a florist's acceptance (`plan/07` §2.1's "until your florist accepts it" and §2.3's "when payment is captured after florist acceptance" are plan corrections, §13). The pre-contract block (010 §8) is rendered by this spec in `test` (labelled) and `live`.
- **Charging before fulfilment is confirmed:** money is taken for an order no florist has yet accepted. The safeguards are the full automatic refund on any cancellation before production (AC-15), the "paid but not routed" monitor (AC-39), spec 016's no-florist cancellation, and the refund invariants (AC-28). A refund returns the price but Stripe keeps its processing fee, a cost the void used to avoid (§13 Q12).
- **Button and price display** (`plan/07` §4, CRD Art. 8(2), `CLAUDE.md`): the button names the obligation to pay and the amount; the amount charged is the order total from the verified quote, in the currency shown; no function accepts another amount; a provider mismatch cancels the payment (AC-11). No payment-method surcharge exists (PSD2 / CRD Art. 19).
- **Geo-blocking** (EU 2018/302, `plan/07` §3, ADR-0006): methods depend on the buyer's **declared** country and the order currency, which the buyer can change freely, never on IP (AC-7). Cards are accepted from every country.
- **PCI DSS:** card data is entered only in Stripe's iframe and never touches our servers or logs, which keeps us at SAQ A. Step 3's CSP allows only Stripe's origins.
- **Security:** signatures verified before storage; replayed and stale signatures refused; an event of the other mode cannot move a payment; restricted live key with only the permissions the runbook lists (PaymentIntents write, Refunds write, Events read, Disputes read); live keys refused outside production; idempotency on every provider write; no amount from the client.
- **Logs and PII:** §11's allow-list only. `client_secret`, the `Stripe-Signature` header, raw bodies and billing details are never logged; the logger's redaction list gains `client_secret`, `clientSecret` and `stripe-signature`. The client secret never appears in our URLs: the return route strips Stripe's parameters with a 303 and sends `Referrer-Policy: no-referrer`. Browser Sentry returns on step 3 only (decisions-log 2026-09-08), with a `beforeSend` that drops request bodies, query strings and form values.
- **Cookies** (`plan/07` §5): Stripe.js sets `__stripe_mid` and `__stripe_sid`, classified essential for fraud prevention. They are set on step 3 in `test` and `live` only; `src/config/cookies.ts` moves both from "declared, unset" to "set" (010 §8), and the cookies page lists them.
- **Accessibility** (`plan/07` §8): §5.3's rules; axe zero serious or critical on step 3 and the confirmation states in four locales; the Element and 3DS frames are Stripe's, given our locale.
- **Durable medium** (CRD Art. 8(7)): spec 016's confirmation email (010 §5.2 names it "spec 017"), a precondition of `live` in spec 010's `legalReadiness()`.
- **AML:** refunds go only to the original method (`plan/07` §9).
