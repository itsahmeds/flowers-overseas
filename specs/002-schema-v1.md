## 1. Problem

Spec 001 shipped the repository, the gates and a deployable shell with no database: `DATABASE_URL` is a placeholder, `supabase/migrations/` holds a `.gitkeep`, `pnpm db:check` prints `no migrations`, the integration Vitest project contains a single `describe.skip` with a TODO citing this spec, and `fo/no-float-money` exists but is disabled. Everything the roadmap schedules after this week — `003` i18n, `005` catalogue and pricing, `006` seed import, `007`/`008`/`009` corridor, shop and PDP pages, `010` checkout, `011` for-florists, `012` admin — reads or writes rows that do not exist. `plan/09` reserves `002` for 15–21 Sep 2026: "schema v1 (all entities in 01 §4, migrations, RLS, seed scripts)".

ADR-0015 (accepted 2026-09-08) changed what that means. Supabase is not used for anything: the database is plain, portable Postgres on **Neon Free (Frankfurt)** today and self-hosted Hetzner Postgres later by dump-and-restore; every image and private upload lives in **Cloudflare R2**; identity is **Auth.js (or Better Auth)** with accounts and sessions in our own tables. So the schema must use nothing a stock Postgres lacks — no `auth.uid()`, no Supabase RLS helpers, no storage buckets addressed through a vendor SDK — and tenant isolation must be expressed as policies keyed on session variables that our own server sets per request. Neon's free tier also caps monthly compute hours, which makes "the database is never on the critical path of a cached page" a cost constraint as well as an SEO one, and makes a cheap usage probe part of the schema deliverable rather than an afterthought.

This spec is therefore the whole data layer at once: the Neon project and its two connection URLs, Drizzle config and generated types, every entity in `plan/01` §4.1 grouped by the module that owns it, the money rule as a column convention with a check constraint, versioned migrations each with a rollback, an RLS design portable to any Postgres, the Auth.js tables and the partner role model, R2 object keys and variant metadata (no bytes in the database), pg-boss's own schema, the order state machine as reference data plus database-level guards, idempotent seed scripts, the real `db:check`, the integration test suite that replaces `describe.skip`, nightly logical backups to R2, and the RoPA rows that make Neon and Cloudflare recorded processors. It ships no user-facing surface.

## 2. Scope

**Provisioning, connection, configuration**

**RLS and roles (portable; §5.5 has the mechanism)**
- Two database roles created by migration `0001`: `app_owner` (owns every object; used only by migrations and `db:check`, over the direct URL) and `app_web` (the runtime role in `DATABASE_URL`, `NOSUPERUSER`, no `BYPASSRLS`, `GRANT`ed DML only). RLS therefore applies to the application by construction rather than by policy discipline.
- Per-request session variables set by `withDbContext`: `app.role` (`public` | `customer` | `partner` | `admin` | `system`), `app.user_id`, `app.partner_ids` (comma-separated), `app.request_id`. Every policy reads them via `current_setting('app.…', true)`; nothing reads a JWT.
- `ENABLE ROW LEVEL SECURITY` on every table plus an explicit deny-by-default (no permissive policy for `app.role = 'public'` except on the public catalogue/geo reference tables). Partner-scoped tables (`partner_*`, `payout*`, `order_assignment`, `delivery_proof`, and `order`/`order_line` through the assignment) are readable only when the row's `partner_id` is in `app.partner_ids`. Customer-scoped tables key on `app.user_id` via `customer.user_id`.
- `db:check` fails when a table has no RLS enabled or no policy, unless it is on a documented exemption list (pure reference data).

**Order integrity (DB-level, defence in depth)**
- `order_event` is append-only: `BEFORE UPDATE OR DELETE` trigger raises; `seq` is monotonic per order enforced by `UNIQUE (order_id, seq)` and assigned inside the transition transaction.
- `order.status` may change only when the session variable `app.allow_status_write = 'on'` is set — a flag only `orderService.transition` sets (spec 015). A `BEFORE UPDATE OF status ON "order"` trigger raises `ORDER_STATUS_DIRECT_WRITE` otherwise, and additionally rejects any `(from, event, to)` triple absent from `order_transition`. This is the database half of the guarantee whose lint half (`fo/no-direct-order-status-write`) has been active since spec 001 (ADR-0009, `plan/12` §2).
- `order_transition` reference rows are seeded from `plan/11` §2 verbatim so spec 015 reads guards from data instead of hard-coding them.

**Jobs, storage seam, probes**

The S3-API implementation and the variant-generation worker are **spec 006** (§3); 002 ships the interface, the key convention, the bucket/env contract and the `media_variant` table.

## 4. User stories

- As the **founder**, I run `pnpm db:migrate && pnpm db:seed` against a fresh database and get a complete, honest demo dataset — eight countries, 84 products, three demo florists per country, a 2026–27 occasion calendar — so that specs 005–012 build against real rows instead of mocks.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

Conventions applied to every table. Primary keys are `uuid` defaulting to `gen_random_uuid()`, except reference tables keyed by a natural code (`locale.code`, `currency.code`, `order_status.key`). Every table carries `created_at timestamptz NOT NULL DEFAULT now()` and, where it is ever updated, `updated_at timestamptz NOT NULL DEFAULT now()` maintained by one shared `set_updated_at()` trigger — sitemap `<lastmod>` reads these (`plan/02` §10: "the real max `updated_at`", never "now"). Seeded rows carry `source text NOT NULL DEFAULT 'seed' CHECK (source IN ('seed','real'))` on the eight tables `plan/10` §4 lists, which is what makes the seed idempotent and non-destructive. Status columns are `text` with a `CHECK` against an explicit value list rather than a Postgres `enum`, because adding a value to an enum inside a transaction is awkward and `CHECK` constraints dump and restore identically. Money is `*_minor bigint` + currency, per §2. Deletes are `ON DELETE RESTRICT` by default; `CASCADE` only from a parent to its own translation/variant rows.

**`i18n`** — `locale(code PK, bcp47, name, is_launch, rtl, fallback_code)`; `message_catalog(id, locale_code FK, namespace, key, value, source CHECK IN ('human','machine'), reviewed bool, reviewed_by, reviewed_at, source_hash, UNIQUE (locale_code, namespace, key))`. Design note, because `plan/01` §4.1 and `plan/03` §5 could be read as contradicting each other: the **runtime** UI catalogue stays `messages/{locale}.json` in the repo (spec 003, `plan/03` §5), and `message_catalog` is the database side of the same model — admin-editable overrides plus the review metadata (`source`, `reviewed`, `source_hash`) that `plan/03` §6's queue and the `noindex` gate need for DB-authored content. Nothing reads it at runtime until 003/012.

**`geo`** — `currency(code PK, minor_unit_exponent smallint NOT NULL, rounding_style CHECK IN ('x99','x90','x9','none'))` seeded EUR, GBP, PLN, RON, CZK, HUF, SEK, NOK, DKK, CHF. `country(id, iso2 UNIQUE, status CHECK IN ('demo','live','disabled'), currency_code FK, vat_rate_bp integer, iana_zone, same_day_cutoff_local time, delivery_days text[], sunday_delivery CHECK IN ('none','peak','always'), guide_published bool, supply_model CHECK IN ('principal','agent') NULL, source, created_at, updated_at)` — `vat_rate_bp` in basis points keeps VAT an integer (`plan/12` §2); ### 5.3 UI (pages, components, states)

None. This spec adds no rendered surface: the two internal routes above return JSON and are `noindex` + secret-gated, and no component, message key or style is touched. States that would normally be enumerated here (loading / empty / error / demo / disabled) are the concern of the specs that render this data — notably the **demo** and **disabled** states, which this spec makes expressible as `country.status` and `fulfillment_partner.status` values so that 007/008 can render them without a code branch per country (`plan/10` §4).

### 5.4 Rendering & caching (per plan/01 §3)

Nothing is rendered, but two constraints on later rendering are set here and are cost as well as SEO constraints (ADR-0015: Neon Free caps monthly compute hours).

- **The database is never on the critical path of a cached page.** Indexable pages stay ISR per `plan/01` §3 with the tags already named there (`home:{locale}`, `country:{iso}`, `catalog:{country}`, `product:{id}`); a cache hit performs zero queries, so crawl volume does not consume compute hours. `generateStaticParams` prebuilding "live countries + top 50 products" (`plan/01` §3) is unchanged and remains the mechanism that keeps first-hit renders bounded.
- **`/api/health` stays database-free** so uptime monitors and Vercel checks never wake the compute; the database probe is the separate secret-gated route in §5.2, called by cron rather than by monitoring.
- `src/lib/cache.ts` (the noop seam from spec 001) is untouched; the first `invalidate()` caller is the admin status flip in spec 012 and the sitemap job in 007. This spec only records which mutations must eventually invalidate which tag, in `docs/runbooks/database.md`, so 007/012 inherit a list instead of guessing.
- Connection posture: web requests use the pooled URL and one short transaction per request (`withDbContext`); migrations, `db:check`, pg-boss and backups use the direct URL (Q6).

## 6. SEO considerations (mandatory)

This spec renders nothing, so its SEO surface is entirely *the data that later pages need in order to be indexable at all*. Every rule in `plan/02` that a page must obey has a column here, and where the rule cannot be enforced in the database it is at least made queryable so `seo-auditor` can check it.

- **Indexability is derived from data, never from code** (ADR-0007, `plan/10` §4). The inputs are `country.status`, `country.guide_published`, `country_locale_content.state`/`reviewed`, `occasion_country.observed`/`indexable_override`, `city.is_indexable`, `product.status`, `product_translation.reviewed`, and a count of active `fulfillment_partner` rows covering a city. A country going live is one `UPDATE` plus `invalidate(['country:PL'])` — no template edit, per `CLAUDE.md`. The six-product rule for a country category and the "≥6 products tagged for the occasion" rule for a country occasion page (`plan/02` §6) are countable from `product_category`/`product_occasion` joined to `country_price`; spec 008 enforces them in its loader, and the seed provides enough products per (country, category) for at least the PL set to pass so 008 can test both sides of the threshold.
- **URL pattern and localised slugs** (`plan/02` §4): slugs live in `*_translation.slug`, ASCII, lowercase, hyphenated, and are unique per locale — `UNIQUE (locale_code, slug)` on `product_translation`, `category_translation`, `occasion_translation`, `country_translation`, and `UNIQUE (locale_code, country_id, slug)` on `city_translation` (city names repeat across countries). Localised *path segments* (`send-flowers-to` / `blumen-verschicken` / `wyslij-kwiaty`) stay in `config/locales.ts` (spec 003), not in the database, because they are code-level routing. Seed slugs are ASCII-folded at seed time (`Kraków Spring` → `krakow-spring`) and the fixture set includes a Polish-diacritic case so 003's transliteration has something to prove.
- **Canonical**: one canonical URL per (locale, country, entity) is a consequence of the uniqueness constraints above plus the country in the shop path (`plan/02` §4.2). Nothing in the schema permits two active slugs for one entity in one locale, so a duplicate-canonical bug cannot originate in the data.
- **hreflang set** (`plan/02` §8): alternates are exactly the locales for which a translation row exists **and** is `reviewed` **and** whose country is indexable — a single query, which is why `plan/02` §8's "generated from the same data as the sitemap" is achievable. `reviewed = false` therefore removes a locale from the alternate set rather than emitting a link to a noindexed page. Spec 007 builds the generator; this spec guarantees the columns exist and are `NOT NULL`-constrained where the query depends on them.
- **Schema.org data** (`plan/02` §9): `Product` + exactly one `Offer` per country-scoped PDP is a database fact — the partial unique index on `country_price` guarantees exactly one active retail row per (product, country, tier, surcharge), and `country.vat_rate_bp` plus VAT-inclusive `retail_minor` guarantee "schema price equals the visible default price to the cent, VAT included". `priceValidUntil` reads `active_to`; `eligibleRegion` reads `country.iso2`; `deliveryTime`/`cutoffTime` read `country.same_day_cutoff_local` + `iana_zone`; `hasMerchantReturnPolicy` is static. `aggregateRating` is emitted only from `review` rows with `verified_order = true` and `moderation_status = 'published'`, of which the seed contains **zero** (`plan/07` §7, `plan/10` §2.1), so a fabricated-rating manual action is impossible in Phase 0 by absence of data. No `LocalBusiness`/`FloristShop` entity exists in the schema at all, which is the structural reason `plan/02` §9's prohibition cannot be violated later by accident.
- **Sitemap membership and `<lastmod>`** (`plan/02` §10): every entity, translation, price and content row carries `updated_at`, so `<lastmod>` can be the real maximum across the four rather than "now". Sitemap children map one-to-one onto queries over the indexability inputs above. `noindex` rows can never appear in a sitemap because both derive from the same predicate.
- **Retired products** (`plan/02` §7): `product.status = 'retired'` + `retired_at` supports the "200 with alternatives for 90 days, then 410" rule without a separate table or a code branch.
- **Thin-content risk**: the seed is where thin content would enter. Mitigations built into this spec: `de`/`pl` product translations are **absent**, not machine-filled, so no unreviewed page can be indexable; `country_locale_content` rows are seeded only for countries whose guide exists, keeping `guide_published = false` elsewhere (`plan/02` §5.1: no corridor page because a country exists in a list); zero reviews, zero delivery photos, zero partner profiles on indexable surfaces (`plan/10` §5). The 84-product skeleton carries names and slugs but **no descriptions** — a product with a null `description_md` must be non-indexable, and spec 005/008 enforce that; this spec makes the null visible rather than papering over it with generated filler.
- **CWV budget impact**: zero client JavaScript is added and no page changes, so spec 001's baseline stands. The indirect risk is TTFB on ISR misses if a render fans out into many queries or a cold Neon compute; §5.4 pins the mitigations (ISR, prebuilt live corridors, DB-free `/api/health`, one transaction per request) and `docs/runbooks/database.md` records the cold-start expectation so 007's Lighthouse runs are read correctly.
- **Crawl efficiency**: unchanged; nothing new is crawlable. The two internal routes are `noindex` + secret-gated and match spec 001's `robots.txt` disallow of `/api/`.

## 7. i18n considerations (mandatory)

No user-facing string ships, but this spec fixes the shape of every localised entity, so getting it wrong here is expensive later.

- **New message keys / namespaces**: none in `messages/*.json` (spec 003 owns the file). Two key *references* are introduced as data: `product_tier.label_key` and `addon.key`, which 005 resolves through the catalogue — data holds a key, never a translated literal, so a new tier never requires a migration to be renamed in three languages.
- **Locale-aware content tables and the reviewed flag**: every localisable entity has a sibling `*_translation` table keyed `(entity_id, locale_code)` with `slug`, the localised fields, and the review triple `translation_status` / `reviewed` / `reviewed_by` / `reviewed_at` / `source_hash` that `plan/03` §6 defines. `source_hash` is what makes drift detectable: changing the English source bumps the hash and flips dependants to stale. The `reviewed` flag is the `noindex` gate of §6 — this is the one mechanism that lets a solo founder run four locales honestly, and it is a column rather than a convention so `seo-auditor` and `/admin/translations` (012) read the same fact.
- **Locale set**: `locale` seeded with `en`, `en-gb`, `de`, `pl` (ADR-0003, `plan/02` §3, pending A1), each with `bcp47`, `rtl = false`, and a `fallback_code` (`en-gb` → `en`). `rtl` and `locale.fallback_code` exist now so the RTL-readiness promise of `plan/03` §4 costs no migration later.
- **Formatting via `Intl`**: nothing formats here, and the schema deliberately stores only formattable primitives — `*_minor` + `currency.minor_unit_exponent` (so `Intl.NumberFormat` can be correct for zero- and three-decimal currencies), `vat_rate_bp` as an integer, `fx_rate_ppm` as an integer, `date` for calendar dates, `timestamptz` for instants, `time` + `iana_zone` for cutoffs (`plan/03` §10: cutoffs are stored as local time plus zone and evaluated in the destination zone). No pre-formatted, locale-baked string is ever stored.
- **Address and phone formats**: `recipient_address.lines text[]` + `postal_code` + `city` + optional `place_kind` accommodates every country order in `plan/03` §8 without a per-country column set; the field order, labels and postcode regex stay in `config/address-formats.ts` (spec 003). Recipient identity is a single `full_name` per `plan/03` §7. Phones are E.164 (`phone_e164`), validated against the **destination** country by 003/005; the seed fixtures include valid and invalid PL/DE/UK postcodes and phones so that validation has a shared corpus.
- **Collation and diacritics**: text is UTF-8 NFC; no `citext` and no custom collation is created, so the dump restores on any Postgres (ADR-0015). Case-insensitive email uniqueness is a `lower(email)` index. Polish collation for city lists is `Intl.Collator` in the application, and `unaccent`-based search arrives with 005 — recorded here so nobody adds an extension in a hurry.
- **Translation review plan and `noindex` gating**: the seed ships `en` only. `de`/`pl` drafts arrive through spec 003's `i18n:draft` script and spec 012's review queue; until a row is `reviewed`, the page is not indexable and carries no hreflang alternate (§6). Corridor guides and legal text never ship machine-only, even noindexed (`plan/03` §6 gate 4) — enforceable here because `country_locale_content.reviewed` is `NOT NULL DEFAULT false` and the seed sets it `false` for every guide it does not have text for.

## 8. Compliance considerations (mandatory)

This is the spec where personal data becomes *storable*, so the controls have to exist before the first row does. No personal data is processed by this spec itself: it creates tables, seeds non-personal demo data, and — apart from the founder's own admin account, if one is created — stores nobody's information until spec 010/013/019 write to it.

- **Data flows added (→ RoPA)**. Two new processors and the flow rows of `plan/07` §1.2 are recorded in `docs/compliance/ropa.md` by the reviewer at PASS (AC-33):
  1. **Neon Inc. — database hosting (Frankfurt, eu-central-1)**. Subjects: buyers, recipients, florist partners, admin users. Categories: everything in §5.1 once written (contact details, delivery addresses, card messages, order and payment metadata, auth sessions). Purpose: operating the service. Basis: Art. 6(1)(b) for buyers, Art. 6(1)(f) for recipients (`plan/07` §1.2), Art. 6(1)(b) for partners. Retention: per `retention_policy` rows + nightly dumps to R2 kept 30 days. Transfers: data at rest in the EU; Neon is a US company, so onward access is covered by its DPA (SCCs/DPF) — DPA to be accepted and filed in `docs/compliance/` (founder action, §12). Sub-processor: AWS eu-central-1.
  2. **Cloudflare — object storage (R2) for product imagery, delivery photos, payout statements, database dumps**. Subjects: recipients (delivery photos may show doorsteps and people), partners, buyers (statements). Categories: image binaries with EXIF stripped before upload, object keys, and encrypted database dumps. Purpose: media delivery and backup. Basis: Art. 6(1)(b)/(f). Retention: delivery photos 2 years (`plan/07` §1.2), dumps 30 days by bucket lifecycle. Transfers: R2 buckets created with **EU jurisdiction restriction**; Cloudflare DPA accepted at account creation.
  The Supabase row that ADR-0008 would have produced is never written, and `plan/07` §1.4's "Supabase project in EU (Frankfurt)" is read as "Postgres per ADR-0015" without editing the plan.
- **Lawful basis and consent**: `retention_policy` is seeded with the basis and period for each flow of `plan/07` §1.2, which makes the privacy policy's tables (§1.6) generated from data rather than transcribed. `consent_log` records choices plus `policy_version` (Art. 7(1) proof, 5-year retention) and stores a truncated IP at most. Nothing in this spec sets a cookie or loads a script, so no consent is required to run it.
- **Data minimisation (`plan/07` §3, §1.3)**, enforced structurally rather than by review:
  - `recipient` has **no email column**; `db:check` fails if one appears (AC-27). Recipient contact is name, address, phone and the card message — nothing else.
  - Delivery-photo assets must be `visibility = 'private'` and `exif_stripped = true`; a trigger rejects a `delivery_proof` row referencing an asset that is not (AC-19). Public gallery use requires `public_use_consent = true`, default false.
  - `consent_log.source_ip_truncated` and `payment.risk_score` are the only fraud-adjacent fields; no full IP or device fingerprint column exists (12-month fraud retention applies to `webhook_inbox.raw` and is in the sweep).
  - `order.recipient_snapshot` is the deliberate exception to deletion: it is pseudonymised in place by the sweep (name initialised, phone dropped, street dropped, city kept for analytics per `plan/07` §1.2) so the order and its invoice survive the 10-year accounting obligation without the recipient's contact details.
- **Retention (`plan/07` §10)**: implemented, not promised. `retention.sweep` runs daily and applies each `retention_policy` row: recipient contact pseudonymised 90 days after delivery unless a dispute is open or the recipient became a customer; delivery photos deleted at 2 years (R2 object and row); buyer personal fields pseudonymised at 3 years with the invoice archive retained and `customer.redacted = true`; fraud signals at 12 months; consent records 5 years after withdrawal. Integration tests drive the clock (AC-20). Periods need founder confirmation (Q7); the seeded values are the plan's.
- **DSAR (`plan/07` §1.5)**: the schema supports export and erasure without special cases — `customer.redacted` / `recipient.contact_redacted` are the "pseudonymise, keep the invoice, flag it" mechanism §1.5 specifies. The self-service routes are spec 019; the runbook (`docs/runbooks/dsar.md`) gains the SQL-level description of what erasure means, since it can now be stated exactly.
- **RLS as the tenant-isolation control**: the partner-scoped policies of §5.5 are the technical measure behind `plan/07` §1.1's "florist partner is a processor for recipient delivery data acting on our instructions" — a partner can read the recipient data of orders offered to them and nothing else, and the boundary is enforced by Postgres rather than by every future query. `app_web` has no `BYPASSRLS`, so a forgotten `WHERE partner_id =` clause leaks nothing. Both a positive and a negative case per partner-scoped table are required tests (AC-16, AC-17), which is `plan/12` §4's integration expectation ("RLS: vendor cannot read another partner's orders") made concrete.
- **Price display (`plan/07` §4, `CLAUDE.md`)**: `country_price.retail_minor` is VAT-and-delivery inclusive by definition, exactly one row is active per (product, country, tier, surcharge), and surcharges are rows (`surcharge_kind`) rather than runtime arithmetic — so "price shown = price charged = schema price" is a data invariant, and the 30-day-lowest-price history the Omnibus Directive requires is the natural consequence of superseding rather than updating rows. `order.vat_breakdown` stores the computed breakdown per rate for invoicing (`plan/06` §4), and `order.supply_model` lets the principal/agent answer (B1) change invoices without a migration.
- **Geo-blocking (EU 2018/302, `plan/07` §3)**: prices are keyed on **destination** country only. There is no buyer-country dimension on `country_price` and no column that could gate access by buyer nationality or location, so the discriminatory-pricing pattern is not expressible. `customer.country_iso2` exists for invoicing and payment-method availability, never for access control (ADR-0006).
- **Accessibility**: no rendered surface, so WCAG conformance is not assessable here — the one accessibility-relevant obligation this spec carries is alt text, and it is discharged structurally: `product_media_alt.alt` is `NOT NULL` per locale and a primary product image without an alt row in a locale makes that locale non-indexable (`plan/01` §6: never auto-generated at render). That is the substantive justification for not having more to say.
- **Logs and PII (`CLAUDE.md`)**: no query text, parameter, row or object key is logged. `withDbContext` logs `request_id`, `app.role` and duration only. The logger redaction list is widened from `name` to `*name` (so `full_name`, `legal_name`, `recipient_name` are caught) and gains `card_message`, `phone_e164`, `postal_code`, `session_token`, `public_token` and `object_key` — the carry-forward recorded on `/review 5` ("spec 002/005 should widen `name` redaction to `*name`"), now due. `order.public_token` and `session_token` never appear in a log, a URL emitted by this spec, or an error message.
- **Security (`plan/01` §9)**: `app_web` is a least-privilege role (DML only, no DDL, no `BYPASSRLS`, no superuser); `app_owner` credentials exist only in the direct URL used by migrations and CI. `webhook_inbox` implements store-before-process ahead of 013. Backups are uploaded to a private R2 bucket with a lifecycle rule; the dump contains personal data once real orders exist, so the runbook requires the bucket to be non-public and the restore drill to use a scratch database (AC-30).

## 11. Observability

- **Neon compute and storage usage** — `db_usage_sample` (one row/day) + `info` line per run + `warn` and a Sentry message at 70% and 90% of the free-tier cap. This is the ADR-0015 guardrail made operational, and the first metric with a business consequence, so it is also the first alert: at 90% the founder decides between throttling preview databases, an earlier Hetzner move, or paying (ADR-0015's recorded alternative).
- **Migration audit** — the applied-migration list (name, hash, applied-at) is printed in the `db-check` CI step summary and exposed as `latest_migration` on `/api/internal/db-health`, so a deployment can be checked against the database it is talking to without opening a console. Every migration run in CI logs its version range; `audit_log` records admin-initiated data changes (country/partner status flips) with `request_id`, actor and before/after.
- **Query-level logging** — `withDbContext` emits one `debug` line per transaction (`request_id`, `app.role`, statement count, duration) and one `warn` above a 200 ms threshold. Never the SQL text, parameters or rows (§8).
- **Job observability** — pg-boss's own tables are the job log; each handler logs start/finish with `request_id` propagated from the enqueuing request (`plan/12` §6) and `actor = system:{job}`. `pending_jobs` on the health route is the cheap signal that the minute tick has stopped.
- **Backups** — the workflow writes the object key and byte size to its step summary; `db.backup_verify` failure is a `warn` + Sentry message, because a silent backup that cannot be restored is the failure mode that matters.
- **What is deliberately not instrumented yet**: order-lifecycle alerts (`paid` without `routed` > 5 min, SLA cascade exhaustion, photo missing > 2 h) belong to spec 025 with the flows that produce them; no dashboard exists in Phase 0 (`plan/08` §7).

## 12. Rollout

- **Feature flags**: none gate this spec (it is schema). It *delivers* the `feature_flag` mechanism every later rollout uses, seeded with the keys Phase 0/1 will flip: `checkout.demo_guard`, `payments.stripe`, `payments.mollie`, `corridor.{iso}`, `locale.{code}`. All default off except `checkout.demo_guard` (on).
- **Environments and data**: local (own Neon branch or a local `postgres:16` container) → PR preview (Q5: per-PR Neon branch, or the shared preview database of `plan/08` §10) → production (the same Neon database in Phase 0; there are no real orders until Phase 1). Previews never point at production data (`plan/01` §10).
