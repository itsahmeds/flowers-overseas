## 1. Problem

The founder cannot see which corridors, locales and pages produce orders. The GA4 tag is wired and dark (spec 004 AC-21, `docs/runbooks/analytics-consent.md`): `NEXT_PUBLIC_GA4_MEASUREMENT_ID` is unset everywhere, no event is defined, and nothing reports a sale. Three things block simply switching it on:

1. **The script budget.** Spec 004 A15 measured 1.8 to 4.5 KB of headroom against 131 072 B Brotli first-load script; `gtag.js` is far larger, and A-founder-2026-10-23 has already raised the budget by 1 KiB, temporarily, for a framework bump. A15 hands the budget question to this spec.
2. **The law.** The current design (spec 004 §2 L94, plan/04 §11) loads the tag before any decision and sends "cookieless pings" under Consent Mode v2 advanced. EDPB Guidelines 2/2023 (final, October 2024) put that kind of device access inside ePrivacy Art. 5(3), and spec 004 A-founder-2026-10-19d clause 3(e) already made a ruling on advanced versus basic mode a step before the id is set. CLAUDE.md says no third-party script loads before consent.
3. **Conversion truth.** plan/01 §2 says conversion truth comes from the payment, not the browser. Spec 002 A6.3 note F3 says `order.captured` fires twice per order and revenue must be read from `payment` rows. Spec 013 §3 leaves the server-side `purchase` to this spec.

This spec defines the event plan, loads the tag only after an analytics grant and off the first-load budget, sends `purchase` and `refund` from the server exactly once per money fact, and writes down the founder's setup steps so that switching on is a set of env values and admin clicks, never a code change.

## 2. Scope

**A. Consent and loading (Consent Mode basic, §5.0)**
- No request to any Google origin and no Google `<script>` element before the visitor grants analytics, on every build. The Consent Mode v2 default-denied bootstrap stays inline (spec 004 AC-18) but no longer queues `js` or `config`.
- After a grant (in the same page view, or on a later page with a valid `fo_consent`), a deferred loader injects `gtag.js` after the window `load` event and when the main thread is idle, configures it (manual page views, sanitised location, signals off, 12-month non-renewing cookie), and starts our event listeners and `web-vitals`.
- Withdrawal stops all sending in the page at once and deletes `_ga` and `_ga_*`.
- First-load cost at most 256 B Brotli; the deferred analytics chunk at most 4 096 B Brotli; `gtag.js` never counts against first load and never loads in a Lighthouse run.

**B. Client event plan (§5.2)**
- `page_view` (manual), `view_item_list`, `select_item`, `view_item`, `select_item_variant`, `select_delivery_date`, `add_to_cart`, `begin_checkout`, `add_shipping_info` (the recipient and delivery-date step saved), `add_payment_info` (Pay pressed), `web_vital`.
- Event dimensions on every event: `locale`, `page_type`; on every page with a destination: `destination_country`, `country_status`, `display_currency`.
- Payloads are built on the server from the same view model the page renders, so the value in an event is the price on the screen (the price-shown rule, applied to analytics).

**C. Server-side events (§5.2)**
- `purchase` through the GA4 Measurement Protocol (EU endpoint), sent once per order from the outbox, triggered by `order.captured` row 2, valued from the `payment` row.
- `refund` through the same path for each succeeded refund of an order whose purchase was sent.
- Only for buyers who had granted analytics when they placed the order.

**D. Data, configuration, operations**
- One migration (`order_analytics`, `analytics_dispatch`, a `retention_policy` row) with its rollback.
- `GA4_API_SECRET` (server only, set by the founder); a separate staging property; `debug_mode` outside production; an optional validation call on staging; a kill switch flag `analytics.mp_send`.
- CSP origins per Google's GA4 guidance in the consent-active build only.
- RoPA row 4, the runbook, the cookie register lifetimes, and the privacy and cookie notice texts handed to the founder.

## 3. Non-goals

- **Google Ads, conversion import, remarketing, enhanced conversions and `gclid` handling** → a later Ads spec. This spec only prepares for it: `purchase` is a key event, and the Measurement Protocol `consent` object carries the marketing answer. Enhanced conversions send hashed email, which the no-PII rule forbids without an ADR.
- **A first-party funnel table or consentless aggregate counts** (plan/04 §11's fallback, plan/11's `analytics_events`) → spec 039 (reporting layer). Order truth already lives in `order` and `payment` (mode, destination, locale, amounts), so the founder's order numbers never depend on the banner.
- **Sending `purchase` for buyers who did not grant analytics**, with random ids or otherwise → not built (§13 Q2).
- **The other plan/04 §14 events**: `select_destination`, `add_addon`, `checkout_progress` (replaced by GA4's `add_shipping_info` and `add_payment_info`), `select_payment_method`, `payment_attempt`, `payment_3ds`, `view_tracking` (spec 018 §8 declares it), `recipient_landing`, `locale_suggestion`, `consent_update`, `florist_lead_start`, `florist_lead_submit` → a later amendment of this spec when a report needs one. `consent_update` and the `consent_state` dimension are dropped outright: under basic mode every event that reaches Google is a consented one, so the value would be a constant.
- **`buyer_country`** (plan/04 §14) → not sent. It is buyer data and the brief rules it out.
- **Chargebacks as refunds in GA4** → spec 039; GA4 revenue is a trend, the `payment` and `payment_dispute` rows are the books.
- **A/B testing** (plan/04 §14, first tests) → its own spec; it needs no third-party script (server-side assignment) and reads GA4 only for reporting.
- **Admin, florist portal, `/dev`, `/demo/vendor-inbox` and the chooser `/`** carry no analytics (spec 012 §8 "No analytics on admin").
- **BigQuery export, Looker Studio** → spec 039.

## 4. User stories

- As a **visitor in the EEA or the UK**, nothing is sent to Google until I say yes to analytics, and when I take it back the site stops at once and removes the cookies.
- As a **buyer**, my name, email, address, the recipient's details and my card message never reach an analytics tool, whatever I chose.
- As the **founder**, I see in GA4 which destination, locale and page lead to orders, and the revenue figure for consenting buyers equals what they were charged, minus refunds.
- As the **founder**, I switch analytics on by creating a property, pasting two values into Railway and flipping one flag; I verify it in DebugView on staging first.
- As **Googlebot**, I get the same HTML as before, with no extra script, and Core Web Vitals are not touched.
- As the **implementer of a later Ads spec**, `purchase` is already a key event with a consent signal, and I add Ads without touching the outbox handler's contract.

## 5. Design

### 5.0 Research basis and the decisions it drives

| Question | What the sources say | Decision |
|---|---|---|
| Basic or advanced Consent Mode | Basic: tags are blocked until the visitor interacts with the banner and "transmits no data to Google prior to user interaction"; Ads uses a general conversion model. Advanced: tags load with denied defaults and send cookieless pings, which give an advertiser-specific model and GA4 behavioural modelling [G1][G2]. Pings carry timestamp, user agent, referrer, a random number and consent state; IP and screen resolution travel as part of the request [G2] | **Basic.** |
| Are cookieless pings outside ePrivacy consent | EDPB Guidelines 2/2023 v2.0 (adopted 7 October 2024) read Art. 5(3) as covering URL and pixel tracking and local processing whose result is sent from the device, not only cookies [E1][E2]. Spec 004 A-founder-2026-10-19d already records that the pings fall inside Art. 5(3). No primary CNIL text on advanced mode was found; a French commentary reports the CNIL sees no particular difficulty with basic mode [C2], and the CNIL says most large audience-measurement offerings do not qualify for its consent exemption "regardless of their configuration" [C1] | Treat any Google request as needing consent in every market. |
| UK | The Data (Use and Access) Act 2025 adds a PECR exception for analytics used solely for aggregate statistics to improve a service; the ICO's final storage and access technologies guidance (April 2026) excludes user-level tracking, advertising measurement and attribution, and sharing beyond helping improve the service [U1][U2] | GA4 with ecommerce attribution is not a clean fit, and one rule for every market is simpler: consent everywhere. |
| Google's own policy | The EU user consent policy covers end users in the EEA, the UK and Switzerland: consent for cookies or local storage where legally required, for personal data used for ads personalisation, disclosure of each party, consent records, revocation [G3] | Our banner, `consent_log` and the cookie notice meet it; ads personalisation stays off. |
| Measurement Protocol | Web streams post to `/mp/collect` with `measurement_id` and `api_secret`; **EU collection uses host `region1.google-analytics.com`**; body needs `client_id` matching the tag's; `session_id` and `engagement_time_msec` make events appear in session reports; events can be backdated up to 72 hours (older ones are clamped to 72 hours under the default `RELAXED`); events meant to join tag events should arrive within 48 hours; at most 25 events and 130 kB [M1]. Optional `consent` (`ad_user_data`, `ad_personalization`), `user_location`, `ip_override`, `device`, `user_data`; 2xx whenever received, no error for malformed data, and on a non-2xx "don't resend the same one"; Google now recommends the Data Manager API for new server-to-server work but keeps MP supported [M2]. Validation at `/debug/mp/collect` returns `validationMessages` and records nothing [M3]. `debug_mode` plus a positive `engagement_time_msec` surfaces events in DebugView [M4] | MP on `region1`, with `client_id`, `session_id`, `timestamp_micros`, `consent`; never `user_location`, `ip_override`, `device`, `user_id` or `user_data`. |
| Exactly once | "Google Analytics deduplicates purchase events with the same transaction ID"; the id must be unique per order, never empty, never reused across users [G5] | Our outbox gives once on our side; GA's deduplication covers the one crash window (§5.2). |
| Ecommerce parameters | `purchase` and `refund` take `transaction_id` (required for both), `value`, `currency`, `tax`, `shipping`, `items`; `value` is the sum of price times quantity; items need `item_id` or `item_name`; `shipping_tier` on `add_shipping_info`, `payment_type` on `add_payment_info`; item-level refund metrics need items [G4] | Items carry VAT-inclusive prices, so `value` is the gross amount charged; `tax` and `shipping` are not sent (§13 Q3). Refunds are value-only. |
| IP | GA4 "does not log or store individual IP addresses from EU, Switzerland, or UK users"; IP is used only for coarse geography, then discarded, before logging on EU, Swiss or UK servers; granular location and device collection can be switched off per region [G6] | We use no IP for anything (ADR-0006). We never send `ip_override`. Granular collection off for all regions. |
| Retention | Standard properties keep user-level and event-level data 2 or 14 months; it affects explorations and funnel reports only; "reset on new activity" can be off [G7]. CNIL caps tracker lifetime at 13 months [C1] | 14 months, reset off (§13 Q4); `_ga` lives 12 months and is not renewed on each visit (§13 Q7). |
| CSP | Google's GA4 guidance: `script-src` `*.googletagmanager.com`; `img-src` `*.google-analytics.com`, `*.googletagmanager.com`; `connect-src` `*.google-analytics.com`, `*.analytics.google.com`, `*.googletagmanager.com` [G8] | Exactly these, only in a build with the id set. |

**What this changes in the plan.** plan/04 §11 (advanced mode, cookieless pings, `client_id` only when granted, aggregate counts otherwise), plan/07 §5 (unchanged in substance: default denied stays), plan/09 Phase 0 AC 7 ("GA4 receives cookieless pings") and spec 004 §2 L94 and AC-21 (tag loads before a decision). The ADR this spec proposes records the reversal; §12 lists the amendment text spec 004 needs.

### 5.1 Data model changes (tables, columns, migrations + rollback)

One migration, `NNNN_analytics_ga4.sql` (next free number when it merges) with `NNNN_analytics_ga4.down.sql`. Both tables belong to the `analytics` module, RLS on, policies for `system` only (no partner, no buyer, no admin read in this spec).

1. **`order_analytics`**, one row per `test` or `live` order, written at placement (§5.2 "Context capture"):
   - `order_id uuid PRIMARY KEY REFERENCES "order"(id) ON DELETE CASCADE`
   - `analytics_consent boolean NOT NULL`, `marketing_consent boolean NOT NULL`, `consent_policy_version text NOT NULL`
   - `ga_client_id text NULL`, `ga_session_id text NULL`, with `CHECK (analytics_consent OR (ga_client_id IS NULL AND ga_session_id IS NULL))` and `CHECK (ga_session_id IS NULL OR ga_client_id IS NOT NULL)`
   - `ga_transaction_id uuid NOT NULL UNIQUE` (random v4 set by the application; **not** the order reference and not `order.id`, so nothing in GA4 is a key a person or a support thread could quote)
   - `created_at timestamptz NOT NULL DEFAULT now()`, `ids_cleared_at timestamptz NULL`
2. **`analytics_dispatch`**, one row per outbox delivery the analytics handler finished:
   - `id uuid PRIMARY KEY`, `order_id uuid NOT NULL REFERENCES "order"(id) ON DELETE CASCADE`, `event_id uuid NOT NULL UNIQUE REFERENCES order_event(id)`
   - `kind text NOT NULL CHECK (kind IN ('purchase','refund'))`, `refund_id uuid NULL UNIQUE REFERENCES refund(id)`, `CHECK ((kind = 'refund') = (refund_id IS NOT NULL))`
   - `outcome text NOT NULL CHECK (outcome IN ('sent','skipped'))`, `skip_reason text NULL CHECK (skip_reason IN ('no_context','no_consent','no_client_id','not_configured','disabled','mode_not_live','too_old','value_mismatch','rejected','no_purchase_sent','ids_cleared'))`, `CHECK ((outcome = 'skipped') = (skip_reason IS NOT NULL))`
   - `http_status integer NULL`, `finished_at timestamptz NOT NULL DEFAULT now()`
   - **`CREATE UNIQUE INDEX analytics_one_purchase_sent ON analytics_dispatch (order_id) WHERE kind = 'purchase' AND outcome = 'sent'`**: the database refuses a second sent purchase for one order.
3. **`retention_policy`** (spec 002): one row, `order_analytics.ga_ids`, 60 days from `created_at` (§13 Q5), executed by spec 002's `retention.sweep`: sets `ga_client_id` and `ga_session_id` to null and `ids_cleared_at` to now.

No column is added to `order`, `payment`, `refund` or `order_event`; no state, transition or event name is added (spec 002 A6 untouched).

**Rollback** (`.down.sql`, reverse order): delete the `retention_policy` row; drop `analytics_dispatch` (index with it); drop `order_analytics`. No guard is needed: these rows are measurement records, not accounting records, and losing them loses only the ability to send a later refund to GA4. The migrate, rollback, migrate round trip of spec 002 runs over it.

**Money.** `toGa4Value(money)` turns integer minor units into a JSON number in major units through the currency's exponent in `src/config/currencies.ts` (all launch currencies have exponent 2), by building the decimal from integer division and remainder, never by multiplying a float. It is the only place in the module that touches an amount; every builder calls it; the client chunk receives finished numbers and does no money arithmetic. `fo/no-float-money` covers `modules/analytics`. Schema price = visible price becomes, here, **event price = visible price**: `pageAnalytics` and `ga4ItemFromProjection` read the same `priceProjection()` the price component renders (spec 005), never a second computation.

**Items.** One builder for client and server, so the same product looks the same in both:

| Item param | Product line | Add-on line | Date surcharge line |
|---|---|---|---|
| `item_id` | `product.sku` (e.g. `FO-BQ-023`) | `addon.key` | `surcharge` |
| `item_name` | the product's `en` catalogue name | the add-on's `en` name | `delivery surcharge` (a constant, not copy) |
| `item_category` | the product's primary `category.key` | `addon` | `delivery` |
| `item_variant` | the tier key (stem count) | none | the surcharge kind key |
| `price`, `quantity` | line unit gross price (VAT and delivery included), quantity | same | same |
| `item_destination_country` | ISO 3166-1 alpha-2, upper case | same | same |
| `index`, `item_list_id`, `item_list_name` | list events only | | |

No item carries a florist, a partner, a city, a postcode, a date or a message.

**Common event parameters.** `locale` (the URL's locale code, e.g. `en-gb`), `page_type` (closed list in `src/config/analytics.ts`, including spec 008's `shop_root`, `country_category`, `country_occasion`, `category_hub`, `occasion_hub`, `occasions_index`, spec 009's `product`, spec 041's page ids, and `home`, `corridor`, `checkout`, `checkout_done`, `tracking`, `blog`), and on any page with a destination: `destination_country`, `country_status` (`live` or `demo`), `display_currency` (ISO 4217). A localised route without a `page_type` fails a type test.

**Client events.**

| Event | When | Parameters beyond the common set |
|---|---|---|
| `page_view` | each route render: first load and each client-side navigation; not on a same-route re-render | `page_location`, `page_referrer`, `page_title` (sanitised, below) |
| `view_item_list` | shop root, category and occasion pages, on load | `item_list_id` (`{country}:{kind}:{key}`), `item_list_name` (the same key, English), `items` in rendered order with `index` from 0, at most 48 |
| `select_item` | a product card activated (click or Enter), before navigation | `item_list_id`, `item_list_name`, `items` (that one card) |
| `view_item` | product page load | `currency`, `value` (default tier's shown price), `items` (one) |
| `select_item_variant` | a tier chosen on the product page (spec 009 declares it) | `currency`, `value`, `items` (one, new variant) |
| `select_delivery_date` | a date chip chosen (spec 009 declares it) | `days_ahead` (integer, destination-local today = 0), `is_same_day`, `has_surcharge` (boolean). Never the date |
| `add_to_cart` | the product page's primary form submitted | `currency`, `value`, `items` (product at the chosen tier) |
| `begin_checkout` | checkout step 1 rendered, `live` or `test` mode | `currency`, `value` (quote total), `items` (quote lines) |
| `add_shipping_info` | checkout step 2 rendered after a successful step 1 save (recipient and delivery date chosen) | as `begin_checkout`, plus `shipping_tier` (`standard` or the surcharge kind key) and `days_ahead` |
| `add_payment_info` | Pay pressed on step 3, before `stripe.confirmPayment` | as `begin_checkout`, plus `payment_type` (`card`, `apple_pay` or `google_pay`, from the Payment Element's selected type) |
| `web_vital` | LCP, CLS and INP, each at most once per page view, final value when the page is hidden | `metric_name`, `metric_value` (ms for LCP and INP; CLS times 1000, rounded), `metric_rating` |

Checkout events never fire in `demo` mode (spec 010 §3). They fire in `test` mode, which exists only outside production (spec 010 AC-2), so test orders reach only the staging property (§13 Q6). A refresh re-fires a step event; GA4 funnels count users reaching a step, so this does not distort them, and no event is deduplicated on the client.

**How payloads reach the browser with no first-load cost.** The server renders the page payload as a `data-fo-analytics` JSON attribute on one hidden element per document, and each product card's item as a `data-fo-item` attribute, from `pageAnalytics(viewModel)`. On cached pages these bytes are identical for every visitor (no cookie read, no `Vary`). The deferred chunk reads them; delegated, passive, capture-phase listeners on `document` handle `select_item`, `select_item_variant`, `select_delivery_date` and `add_to_cart`, and defer their work to idle time so INP is not touched. Spec 013's Payment Element island calls `window.__foAnalytics?.track('add_payment_info', { payment_type })` (optional chaining: a no-op when analytics is not running). An event triggered before the chunk has loaded is not sent, by design.

**Location sanitising.** `sanitisePageLocation(url, routeClass)` returns origin plus path, with every segment of a private route class replaced by its parameter name (`/{locale}/track/:token`, `/r/:code`, any route `src/config/analytics.ts` lists as private), and drops the query string except `step` and the five `utm_*` keys (`ALLOWED_QUERY_KEYS`). The same function sanitises a same-origin `page_referrer`; a cross-origin referrer is kept as the browser sends it (our `Referrer-Policy` already trims ours). On private routes `page_title` is replaced by the `page_type` value. This absorbs spec 018 §8's rewrite rule.

**gtag configuration** (in the deferred chunk, after the grant): `send_page_view: false`, `page_location` and `page_referrer` sanitised, `allow_google_signals: false`, `allow_ad_personalization_signals: false`, `cookie_expires: 31536000`, `cookie_update: false`, `cookie_flags: 'SameSite=Lax;Secure'`, `debug_mode: true` only when `NEXT_PUBLIC_APP_ENV` is not `production`. No `user_id` is ever set. The bootstrap's `url_passthrough: false` and `ads_data_redaction: true` stay.

**Loading and withdrawal.** `startAnalyticsIfGranted()` runs from spec 004's first-load consent loader: it reads `data-fo-ga4` from the bootstrap element and `fo_consent` (parsed as spec 004 parses it; wrong version, forged or unparsable means no consent), and only with an id and `a: true` waits for `load` plus idle (fallback timeout) and imports the deferred chunk. The consent island calls it right after a Save that grants analytics, so no reload is needed. On a Save that withdraws analytics, the chunk sets `window['ga-disable-' + id] = true`, issues the denied `consent update`, removes its listeners and deletes `_ga` and `_ga_*` for the site's domain.

**Client event schemas** (zod, `.strict()`, used in unit tests and in the chunk's dev assertion; the production chunk ships no zod): `PageAnalyticsSchema`, `Ga4ItemSchema`, `ClientEventSchema` (discriminated union on `name`, one member per row above).

**Context capture at placement.** Spec 010's `placeOrderAction`, after `orderService.place` commits for a `test` or `live` order, calls `recordOrderContext(orderId, readAnalyticsContext(cookies(), env))`. `readAnalyticsContext` parses (zod: `AnalyticsContextSchema`, `GaClientCookieSchema`, `GaSessionCookieSchema`):
- `fo_consent`: `analytics_consent`, `marketing_consent`, `consent_policy_version`; missing or invalid means both false.
- `_ga` (`GA1.<n>.<random>.<timestamp>`) to the client id `<random>.<timestamp>`, and `_ga_<id without G->` in either the `GS1.<n>.<session_id>.…` or the `GS2.<n>.s<session_id>$…` form to the session id; any other shape gives null. Both are read **only** when `analytics_consent` is true; a `_ga` left over from before a withdrawal is ignored.
A failure to write the row is logged (`analytics.context_failed`, warning) and never fails or delays the order; the handler then skips with `no_context`. Checkout routes are already `no-store`, so reading cookies there changes no cache rule.

**The outbox target.** Target `{ name: 'analytics.ga4', audience: 'system' }`, added to `src/modules/orders/outbox/routes.ts`:

| Event | `demo` | `test` | `live` |
|---|---|---|---|
| `order.captured` | none | `analytics.ga4` (acts on row 2 only) | `analytics.ga4` (acts on row 2 only) |
| `order.refunded_partial`, `order.refunded_full` | none | `analytics.ga4` | `analytics.ga4` |

`ga4OutboxHandler({ eventId, orderId, type, fromStatus, toStatus, mode })` is registered in spec 013's `HandlerRegistry`. It never throws for a business reason; it throws only for a retryable transport failure. In order:

1. **Purchase** (`order.captured` with `toStatus = 'paid_unrouted'`; any other `order.captured`, such as row 14, returns at once and writes nothing):
   - Skip, recording the reason, when: the id or secret is unset (`not_configured`); flag `analytics.mp_send` is off for the environment (`disabled`); `APP_ENV = production` and `mode` is not `live` (`mode_not_live`); no `order_analytics` row (`no_context`); `analytics_consent` false (`no_consent`); no client id (`no_client_id`); more than 71 hours since `payment.captured_at` (`too_old`); a sent purchase already exists for the order (no row is written: the delivery is already done).
   - Build items from the order lines; if their sum in minor units differs from `payment.amount_captured_minor`, skip `value_mismatch` and raise the alert.
   - `POST https://region1.google-analytics.com/mp/collect?measurement_id={id}&api_secret={secret}` with exactly: `client_id`, `timestamp_micros` (`payment.captured_at`), `consent: { ad_user_data, ad_personalization }` (both `GRANTED` only when `marketing_consent`, else `DENIED`), and one event `purchase` with params `transaction_id` (`ga_transaction_id`), `value` (`toGa4Value` of `payment.amount_captured_minor`), `currency` (`payment.currency_code`), `items`, `session_id` (when held), `engagement_time_msec: 1`, `locale`, `destination_country`, `country_status: 'live'` (or the country's status for `test`), `payment_type`, and `debug_mode: 1` only outside production. Schema: `MpPurchaseBodySchema`.
   - 2xx: insert `analytics_dispatch` `sent`. Any 4xx: insert `skipped` `rejected` with `http_status`, raise `analytics.rejected`, do not retry (Google: do not resend [M2]). Network error, timeout (5 s) or 5xx: throw, so the dispatcher retries with its backoff; its 8th failure makes the delivery `dead` with spec 013's `outbox.dead`.
2. **Refund** (`order.refunded_partial` or `order.refunded_full`): skip `not_configured`, `disabled`, `mode_not_live` as above; `no_purchase_sent` when no `sent` purchase exists for the order; `ids_cleared` when the client id is null; `too_old` past 71 hours from `refund.succeeded_at`. Otherwise one `POST` with event `refund`, params `transaction_id` (same as the purchase), `value` (`toGa4Value` of the event's `amount_minor`), `currency`, `engagement_time_msec: 1`, `debug_mode` as above, the same `client_id` and `consent`, `timestamp_micros` = `refund.succeeded_at`. No items (§5.0). Schema: `MpRefundBodySchema`. One per `refund_id` (unique).

**Exactly once.** The dispatcher delivers each `(outbox row, target)` once (spec 013 AC-20); the handler checks for an existing `sent` row first; the partial unique index refuses a second sent purchase. The one window left (Google answered 2xx, the process died before the insert) leads to a resend with the same `transaction_id`, which GA4 deduplicates for web streams [G5].

**Validation on staging.** With `GA4_MP_VALIDATE=true` (the env schema refuses it when `APP_ENV = production`), `postMp` first posts the same body to `https://region1.google-analytics.com/debug/mp/collect`, parses the answer with `MpValidationResponseSchema`, and logs the number of `validationMessages` and their `validationCode` values (never `fieldPath` values or the body), then sends for real.

**Environment** (`src/lib/env.schema.ts`, `.env.example`):
- `NEXT_PUBLIC_GA4_MEASUREMENT_ID` (exists): the staging property's id on staging, production's on production, unset on PR environments, locally and in CI (CI's consent-active build uses `G-FIXTURE00`, spec 004 clause 8).
- `GA4_API_SECRET` (new, server only, optional): accepted only when the measurement id is set; a variable named `NEXT_PUBLIC_GA4_API_SECRET` fails validation; the error message never prints a value. It is created and pasted into Railway by the founder (§12); no agent reads, writes, echoes or handles it.
- `GA4_MP_VALIDATE` (new, optional boolean): refused in production.

**Jobs.** No new job: the handler runs inside spec 013's `outbox.dispatch`; retention runs inside spec 002's `retention.sweep`.

## 11. Observability

- **Logs** (spec 001 logger, fields of §8 only): `analytics.dispatch` (one line per handler run: `order_id`, `event_id`, `kind`, `outcome`, `skip_reason`, `http_status`, `duration_ms`), `analytics.context_failed` (warning), `analytics.validation` (staging only: `validation_count`, `validation_codes`).
- **Alerts** (Sentry, routed as spec 013's): `analytics.value_mismatch` (items do not sum to the captured amount: a money defect somewhere upstream), `analytics.rejected` (Google refused a body: a schema defect). A dead delivery raises spec 013's `outbox.dead` with `target = analytics.ga4`.
- **Reconciliation, by hand:** the runbook gives one SQL query comparing `live` orders paid in a day with `analytics_dispatch` outcomes by reason, so a drop in "sent" can be told apart from a drop in consent.

## 13. Open questions

Each has a recommended default; the founder can answer in one word.

- **Q1. Consent Mode basic instead of advanced?** Nothing reaches Google before a yes; GA4 loses behavioural modelling of refusing visitors. This reverses plan/04 §11 and plan/09 Phase 0 AC 7 and needs the proposed ADR. **Recommended: yes, basic.**
- **Q2. Send server-side `purchase` for buyers who refused analytics, with random ids?** No device access happens, but the buyer said no, and the data still goes to Google. **Recommended: no.** Order truth stays in our database (spec 039 reports it).
- **Q3. GA4 `value` as the gross amount charged (VAT included), surcharge as an item, no `tax` or `shipping`?** Google's examples keep tax and shipping outside `value`, but our prices are VAT-inclusive by law and the founder reads revenue as what buyers paid. **Recommended: yes, gross.**
- **Q4. GA4 data retention 14 months (not 2), reset on new activity off?** Needed for year-on-year peaks (Mothering Sunday, Dzień Matki); standard reports are unaffected either way. **Recommended: 14 months.**
- **Q5. Keep the GA client and session id on the order for 60 days?** Refunds after that are not sent to GA4. **Recommended: 60 days.**
- **Q6. Measure test orders in the staging property (refining spec 010 §3)?** It is the only way to verify the server path in DebugView before real money. **Recommended: yes.**
- **Q7. `_ga` lifetime 12 months, not renewed on each visit?** Matches plan/07 §1.2 (6 to 12 months) and stays under CNIL's 13-month cap; costs some returning-user continuity. **Recommended: yes.**
- **Q8. Property currency GBP and time zone Europe/London?** GA4 converts other currencies to the property currency in reports; the first corridor is UK buyers. **Recommended: GBP, Europe/London.**
- **Q9. Include `web-vitals` RUM now (in the deferred chunk)?** About 2 KB of the chunk's 4 KB, consenting visitors only. **Recommended: yes.**
- **Q10. Which entity accepts Google's data processing terms and is named as controller?** The privacy notice and RoPA must name the registered company that `src/config/company.ts` will carry. **Recommended: activation waits for the founder's company decision; the code merges dark before it.**
- **Q11. Lawyer check before the production id is set?** With basic mode the advanced-mode question of spec 004 clause 3(e) falls away; the privacy and cookie notice wording still needs the lawyer. **Recommended: lawyer reviews the notice texts; it is a runbook step, not a code gate.**
