## 1. Problem

Spec 012 v0 gave admin a sign-in, an audit trail, florists, applications, a read-only order queue and two checkout flags. Everything a buyer actually sees is still authored in the repository: the 84 bouquets and their prices in `src/config/catalogue/*.data.ts` (ADR-0017), the product copy in `seed/data/copy/**`, the photos in `seed/data/media.json` and `public/media/`, and each country's status and operations in `src/config/countries.ts`. Changing any of them is a pull request. Specs 003, 004, 007, 008 and 041 each record a bounded deviation from `CLAUDE.md`'s "Country/partner go-live is a data flip in admin, never a code change" and say it is retired by spec 012; v0 deferred that to this spec.

Three things make it urgent now. On 2026-10-19 the founder set the florist model: "florists set their own bouquets and prices; the site catalogue is placeholder, it is to be replaced by florists", and "ordering will open as soon as the florist signs up". On 2026-10-20: "start working on the CMS as well". And the site is live on Railway behind Cloudflare (single replica, Amsterdam), hidden from search engines ("keep hidden for now", 2026-10-19). Poland was set `live` in `countries.ts` for the launch and TASK-239 (in build) sets it back to `demo` until ordering opens. So the first florist's bouquets, photos and prices must go on sale without a code change, before the site is opened to search engines, and every price shown must still equal the price charged.

The advisor's review of 2026-10-04 (H1, H2, §4) set five things this spec must settle before anything else (spec 012 §15.0). §2.0 settles them.

## 2. Scope

### 2.0 Settled first (spec 012 §15.0)

1. **How a page that a change creates comes to exist (advisor H2).** The `[locale]` layout exports `dynamicParams = false`, which binds every depth, so a URL the build did not emit is a 404 (`src/app/[locale]/layout.tsx` L65; the depth-4 file's own `true` is inert, L84–86). **Chosen: option (a), refined.** Changes split in two:
   - *Content changes* (a price, a name, a description, a photo, a country's robots state) change pages that already exist. They show at the edge within 60 s through `invalidate()`, with no rebuild.
   - *Structural changes* (a URL that must start or stop existing: a new bouquet, a bouquet removed from a country, a category crossing the six-product floor, a country occasion or city page that a go-live creates) appear at the next **publish**: one rebuild of the commit already live, triggered from admin (§2.3). A go-live flip requests a publish by itself. Nothing in the repository changes, so it stays a data flip.
   Option (b), turning `dynamicParams` on, is **rejected**: it reopens spec 003's locale gate and spec 008's 404 rule at every depth, and every probe of a random slug would cost a database query on a cold Neon compute. It is revisited only if a publish build passes 10 minutes (§12 exit signal).
2. **The build reads the database.** `next build` reads through a read-only login (`app_build`, §5.1). If the database is unreachable the build fails. Railway keeps serving the previous deployment when a build fails (spec 040), so an outage delays a publish or a release and never takes the site down. There is **no fallback to the repository files**, because a build from files while checkout charges from the database is the "shown ≠ charged" failure `CLAUDE.md` forbids.
3. **The review cutover must not quietly un-index (advisor §4).** Slice A moves review authority only for catalogue text and photos. Today no product copy row in any locale is reviewed (`seed/data/copy/*/products.json`: zero `"reviewed": true`), and 171 photo approvals are recorded in `seed/data/media.json`. So the import cannot un-index a product page that is indexable now, and AC-2 proves the public surface is identical before and after. The risky part, UI strings, guides and legal pages (526 English approvals), moves in slice B under its own parity criterion (AC-30).
4. **Imported approvals show their true history.** They are imported with `channel = 'import'` and their recorded name and date verbatim. Admin shows them as "imported, not re-read" until a signed-in reviewer approves them again. They keep counting for indexability (otherwise AC-2 and AC-30 would fail and pages would drop out); re-reading them is the founder's to schedule (§13 Q8).
5. **Production seed before checkout.** `pnpm db:seed --insert-only` adds missing rows and changes none; a plain seed refuses to run when `APP_ENV=production` (AC-1). The founder runs it against production before the cutover release (§12), which also gives spec 010's first order every row it needs.

### 2.2 The master copy and the cutover (slice A; proposed ADR-0021)

- **The database becomes the only runtime source** for: products, tiers, facets, product copy per locale (`product_translation`), prices (`country_price`, `addon_country_price`), photos and alt text (`media_asset`, `product_media`, `product_media_alt`), and countries (status, `guidePublished`, `corridorPagePublished`, operations, `first_live_at`). The repository files that author them today become **seed**: they fill a fresh database (local, CI, preview, staging) and remain the test fixtures, and no production page reads them again.
- **Stays in the repository** (unchanged by this spec): UI strings (`messages/**`), corridor guides, trust, help and legal pages, add-on and category and occasion definitions (their copy becomes editable in slice B), the locale registry and the site-link registry (their switches become overlays in slice B).
- **The swap is one composition root per family**, inside its module: spec 005's catalogue, price and FX providers (`src/modules/catalog`, built by TASK-070, spec 005 §9 items 27 and 28) and a new `dbCountryRegistry` in `src/modules/geo`. `production`, `staging` and `preview` select the database providers; `development` and `test` without a database URL select the static ones (AC-3). No call site outside the two modules changes.
- **Parity before the switch.** `pnpm catalogue:parity --target=<database>` compares, for every URL the build emits in every locale, the fingerprint under the static and the database providers: status, robots directive, canonical, hreflang alternates, sitemap membership, the visible default price and currency, and JSON-LD `Offer.price`. The cutover release ships only when it is empty against production (AC-2). This is what forces the seed to agree with `countries.ts`, whatever Poland's status is there at the cutover (`demo` once TASK-239 merges).
- **Insert-only seed** (AC-1): `seed/index.ts` gains `--insert-only` and refuses to run without it when `APP_ENV=production`. In every mode, a row whose entity or parent product, country or florist has `source = 'real'` is never changed (spec 012's audit trigger sets `source = 'real'` on every admin write).
- **Rollback** of the cutover is reverting its PR: the static providers return; database rows stay. Rows written in admin after the cutover would then be invisible until it is re-applied, which the runbook states.

### 2.3 Publishing: how structural changes appear (slice A)

- **The existence manifest.** The build writes one manifest: every URL the build emitted, per locale, which is exactly the union of the routes' `generateStaticParams` output. Its SHA-256 is the deployment's `existenceHash`, reported by `GET /api/health` beside the commit.
- **Existence at runtime is "the database says so AND the manifest has it".** The resolver (`resolveLocalePath`) and every existence predicate that feeds links, listings, sitemaps and hreflang are composed that way. So a bouquet made active after the last build is invisible everywhere (404 at its URL, absent from every grid, link, sitemap child and hreflang cluster) until the next publish, and a link never points at a page that does not exist. A bouquet removed after the build answers 404 at once and leaves every list at the same moment.
- **`/admin/publish`** shows what the database would add and remove against the running manifest, per locale, with counts and the list of URLs, the current commit and `existenceHash`, and the history of publish runs. **Publish** creates a `publish_run` and asks the environment's **publish target** for one deploy of the environment's tracked branch head: `release` in production (spec 040 §14 A3), `main` in staging. It never builds any other commit, so a publish cannot undo or skip a release.
- **Publish targets** sit behind one interface in `src/lib/publish.ts`: `railway` (Railway's public API with an environment-scoped project token, sent in the `Project-Access-Token` header ([Railway docs](https://docs.railway.com/integrations/api)); the mutation, `environmentTriggersDeploy` or `deploymentRedeploy` ([Railway docs](https://docs.railway.com/integrations/api/manage-deployments)), is fixed in the task's first step by checking that the build log shows a fresh `next build` of the branch head), `fake` (tests) and `none` (development, and any host without a target; Publish is absent with the reason shown). There is no Vercel target (§13 Q16, C2): Vercel builds nothing today, so on the cold fallback of ADR-0018 Publish is absent and structural changes wait for a return to Railway.
- **A run** moves `requested → building → deployed → verified`, or to `failed` or `timed_out` (after 30 minutes). A pg-boss job `catalogue.publish` triggers the deploy and polls its status once a minute. The new deployment verifies itself at boot: it marks the open run `verified` only when its own `existenceHash` equals the run's expected hash and its commit equals the head recorded at request. After `verified`: `invalidate(['sitemap'])` once, then every added URL is requested once (`pnpm cache:warm`'s function), so no buyer pays for the first render.
- **Guards** (AC-6, AC-8): one open run per environment; at most 10 runs per environment per calendar day (§13 Q14); and once the placeholder window is closed (§2.5), a publish whose removal list contains a URL that is indexable in the running deployment is refused, naming the URLs. Before the window closes, removals are allowed: the site is hidden from search engines, so no URL is in an index yet, and no placeholder product page was ever indexable (§2.0 item 3). This is why the window must close before indexing opens.
- **Any build publishes.** A normal release (`/launch`) also builds from the database, so pending structural changes go out with it. The publish page says so.
- **Edits made while a build runs (advisor F1).** A content edit saved during a build is invalidated on the old container, and the new deployment would otherwise serve the data it built with until ISR's one-hour backstop. So the build records `dataAsOf` in the manifest: the database's `now()` read before its first catalogue query. At boot, every deployment (publish or release) reads every product, price, product copy, photo attachment and country row whose `updated_at` is later than `dataAsOf` and calls `invalidate()` once with the union of their §5.4 tag sets (nothing when nothing changed). A price changed mid-build is then in the edge HTML within 60 s of the new deployment going live (AC-38).

### 2.4 Review of catalogue text and photos (slice A; proposed ADR-0022)

- **The ledger** (`review_attestation`, §5.1) is append-only. Each row binds a decision (`approved`, `changes_requested`, `rejected`) to a subject (kind, reference, locale), the SHA-256 of the exact text or image reviewed (`value_hash`), the hash of the English source it was reviewed against (`source_hash`), the attester's user id and `display_name`, and the database's `now()`. A subject is **reviewed** exactly when its latest decision is `approved` and its `value_hash` equals the hash of what is served now.
- **The product copy subject** is one (product, locale): its hash covers name, slug, description, SEO title, SEO description, and the alt text of every image attached to the product in that locale. Changing any one of them makes that locale unreviewed, which spec 005's `isProductIndexable` already turns into `noindex`, sitemap exclusion and hreflang exclusion (AC-12). The **photo subject** is one `media_asset`, hashed by its `checksum_sha256`.
- **One writer.** `attest()` in `src/modules/i18n` is the only code that writes the ledger and the only code that may set `product_translation.reviewed` / `reviewed_by` / `reviewed_at` and `media_asset.review_state` / `reviewed_by` / `reviewed_at`. Postgres enforces it with `review_write_guard()`: those columns change only under `SET LOCAL app.allow_review_write = 'on'` (else `REVIEW_DIRECT_WRITE`), and `reviewed = true` or `review_state = 'approved'` needs an `approved` ledger row for that subject with the current hash in the same transaction (else `REVIEW_WITHOUT_ATTESTATION`). The lint rule `fo/no-direct-review-write` catches the attempt first (AC-10, AC-14).
- **Who may attest.** A signed-in user with a non-empty `display_name` and the subject's locale in `reviewer_locale` (photos: the `media.review` permission). The founder holds `en` and `en-gb`; a native reviewer holds `pl` or `de` (§13 Q7). Copy approval stays a human's own act: no agent, script or seed can approve, because only `attest()` under a signed-in admin session (or the one-time import) writes the ledger.
- **The import** (`pnpm attestations:import --only=catalogue,media`) carries every product copy entry (`seed/data/copy/*/products.json`) and photo entry (`seed/data/media.json`) with a recorded approval, name and date into the ledger as `channel = 'import'`; an entry missing a name or a date is imported unreviewed and listed. Category and occasion copy keep their seeded flags until slice B. It is idempotent and writes `seed/data/attestations.json`, the ledger's seed for fresh databases, which `db:seed` replays as its last step (AC-13).
- **Attester names** are personal data: 3 years after an attester's account is deactivated, `attester_name` is replaced by "Reviewer {n}" (n stable per user) (AC-28).

### 2.5 Products and florist bouquets (slice A)

- **Who enters bouquets in v1: admin only** (the founder, or a `content` user). The florist sends photos of 5 to 10 bouquets with prices (the outreach kit asks exactly that); the founder enters them. Florist self-service proposals through the vendor portal are a later spec (§3), argued in §13 Q4.
- **Product editor** (`/admin/catalogue/products/[sku]`, tabs: details, sizes, copy, photos, prices, margin): SKU, the six facets from the closed taxonomy (`src/config/catalogue/schemas.ts`; a new facet value stays a code change), stem count, vase, freshness days, substitution class, `partner_only`, status; **sizes** (`product_tier`: key, label key, stems, sort, exactly one default); **copy** per locale (name, slug, description, SEO title, SEO description), with its review state and an Approve button for a user granted that locale.
- **A florist bouquet** is a product saved with a **supplier florist**. The save writes the product and that florist's `partner_catalog_mapping` row (can fulfil, the florist's price as payout in integer minor units and the florist's payout currency) in one transaction, through spec 012's `saveMapping` (AC-17). Spec 016's routing already offers an order only to florists whose mapping can fulfil it, so a bouquet only its florist makes is routed only to that florist, with no routing change.
- **A bouquet is saleable only if a real florist can make it (advisor F3).** In `production` and `staging`, for a `live` country, the database provider's `availability()` counts a florist only when it is `active`, not `demo`, has a `partner_catalog_mapping` that can fulfil the product and size, and has coverage in the country. Spec 002's seeded demo florists and their mappings never make a product saleable there. An unsaleable product's page still exists (no URL changes, so no publish and no AC-8 conflict) and renders the "cannot be sent" verdict `availability()` already carries (no `Offer` for sale, no buy control), worded with an existing reviewed key, such as the date picker's `unavailable` line; if none fits, the implementer stops and reports the key and its text rather than adding one (the copy share has no headroom); spec 010's placement re-checks `availability()` and refuses the order. **Before Poland goes live** (Poland `demo`, TASK-239): checkout runs only in demo mode, whose orders route to demo florists by spec 016's mode pairing and take no money, and the go-live preflight (§2.8) refuses the flip until at least six products are saleable by this rule. **After Poland goes live**: the rule is checked on every render and every placement, so a placeholder with only demo mappings, or a bouquet whose only florist is paused, cannot be bought (AC-39).
- **The relay stays invisible to buyers** (founder ruling 2026-10-14). Copy containing the legal name or city label of any non-demo florist, or a word of spec 004's buyer-copy ban list ("partner", "vendor", "relay" and the rest), is refused. A florist's name, code and photo credit never reach public HTML (AC-17).
- **Validators are shared with the gates.** The rules `catalogue:check` and `seed:check` apply to files are extracted into pure functions in `src/modules/catalog/validate/`, each with a stable rule id, and run on every admin save (AC-15). **Hard rules refuse**: slug shape (ASCII, lowercase, hyphenated, `plan/02` §4) and uniqueness per locale; odd stem counts (spec 005, founder ruling 2026-10-14); exactly one default size; integer minor units; currency equal to the country's; one open price row; the ban list; no price literal in copy; `seoTitle` ≤ 60 and `seoDescription` ≤ 155 characters; no email-, phone- or URL-shaped string; no competitor brand name. **Soft rules warn** and save only with an override reason, stored on the audit row: description outside 60 to 90 words, a price outside its `plan/10` §2.3 band, a price not ending as the currency's rounding style.
- **Status**: `draft → active` needs an `en` name, slug and description, at least one size with exactly one default, an approved primary photo, and an open price in at least one country. `active → retired`, **removing a product from a country** (closing its open price with no successor), and a **slug edit** are refused for an **exposed** product (AC-16).
- **Exposed** means: priced (now or in the past) in a country whose `first_live_at` is set, **and** the placeholder window is closed or the product is not a placeholder (`source = 'real'`). **The placeholder window** is a registered global flag, `catalogue.placeholder_window`, on from the cutover; while on, `source = 'seed'` products can be retired, removed from Poland and renamed freely, because none of them is indexable. The founder turns it off when opening the site to search engines; it cannot be turned back on (§13 Q6). After that, a retired-product page (`plan/02` §7: 200 with alternatives for 90 days, then 410) is a precondition of retiring an exposed product, and that page is a later spec (§3).

### 2.6 Prices and margin (slice A)

- **Typed as text, stored as integers.** `parseMinorInput(text, currency)` parses by string arithmetic against the currency's exponent: `.` or `,` as the decimal separator, no grouping, no sign, no exponent, never a float (AC-18).
- **A change supersedes, once a buyer could have seen the price.** The open row gets `active_to` = today in the country's zone and a new open row starts today; `retail_minor` is never updated. Spec 002's `CHECK (active_to IS NULL OR active_to > active_from)` already makes a second change on the same day impossible, so "one change per day" (§13 Q9) is a database fact. Old rows stay for the 30-day lowest price (`plan/07` §2.1).
- **Before the first `draft → active`, prices are freely replaceable (advisor F2).** `product.first_active_at` (§5.1) is set once by a trigger at the first `draft → active`. While it is null, no page, quote or `lowestPriceInLast30Days` reads the product, so a price row may be deleted and re-entered any number of times a day (a typo fixed an hour after entry). From `first_active_at` on, only supersede is allowed (AC-19).
- **The amount typed is the all-in price**, VAT and delivery included, for the destination country. The form has no net-of-VAT field and no buyer-country field (AC-20, `plan/07` §3, §4).
- **The confirmation** shows the old and new price formatted in each launch locale (`229,00 zł`, `PLN 229.00`), the change in per cent, a warning beyond ±30 %, and `lowestPriceInLast30Days`.
- **Margin view and suggested price** per (product, size, country): gross, VAT, net, the lowest and highest florist payout among active and onboarding florists mapped to it (converted with spec 005's dated rate when the payout currency differs), margin, and the payout share of net. The **suggested price** is the highest payout divided by 0.60, plus VAT, rounded up to the currency's rounding style (`plan/06` §2: florist payout 55 to 65 % of net retail). A price whose payout share exceeds 65 % saves only with an override reason; a price whose net (the price before VAT) is at or below the highest payout is refused, because it loses money (AC-21; §13 Q5).
- **One price source.** The product page, its JSON-LD `Offer`, spec 011's payout example and spec 010's checkout all read spec 005's one price provider, now the database one, so the visible price, the schema price and the charged price stay one integer (AC-19). Cache lag is covered by spec 010's signed quote and its "the price changed" notice.

### 2.7 Photos (slice A)

- **Upload** (`POST /admin/api/media`, a route handler with a 15 MB body limit; JPEG, PNG or WebP; at most 40 megapixels; SVG and HEIC refused): the image is decoded, re-encoded with every metadata block dropped (EXIF, GPS, XMP, IPTC), stored in R2 under `originals/{assetId}` through `src/lib/storage.ts`, a `media_asset` row is written with the provenance spec 006 §2.4 requires for its source, and `media.derive_variants` is enqueued (AC-22). Both depend on TASK-082 and the R2 loader flip, TASK-083.
- **Florist photos** are `source = 'partner'` with `supplier_partner_id` set, `credit` = the florist's code (internal only) and `licence` = the florist's `terms_version` at upload. A florist photo cannot be approved while that florist has no recorded terms, because the florist agreement is what grants the licence (§13 Q11). ## 4. User stories

- As the **founder signing the first Warsaw florist**, I create their five bouquets from the photos and prices they emailed, see the suggested price and my margin, approve the English text and the photos, press Publish, and within minutes the bouquets are on the Polish shop pages; the placeholder bouquets are gone from Poland.
- As the **founder changing a price**, I type `249,00` for PLN, see it in all four languages, the change in per cent and the lowest price of the last 30 days, and confirm; the product page, its structured data and the checkout show the new price within a minute, and the old one stays on record.
- As the **founder taking Germany live later**, I open Germany, read exactly what is missing, fix it, type `DE`, and the German pages become live, indexable and in the sitemap, with no code change.
- As a **native Polish reviewer**, I sign in with an email link, approve the Polish text of each bouquet under my own name, and nothing I have not approved can make a Polish page indexable.
- As **Googlebot**, a product page is indexable only after a named person approved its exact words, its price in the HTML equals the checkout's, and no link points at a page that does not exist.
- As an **implementer agent**, I cannot mark text approved, change a price in place, or flip a country by writing SQL or editing a file: the database refuses.

## 6. SEO considerations (mandatory)

- **Indexability stays one predicate** (ADR-0007, spec 007's rule engine), fed by data: `country.status`, the corridor flags, the six-product floor (spec 008), and review state, now from the ledger for product copy and photos. Admin writes facts the predicate reads, never a robots directive.
- **Cutover parity** (AC-2): status, robots, canonical, hreflang, sitemap membership, visible price and `Offer.price` for every built URL are identical before and after the cutover; the release ships only on an empty diff against production.
- **No link to a page that does not exist**: runtime existence is database ∧ manifest (AC-5), and every link renderer, listing, sitemap builder and hreflang cluster reads that one predicate, so internal links, sitemaps and hreflang cannot disagree (`plan/02` §8, §10, §11).
- **URL stability** (`plan/02` §4, §7): slugs follow the existing rules through the shared validators; an exposed product's slug cannot change and it cannot be retired or removed from a live country (AC-16); after the placeholder window closes, a publish that would remove an indexable URL is refused (AC-8). So admin cannot orphan an indexed URL or create a duplicate canonical.
- **Thin content**: the go-live preflight refuses a country with no operations data, no active florist, an unpriced product or an unreviewed live-state corridor text (`plan/02` §5.1, §5.2); the shared validators refuse short or duplicate copy patterns, banned words and price literals on every save, not only in CI.
- **Schema and price**: `Offer.price` = visible price = `quote()` after every change (AC-19), because prices are superseded rows read by spec 005's one projection; `Offer` is still emitted only for `live` countries (`plan/02` §9), and offered for sale only for a saleable product (AC-39), so structured data never advertises a bouquet no real florist can make; a price edited during a build cannot linger in the HTML (AC-38). No `LocalBusiness` claim can appear: florist names never reach a page (AC-17).
- **hreflang**: an alternate exists only for a locale whose product copy is attested for its current hash; editing Polish text removes the Polish alternate and the page's Polish indexability until re-approved (AC-12), and reciprocity holds because the cluster and the sitemap read the same predicate.
- **Sitemaps and `<lastmod>`**: admin writes advance `updated_at` (spec 002 trigger), so `<lastmod>` stays truthful; a verified publish purges the sitemap index and children; a go-live flip purges them too.
- **CWV**: no public page gains JavaScript or a rendering change; uncached renders read Neon, and `cache:warm` requests every added URL after a publish so the first visitor gets edge HTML. Photos go through spec 006's variant ladder and the existing image budget (≤ 200 KB above the fold on a mobile PDP). Lighthouse budgets are unchanged and still gate CI.
- **Crawl**: a publish changes the URL set only through the build, so Googlebot never meets a link to a 404 between publishes; removals happen while the site is hidden and the placeholder window is open, and no placeholder product URL was ever indexable (§2.0 item 3); after the window closes, AC-8 refuses removing an indexable URL.
- **Bulk upload (slice A.2, §14.11)**: an upload creates only drafts and removes nothing, so it adds or drops no URL (the publish diff is unchanged by an Apply, AC-43); slugs pass the same rules and an exposed product's slug cannot change (AC-46); uploaded copy is unreviewed, so a changed locale leaves the index, the sitemap and hreflang until a named reviewer approves it, and the preview flags every approved locale an upload would reopen (AC-42, AC-45); prices keep visible = schema = charged (AC-44).

## 7. i18n considerations (mandatory)

- **New message keys**: admin only, in `messages/admin/en.json` under `admin.catalogue`, `admin.media`, `admin.countries`, `admin.publish`, `admin.review` (slice B: `admin.translations`). They sit in spec 003 A17's `admin` surface, so they do not count toward any public locale's unreviewed share. **Slice A adds no public message key** (AC-27): product names, descriptions and alt text are database data, not message keys. This matters because `en-gb`'s unreviewed share has no headroom.
- **Product copy per locale** lives in `product_translation` (`plan/03` §5): `en`, `en-gb`, `de`, `pl`. Each locale is edited only by a user granted it and approved only by such a user (AC-11). Slugs are ASCII-folded per locale (`bukiet-roz`, never `bukiet-róż`).
- **Formatting**: every amount through `formatMoney` from integer minor units, previews in all four launch locales; dates and instants through `format.ts` with the zone named (price change dates in the country's zone, audit and publish instants in the viewer's `admin_profile.time_zone`). Money input is parsed by string against the currency's exponent, never by `parseFloat` (AC-18).
- **RTL**: logical properties only (lint applies); no RTL locale ships.
- **Bulk upload (slice A.2, §14.11)**: copy columns per locale (`name_pl`, `slug_pl`, …) for the four launch locales, accepted only in the uploader's granted locales (§13 Q22); files are UTF-8, so Polish and German diacritics round-trip; money cells parse by `parseMinorInput`, accepting `229,00` and `229.00` alike; admin strings and the template's instructions sheet come from `messages/admin/en.json` (`admin.catalogue.import`); column ids are fixed ASCII identifiers, not translated; no public message key (AC-27).
- **Address and phone formats**: none captured or shown by this spec.
- **Translation review and `noindex` gating**: the ledger is `plan/03` §6's mechanism. Text typed or edited in admin starts unreviewed; a granted reviewer attests the exact text; indexability and hreflang read the result through `isProductIndexable`; an edit reopens the subject; a change to only the English source marks other locales stale and keeps them indexable (`plan/03` §6 step 5). The founder approves `en` and `en-gb`, native reviewers `pl` and `de`. Slice B extends the same ledger to UI strings, guides and legal pages, keeping the 5 % share rule with the ledger as input.

## 11. Observability

- **Every admin write** is an `audit_log` row with request id, actor and action (spec 012's trigger); the request's log line carries the same request id, the action and the duration, never values.
- **Events logged** (`info`, no PII): `catalogue.import.previewed` / `.applied` / `.refused` / `.expired` (import id, format, bytes, row and SKU counts, counts per outcome, rule ids with counts; never a cell value or the file name), `catalogue.product.saved` (sku, fields changed by name), `catalogue.price.superseded` (sku, country, tier, old and new minor units, currency), `catalogue.review.attested` (kind, ref, locale, decision; no name), `media.uploaded` (asset id, source, bytes), `country.status` (iso2, from, to), `publish.requested` / `.building` / `.deployed` / `.verified` / `.failed` / `.timed_out` (run id, environment, added and removed counts, head SHA, duration), `cache.invalidate` (tags, URL count, origin and edge outcomes), `cache.warm` (URLs, failures).
- **Warnings and Sentry**: a failed or timed-out publish; a verified deployment whose `existenceHash` does not match its run (`error`); a failed purge after an admin write (the change is saved but not yet visible); `REVIEW_DIRECT_WRITE`, `REVIEW_WITHOUT_ATTESTATION`, `STATUS_FLIP_OUTSIDE_ADMIN` in production (`error`: a bug or a bypass attempt); a build that could not reach the database (CI and Railway build logs).
- **Cost signals**: publish runs per day on `/admin/publish`; Railway build minutes in the Railway dashboard; Neon compute through `neon.usage_probe` (spec 002).
- **Not here**: order-lifecycle alerts (spec 025), admin analytics (`plan/11` §7).

### 14.2 The file (§13 Q19, Q27)

- **One definition, `IMPORT_COLUMNS`**, in `src/modules/catalog/import/`: per column its id, level (product, size, price), whether it is required on a create row, its kind (text, money, integer, yes/no, closed list, currency, country) and its zod schema. The parser, the template, the export and the preview all read it, so the template's columns cannot drift from what the parser accepts.
- **One row per (SKU, size, country)**, in one table: a `products` sheet in XLSX, the whole file in CSV. Product-level cells may be blank on later rows of the same SKU, size-level cells on later rows of the same size; a filled cell must equal the SKU's (or size's) first filled value. A row with `country` blank carries a size with no price.

| Columns | Level | Rule (the single editor's, §2.5 to §2.7) |
|---|---|---|
| `sku` | product | required; the SKU pattern of `src/config/catalogue/schemas.ts`; a SKU in the database makes the row an update, a new one a create |
| `florist` | product | required; the code of an existing florist, the bouquet's supplier (§2.5); a demo florist only outside `production` |
| one column per facet, named by its id in `schemas.ts` | product | values from the closed taxonomy; a multi-valued facet separates values with `\|` |
| `stem_count`, `vase`, `freshness_days`, `substitution_class`, `partner_only` | product | as the details tab; yes/no columns take `yes` or `no` |
| `size`, `size_label`, `size_stems`, `size_sort`, `size_default` | size | as the sizes tab; exactly one default per SKU |
| `florist_price`, `florist_currency` | size | the florist's price for that size, as text; the florist's payout currency |
| `country`, `price`, `currency` | price | ISO code of a seeded country; the all-in selling price as text, blank for the suggested price (§14.6); the country's currency |
| `name_{l}`, `slug_{l}`, `description_{l}`, `seo_title_{l}`, `seo_description_{l}` for `en`, `en-gb`, `de`, `pl` | product | the copy tab; `en` name and description required on a create row |
| `primary_photo`, `primary_alt_{l}` | product | the main photo's file name (§14.8) and its alt text per locale |

- **Blank never clears.** On an update row a blank cell means "no change". Clearing a value, removing a size or taking a bouquet off a country is done in the editor (§13 Q23).
- **The template** (`GET /admin/api/catalogue/import/template?format=xlsx|csv`): the XLSX has the `products` sheet (header row only, money columns in text format `@` so `229,00` is kept as typed, in-cell lists for closed values), an `instructions` sheet (what each column means, from `messages/admin/en.json`) and a `lists` sheet (allowed values); only `products` is read back. The CSV template is the header line. With `florist=<code>` (Q27) it is the **export**: one row per (SKU, size, country with an open price) of that florist's `real` products, with current values, so the founder edits and re-uploads; an unchanged file previews as all `skip` (AC-40).
- **Formula injection.** Every exported cell whose first character is `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with `'` (defence in depth: §14.4's rule keeps such values out of copy in the first place).

### 14.3 Reading the file (§13 Q25)

- **Formats**: `.csv` in UTF-8 (BOM optional; `,` or `;` delimiter read from the header line, which covers a Polish Excel export; RFC 4180 quoting; CRLF or LF) and `.xlsx`, recognised by its zip signature, not its name. `.xls`, `.xlsm`, `.ods`, an `.xlsx` with a VBA part, and bytes that are not valid UTF-8 are refused.
- **Limits**: 2 MB per file; 1,000 data rows; 200 distinct SKUs; 2,000 characters per cell; an `.xlsx` whose parts expand beyond 20 MB in total or that has more than 100 entries is refused (zip bombs), with the 20 MB counted as bytes actually inflated: the inflate is streamed and stopped at the limit, and the sizes the zip headers declare are never trusted, because they can lie (advisor F3); XML parts are parsed with DTD and entity processing off, and a DTD or entity declaration refuses the file (XXE). Formulas are never evaluated and external links never followed; a formula cell is a row error even with a cached value.
- **No floats.** A money cell must be a text cell; a number-typed cell in a money column is a row error ("format the column as text, as the template does"), because reading it would go through a floating-point number. Integer columns (`stem_count`, `size_stems`, `size_sort`, `freshness_days`) accept digits only, or a number cell holding a safe integer.
- **Header**: column ids match `IMPORT_COLUMNS` (order free, case-insensitive); an unknown, duplicated or missing required column refuses the file, so a mistyped column or an extra column of personal notes is never silently dropped or stored.
- **The library**: one maintained XLSX reader and writer, pinned, chosen in task 14a's first step with `pnpm audit` clean and its XML parsing configured as above. The npm `xlsx` 0.18.x package is excluded (open advisories CVE-2023-30533 and CVE-2024-22363). Parsing runs in the request, in memory; the file is never written to disk or R2.

### 14.4 Validation and the dry-run preview (§13 Q24)

- `planImport(parsed, actor)` is pure over a read snapshot of the database. For each row it builds the input the single editor would send (`ProductEditSchema`, `TierEditSchema`, `ProductCopyEditSchema`, `PriceChangeSchema`, the mapping input of `saveMapping`) and runs the **same functions in `src/modules/catalog/validate/` with the same rule ids** (AC-15's fixtures are reused). Hard rules make the row an `error`; soft rules warn.
- **One new shared hard rule**, `copy.formula_lead`: any free-text field (copy, alt text, `sku`, `size_label` and every other text column of `IMPORT_COLUMNS`, and the same fields in the editor) that after trimming starts with `=`, `+`, `-`, `@`, `'`, a tab or a carriage return is refused, in the editor and `catalogue:check` too (AC-15 covers it). So no stored value ever needs §14.2's export prefix, and an unchanged export re-uploads as all `skip` (advisor F4). If any seed copy fails it, the implementer stops and reports the entries rather than editing them.
- **Within-file checks**: product-level or size-level values that differ across rows of one SKU or size; two rows for one (SKU, size, country); no default or two defaults; one slug for two SKUs in a locale; a slug taken in the database. Every row involved is an error.
- **Outcomes**: `create` (new SKU), `update` (some field differs, each change listed old and new), `skip` (identical to the database), `error` (each failed rule id and column). A row that would reopen an approved copy locale is a soft warning, `copy.reopens_approved`, naming the locale ("approved Polish text changes: Polish leaves the index until re-approved"), and needs a reason before Apply (advisor F1).
- **Warnings and reasons** (Q24): one reason per soft rule id per import, typed in the preview, listing the rows it covers; stored with the import and on the audit row of every entity it covers.
- The preview is a page (`/admin/catalogue/import/[id]`), paginated by 100 rows, filterable by outcome, with the counts on top. Building it writes only the `catalogue_import` row (AC-42).

### 14.5 Apply: all or nothing (§13 Q18)

- Apply is offered only when there is no error row and every warning has a reason; otherwise it is absent with the reason shown.
- Apply opens one transaction, locks the affected products (`SELECT … FOR UPDATE`), recomputes the plan from the stored payload and the current data, and compares its hash with the preview's. If they differ (someone edited a product, a price changed, a florist was paused), it writes nothing and asks for a new preview. Otherwise it calls, in order, `createProduct` / `updateProduct`, `saveTier`, `saveMapping` (the florist's price), `saveCopy`, `replaceDraftPrice` or `supersedePrice`, each with the transaction handle; any failure rolls everything back. After commit it calls `invalidate()` once with the union of the commands' tags (§5.4) and records `applied`.
- **What it never does** (Q23, Q26): change a product's status, close a price without a successor, delete a row, touch a `source = 'seed'` product, or change a country's status or `first_live_at` or any feature flag (`checkout.open`, `catalogue.placeholder_window` and the rest): the import module calls neither `setCountryStatus` nor a flag command, and spec 012's `status_flip_guard()` would refuse it anyway (AC-45, advisor F2). Created products are `draft` and `real`; they get a URL only after activation in the editor and a publish (§2.3), so an Apply leaves the publish diff unchanged.
- An import is applied at most once; a preview expires 24 hours after upload.
- If the founder chooses per-row apply in Q18 instead, AC-43 is rewritten before `/plan-tasks`: each row in its own transaction, failures listed, and a SKU's rows grouped so a bouquet is never half saved.

### 14.6 Prices (§13 Q20)

- **Text to integers** by `parseMinorInput` only (AC-18's rules: `.` or `,` decimal, no grouping, no sign, no exponent). `currency` must equal the country's currency and `florist_currency` the florist's payout currency.
- **Supersede, never update**, exactly as §2.6: for a product with `first_active_at` set, a changed price goes through `supersedePrice`, and a second change to the same (product, country, size) on the same day is a row error at preview; for a draft, `replaceDraftPrice`. Surcharges (spec 005) are not in the file and are not touched.
- **The florist's price is the input.** Each size's `florist_price` is saved as that florist's payout through `saveMapping`. A blank `price` takes `suggestedPrice` (§2.6: the highest payout among mapped florists, converted at spec 005's dated rate when currencies differ, divided by 0.60, plus VAT at the country's `vat_rate_bp`, rounded up to the currency's rounding style), marked "suggested". A typed `price` gets §2.6's margin checks: payout share above 65 % warns, net at or below the highest payout is refused. A country without `vat_rate_bp` makes its price rows errors.
- **The amount is all-in**, VAT and delivery included: `ImportRowSchema` has no net-of-VAT and no buyer-country key (AC-20's rule, `plan/07` §3, §4).
- The preview shows each changed price old and new through `formatMoney` (in `en` and the country's locale), the change in per cent and `lowestPriceInLast30Days`. On an active product (its `first_active_at` set) the new price is live within 60 s of Apply, with no publish, so a change beyond ±30 % is a soft warning, `price.change_over_30`, that needs a reason (Q24's mechanism); on a draft it is a flag only (advisor F1).

### 14.7 Copy, review and slugs (§13 Q22)

- Copy is saved through `saveCopy`, so an upload is unreviewed text: Apply writes no ledger row and can set no review column (`review_write_guard()`, §2.4). A created locale starts unreviewed; a changed approved locale becomes unreviewed by its hash (AC-12). The report lists every unreviewed subject with a link to its copy tab, where a granted reviewer approves it under their own name. There is no bulk approval (§3).
- **Locale grants** (Q22): a copy or alt column in a locale outside the uploader's `reviewer_locale` grants is a row error, as in the editor (AC-11).
- **Slugs** follow §2.5's rules: a blank `slug_{l}` on a create row is derived from the name by the slug rule's ASCII fold (`bukiet-roz`) and shown in the preview; a malformed, repeated or taken slug is an error, never suffixed silently; an exposed product's slug cannot change (AC-16).
- The relay stays invisible: the ban list and the florist-name rule apply to every copy cell (AC-17).

### 14.8 Photos: a second step, by file name (§13 Q21)

After Apply, while the payload is held (24 hours), the report offers "Add photos": several files dropped at once, each matched to a `primary_photo` cell of that import by file name (Unicode NFC, case-insensitive). Each match goes through `POST /admin/api/catalogue/import/[id]/photos`, which calls `uploadOriginal` with every rule of §2.7 (15 MB, 40 megapixels, metadata stripped, SVG and HEIC refused), provenance `source = 'partner'`, `supplier_partner_id` = the row's florist, licence = the florist's `terms_version`, then attaches it (primary only when the product has none) with its `primary_alt_{l}` rows. It stays `pending` until approved through `attest()` (AC-23), and a florist without recorded terms cannot have it approved (§13 Q11). A file that matches no cell, or more than one product, is refused and listed. URLs are not accepted: no import code fetches anything from the internet (no SSRF path, no unknown provenance). Further photos are added in the editor.

### 14.9 Data model: `NNNN_catalogue_import` (migration and rollback)

- No column is added to an existing table; no `float`, `enum` or extension. **Rollback** (`.down.sql`, run by the round-trip test): detach the trigger, delete the retention row, drop the table. Products, prices and mappings written by applied imports are ordinary rows and stay.

## Appendix A. Proposed ADR-0021: the database is the master copy of the catalogue, prices, photos and countries; structural changes publish by rebuilding the live commit

*Text for `/adr` if the founder accepts §13 Q1 to Q3. Not an ADR file.*

**Status**: proposed. **Supersedes**: ADR-0017 in part (the authored dataset stops being the runtime source; it remains the seed and the fixtures). **Related**: ADR-0007, ADR-0015, ADR-0018, specs 002, 005, 006, 012, 012b.

**Context.** Bouquets, prices, photos and country switches are repository files, so every change is a pull request, contrary to "Country/partner go-live is a data flip in admin, never a code change". Florists now supply their own bouquets and prices (founder, 2026-10-19), which makes catalogue changes frequent. The `[locale]` layout's `dynamicParams = false` means a URL must exist at build time.

**Options.** (1) Keep files, edit through generated pull requests: every change needs review and CI, and the founder cannot act alone. (2) Database as master copy, builds read it, structural changes appear by rebuilding the live commit from admin ("publish"). (3) Database as master copy with on-demand rendering of unknown URLs (`dynamicParams = true`): no rebuild, but the 404 gate of specs 003 and 008 weakens and every probe costs a query; needs a trial.

**Decision.** Option 2. The database is the only runtime source for products, sizes, product copy, prices, photos and countries; the files become seed. Builds read the database through a read-only role and fail closed. Runtime existence is "database ∧ build manifest". Publish rebuilds the environment's tracked branch head through a host adapter; a go-live requests it.

**Consequences.** Easier: the founder changes catalogue, prices and countries alone, audited, with no code change; price shown = price charged keeps one origin. Harder: production data is on the build path (an outage delays a publish or release, never takes the site down); each publish costs a Railway build of a few minutes; backups become mandatory before the cutover; edits to the seed files no longer change production. Revisit option 3 if a publish build exceeds 10 minutes or publishes exceed 10 a day.

## Appendix B. Proposed ADR-0022: review is an attestation ledger bound to the exact text

*Text for `/adr` if the founder accepts §13 Q7 and Q8. Not an ADR file.*

**Status**: proposed. **Related**: ADR-0007, specs 003 (`plan/03` §6), 005, 006, 007, 041, 012b.

**Context.** A `reviewed: true` flag in a file or a row decides whether a page is indexable, and anything that can edit the file or row can set it: 526 English approvals were "transcribed by TASK-091", and guides were approved "without a personal skim". Copy approval must be a named human's own act.

**Options.** (1) Keep flags, police them in review. (2) An append-only ledger: each approval binds a named, signed-in reviewer, a server time and the SHA-256 of the exact text; a subject is reviewed only while its text still hashes to the approved value; the database refuses a flag set without a matching ledger row. (3) Approvals as signed git commits by the founder: no native reviewers without repository access.

**Decision.** Option 2, in two steps: catalogue text and photos first (spec 012b slice A), UI strings, guides and legal pages second (slice B), each behind a parity check that the indexable URL set does not change at the switch. Imported approvals keep their recorded names, are marked imported, and keep counting until re-confirmed.

**Consequences.** Easier: no agent, script or seed can approve text; editing approved text un-approves it automatically; reviewers need only an email address. Harder: one more table and guard; file-backed texts need a build-time hash index; attester names are personal data, pseudonymised three years after the reviewer leaves.
