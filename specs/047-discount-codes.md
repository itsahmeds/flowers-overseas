## 1. Problem

The launch plan's main growth channel is the Polish community in the UK (`plan/00`, `PRODUCT-PLAN-2026-10-24.md` rows E and F). The founder wants to hand community groups, Polish shops, churches and other partner organisations a code their members type at checkout ("POLONIA10"), so a first order costs a little less and the founder can see which group sent which orders. Nothing in the codebase can do this today: spec 005's price is one public price per (product, country, tier), spec 010's checkout has no field for a code, and spec 013 charges exactly the order total that spec 010 wrote.

A discount touches the four things this project treats as hardest: money (integer minor units, the total charged), price display (price shown = price charged; schema price = visible price), VAT (the tax is due on what the buyer actually pays), and consumer law on reductions (EU Omnibus Art. 6a and the UK's pricing rules on reference prices). It also touches the florist's pay, which must not move: we pay for the promotion, not the florist. This spec draws all of that once, so the feature is small to build and cannot leak into the public price, the schema, the Google Shopping feed or the payout.

## 2. Scope

Each bullet is testable; §9 names the AC.

**Codes, made in admin**
- `/admin/discounts` lists codes; `/admin/discounts/new` creates one; `/admin/discounts/[id]` shows and edits one. Admin English only (spec 012 §13 Q9).
- A code has: the code text (6 to 32 characters, A to Z and 0 to 9; typed case, spaces and hyphens ignored), an internal **campaign label** (for example "Polish Saturday school, Ealing"; never shown to buyers), a kind (**percent** off, 1 % to 50 %, stored in basis points; or **fixed** amount off, stored per currency in integer minor units), a minimum order per currency (integer minor units; required for fixed codes), a start instant and an optional end instant, an optional **total** use cap, a **per buyer email** use cap (default 1), an optional list of destination countries (empty means all), an optional list of products (empty means all), a status (`active` or `disabled`) and an internal note.
- A "Generate" button proposes a random 10-character code from an alphabet without look-alike characters (no I, L, O, U, 0, 1), for codes that should be hard to guess.
- Once a code has been used on a live order, its kind, value and per-currency amounts are frozen; to change the offer the founder creates a new code. Caps, the end instant, the status, the label and the note stay editable.
- The create and edit screens show, before saving, a **cost preview**: for each product and country in scope, the price, the discount at that price, the VAT, our worst-case florist pay (spec 012b's highest mapped payout) and the margin after discount, with a warning row where the margin is at or below zero. They also show a **reduction-claim warning** when any product in scope had a lower price in the last 30 days than today (spec 005's `lowestPriceInLast30Days`), because a public "X % off" claim would then be measured against that lower price (§8).
- Every write is audited by spec 012's trigger (actions `discount.create`, `discount.update`, `discount.disable`). Roles: `admin` creates and edits; `admin` and `finance` read.

**Codes, entered at checkout (an addition to spec 010's step 3)**
- On step 3 ("Check and place your order"), above the totals, a collapsed control "Add a discount code" (a `<details>` element, so it works without JavaScript) opens one text field and an "Apply" button. It renders only when the flag `checkout.discount_codes` is on for the destination (country scope, default off).
- Applying a valid code adds one line to the summary, "Discount ({code})", with a negative amount, and every total on the page (summary panel, mobile sticky bar in `demo`, the place or pay button, the VAT split) shows the discounted amount. "Remove" takes it off. One code per order: applying another code replaces the first, and the page says so.
- Applying an invalid code keeps the order as it was and shows one message that says how to fix it (§7 keys). An unknown or disabled code gets the same generic message, so the field cannot be used to discover which codes exist.
- At placement the code is checked again under a lock. If it has ended, run out or no longer applies, nothing is placed and step 3 shows the new total with the reason, exactly as spec 010 handles a price change (AC-17 there). Nothing is ever charged at an amount the buyer did not see last.

**Money: who pays for the discount**
- The discount is computed in the order's currency, in integer minor units: percent codes round half up to the nearest minor unit; fixed codes take the amount set for that currency (a currency with no amount means the code does not work in that currency).
- The discount is spread over the order's eligible lines in proportion to each line's price, by largest remainder with ties to the earlier line, so the line shares are integers that add up to the discount exactly. Each line then has a **paid amount** (price minus its share).
- VAT is computed by spec 005's `vatBreakdown()` on the paid amounts, rate by rate, so a bouquet at 8 % and chocolates at 23 % each carry their own share of the discount and their own VAT.
- `order.buyer_total_minor` is the discounted total; spec 013 charges exactly that, so price shown = price charged holds with no change to spec 013.
- **The florist's pay never changes.** `order_line.partner_payout_minor` is set from `partner_catalog_mapping` as today; no code in `modules/partners`, routing or payouts reads a discount. We absorb the discount out of our margin.
- **Refunds** cannot exceed what was charged (spec 013's invariant already holds, because the captured amount is the discounted total). A partial refund for one line (for example a missing add-on) is capped at that line's paid amount; `linePaidAmounts(orderId)` gives spec 020's refund page those figures. A refund never brings the code's use back (§5.2 counting).

**Price display and the public price**
- The product page, every listing, the Product and Offer schema, the sitemap and any product feed (Google Shopping, roadmap idea D) keep the public, undiscounted price. A code changes nothing that is rendered before checkout step 3, and nothing that is cached.
- No strike-through, no "was" price, no reference price and no "you save X %" anywhere. The discount appears only as its own line with the code and the amount taken off; the lines above it show today's price as normal text.

**Abuse limits**
- Five failed code attempts on one checkout within 15 minutes lock the field for that checkout for 15 minutes; a locked field does not look anything up. More than 100 failed attempts across the site within 10 minutes raises one Sentry warning (an in-process counter, enough because production runs one replica, ADR-0018; the per-checkout counts live on the draft row). No IP address is read or stored for this (Cloudflare's existing rate limit stays the edge layer, spec 040).
- The code never travels in a URL: it is posted in a form body; no route accepts a code from a query string; there is no "share this code as a link" feature.
- The code string is never written to logs, Sentry or analytics. Logs and analytics carry the code's id and its campaign label.
- Use caps are enforced inside the placement transaction with the code row locked, so concurrent orders cannot exceed a cap.
- The per-email cap counts the buyer's email in a folded form (lower case, and any `+tag` in the part before the @ removed), so "anna+1@example.com" and "Anna@example.com" count as one buyer.

**Analytics, and what the founder sees**
- Events declared here, emitted by spec 023 (never for `demo` or `test` orders): `discount_code_applied` and `discount_code_rejected` (with the reason), and on `purchase` the GA4 `coupon` parameter set to the **campaign label** (not the code) plus the `discount` value in the order currency.
- The codes list shows, per code: status (scheduled, active, ended, used up, disabled, computed from data), live uses so far against the cap, and the total discount given per currency.
- `discountFinanceRows(filter)` is the read model spec 030b's finance view renders: per order and per code, the price before discount, the discount, the amount charged, VAT, florist pay, and margin after discount, each in the order currency and in the base currency through the order's FX snapshot.

**The referral hook (no referral feature)**
- Every code is created through one function, `issueCode(input, actor)`, which the admin actions call. The `discount_code.source` column takes `admin` today and allows `referral`, and `issuer_ref` can hold a later issuer's id. Nothing else is built for referral; the founder has not decided it (`PRODUCT-PLAN-2026-10-24.md` row E).

**Docs and records**
- RoPA update, runbook `docs/runbooks/discount-codes.md`, the architecture doc row for `modules/discounts`, artboards before `/plan-tasks`.

## 3. Non-goals

- **Referral codes** ("give 10 %, get 10 %"), codes issued per person, automatic codes after an order → a later spec if the founder says "referral ok". §2's hook is all that ships.
- **Codes in the express wallet on the product page** (spec 010 §14 A-founder-2026-10-24). The wallet sheet has no code field; a buyer with a code uses the normal checkout. Revisit if the express path proves popular.
- **Sale prices, "was/now", strike-through, countdown sales, site-wide automatic discounts, a promotions page.** These are price reductions announced by us and need Omnibus Art. 6a's 30-day lowest price on the page (spec 005 already has the figure). A later spec, with a lawyer's reading, if ever.
- **Free orders (100 % codes), free add-on codes, "buy two get one", gift cards and store credit.** A free order has no payment and needs a path spec 013 does not have; gift cards are `plan/05` row 24, Phase 4.
- **Stacking codes**, codes combined with other offers. One code per order.
- **Codes shown or typed on the product page, in step 1 or step 2.** Step 3 only (§13 Q3).
- **Discount lines in the confirmation email and the invoice PDF** → specs 016 and 018 render the order's lines; this spec gives them the data (§12 requirements). The **refund page** → spec 020, using `linePaidAmounts`. **Florist payouts** → spec 030, unchanged by design. **The finance screens** → spec 030b, using `discountFinanceRows`. **GA4 sending** → spec 023.
- **Discounts that change the florist's pay** or any "shared cost" with a florist. Never; the founder's rule (§2).
- **Editing `CLAUDE.md`, `plan/*` or an accepted ADR.**

## 4. User stories

- As the **founder**, I make a code "POLONIA10" for 10 % off first orders from the Ealing Saturday school, valid to 30 November, up to 200 uses, once per buyer, and I can see how many orders it brought and what it cost me.
- As the **founder**, before I save a code I see whether any bouquet would sell below what I pay the florist, so a typo cannot lose money on every order.
- As a **buyer in Manchester** sending to my mother in Kraków, I type the code my church newsletter gave me on the last step, see "Discount (POLONIA10) −£4.50" and the new total on the pay button, and I am charged that total, VAT included.
- As a **buyer whose code has ended**, I am told plainly that it has ended, and my order is unchanged.
- As a **florist**, I am paid exactly the same for a discounted order as for any other.
- As the **founder's accountant**, each order shows the VAT on what the buyer actually paid, split by rate, and the discount spread across the lines.
- As **Googlebot and Google Shopping**, I see the same public price on the page, in the schema and in the feed, whatever codes exist.
- As **someone guessing codes**, I get five tries per checkout and then a wait, and every wrong code looks the same.

**Invariants checked at placement, in the placing transaction** (application code with an integration test, not a trigger): `sum(order_line.discount_minor) = order_discount.amount_minor`; `order.buyer_total_minor = sum(unit_retail_minor * qty) - order_discount.amount_minor`; `order.vat_breakdown` equals `vatBreakdown()` over the paid amounts. An order with no code has no `order_discount` row and every `discount_minor` is 0, so every existing order and test is unchanged.

**Rollback** (`NNNN_discount_codes.down.sql`, reverse order). A guard first: if any `order_discount` row has `mode = 'live'`, the down file raises `DISCOUNT_ROLLBACK_LIVE_ORDERS` and changes nothing, because a live discounted order is part of the accounting record (the same rule as spec 013's A7 rollback). Otherwise: detach the audit triggers; drop the flag rows; drop the `checkout_draft` columns; drop `order_line.discount_minor`; drop `order_discount`, `discount_code_product`, `discount_code_country`, the constraint trigger and its function, `discount_code_currency`, `discount_code`. The migrate, rollback, migrate round trip of spec 002 runs over it.

### 5.2 API / server actions / jobs / events (zod schemas named)

```
src/config/discounts.ts               limits: percent 100..5000 bp, code length 6..32, generated length 10,
                                      alphabet, attempts 5 per 15 min, lock 15 min, site alert 100 per 10 min
src/modules/discounts/                new module (architecture doc §3 gains the row); public index.ts only
  schemas.ts                          the zod schemas below
  normalise.ts                        normaliseCode(input) → string | null ; emailKey(email) → string
  issue.ts                            issueCode(input, actor) → the one insert path; generateCode()
  evaluate.ts                         evaluateCode(ctx) → Evaluation   (pure)
  allocate.ts                         discountAmount(code, subtotal) ; allocateDiscount(lines, amount)   (pure)
  redeem.ts                           lockAndCount(codeId, mode, emailKey, tx) → counts under FOR UPDATE
  attempts.ts                         recordFailure(draftId), isLocked(draftId)
  finance.ts                          discountFinanceRows(filter), codeStats(codeId)
  index.ts
src/modules/checkout/                 (spec 010's module) gains applyDiscountAction, removeDiscountAction;
                                      draftTotals() and placeOrderAction call discounts' public API
src/modules/orders/                   gains linePaidAmounts(orderId)
src/app/admin/discounts/…             pages, thin; actions in modules/admin
```

**Pure functions** (signatures only):
- `normaliseCode(raw: string): string | null`: trims, removes spaces and hyphens, uppercases A to Z only; returns null for anything outside A to Z and 0 to 9 after that (so a Turkish dotless i or an emoji never reaches the database).
- `emailKey(email: string): string`: lower case, `+tag` removed from the local part, then SHA-256 hex. Used only for the per-email count.
- `discountAmount(code: AppliedCodeTerms, subtotal: Money): Money`: percent: `floor((subtotal.minor * percent_bp + 5000) / 10000)`, integers only (round half up); fixed: the currency's `amount_off_minor`, never more than the subtotal.
- `allocateDiscount(lines: PricedLine[], amount: Money): AllocatedLine[]`: proportional to each eligible line's price, largest remainder, ties to the earlier line; the shares add up to `amount` exactly; a line's share never exceeds its price.
- `evaluateCode(ctx: EvaluationContext): Evaluation`: `ctx` = the code row and its currency, country and product rows, `now`, the order's destination, product, currency and subtotal, the buyer's `emailKey` (or none before step 2), and the counts from `lockAndCount`. Returns `{ ok: true, amount, allocation }` or `{ ok: false, reason }` with `reason` in `DiscountRefusalReason`: `unknown` (also used for `disabled`), `not_started`, `ended`, `wrong_destination`, `wrong_product`, `wrong_currency`, `below_minimum`, `used_up`, `already_used_by_you`, `locked`. The order of checks is the order of this list after `unknown`, so the buyer gets the most useful reason first.

**Eligible lines** (amended by §14 A-orchestrator-2026-10-25 item 2: one code per purchase). With one bouquet per order (spec 010 §13 Q11), when the product is in scope, every line is eligible: the bouquet, its date surcharge and its add-ons (§13 Q2). When a basket arrives, eligible lines become each in-scope product with its own add-ons and surcharge; the functions already take a list.

**Counting uses** (`lockAndCount`). Inside the placing transaction: `SELECT … FROM discount_code WHERE id = $1 FOR UPDATE`, then count `order_discount` rows of the same `mode` whose order's status is **not** in `abandoned`, `payment_failed`, `cancelled`, `cancelled_refunded` (spec 002 §14 A6's names), in total and for this `email_key_sha256`. No counter column is kept, so nothing needs releasing: an order that is never paid, or is cancelled before we start preparing it, stops counting by its status alone. A refund on a delivered order does not change the count. `demo` and `test` orders never count against `live` caps.

**Zod schemas:**
- `DiscountCodeInputSchema`: admin create and edit: `{ code (6..32 after normalising, unique), campaignLabel (1..80), kind, percentBp?, currencies: { currency, amountOffMinor?, minOrderMinor }[], startsAt (ISO with zone), endsAt?, maxRedemptions?, maxPerEmail?, countryIds: uuid[], productIds: uuid[], note? }`, with the cross-field rules of §5.1 repeated so the form shows them per field before the database would refuse.
- `IssueCodeInputSchema`: the same plus `source: 'admin' | 'referral'` and `issuerRef?`; `issueCode` parses it. Only `source: 'admin'` is reachable from any screen.
- `ApplyDiscountSchema`: `{ code: string (1..64 raw) }` from step 3's form body. `RemoveDiscountSchema`: `{}`.
- `DraftDiscountSchema`: the draft's applied code id plus the evaluated amount and allocation, included in what spec 010's `draftTotals()` returns.
- `ReviewStepSchema` (spec 010) is unchanged: its `confirmedTotalMinor` is now the discounted total when a code is applied, and the server's comparison does the rest.
- `OrderDiscountSchema`: the `order_discount` row as a type. `DiscountFinanceRowSchema`: `{ orderId, reference, placedAt, mode, codeId, campaignLabel, currency, grossBeforeMinor, discountMinor, chargedMinor, vatMinor, payoutMinorInBase, baseCurrency, grossBeforeBaseMinor, discountBaseMinor, chargedBaseMinor, marginAfterBaseMinor }`.
- Event payloads: `order.placed` (spec 010's `OrderPlacedV1`) gains the optional additive fields `discount_code_id` and `discount_minor` (allowed by `plan/11` §2, "adding a field is additive"). The code string is never in a payload.

**Server actions:**
- `applyDiscountAction` (spec 010's step-3 form, Origin-checked like every server action): load the draft by cookie, re-run `checkoutMode()`, check the flag for the destination, check `isLocked`, parse, normalise (null means `unknown`), look the code up, count (outside a lock: an advisory count, the binding one is at placement), `evaluateCode`; on success store `discount_code_id` on the draft and re-render step 3 with the new totals; on failure `recordFailure` (only for `unknown`, `not_started`, `ended`, `wrong_*`, `below_minimum`; caps do not count as guesses) and re-render with the reason's message, the typed value kept.
- `removeDiscountAction`: clears the draft's code, re-renders.
- `placeOrderAction` (spec 010) gains one step, after the quote and date re-checks and before `orderService.place`: when the draft has a code, `lockAndCount` and `evaluateCode` again in the same transaction. A refusal or a different amount writes nothing, clears the code from the draft only on refusal, and re-renders step 3 with `checkout.discount.changedAtPlacement` naming the old and new totals; the buyer must press the button again. On success `place` writes the lines with their `discount_minor`, the discounted `buyer_total_minor` and `base_total_minor`, the `vat_breakdown` of the paid amounts, and the `order_discount` row, in the one transaction spec 010 already uses.
- Admin: `createDiscountCode`, `updateDiscountCode`, `disableDiscountCode` in `modules/admin`, each `requirePermission('discounts.write')` first, then `withAdminContext({ action })`, then `issueCode` or the update; `discounts.read` for the list and detail. `ADMIN_PERMISSIONS` gains `discounts.read` (admin, finance) and `discounts.write` (admin).

**Read models:**
- `linePaidAmounts(orderId): { lineId, kind, paidMinor, currency, vatRateBp }[]` in `modules/orders` (spec 020's refund page; spec 018's invoice).
- `discountFinanceRows(filter: { from, to, codeId?, countryIso?, mode? }): DiscountFinanceRow[]` and `codeStats(codeId): { liveUses, discountByCurrency: Money[] }` in `modules/discounts`. Margin after discount = charged net of VAT minus florist pay, in the base currency at the order's FX snapshot; florist pay is read from `order_line.partner_payout_minor` once routed, else shown as "not yet assigned" (no estimate is invented). Processor fees are spec 030b's to add when spec 013's payment rows carry them.

**Jobs:** none.

## 8. Compliance considerations (mandatory)

- **Data flows → RoPA** (`docs/compliance/ropa.md`). The existing "Live orders" row (spec 010 §8 row 3, spec 013) gains: "the discount code used, its amount, and a hashed key of the buyer's email for the code's per-buyer limit (purpose: apply the promotion the buyer chose and keep its limits; basis Art. 6(1)(b); retention with the order and its accounting record; recipients: none beyond the existing processors)". No new processor, no new subject. The checkout-drafts row gains "the code typed, until placement". Admin users' actions on codes are in `audit_log` (spec 012's existing row).
- **Price shown = price charged (`plan/07` §4; `CLAUDE.md`).** The total on step 3, in the button and on the confirmation is the discounted total, which is `order.buyer_total_minor`, which is the amount spec 013 charges. A code that stops working between applying and paying is never charged at either amount silently: placement stops and shows both totals (AC-14).
- **Schema price = visible price.** The product page's visible price and its `Offer.price` are the public price; neither ever reflects a code (AC-20).
- **Price-reduction rules, EU (Omnibus Directive 2019/2161, which added Art. 6a to the Price Indication Directive 98/6) and UK (DMCC Act 2024 Part 4, which replaces the unfair-trading regulations, and the CMA's pricing guidance).** Our position, for the lawyer to confirm ⚖️:
  1. We show **no reference price**: no strike-through, no "was", no "RRP", no "you save X %" and no percentage in any discount element on buyer pages. The discount line states only the amount taken off today's price for this order.
  2. A code typed by the buyer is a reduction for the members of a group, applied at checkout to the price on the page. The Commission's guidance on Art. 6a (2021/C 526/02) places individualised reductions and loyalty schemes outside Art. 6a; whether a code handed to a community group's members counts as one is the lawyer's call. Where a code is announced publicly with a percentage (a poster, a community post), we treat it as a reduction announcement: the percentage must be true against the 30-day lowest price of every product in scope. The admin's reduction-claim warning (§2) flags any product whose price was lower in the last 30 days, so the founder can narrow the products or the wording. The UK position is the same in substance: a percentage must not mislead about the saving.
  3. We never raise a price before a promotion to offset it: spec 012b's price-change screen already shows the 30-day lowest price beside any change.
  4. Codes are not personalised pricing by automated decision-making (CRD Art. 6(1)(ea)): a person typed the code; no profile chooses the price.
- **VAT on the discounted amount 🧾.** A discount given at the time of sale reduces the taxable amount (VAT Directive 2006/112 Art. 79(b); HMRC's VAT Notice 700 treats an unconditional discount at the time of sale the same way). We compute VAT on each line's paid amount at that line's rate (§2). The operating entity is now a Wyoming LLC (PR 348); the VAT treatment of our sales (principal or agent, registrations) is the accountant's open question before any real charge (`plan/06` §4), and this spec only fixes the arithmetic, which holds under either model because it spreads the discount by line and keeps rates per line. The accountant confirms (a) VAT on paid amounts with the discount spread by value, (b) how the invoice shows it (spec 018), (c) whether the florist's self-billing statement is untouched (it is, by design).
- **Unfair terms and clarity:** each code's limits that can refuse it (end date, minimum, destinations, bouquets, once per buyer) are stated in the refusal message the moment they apply; the founder states them in any announcement (runbook).
- **Geo-blocking (EU 2018/302, ADR-0006):** a code may be limited by **destination** (the service is different) but never by the buyer's country, IP, nationality or language. `evaluateCode` takes no buyer-country, IP or locale argument (signature test, AC-29).
- **Logs and PII:** the code string, the email key, and the buyer's email never appear in logs, Sentry or analytics. Logged: `request_id`, `draft_id`, `order_id`, `discount_code_id`, `reason`, `mode`, `country_iso`. The logger's redaction list gains `code`, `discount_code`, `promo`, `coupon`; Sentry's `beforeSend` already drops checkout bodies (spec 010 §8).
- **Security:** the per-checkout lock and the site alert; codes are not secrets but are treated as such in logs; caps enforced under a row lock; Origin checks on every action; zod at every boundary; RLS keeps codes and order discounts away from public and florist roles.
- **Accessibility (WCAG 2.2 AA):** §5.3's rules; axe zero serious or critical on step 3 with the control in each state, in four locales; keyboard-only apply and remove.
- **Honesty and buyer voice:** no buyer key mentions a florist, a partner or fulfilment (`RELAY_PATTERNS`, spec 041 §14; AC-31). The campaign label (which may say "partner") is never rendered to a buyer.

## 13. Open questions

The spec stays `proposed` until the founder answers; each has the default this spec is written against.

- **Q1 How big can a discount be?** Default: **1 % to 50 % for percent codes; a fixed amount at most half the code's minimum order in that currency; no free orders.** A free order needs a no-payment path that does not exist. Alternative: allow up to 100 % (needs a new payment-free order path in spec 013).
- **Q2 What does a percent code apply to?** Default: **the whole order for a bouquet in scope: bouquet, date surcharge and add-ons.** Simple for the buyer ("10 % off your order"). Alternative: the bouquet only, which protects add-on margin but reads as smaller.
- **Q3 Where is the code typed?** Default: **checkout step 3 only, behind a quiet "Add a discount code" link.** An open empty box makes buyers leave to hunt for codes. Alternatives: on step 1, or on the product page (the product page would then need a no-cache path).
- **Q4 Once per buyer by default?** Default: **yes, once per buyer email per code, with `+tag` aliases counted as the same email.** Alternative: unlimited per buyer unless set.
- **Q5 Does a use come back when an order is not completed?** Default: **yes when the order is never paid or is cancelled before we start preparing it; no after a refund of a delivered order.** Alternative: every placed order uses up the code for good.
- **Q6 Below-cost protection.** Default: **a warning on the admin screen before saving, never a block at checkout.** The founder decides to absorb the cost. Alternative: refuse to save a code that would sell any in-scope bouquet below the highest florist pay.
- **Q7 Reduction claims (Omnibus and UK rules) ⚖️.** Default: **no strike-through, no "was" price, no percentage on buyer pages; the discount line shows only the amount off today's price; announcements by us or by community groups quote the percentage only if every in-scope price has not been lower in the last 30 days (the admin warning shows this); the lawyer confirms.** Alternative: show "was/now" prices, which needs the 30-day lowest price on every page that shows them and a lawyer's sign-off first.
- **Q8 VAT on the discounted price 🧾.** Default: **VAT on what the buyer pays, with the discount spread over the lines by value, each line at its own rate; the accountant confirms under the Wyoming LLC before the first real charge.** Alternative: whatever the accountant rules; only `allocateDiscount` changes.
- **Q9 Do codes work on demo orders?** Default: **yes, so the founder can try them on the live site; demo uses never count against real caps.** Alternative: real and test orders only.
- **Q10 Code format.** Default: **6 to 32 letters and digits, case and hyphens ignored; "Generate" makes a 10-character code that is hard to guess.** Alternative: allow other characters (Polish letters), which makes codes harder to type on foreign keyboards.
- **Q11 Should a wrong code say why?** Default: **yes for real codes (ended, minimum not reached, wrong destination), one generic message for codes that do not exist or are disabled.** Alternative: one generic message for everything (safer against guessing, less helpful).
- **Q12 Which admin roles?** Default: **`admin` creates and edits; `finance` reads.** Alternative: `admin` only.
- **Q13 Time zone for start and end.** Default: **entered in UK time (Europe/London) with the zone shown and changeable per code; stored in UTC.** Most promotions are for UK communities. Alternative: the destination's time zone.
- **Q14 The switch.** Default: **off everywhere until the founder turns it on per destination in admin.** Alternative: on for Poland from the first deploy.
- **Q15 (opened by §14 A-orchestrator-2026-10-25; design gap G8 of PR 426): A code and checkout express on step 3.** Spec 013's express panel sits at the top of step 3 "Your details" and places the order without passing step 4, where the code control is, so a buyer with a code who taps Apple Pay on step 3 would pay without it. **Recommended default (Option B, drawn in PR 426): the same quiet `<details>` control "Add a discount code" also renders on step 3, directly above the express panel, whenever the panel renders and the flag is on for every line's destination. Applying or removing a code there re-renders step 3; the compact block then lists the discount line and the reduced total, and the wallet amount (spec 013 X.2) is that reduced total. A code applied on either step shows on the other. Spec 050's friend's offer and store credit, which apply without a buyer action, are in that total either way and listed in the block; "Keep my credit for later" stays on step 4.** Alternative (Option A): the panel steps aside (is not rendered) while the draft holds any reduction or the code control is open, so those buyers pay on step 4.
