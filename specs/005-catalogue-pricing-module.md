## 1. Problem

Every money-bearing page in Phase 0 and Phase 1 reads the same three answers: *what is this product*, *what does it cost to send it to this destination in this currency*, and *can it be sent at all*. Nothing in the repository can answer any of them. `src/modules/catalog` is an empty barrel whose owning-spec comment already says "spec 005" (`docs/architecture.md` §3); spec 002 shipped the columns on paper only and is parked (TASK-013 `blocked`, no Neon project); spec 003 shipped `formatMoney` with nothing to format; spec 004 is shipping a `Grid` primitive and a `Media` wrapper with nothing to put in them and a currency chip that is text. `plan/09` reserves 22–28 Sep 2026 for "`005` catalogue + pricing module (products, tiers, add-ons, `country_price`, FX)", and specs 006 (seed import), 007 (corridor), 008 (shop/category/occasion), 009 (PDP), 010 (checkout), 012 (admin), 013 (payments) and 018 (invoices) are each a consumer of this module's read API. Written after them it is a refactor of seven specs; written now it is the contract they are built against.

Two invariants make this the highest-consequence spec of the phase, and both are cheap now and expensive later. The first is **`CLAUDE.md`'s money rule**: prices are integer minor units plus a currency, VAT and delivery are included, the price shown is the price charged, and the price in `Offer` schema equals the price on the page to the cent (`plan/02` §9, `plan/04` §2.2, `plan/07` §4). That is not a coding convention — under the Price Indication Directive, the CRD as amended by Omnibus and the UK DMCC's drip-pricing ban it is the law, and under `plan/02` §15 a structured-price that disagrees with the visible price is a manual-action risk. The second is that **prices differ by destination and never by buyer** (`plan/07` §3, EU 2018/302): the whole pricing surface is keyed on the destination country in the URL, with display currency a cookie-level presentation choice that must not fragment cached HTML (`plan/03` §1, `plan/02` §3). Both invariants are structural, so this spec spends its design budget making them *unexpressible to break* rather than documented.

Three constraints shape the design more than `plan/06` §2.2 does. **There is no database**: spec 002 is parked, so 005 must be implementable, testable and demoable with no Postgres at all, behind the same provider seam spec 003 used for the locale registry and spec 004 used for countries, links and company identity. **This module adds no client JavaScript**: spec 004 §14 A1 measured 1 434 B of headroom on locale documents against the corrected 128 KB Brotli budget, and the homepage islands still to land are already spoken for — so every read function in 005 is server-side, and the client-side currency repaint that consumes 005's price table is spec 008's island, paid for from 008's budget. **`fo/no-float-money` is still disabled** (spec 001 TASK-004: "fixture-only in 001, enforced from spec 005"); spec 002 §2 promised to bring it forward, spec 002 is parked, so this spec is the first code with money in it and enabling the rule is its first task.

## 2. Scope

Each bullet is testable; §9 names the AC.

**The no-database seam (read this first)**

- `src/modules/catalog/` is the module (the name is `plan/01` §5's, `docs/architecture.md` §3's row and spec 001's lint fixtures' — not `catalogue`, §5.2). Pricing lives **inside** it as `catalog/pricing/*`, because `plan/01` §5 assigns "products, categories, occasions, **pricing**, translations" to one module; no `pricing` module is created and no module boundary is added.
- `CatalogueProvider` (products, tiers, categories, occasions, tags, add-ons, media links, translations) and `PriceProvider` (`country_price`, `addon_country_price`, price history) and `FxRateProvider` (`fx_rate` rows by `as_of`) are three interfaces with **one** implementation each in Phase 0: `staticCatalogueProvider`, `staticPriceProvider`, `staticFxRateProvider`, all backed by repo data (below). Spec 002/006 add `dbCatalogueProvider` / `dbPriceProvider` / `dbFxRateProvider` behind the same interfaces and swap the composition root **inside** `src/modules/catalog`; no file under `src/app/`, `src/modules/seo/`, `src/modules/ui/` or `src/emails/` changes. A unit test asserts the barrel exports no provider object, no dataset path and no `drizzle`/`postgres` import (AC-2), and `pnpm check:no-db` covers the module and the new config files.
- **Callers never touch a provider.** Everything outside the module uses the barrel functions of §5.2 (`getProduct`, `listProducts`, `resolvePrice`, `priceProjection`, `priceTable`, `fromPrice`, `availability`, `quote`, `cacheTagsFor`).
- **The dataset is authored once, here, and projected for spec 002 and 006.** `src/config/catalogue/` holds `products.data.ts`, `tiers.data.ts`, `categories.data.ts`, `occasions.data.ts`, `addons.data.ts`, `prices.data.ts`, `fx.data.ts` — plain constants, zod-parsed at module load, no imports beyond the schemas — plus `toProductRow()`, `toProductTierRow()`, `toCategoryRow()`, `toAddonRow()`, `toCountryPriceRow()`, `toAddonCountryPriceRow()`, `toFxRateRow()` projecting **exactly** spec 002 §5.1's column sets, each pinned by a unit test in the `toLocaleRow()` / `toCurrencyRow()` precedent (spec 003 AC-4). When 002 unparks, its seed and 006's importer read the projections rather than restating the catalogue, so the two cannot drift (§13 Q9).
- Dataset content: the **84-SKU skeleton** of `plan/10` §2.1 (40 bouquets, 14 arrangements, 8 plants, 10 funeral, 12 gift sets) with the six facets of `plan/10` §1.1, the tier structure of §2.2, the 6 add-ons of §1.1, the price bands of §2.3 for the 8 seeded countries, and one committed ECB rate snapshot. Deliberately **absent**: product descriptions, imagery, `de`/`pl` translations, reviews, partner payouts beyond the seed share (§3).

**Taxonomy (`plan/10` §1.1)**

- Six facets on one product record: `product_type` (exactly one), `occasion` (many), `flower_type` (many, one primary), `colour` (many, one primary), `price_tier` (derived per country), `style` (one) — plus the attributes of `plan/10` §1.1 (stem-count tiers, vase flag, freshness days, allergen note, substitution class, `partner_only`). Every facet value is a **key**, never a label; labels resolve through the message catalogue (§7).
- Read API for categories, occasions and tags with the counters the page loaders need: `countProductsIn(category, country)` and `countProductsFor(occasion, country)`, which are the **six-product rule** of `plan/02` §6 as a function rather than a judgement, and `hasIndexableProducts(country, locale)`. 005 supplies the counts; 008 enforces the threshold in its loader.
- Facet resolution for URL-driven filtering: `resolveFacets(searchParams)` returning a parsed, canonical, order-independent facet set plus an `indexable: false` verdict for every parameterised combination (`plan/02` §7 — facets are `noindex` query parameters, and only an authored path like `/poland/flowers/red-roses` is indexable; 005 exposes `isAuthoredFacetPath()` returning `false` for everything in Phase 0).

**Tiers and add-ons**

- `product_tier` read model: `tierKey`, `labelKey`, `stems`, `sort`, plus **`isDefault`** (the tier preselected on the PDP; `plan/04` A/B test #2 is "12 vs 18 stems", so which tier is default must be data — schema amendment request, §13 Q8). Tier steps follow `plan/10` §2.3 (~+30% and +60% from the smallest) but the **stepped amounts are authored rows, not computed at render**: a percentage applied at render is a float and a rounding bug (§5.2).
- Add-ons are a separate entity priced per destination country (`addon_country_price`), never bundled into the product price, always **default off** (CRD Art. 22, `plan/07` §2.1: no pre-ticked extras — asserted by AC-19, there is no `defaultSelected` field to set), and carrying their **own VAT rate** where it differs from flowers (PL: chocolates 23% vs flowers 8%, `plan/06` §4 must-confirm item 4 — schema amendment request, §13 Q3/Q8).
- `wine` is behind the feature flag `addon.wine.{country}` (`plan/10` §1.1 "disabled where unlicensed"); `cake` is `partner_only`; `card` is priced 0 and still rendered as a line so the invoice and the summary agree.

**Pricing (`plan/01` §4.3, `plan/06` §2.2, `plan/07` §4)**

- One money type, `Money = { amountMinor: bigint-safe integer, currency: CurrencyCode }`, reusing spec 003's `MoneySchema` and `formatMoney`; **`formatMoney` stays the only formatter in the codebase** and 005 adds no `Intl` call (`fo/no-adhoc-intl` already forbids it).
- `resolvePrice({ productId, tierKey, countryIso, deliveryDate? })` → `PricePoint { amountMinor, currency, vatRateBp, vatAmountMinor, netAmountMinor, deliveryIncluded: true, surcharges: Surcharge[], activeFrom, activeTo, priceVersion }`, read from the single active `country_price` row per (product, country, tier, surcharge) that spec 002's partial unique index guarantees. **There is no variant of this function that returns a price without VAT, without delivery or without the date's surcharges**: the all-in amount is the only amount the type can carry, which is how `plan/07` §4's drip-pricing prohibition becomes unexpressible to break rather than reviewed for.
- Surcharges (Sunday +€4 equivalent, Valentine's/Women's Day +€6 equivalent, `plan/10` §2.3) are `country_price` rows with `surcharge_kind` and date bounds, returned by `dateSurcharges(countryIso, dateRange)` so 009 can put the amount **on the date chip before selection** (`plan/07` §4). Never computed with a multiplier.
- `vatBreakdown(lines)` → per-rate integer `{ rateBp, netMinor, vatMinor, grossMinor }[]`, mixed rates supported (PL 8% flowers + 23% add-ons), summing to the gross total exactly (property test, AC-13). This is the input to `order.vat_breakdown` (spec 015) and the invoice (spec 018); 005 computes it and stores nothing.
- `lowestPriceInLast30Days(productId, tierKey, countryIso, asOf)` over the superseded price history — the Omnibus Art. 6a figure (`plan/07` §2.1). No "was/now" UI exists in Phase 0 and none may be added without this number.

**FX and rounding (`plan/01` §4.3, `plan/06` §2.2, `plan/13` B7)**

- All conversion is integer arithmetic: `amountMinor × rate_ppm × (10 000 + FX_BUFFER_BP) / (1 000 000 × 10 000)`, with `FX_BUFFER_BP = 250` (2.5%, `plan/06` §2.2, B7 default) as named config, then **psychological rounding upward** to the target currency's `roundingStyle` from `src/config/currencies.ts` (`x99 | x90 | x9 | none`). Upward, never nearest: rounding down could put the charged amount below the converted cost, and the buffer exists to absorb intraday movement, not to be eroded by rounding.
- `convert(money, toCurrency, rate)` is pure and total; `fxRateFor(base, quote, asOf)` fails **closed**: when the newest rate is older than `MAX_FX_AGE_HOURS` (default 48) the function returns `null`, the caller falls back to the destination country's own currency, and the page renders the native price rather than a guessed one. A stale rate never becomes a displayed price.
- The **displayed currency in cached HTML is the locale's default** (`plan/02` §3, `plan/03` §1) — never the cookie, never a header — so cached HTML is byte-identical for every visitor and carries no `Vary`. `priceTable(product, country)` emits the small JSON table of prices in the supported display currencies that `plan/02` §3 requires, embedded in the HTML for 008's island to repaint from without a fetch, with the `fxAsOf` date and the rate stamped in it so the repaint cannot invent a rate.
- `fx.refresh` (declared in spec 002 §5.2, daily 06:00 CET, ECB reference rates) gets its implementation only when the database exists (§12 task 12). Phase 0 uses the committed snapshot in `fx.data.ts`, dated, so every price in the demo is reproducible and every test is deterministic.

**Availability (data model here, UI and date maths elsewhere)**

- `availability({ productId, countryIso, date? })` → `{ schemaAvailability: "InStock" | "OutOfStock" | "PreOrder", reasonKey, saleable: boolean }` derived from data only: `country.status`, `product.status`, an active `country_price` row, and ≥1 active partner able to fulfil the product with coverage in the destination (`partner_catalog_mapping.can_fulfil` + `partner_coverage`). A `demo` country is `saleable: false` with `reasonKey = "country.demo"` and emits **no** `Offer` at all (ADR-0007, `plan/02` §9).
- **Availability by date is a seam, not an implementation.** `CutoffEvaluator` (`nextAvailableDate`, `isDateAvailable`, `cutoffFor`) and `CapacityProvider` (`remainingCapacity(city, date)`) are declared here with the types 009 and 031 implement and a `staticCutoffEvaluator` good enough for tests (cutoff local time + IANA zone from `country`, weekly days, holiday list). 005 owns no date arithmetic, no holiday evaluation and no occasion-date rule (`plan/03` §9, §10 → spec 009).

**Read-side API, caching, boundaries**

- Every exported read function is server-side, synchronous or `async` over a provider, zod-parsed at its boundary (`plan/12` §2), and returns a view model — **the same view model the UI renders and `modules/seo`'s JSON-LD builder reads** (`plan/02` §15's "structured data ≠ visible content" guard is discharged by construction: `priceProjection()` has exactly one caller shape and AC-11 pins that the offer projection's `price` is the projection's `displayPrice`).
- `cacheTagsFor(entity)` returns the `plan/01` §3 tag names (`catalog:{country}`, `product:{id}`, plus `country:{iso}` for status flips) so 007/008/012 invalidate through `src/lib/cache.ts` and no module string-builds a tag.
- **No pricing function accepts a buyer country, IP, header or locale-derived location** (EU 2018/302, ADR-0006). A signature test enumerates every exported pricing function and fails on a parameter matching `/buyer|ip|geo|visitor/i` (AC-18) — the geo-blocking prohibition as a gate.
- `fo/no-float-money` **enabled** in `eslint.config.mjs` for `src/`, `seed/`, `scripts/` and `src/config/` in this spec's first task (spec 001 TASK-004's "enforced from spec 005"; spec 002 AC-6 becomes a regression check when it unparks).

**Docs, fixtures, gates**

- `tests/fixtures/catalogue.ts`: the price-band table of `plan/10` §2.3 as expected values per (tier, country), an FX conversion table with hand-computed integer expectations, and a mixed-VAT basket — the shared corpus 008/009/010/013/018 assert against.
- `pnpm catalogue:check` (new script + CI job on `needs: typecheck`, the placement rule of spec 001 §14 A9): dataset integrity (every SKU has ≥1 tier and ≥1 active price per seeded country; every price inside its `plan/10` §2.3 band; exactly one active row per (product, country, tier, surcharge); exactly one default tier per product; every facet value in the taxonomy; every `labelKey` present in `messages/en.json`; no product with a `de`/`pl` translation that is unreviewed **and** referenced as indexable), and the projection column sets.
- `docs/runbooks/pricing.md` (new): how a price is set and superseded, how to read a `PricePoint`, what happens when FX is stale, how the 30-day-lowest figure is produced, and the checklist for changing a band. `docs/architecture.md` §2 (the new config directory) and §3 (the `catalog` row moves from "empty barrel" to its Phase 0 state). `.env.example` + `src/lib/env.schema.ts`: nothing new (FX has no key until task 12).

## 3. Non-goals

- **Any page, route, component or rendered surface** → 007 (corridor), 008 (shop/category/occasion, the currency menu, the `fo_currency` write and the client repaint island), 009 (PDP, date picker, price block, `aria-live` price announcements), 010 (checkout). 005 ships view models and no JSX.
- **The JSON-LD builders themselves** (`Product`, `Offer`, `OfferShippingDetails`, `MerchantReturnPolicy`, `AggregateOffer`) → spec 007 `modules/seo/schema/*`. 005 ships `offerProjection()`, the typed input those builders consume, and the test that its price equals the visible price (AC-11).
- **Cutoff, holiday, occasion-date and time-zone arithmetic** (`plan/03` §9, §10) → spec 009; **capacity** → 024/031. 005 declares the two seams and a test-grade static evaluator, and owns no calendar.
- **Product descriptions, imagery, prompts, R2 objects and image variants** → spec 006 and ADR-0014. 005's dataset carries names, slugs and facets; a product with a null description is non-indexable and 005 makes that queryable (`isProductIndexable`, §7) rather than filling it.
- **`de`/`pl` translation content** → founder + native reviewer (`plan/13` B12) through spec 003's `i18n:draft` and spec 012's queue. 005 adds `en` message keys only.
- **Migrations, RLS, seed scripts, `db:check`** → spec 002, unchanged and not re-specified. Where 005 needs a column 002 lacks it is a **schema amendment request in §13 Q8**, never a silent change and never a migration written here.
- **Partner payouts, margin views and routing** → `partner_catalog_mapping` is spec 002's table, admin's margin view is 012's, routing is 016's. 005 reads no payout and computes no margin: the retail price is independent of which partner fulfils (`plan/06` §3).
- **Orders, baskets, order lines, `orderService.transition`** → 010/013/015 (ADR-0009). `quote()` returns a stateless, unstored price quote; it writes nothing and touches no order table.
- **Payments, presentment, settlement, Stripe/Mollie currency support** → 013/014. 005 says what the price is; 013 charges it and records `fx_rate_snapshot` on the order.
- **Search, ranking, "sorted by bestsellers" and its Omnibus disclosure** → 008. 005 exposes a deterministic default sort key and no relevance model.
- **"Was/now" price-reduction UI** — deliberately not built (the 30-day figure exists so that it *can* be, lawfully, later).
- **Editing `CLAUDE.md`, `plan/*`, an accepted ADR, or spec 002's text.** Two tensions are recorded rather than resolved: the dataset-ownership contract with 002/006 (§13 Q9) and the currency `roundingStyle` conflict between `plan/10` §2.3 and `src/config/currencies.ts` (§13 Q1).

## 4. User stories

- As a **buyer in London sending to Warsaw**, the £ price on the card, on the product page, in the summary and on my statement are the same number, and it already contains VAT and delivery — so nothing appears later that I did not agree to.
- As a **buyer in Berlin sending to Warsaw**, I see the Polish florist's price converted to EUR at a dated rate and rounded to €x.90, and if I switch the menu to PLN I see and am charged the Polish list price — the two are different numbers for an honest reason and both are exactly what I pay (`plan/03` §1).
- As **Googlebot**, the `Offer` price in the JSON-LD equals the price rendered in the HTML to the cent, in the currency the URL's locale defaults to, and there is no `Offer` at all for a country that is not live.
- As a **French buyer and a German buyer**, we see the same price for the same bouquet to the same Warsaw address, because nothing in the pricing path knows where either of us is (EU 2018/302).
- As the **founder taking Poland live**, the price bands are rows I supersede in admin, and nothing in `src/` changes — including when the first three florists tell me the payout is wrong (`plan/13` B13).
- As the **implementer of spec 009**, "what does this tier cost on this date to this country" is one typed call whose result cannot omit VAT, delivery or the Sunday surcharge, and "when can it arrive" is a seam I fill rather than a number I guess.
- As the **implementer of spec 013**, the amount I hand Stripe comes from a quote the buyer saw, stamped with its FX rate and its expiry, so a capture never differs from a page.
- As the **accountant asking about mixed rates**, the 8%/23% split for a bouquet with chocolates is a function with a property test, not a spreadsheet.
- As the **reviewer agent**, "does the schema price equal the visible price" and "does any pricing function know the buyer's location" are both tests.

## 5. Design

### 5.1 Data model changes (tables, columns, migrations + rollback)

**None in this spec.** No migration file, no rollback file, no `DATABASE_URL` read, no integration test needing Postgres — the same deliberate consequence of spec 002's parked provisioning that shaped spec 003 §5.1 and spec 004. The persistence target is spec 002 §5.1's `catalog` group (`product`, `product_translation`, `product_tier`, `category*`, `product_category`, `product_occasion`, `addon*`, `addon_country_price`, `country_price`, `media_asset`, `media_variant`, `product_media`, `product_media_alt`) plus `geo`'s `currency`, `country` and `fx_rate`, and it is **not restated here**.

| Phase 0 (this spec) | Later owner | Contract that prevents drift |
|---|---|---|
| `src/config/catalogue/products.data.ts` + `staticCatalogueProvider` | spec 002 seed / spec 006 import → `product`, `product_translation` | `toProductRow()` / `toProductTranslationRow()` project exactly 002 §5.1's columns; unit test pins the key lists |
| `tiers.data.ts` | → `product_tier` | `toProductTierRow()`; **needs `is_default`** (§13 Q8) |
| `categories.data.ts`, `occasions.data.ts` | → `category*`, `occasion*`, `product_category`, `product_occasion` | `toCategoryRow()` etc. |
| `addons.data.ts` | → `addon`, `addon_translation`, `addon_country_price` | `toAddonRow()`, `toAddonCountryPriceRow()`; **needs `vat_rate_bp`** and a one-active-row index (§13 Q8) |
| `prices.data.ts` | → `country_price` | `toCountryPriceRow()`; history is superseded rows, never updates |
| `fx.data.ts` (one dated ECB snapshot) | → `fx_rate`, written by `fx.refresh` | `toFxRateRow()`; `rate_ppm` integer |
| `src/config/currencies.ts` `roundingStyle` (spec 003) | already seeded by 002 | 005 is the first consumer; the `plan/10` §2.3 conflict is §13 Q1 |

Three **schema amendment requests** to spec 002 are consequences of this design and are listed as founder decisions in §13 Q8, not applied here: `addon_country_price.vat_rate_bp integer NOT NULL`, a partial unique index `(addon_id, country_id) WHERE active_to IS NULL` mirroring `country_price`'s, and `product_tier.is_default boolean NOT NULL DEFAULT false` with a one-per-product partial unique index. Each is additive, each has a one-line rollback, and each lands inside spec 002's migration `0003` when 002 unparks — which is why they must be answered before 002 is implemented, not after.

Rollback of this spec is `git revert` of its task commits: there is no state to unwind.

### 5.2 API / server actions / jobs / events (zod schemas named)

**Module name ruling.** The directory is `src/modules/catalog`, not `catalogue`. `plan/01` §5, `docs/architecture.md` §3's row ("`catalog` | products, categories, occasions, pricing, translations | spec 005 | empty barrel"), the `MODULES` manifest in `scripts/check-layout.ts` and spec 001 AC-9's lint fixtures (`@/modules/catalog/internal/pricing`) all use the US spelling; renaming would touch three gates and an approved spec's fixtures for an aesthetic. British spelling stays in prose and in the *dataset* directory name (`src/config/catalogue/`), which is a config path and not a module. That path applies if §13 Q9 is answered "005 owns the dataset"; if it is answered "spec 002's seed owns it", the dataset moves to `seed/catalogue/` and the static provider reads it from there with no other change. Default: `src/config/catalogue/`, matching the `src/config/*` precedent 003 and 004 established for zod-parsed, database-free authored data. [agent-inferred]

Zod schemas, parsed at module load (dataset) or at the boundary (`plan/12` §2):

- `ProductSchema`, `ProductTierSchema`, `CategorySchema`, `OccasionSchema`, `AddonSchema` — facet values as closed enums drawn from `plan/10` §1.1, so an unknown `product_type` is a type error and a parse error.
- `MoneySchema` — **reused from spec 003**, not redefined: `{ amountMinor: z.number().int(), currency: CurrencyCode }`.
- `PricePointSchema` — all-in gross plus its own decomposition, refined so `netAmountMinor + vatAmountMinor === amountMinor` and `deliveryIncluded === true`; a `PricePoint` that does not satisfy both cannot be constructed.
- `SurchargeSchema` — `{ kind: "sunday" | "peak_day", amountMinor, currency, appliesFrom, appliesTo, labelKey }`.
- `FxRateSchema` — `{ base, quote, ratePpm: z.number().int().positive(), asOf: dateString, source }`.
- `PriceProjectionSchema` — the single view model: `{ displayPrice: Money, displayLocale, destinationCurrencyPrice: Money, vatRateBp, vatLabelKey, deliveryIncluded, surcharges, fxAsOf?, ratePpm?, priceVersion, availability }`.
- `PriceTableSchema` — `{ productId, tierKey, fxAsOf, entries: Record<CurrencyCode, integer> }`, with a **size refinement**: ≤6 currencies, ≤512 B serialised per tier (§6).
- `AvailabilitySchema`, `FacetSelectionSchema` (canonicalised, order-independent), `QuoteSchema` (`{ quoteId, lines, totalMinor, currency, fxAsOf, ratePpm, priceVersion, expiresAt, digest }`).

Behavioural contracts worth pinning:

- `resolvePrice` reads the **one** active row; two active rows is a data error that throws rather than a silent pick (spec 002's index makes it impossible in Postgres, and `catalogue:check` makes it impossible in the dataset).
- `convert` is pure, total and integer-only; `roundToStyle` is monotone and never returns less than its input.
- `quote()` is stateless: the digest is an HMAC over the quote fields with a server secret, so 013 can verify a quote it did not issue without a table. It contains **no PII** — product ids, tier keys, amounts, currency, rate and expiry only (§8).
- `verifyQuote(quote, now)` returns `expired | tampered | ok`, and on `expired` the caller (010/013) **re-derives and shows the new price for explicit re-confirmation**; a silently higher charge is not reachable through this API.
- No server action, no route handler, no job implementation, no event. `fx.refresh` stays a declaration in `src/jobs/index.ts` (spec 002 §5.2) until task 12.

### 5.3 UI (pages, components, states)

**None.** This spec renders nothing. The states that would normally be enumerated here are the concern of the specs that render this data, and 005's job is to make each one a *value* rather than a code branch:

| State | Rendered by | Made expressible here |
|---|---|---|
| loading | 008/009 (Suspense over a server read; no client fetch on indexable pages) | read functions are awaited server-side, so an indexable page has no loading state at all (`plan/02` §14) |
| empty | 008 (category with <6 products) | `countProductsIn()` returns the count; the threshold is 008's |
| error | 008/009 | `resolvePrice` throws on missing/ambiguous price rather than returning a fake zero; a page with no resolvable price must not render a buy path |
| demo | 007/008/009 | `availability().saleable === false`, `reasonKey = "country.demo"`, no `Offer`, "from" estimate only (`plan/10` §5) |
| disabled | 008 | `product.status = 'retired'` + `retiredAt` supports 200-with-alternatives then 410 (`plan/02` §7) |
| stale FX | 008/009 | `fxRateFor()` returns `null` → projection falls back to the destination currency; the page states the currency it is quoting in, never an unstamped conversion |

### 5.4 Rendering & caching (per plan/01 §3)

- Price-bearing pages stay **ISR** with the strategies `plan/01` §3 already fixes: category/collection 1 h + tag `catalog:{country}`, product 1 h + tag `product:{id}`, corridor 24 h + on-demand when prices change, keyed on locale × country (never on the currency cookie). 005 adds no new rendering mode and no dynamic route.
- **The database is never on the critical path of a cached page** (spec 002 §5.4, and a Neon compute-cost constraint under ADR-0015): a cache hit performs zero reads, and on a miss `resolvePrice` is one query per (product, country) batch, not one per tier.
- **FX and cache freshness — the crux.** The rate can move while HTML is cached. Three mechanisms keep "price shown = price charged" true anyway: (a) the 1 h ISR window plus the daily 06:00 CET refresh bound the staleness to roughly an hour of a single day's rate; (b) the 250 bp buffer exists to absorb intraday movement, so a within-buffer move costs margin, not correctness; (c) the buyer is charged the amount from the **quote** the page issued, valid for the lock window (§13 Q5), and `fx.refresh` additionally calls `invalidate(['catalog:{iso}'])` for every live country so the next request re-renders. When a rate is older than `MAX_FX_AGE_HOURS` the projection stops converting entirely rather than serving a stale number.
- `cacheTagsFor()` is the only tag builder; `src/lib/cache.ts` stays the invalidation seam (a noop until 007/008 wire the Vercel adapter). 005 calls `invalidate()` nowhere — 012's admin price edit and task 12's `fx.refresh` are the first callers, and the tag list they must purge is recorded in `docs/runbooks/pricing.md` so they inherit it rather than guess.
- `generateStaticParams` prebuilding "live countries + top 50 products per locale" is unchanged; 005 exposes `topProductsForPrebuild(country, locale, n)` as the deterministic ordering that build step needs.

## 6. SEO considerations (mandatory)

005 renders nothing, so its SEO surface is *the price and availability data every indexable money page depends on* — and the place where a structured-data manual action would originate if it were wrong (`plan/02` §15).

- **Indexability inputs.** `isProductIndexable(product, locale, countryIso)` is the single predicate 008/009 and the sitemap builder call, and it is derived from data only (ADR-0007, `plan/10` §4): `country.status === 'live'`, `product.status === 'active'`, an active `country_price` row exists, a **non-null description** in that locale, the translation `reviewed`, and spec 003's `isLocaleIndexable(locale)`. A `demo` country yields `false` with no code branch per country, so a country flip is a data flip. Because the predicate and the sitemap query share one function, a `noindex` product can never appear in a sitemap (`plan/02` §10).
- **Canonical and URL pattern.** No URL is created here. 005 supplies the localised slugs (`product_translation.slug`, unique per locale by spec 002's constraint) and the destination-country key that makes one canonical per (locale, country, product) possible (`plan/02` §4.2). Facet parameters are parsed but always `indexable: false`, and `isAuthoredFacetPath()` returns `false` for everything in Phase 0 — so no price- or colour-facet URL can become indexable by accident (`plan/02` §7). No price appears in any URL, ever.
- **hreflang.** Unchanged mechanism (spec 003 `alternatesFor()`, spec 007 renders it). 005's contribution is that a locale with no reviewed product translation is excluded by `isProductIndexable`, so an alternate never points at a page that would be `noindex` (`plan/02` §8).
- **Schema.org — the price identity.** `offerProjection()` is the typed input to spec 007's `Offer` builder and is derived from the **same `PriceProjection`** the price block renders: `price` = `displayPrice.amountMinor` formatted to the currency's exponent, `priceCurrency` = the locale's default currency (the same one in the HTML — the cookie override never changes the JSON-LD, because the override is a client repaint on identical cached HTML, `plan/02` §3), `availability` from `availability()`, `eligibleRegion` = destination ISO, `priceValidUntil` = the active row's `active_to` (or the FX snapshot's validity where a conversion is involved), `shippingDetails.shippingRate = 0` because delivery is included in the price by definition, `hasMerchantReturnPolicy = MerchantReturnNotPermitted` (perishables, `plan/07` §2.1). **Exactly one `Offer`** per PDP, which spec 002's partial unique index guarantees, and **no `Offer` for a non-live country**. AC-11 asserts the identity `offerProjection().price === renderedDisplayPrice` on a fixture matrix, and spec 001's `validate-schema` CLI already carries an `Offer.price == visiblePrice` check that this makes satisfiable.
- **`AggregateOffer` and "from" prices.** Country-scoped category pages show `fromPrice()` as *visible* text only and emit no `Offer` (a from-price is not the price of any purchasable configuration, so publishing it as an `Offer` would break the price identity). Country-**less** hubs (`/{loc}/flowers/roses`) have no destination and therefore no currency of supply: in Phase 0 they show no money at all, which is §13 Q10's default and the only option that cannot mislead.
- **Thin content.** The one real risk this module could create is price-variant page inflation: the same product at N country URLs (`plan/02` §4.2) and, worse, a page per display currency. Both are refused structurally — currency is never in a URL and never varies HTML, and products are indexable only in `live` countries, so N is 1 for years. A product with no description is non-indexable rather than filled with generated copy (spec 002 §6). No price range, price band or "under X" page is created (those are facets until demand proves them, `plan/10` §1.1).
- **CWV budget.** 005 ships **zero client JavaScript** (AC-3, asserted against spec 004 §14 A1's 128 KB Brotli ceiling and the 1 434 B of remaining headroom on locale documents): all reads are server-side, and the currency repaint island is 008's, paid from 008's budget. The only page-weight cost 005 adds is HTML: the embedded price table, capped by `PriceTableSchema` at ≤6 currencies and ≤512 B serialised per tier (~1.5 KB for a three-tier PDP before compression), which is the price of avoiding a client fetch for a currency switch and is cheaper than any alternative. TTFB on ISR misses is bounded by the batched query shape of §5.4.
- **Crawl efficiency and quality gates.** `pnpm catalogue:check` is a build gate, so a dataset that would produce an indexable page with no price, no description or an out-of-band price fails CI rather than reaching Googlebot. **Re-enabling `fo/no-float-money` is part of this SEO story, not only a code-hygiene one**: a float in a price is how the JSON-LD and the HTML come to differ by a cent, which is exactly the structured-data mismatch `plan/02` §15 lists as a manual-action risk.

## 7. i18n considerations (mandatory)

- **New message keys, namespace `catalog`** in `messages/en.json` (`en-gb` overrides only where British wording differs; `de`/`pl` re-drafted by `pnpm i18n:draft` and therefore unreviewed, which correctly keeps those locales non-indexable — spec 003 §6):
  - `catalog.tier.stems` — ICU plural, `{count, plural, one {# stem} other {# stems}}`; **Polish is the acid test** (few/many/other, `plan/03` §7) and is a required unit-test case.
  - `catalog.tier.size.{s,m,l}` for arrangements, `catalog.tier.single` for plants (`plan/10` §2.2).
  - `catalog.price.inclusive` — the VAT-and-delivery wording, authored per locale ("incl. VAT and delivery", "inkl. MwSt. und Versand", "w tym VAT i dostawa"), because the phrasing is a legal formula in DE and PL, not a translation (`plan/07` §4, `plan/02` §13).
  - `catalog.price.from` — `{price}` interpolated, never concatenated.
  - `catalog.addon.{key}.name` / `.description` for the six add-ons; `catalog.addon.allergen` for the gift sets that need it.
  - `catalog.facet.{facet}.{value}` for every taxonomy key of `plan/10` §1.1 — this is why facets are keys in the data.
  - `catalog.availability.{inStock,outOfStock,countryDemo,noPartner,fxUnavailable}` — every `reasonKey` §5.2 can return has a string, so no state renders untranslated.
  - `catalog.surcharge.{sunday,peakDay}` for the date chip (`plan/07` §4 requires the surcharge to be legible *before* selection).
- **Product names are not message keys.** Evocative names ("Amber Hour", "Vistula Red") live in `product_translation` and stay untranslated by convention (`plan/10` §2.2: the name stays, the descriptor localises); they are registered in `content/i18n/glossary.en.md`, whose "Product and tier names" row was written for exactly this moment ("When spec 005 names a bouquet tier, it lands in this table before it lands in a catalogue"). Tier **labels** are keys; tier **names** do not exist.
- **Formatting.** `formatMoney` from spec 003 is the only money renderer and 005 constructs no `Intl` object (`fo/no-adhoc-intl` allows only `format.ts`/`collate.ts`). VAT rates go through `formatPercentFromBasisPoints`, so "19 %" (de, with the space) and "23%" (pl) are CLDR's problem and not ours. Currency symbol placement, grouping and the ISO code in `aria-label` are spec 003's decisions, including the `en-150` GBP placement ruling that spec 003 §14 explicitly assigned to `src/config/currencies.ts` — i.e. to this spec if a per-currency display override is ever needed (default: none needed; §13 Q1 keeps the file the single home).
- **Locale default currency, not the cookie.** `priceProjection(locale, …)` takes the locale and uses its `currencyDefault`; the `fo_currency` cookie is read by 008's island only. This is what keeps cached HTML identical for everyone and is the i18n rule most easily broken by a well-meaning "just read the cookie server-side" — so no 005 function accepts a currency override at all except `priceTable()`, which enumerates *all* supported ones (AC-9).
- **RTL.** No layout ships, so nothing to mirror; the two rules 005 hands forward in `docs/runbooks/pricing.md` are that a price is rendered by `formatMoney` (which yields correctly ordered symbol and digits under `dir="rtl"`) and that any product name or card message rendered beside a price is wrapped in `<bdi>` (spec 003's rule, first applicable in 009/010).
- **Address and phone formats**: not touched; they are spec 003's config and spec 010's forms. Delivery **address** never enters a price (the price is keyed on country, and — from 009 — on city only for availability, never on postcode-level pricing), which is also what keeps geo-blocking compliance simple.
- **Translation review plan and `noindex` gating.** The dataset ships `en` only. A product is indexable in a locale only when its translation exists, is `reviewed` and carries a description (§6), so an unreviewed machine draft can never be indexed; `catalogue:check` fails if the dataset marks a locale indexable while its translation is machine-unreviewed. `de`/`pl` catalogue copy is a founder/reviewer activity (`plan/13` B12), not a task here.

## 8. Compliance considerations (mandatory)

- **Data flows added → RoPA: none.** The catalogue holds no personal data — no subject, no category, no basis, nothing to record — and `quote()` deliberately keeps it that way (below). `docs/compliance/ropa.md` is therefore unchanged by this spec, and that is the substantive answer rather than an omission: the first row this module could ever cause is spec 013's payment record.
- **Price display law — the core of this section.** `plan/07` §4 and `CLAUDE.md` require that the total price including VAT and all unavoidable charges is shown before the buyer commits (CRD Art. 6, Price Indication Directive, UK DMCC drip-pricing ban). 005 discharges it structurally, not by review: `PricePoint` cannot represent a partial price (`deliveryIncluded: true` is a literal type and the net/VAT/gross refinement is enforced by the schema); surcharges are rows returned with the date so the amount is legible **before** date selection; `quote()` produces one total; and there is no exported function that returns a price excluding anything. Currency clarity (symbol + ISO in `aria`) is spec 003's formatter; the "you pay in GBP, the florist is paid in PLN" line is 010's copy over 005's `destinationCurrencyPrice`.
- **Omnibus Art. 6a (30-day lowest price).** Implemented as `lowestPriceInLast30Days()` over superseded price rows — possible only because spec 002 supersedes rather than updates. No reduction UI ships, so no announcement can be non-compliant; when one is built, the number is already there and tested (AC-14).
- **Omnibus / DMCC ranking transparency.** 005 exposes a deterministic default sort and no personalised or paid ranking, so 008's "sorted by bestsellers" disclosure has something true to describe. No pricing is personalised: `resolvePrice` has no customer, session or history parameter, so behavioural price discrimination is not expressible (also a DMCC and a fairness position, not only GDPR).
- **Geo-blocking Regulation (EU 2018/302, ADR-0006).** Prices are keyed on **destination** country only. AC-18 enumerates every exported pricing signature and fails on a buyer/IP/geo parameter; there is no buyer-country dimension in the dataset, in `country_price` (spec 002 §8 made the same point) or in any function, so "a French and a German buyer sending to Warsaw see the same price" is a property of the type system. Availability differences are destination-based ("we do not deliver there yet"), which Art. 3 permits.
- **Consumer information duties.** CRD Art. 22 (no pre-ticked extras): add-ons have **no** default-selected field to set, and AC-19 pins that the add-on type cannot express one. The perishable-goods withdrawal exemption (Art. 16(d), UK CCRs reg. 28(1)(c)) is disclosure copy on the PDP and at pay (009/010), and 005's contribution is `hasMerchantReturnPolicy = MerchantReturnNotPermitted` in the offer projection so the structured data agrees with that disclosure. Non-perishable add-ons sold with flowers are a live legal question (`plan/13` B6): 005 keeps add-ons as separate priced lines with their own VAT rate precisely so a different withdrawal treatment can be applied later without a schema change.
- **VAT.** `vatBreakdown()` produces the per-rate integer split the invoice needs (`plan/06` §4: PL 8% flowers vs 23% add-ons is item 4 of the accountant's must-confirm list), stores nothing, and is model-agnostic: the principal/agent decision (B1) changes who invoices, not the arithmetic, and `order.supply_model` (spec 002) carries it. Rates are integers in basis points end to end — no float touches a tax figure.
- **Accessibility (EAA, WCAG 2.1 AA).** No rendered surface, so conformance is not assessable here; the two obligations 005 can discharge structurally it does: every price-adjacent state has a `reasonKey` with a message key, so nothing is conveyed by colour or by an untranslated blank (WCAG 1.4.1, 3.1.1); and `PriceProjection` exposes the price as structured parts (amount, currency, VAT label, surcharges) rather than a pre-built string, so 009 can compose the `aria-live` announcement `plan/04` §16 requires for a price change on tier or date selection. That is the substantive reason there is not more to say.
- **Logs and PII (`CLAUDE.md`).** 005 logs at most `{ sku, tier_key, country_iso, currency, fx_as_of, duration_ms, request_id }` — no buyer, no recipient, no address, no basket contents, no quote digest. The quote token is the one place a leak could be designed in and is not: it carries product ids, tier keys, integer amounts, currency, rate, expiry and an HMAC, so it can appear in a form field or a log without disclosing anything about a person, and it is not a bearer token for any account. The logger's redaction list needs no widening for this spec (spec 002 already owes the `*name` widening carried forward from `/review 5`).
- **Security.** The quote HMAC uses a server-only secret through `lib/env.ts` (no new key until 010/013 issues the first quote in a request — §13 Q5 decides whether the secret lands here or there); `verifyQuote` is constant-time on the digest; a tampered or expired quote is refused, never repriced upward silently. The dataset is committed code, so a price change is a reviewed diff in Phase 0 and an audit-logged admin action from spec 012 (`plan/10` §4: "no PR flips a country or partner status through code").

## 11. Observability

- **Structured logs only, at the read boundary**: one `debug` line per catalogue/pricing read with `{ request_id, sku_count, country_iso, currency, fx_as_of, duration_ms }` and one `warn` above 50 ms, so a slow ISR miss is visible without a dashboard. Never a buyer, a basket, a quote digest or a SQL string (§8).
- **The three signals with a business consequence**, all `warn` + a Sentry message, because each silently produces a wrong price if unnoticed: (1) **FX stale** — the newest rate older than `MAX_FX_AGE_HOURS`, which means every non-native display currency has stopped converting; (2) **price missing** — `resolvePrice` found no active row for a (product, country, tier) that a page asked for, which is a data hole on a live country; (3) **price ambiguous** — more than one active row, which should be impossible under spec 002's index and therefore indicates a migration or a seed defect.
- **`catalogue:check` step summary** in CI prints price coverage per country and the count of products that are indexable per locale — the cheapest early warning that a country flip would produce thin pages.
- **Deliberately not instrumented yet**: margin per order (needs payouts and fees → 012/020), price-change audit (needs `audit_log` writes → 012), conversion by tier (needs GA4 → 023), FX cost realised vs buffer (needs settlement data → 013). No dashboard exists in Phase 0 (`plan/08` §7).

## 13. Open questions

**Resolved 2026-09-09 (founder: "accept defaults"; each recommendation below is the binding answer):** Q1 EUR/GBP `x90`, PLN `x9`, HUF `x90`; Q2 ECB daily rates, 2.5% buffer, 48 h max age then destination currency; Q3 add-ons priced per country with their own VAT rate; Q4 stem-count / S-M-L / single tier names, plain (no marketing word); Q5 30-minute signed quote, secret lands in spec 010; Q6 middle tier preselected via `product_tier.is_default`; Q7 surcharges as dated rows; Q8 all three spec 002 amendments folded into migration `0003` (spec 002 §14 A1); Q9 this spec owns the dataset in `src/config/catalogue/*.data.ts`; Q10 no money on destination-less hubs in Phase 0; Q11 EUR, GBP, PLN only behind `currency.{code}` flags. Original questions kept below for the record.

Each has a recommended default; the spec is `draft` until they are answered and the founder marks it `approved`.

- **Q1 — What should prices end in, per currency?** There is a real conflict to settle, not just a preference. `plan/10` §2.3 says prices end in **.90/.99 for EUR/GBP** and in **9 for PLN** (its bands are 149 / 199 / 269 / 359 zł — whole złoty ending in 9), but `src/config/currencies.ts` (shipped by spec 003) currently sets **PLN to `x90`**, which would produce 149,90 zł. One of the two has to move, and this spec is the first code that reads the field. There is also a carry-forward from `/review 14`: HUF is set to `x9` and "`x90` is the Hungarian convention". **Recommendation:** EUR and GBP `x90` (€45,90 / £45.90 — reads as a price, avoids the .99 discount-retailer feel that works against a trust-led brand); **PLN → `x9`** (149 zł, matching `plan/10` §2.3 and Polish florist practice); HUF → `x90` (990 Ft endings); everything else `x90`. The change is three lines in one config file plus its test. Answer this first: every seeded price depends on it.
- **Q2 — Where do exchange rates come from, how often, and what happens when they are old?** **Recommendation:** ECB daily reference rates (free, authoritative, one request/day, already named in `plan/01` §8), refreshed at 06:00 CET by `fx.refresh`, with a **2.5% buffer** (`plan/06` §2.2 and the `plan/13` B7 default) and a **48-hour maximum age**, past which we stop converting and show the destination country's own currency instead of a guessed number. The trade-off to accept: ECB publishes on working days only, so a Monday-morning rate is Friday's — which is exactly what the buffer is for. Alternative considered: a commercial FX API with intraday rates (more accurate, a paid dependency, a new processor, and a rate that moves under a cached page). Confirm the buffer size too: it is the difference between absorbing a currency move and eating it.
- **Q3 — Are add-ons priced per destination country, and do they carry their own VAT rate?** **Recommendation: yes to both.** Per-country pricing because chocolates cost what a Warsaw florist sources them for (`plan/10` §2.3 already lists a PLN column for add-ons), and their own VAT rate because in Poland chocolates are 23% while flowers are 8% — a single country-level rate would produce a wrong invoice on the very first mixed order (`plan/06` §4 item 4). The cost is one extra column and one extra index in spec 002 (Q8). Alternative: price add-ons in EUR and convert — cheaper to seed, but then an add-on's price moves with the exchange rate while the bouquet's does not, which is hard to explain and looks like drip pricing.
- **Q4 — How is a size tier named in each language?** **Recommendation:** by **stem count where the product has one** ("12 stems", "18 stems", "24 stems" — `plan/04` §2's finding that stem-count tiers beat "Deluxe/Premium" adjectives, and one of the few places we can be concretely honest), by **S/M/L** for arrangements where a stem count is meaningless, and "single" for plants. Implemented as ICU plural keys, so Polish gets *łodyga / łodygi / łodyg* correctly and the label is never concatenated. What needs your answer is whether the PDP shows "12 stems" or "Classic · 12 stems" — the second reads better on a card but adds a marketing word per tier per locale for the native reviewers to agree.
- **Q5 — How long is a price locked between the product page and payment, and where does the lock live?** **Recommendation: 30 minutes**, as a stateless signed quote issued with the page and verified at payment; if it has expired, 010 re-derives the price and asks the buyer to confirm the new one — never charges a different amount silently. 30 minutes covers a normal checkout with room for a distraction, and is short enough that the FX buffer covers any move inside it. The sub-question: the quote needs one server secret (`QUOTE_SIGNING_SECRET`), and it can land in this spec's env schema or in spec 010's when the first quote is actually issued in a request. **Recommendation: spec 010**, so 005 adds no key it does not use. Alternatives: no lock at all (the buyer can be charged a different number than they saw — unacceptable under `plan/07` §4), or a stored quote table (needs the database, which is parked).
- **Q6 — Which tier is preselected on the product page?** **Recommendation: the middle tier** (18 stems on a 12/18/24 bouquet), which is `plan/04` §16's A/B test #1(2) baseline and the standard anchor-pricing choice. This needs a `product_tier.is_default` column (Q8) because a preselected tier chosen in code could not be A/B tested or changed per product later.
- **Q7 — Are Sunday and peak-day surcharges rows, or a rule?** **Recommendation: rows** — `country_price` rows with `surcharge_kind` and date bounds, seeded at +€4 (Sunday) and +€6 (Valentine's, Women's Day) equivalents per `plan/10` §2.3. Rows mean a peak surcharge is set in admin per country per year and shows on the date chip with an exact amount; a rule means a percentage, a float and a number that cannot be shown before the date is picked (which `plan/07` §4 requires). The cost: someone has to add rows each year, which is a `docs/runbooks/peak-day.md` item.
- **Q8 — Three additions to spec 002's schema; may they be folded into its migration `0003`?** All three are additive, each has a one-line rollback, and each exists because 005 found a gap while 002 is still unimplemented: (a) `addon_country_price.vat_rate_bp` (Q3's mixed rates); (b) a partial unique index on `addon_country_price (addon_id, country_id) WHERE active_to IS NULL`, mirroring `country_price`'s, so add-ons also have exactly one active price and a superseded history for Omnibus; (c) `product_tier.is_default` with a one-per-product partial unique index (Q6). **Recommendation: accept all three, folded into spec 002's `0003`** rather than a follow-up migration — 002 has not been implemented, so this is free today and a second migration tomorrow.
- **Q9 — Who owns the catalogue dataset: this spec, or spec 002's seed?** **Recommendation: this spec.** `src/config/catalogue/*.data.ts` becomes the single authored source, zod-parsed, no database, exactly as spec 003 did for locales and spec 004 for countries and links; spec 002's seed and spec 006's importer read `toProductRow()`-style projections rather than restating 84 products in a second place. The alternative (dataset in `seed/`, imported by the provider) keeps 002's text literally intact but puts the Phase 0 demo's only catalogue behind a directory whose scripts cannot run without a database. Confirm, because it decides task 2's file paths and one sentence of spec 002's §2.
- **Q10 — On a page with no destination chosen (`/en-gb/flowers/roses`), do we show money at all?** **Recommendation: no money in Phase 0.** A "from £34" on a destination-less hub is not the price of anything purchasable: it would be a minimum across countries converted at today's rate, it cannot match any `Offer`, and under the DMCC/Price Indication rules an indicative price that no configuration matches is the shape of problem those rules exist for. The hub's job is to get the destination picked (`plan/04` §4). Alternative: show "from" with an explicit "to Poland" qualifier once a destination is remembered — worth revisiting in Phase 1 with real data, and cheap because `fromPrice()` already exists.
- **Q11 — Which display currencies do we actually offer at launch?** `plan/03` §1 lists eleven; spec 003 configured ten; Stripe presentment and our settlement position (B7) make only some of them a currency we can genuinely *charge*. **Recommendation: EUR, GBP and PLN only in Phase 0**, each behind a `currency.{code}` flag, with the other seven configured but off — because a currency we display and cannot charge breaks the one invariant this whole spec exists to protect. Turning one on later is a flag flip plus an FX row, not a code change.
